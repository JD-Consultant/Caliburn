# 0061. 逐項任務子對話與主要職責歸納建議

- 狀態：**Proposed**
- 日期：2026-08-07
- 依據：[`docs/specs/2026-08-07-behavioral-indicator-depth-and-icap-reference-flow-research.md`](../specs/2026-08-07-behavioral-indicator-depth-and-icap-reference-flow-research.md) §5.3／§5.5／§6
- 延續：[0060](0060-enterprise-jd-indicator-depth-and-icap-reference.md)（同一批產品裁決的第二半；
  0060 已預告本 ADR 的範圍）
- **翻案**：[0059](0059-ai-assisted-duty-suggestion.md) **決定 1**（不做「從穩定 Task 歸納 Duty」）——見決定 12；
  0059 的**決定 2–5／7–11 原樣沿用**
- 沿用：[0055](0055-hybrid-job-discovery-and-ttop-formation.md) 決定 4／5（Task 穩定後才共同定義 O/P；
  工作故事不得直接成為 Task）、[0049](0049-opks-derived-axes-evidence-whitelist-and-document-authority.md)

## 脈絡

ADR 0060 修正了行為指標的判準與 reference 接線，但沒有處理**訪談本身的組織方式**。
owner 於 2026-08-07 裁決：Task 訪談與「產出／行為指標」訪談**分成兩個對話**，
骨架（主要職責＋工作任務）歸一部分、個別任務的深入歸另一部分。

這對現行實作是實質改動。現況只有一條對話：

- `list_conversation_turns()` 只撈 `consultant_opening`／`employee_turn` 兩種 Journal kind，
  依 `journal_sequence` 展平成單一扁平序列；
- `ConversationTurn` 只有 `turn_id`／`speaker`／`text`，**沒有任何 scope 概念**；
- `DocumentRecord.active_question` 是**單一**的——一份文件同時只能有一個待答問題。

同時，ADR 0059 決定 1 排除了「從穩定 Task 歸納 Duty」，理由是 Task 的數量與穩定度要等 R9 pilot
才知道。但 ADR 0060 接上 iCAP 之後，出現了一個**不需要等 pilot 就能確定**的情境：
員工採用官方主要職責後，訪談產出的工作必然有一部分落在官方框架之外
（企業內部版本來就比公版細，這是 0060 的產品前提）。這些「尚未歸入職責的任務」
是結構性必然，不是待驗證的假設。

## 決定

### A. 對話的組織與範圍

1. **兩個對話區分開，職責不同**：
   - **骨架對話**（文件層，一份文件一條）：找出工作任務、處理任務邊界與待訪談清單。
     這是現行 `submit_employee_turn()` 那條線，**行為不變**。
   - **任務子對話**（每項工作任務各一條）：深入該任務的工作產出與行為指標。
1a. **骨架對話先取得責任範圍的粗略輪廓，再進入開放敘事。** 現行固定開場
   （`CONSULTANT_OPENING_TEXT`：「先不用照職稱回答：你這個職位最主要替誰解決什麼問題？」）
   問的是**目的**；本 ADR 追加**責任範圍**（「大概負責哪幾塊」）作為開場的一部分。
   **這不牴觸 ADR 0055 的防錨定考量**：問員工他負責什麼，與給員工一份清單讓他認領，
   是完全不同的動作——後者才是 Morgeson 測到膨脹的情境。
   ADR 0046 的「固定持久開場」機制不變，改的只是開場內容。
2. **工作產出與行為指標在同一條子對話裡一起談。** 官方語意本就耦合——O 是「對應該工作任務
   **及行為指標**之關鍵產出項目」，且上一項任務的 O 常成為下一項任務 P 的輸入條件
   （`T2.1` 產出企劃資源清單 → `P2.2.1 依企劃資源清單，進行活動前置確認`）。
   提問形狀因此固定為兩問：**「這項工作你具體做哪些事」→ P；「做完交出什麼、下一步誰拿去用」→ O。**
3. **O 可以沒有。** 21.8% 的官方任務沒有工作產出（ADR 0060 決定 20）。
   子顧問**不得**因為 O 欄位空著而追問到員工硬掰出一個產出。
4. **子對話仍受 ADR 0055 決定 4 約束**：工作故事不得直接成為行為指標。
   STAR 之類的框架可用於**取材**，但單一事件敘述必須經跨事件歸納才能成為穩定的 P。
5. **追問到具體為止，但有停止條件。** 員工說不出具體時顧問應追問
   （owner 裁決；企業內部版的價值就在具體度），
   但**同一個具體化缺口至多追問兩次**，仍得不到就收下現況、標記該條可再深入、繼續往下。
   ADR 0055 的負面後果已警示「需防止故事訪談無限延伸」，無出口的追問會把員工困住。

### B. 儲存形狀

6. **新增 Journal kind 承載子對話，不改既有 `CompletedTurnPayload`。**
   沿用 OPKS（ADR 0049）與 AI-Duty（ADR 0059 決定 2）的既有慣例：新能力走獨立形狀，
   不擴充已驗證的既有契約。具體地：
   - 新 kind 的 payload 帶 `task_id`，其餘結構比照 `CompletedTurnPayload`；
   - **`list_conversation_turns()` 的行為不變**——它繼續只投影骨架對話。
     子對話另走一支 per-task 查詢。
   這條的關鍵理由是**回歸風險**：`list_conversation_turns()` 同時餵給下一輪 packet 與
   Consultation View，把子對話混進去會改變骨架對話的模型輸入，而那是已付費驗證過的路徑。
7. **`active_question` 需要 per-task 版本。** 現行 `DocumentRecord.active_question` 是單一的，
   而子對話各自有待答問題。第一版採**每項任務一個 active question**，
   與文件層的 active question 並存、互不覆寫。
   缺它的後果是具體的：`support_links.question_turn_id` 的來源消失，員工的短答無法被解讀。
8. **子對話與骨架對話共用同一條 authority seam**（`commit_authority_change()`）與同一個
   `authority_generation`。**不建第二套交易語意**；O/P 提案仍是既有的 `OpksProposal`，
   不新增第三種 Proposal（ADR 0050／0051 全部維持）。

### C. 兩個對話之間的資訊流

9. **子對話結束時，向骨架對話回傳「結果摘要 ＋ 被標記的新線索」，不回傳逐字內容。**
   逐字回傳會讓骨架 packet 隨任務數線性膨脹並稀釋模型注意力；完全不回傳則會漏接
   員工在子對話裡順口提到的新工作。
10. **「新線索」是子顧問的一項顯式輸出職責**：員工提到、但不屬於當前任務的事。
    它進入骨架 packet 的一個獨立區段，供骨架顧問決定要不要追問。
    **它不是 open issue、不直接進 Work Model**——`apply_task_analysis_result()`
    仍是唯一寫入者，新線索只是骨架顧問的輸入材料。
10a. **新線索不打斷當前子對話**：談完該項任務才處理，不即時跳回骨架對話。
    深談的價值來自連續性，為了一條順口提到的線索中斷它並不划算。
    線索因此會積壓，去處是 ADR 0060 決定 11a 的同一份待訪談清單——
    **它必須被看得見地保存**，否則「不打斷」會變成「弄丟」。
11. **「哪些任務可以開始談 O/P」由 application 端決定性規則判斷，不由模型輸出。**
    規則：已進 Current JD、沒有未解的邊界爭議、尚無任何行為指標。
    UI 據此提示，模型的 `next_question` 本就是自由文字、可自然引導。
    **這條的目的是保護 `task_analysis_result_v2`**——為了一個引導提示新增輸出欄位，
    會觸發 ADR 0042 決定 7 並需要重跑付費複驗，代價與收益完全不成比例。

### D. 主要職責歸納建議（翻案 0059 決定 1）

12. **翻案 ADR 0059 決定 1，但範圍嚴格限縮。** 0059 排除的是「不知道 Task 數量與穩定度
    就做完整歸納」；本 ADR 授權的**不是**完整歸納，而是兩個範圍：
    - **尚未歸入職責的任務**——AI 建議它們該歸入哪一項既有職責，或是否自成一項新職責；
    - **員工主動要求**時，才對既有結構提出調整建議。

    翻案理由是 ADR 0060 造成的結構性必然：員工採用官方職責框架後，
    企業內部版的實際工作必然有一部分落在框架外。這不需要 pilot 資料就能確定，
    0059 決定 1 的顧慮對這個範圍不適用。
13. **重點是「確認歸納是否正確」，不是自動整理。** 沿用 0059 決定 5：
    職責切分是語意判斷、verifier 攔不住，候選必須逐條由員工決定。
14. **不預設重組既有結構。** 系統不主動打散員工已採用的職責——
    那會使匯出位置碼（`T{i}.{j}`）整批變動，而第一版沒有版本歷史可以解釋差異
    （ADR 0058 決定 5 已為同一理由把排序切片排在匯出之前）。
15. **員工主動要求重組時，必須明確告知會改變匯出編號。** 畫面上刻意不顯示位置碼
    （ADR 0052 決定 10），所以員工看不見這個影響——必須用文字講出來，不能靜默重排。

## 後果

### 正面

- 骨架對話的模型輸入與 Consultation View 完全不變，已付費驗證的路徑零回歸風險。
- O/P 一起訪談對應官方語意，提問形狀固定為兩問，不需要員工理解 O 與 P 的差別。
- 決定 11 讓「訪談引導進 O/P」在不動 `task_analysis_result_v2` 的前提下達成，
  省下一次付費複驗。
- Duty 歸納限縮在「尚未歸入職責的任務」後，價值明確且不與 iCAP 官方框架打架。

### 負面／代價

- **訪談總量顯著增加。** 一份 JD 常見 10–15 項任務，每項一條多輪子對話，加上骨架對話，
  員工的總對話量可觀。第一版無法預估完成率——若 R9 pilot 顯示員工撐不完，
  **優先調整方向應為「挑核心任務談深」而非「每項都談淺」**，因為具體度正是產品價值所在。
- 新增 Journal kind 與 per-task active question，需要 migration。
- 決定 9／10 會在骨架 packet 新增一個區段，**屬 ADR 0042 分界的判斷層改動**，
  與 ADR 0060 決定 2–4 一樣需要一次 Opus／Sonnet 複驗才能上線；兩者可合併驗證。
- 決定 5 的「至多兩次」是本 ADR 提出的工程停止條件，**沒有任何實證依據**，
  第一版只是防止無限循環，不宣稱是最佳值。
- 翻案 0059 決定 1，而 0059 距今僅一日。理由是 0060 改變了前提（iCAP 接線），
  不是原決定當時判斷有誤。

## 不在本 ADR 範圍

- 子對話 payload 的欄位級 schema、`active_question` 的具體儲存位置與 migration——留給 plan。
- 「新線索」在骨架 packet 中的 rendering 措辭——留給 plan，但須與 ADR 0060 決定 2–4
  的複驗合併驗證。
- 子對話的 wire schema 與 Static Instructions 內容（含 5W2H 的具體引導措辭）——留給 plan，
  受 ADR 0060 決定 1–2 約束（P 是行為描述、不得補數值）。
- 企業內部版每項任務的行為指標合理條數與品質 rubric（ADR 0060 決定 21 已明示不設門檻）。
- 完整的職責結構重組（決定 14 已排除預設行為；員工主動要求的路徑其 UX 細節留給 plan）。
