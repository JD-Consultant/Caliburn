- 日期：2026-09-24
- 最近核對：2026-09-29；補入核心閉環與取捨的討論準則，不改已確認的資料保存審查方法或具體儲存分配。
- 狀態：Owner 已確認採用此**討論方向**；本文件細節待 Owner 複核。它只規範後續如何討論與記錄，不自行批准任何產品架構或施工。
- 適用範圍：Caliburn 的跨層架構、資料權責、生命週期、重要契約與相應開發文件。這些文件是**隨設計與實作持續維護的工程資產**，不是一次性交付物。局部修字或已有決策內的純實作細節，不強制套用全套章節。
- 方法來源：下方列出的業界公開方法。本稿**獨立撰寫**，不以 Caliburn 舊架構、舊文件分類或既有討論流程作模板，也不要求新架構相容舊實作。舊程式與文件只在查明現況、保存歷史、識別既有有效產品限制時作證據；新目標架構按效果與取捨重新設計。

## 1. 核心規則

**先確認要達成的產品效果與不可違反的事實，再以現況和成熟公開做法共同推敲責任、資料邊界、生命週期與取捨，最後才定具體實現。**研究不是等責任圖畫定後才開始：業界可能以不同方式切分 session、Agent、workflow、工具環境與正式業務資料；本案既有的 A／B1／B2 或 State 分類也只是待驗的描述，不能強迫其他方案套進去。不能因現有程式已這樣寫，便倒推「這就是應有設計」；也不能因研究文檔曾提出候選，就宣稱已成正式需求。

**2026-09-29 討論取捨補充：**以「員工說明實際工作 → 顧問釐清與理解 → 有據、逐步寫出高品質 JD → 讓人回看及修正」的核心價值閉環檢查新需求。先問一項能力是否直接創造價值、使閉環可運作，或使資料與結果值得信任；沒有具體阻塞或反例，不因技術名稱流行便增設 Agent、狀態、儲存或通用規則引擎。介面、恢復與證據可能是必要的信任條件，不因不是直接寫稿就一律刪掉；「固定砍掉某個比例的功能」、產品存活率或營利說法不作架構事實或施工門檻。這是討論方法，不替代各項產品決策與驗收。

### 先建立整體概念，不把概念名稱當成元件

第一輪先用使用者旅程與資訊變化描述**產品需要具備的能力**：長訪談如何持續掌握員工的完整工作、分析如何跨模型步驟及聊天回合延續、原話如何整理成案例與工作理解、何時有足夠依據撰寫或修訂 JD，以及人如何回查 AI 編輯的依據。這是概念圖，不是執行部署圖。

例如「Working State」在概念層只表示**必要的分析能跨步驟、跨回合延續，不必每次從頭分析**；此時不預設它有哪些欄位、是否只有一個元件，或必須由某個框架 state、資料表、工具或 Agent 實現。同理，案例整理、工作理解、上下文延續是要達成的責任與效果；後續才比較由現有元件、框架原生能力或其他方案實現。

概念討論只先回答 **做什麼、為什麼、與其他能力如何銜接、什麼不可遺失或誤判**；不要求先回答 class、API、資料表、套件與部署拓撲。概念骨架得到確認後，再逐一展開各能力的資料契約、生命週期、責任分配與候選實現。現有專案是可核對的底稿，不是「同名概念必須保留同名實作」的承諾。

每一項陳述都必須能分辨：

| 類別 | 意義 | 寫法要求 |
|---|---|---|
| 現行實作／實測 | 現在程式或測試實際做了什麼 | 指向程式、測試或可重現紀錄；標明測試層級及限制 |
| 已生效的產品／架構決策 | 決策者已確認的效果及其適用範圍 | 給可追溯位置，區分已生效於現行產品，或僅適用於新目標 |
| 目標設計 | 已同意但尚未完成的未來行為 | 明寫「目標／未實作」，不畫成現況 |
| 候選／推論 | 仍待比較或證實的做法 | 說清假設、依據、反例與停止條件 |
| 歷史／已取代 | 當時為何那樣決定或實驗 | 保留先後與 successor，不作現行施工指令 |
| 未決 | 資料不足或需要 Owner 取捨 | 寫成可回答的問題，指出阻塞什麼 |

同一張圖或同一段流程不得默默混合「現行」與「目標」。需要比較時，並列兩者並標出差異。文件寫下來也不代表已實作；實作通過單元測試也不代表真實使用者旅程已通過。

## 2. 每次討論如何開始

先用一個**可回答的問題**界定本輪，而不是用「重設整個系統」作題目。開題時最少說清楚：

1. **目的與使用者效果**：誰在什麼情境遇到什麼問題；成功時使用者看見什麼。
2. **已定邊界**：哪些效果、資料權威或限制已確認；哪些現行實作只是過渡。
3. **本輪問題**：這次只決定哪一個跨層契約或生命週期分歧；為何它現在阻塞下一步。
4. **代表性反例**：至少一個正常情境，以及足以暴露錯誤的中斷、競爭或版本變動情境（若適用）。
5. **本輪不決定**：相鄰但不阻塞的問題列入 parking lot，不在回答時暗中順便裁決。

先確認已明確的產品目的與限制，再辨認現行 owner；**現行 owner 不自動成為目標 owner**。不用每次重讀全部歷史。討論中若發現新問題會改變使用者效果、資料 authority、不可逆後果、明顯成本或跨層契約，先停在該分歧，展示證據與選項並問 Owner。可逆且效果等價的工程細節可在核准設計內自行處理，不要求 Owner 選每個類別或函式。

## 3. 架構討論的固定順序

以下是**檢查順序**，不是要求每輪重寫九份文件。已有可靠答案就引用並前進；只展開與本題相關的部分。

第 8 項是**記錄和比較候選方案的檢查點**，不是「到第 8 項才准查外部資料」。從第 2 項起就應按問題查成熟做法與現有實現，讓來源證據修正第 3–7 項的責任、資料和時序劃分；若新證據推翻暫定分類，回到受影響步驟重畫，不能只在最後附一段「業界比較」。已確認的產品效果保持可追溯，分類、元件數量與術語則不預設為業界共識。

1. **整體概念與使用者旅程**：先畫能力與資訊如何銜接，不預設物理元件或目前的框架切法。
2. **產品效果與反例**：先說必須成立／不得發生什麼，不用框架術語代替需求。
3. **靜態邊界**：概念確定後，再分配執行責任與外部依賴；誰擁有哪種資料與業務判斷，跨邊界輸入／輸出是什麼。
4. **資料真相與身分**：原始、衍生、候選、正式發布、快取與模型上下文各自是什麼；誰能修改，誰只能讀；ID、版本、引用與來源由誰產生、核對與保存。
5. **正常生命週期**：觸發、准入、固定輸入範圍、執行、候選、驗證、提交／發布、使用者或其他元件可見的時間點、完成條件。
6. **異常與並行生命週期**：重複通知、取消、中斷、超時、失敗、重啟、恢復、版本衝突、部分副作用、過期資料。區分「已收到」「已持久保存」「已完成」「已發布」，不能用一個成功標記混寫。
7. **跨層契約**：受影響的讀／寫入口、模型看得到什麼、Runtime 推得出什麼、編輯與背景任務如何銜接；檢查是否出現第二份 authority／validator／receipt。
8. **候選作法與外部依據**：比較主流公開契約、現成框架能力與本案特有規則；不要把某大廠的表面行為當作已知內部實作。
9. **取捨與決定**：列 2–3 個實質不同的方案（若確有分歧）、產品效果、複雜度、成本、風險、可逆性與建議；Owner 只裁決真正的產品分歧。
10. **可驗收條件與文件去向**：寫出可觀察的 pass／fail、哪一層證據能證明、哪些仍未驗；把討論、核准設計、施工與實測分開，不把討論稿直接當 implementation plan。

在概念階段不裁決元件。進入實現階段後，若第 3–7 步已足以證明某種成熟方案可完成需求，明寫「不新增元件」；若不夠，先指出**哪個具體反例**逼迫增加能力，不先命名新 Agent、queue、資料表、registry 或 generic framework。現行實作可以沿用、修改或替換，按證據與產品效果判斷，不設「必須整合舊架構」的前提。

## 4. 如何把生命週期寫清楚

對重要的持久資料、背景工作、互動回合或編輯操作，用**代表性流程**回答下列問題。討論中可先用短文字或草圖釐清，收斂後須能直接畫出相應的流程／狀態／時序圖；不要為每個 trivial CRUD 畫大圖。

| 要問的問題 | 必須能讀出的內容 |
|---|---|
| 何時開始？ | 觸發事件、准入條件、何時算已持久接受；模型意圖不等於已接受 |
| 讀取什麼？ | 資料來源、範圍、讀取基準／版本、哪些可按需回查、哪些不能被摘要替代 |
| 誰做什麼？ | 模型、App／Runtime、業務 Domain、資料庫、背景工作與使用者的各自責任 |
| 中途留下什麼？ | 暫存候選、正式紀錄、回執、可恢復檢查點與外界可見性；只在真有需要時定義 |
| 何時生效？ | 驗證與原子提交／發布邊界；其他讀者何時才可把結果當正式資料 |
| 失敗怎麼辦？ | 可安全重試與不可重送的操作、重啟恢復、版本衝突、未知結果與停止條件 |
| 如何結束？ | 成功、失敗、取消或需人工處置的終局；哪些後續義務仍存在 |
| 如何證明？ | 可查回的狀態、來源／版本與對應層級的測試或使用者旅程 |

**版本與引用要沿完整鏈問。**若上游物件引用下游版本，須說明下游變更後上游何時重核、何時產生新版本、歷史快照能否重現；也要問尚未正式發布時，上游或使用者可依哪個已核對來源先繼續工作。這裡是討論檢查項，不替各層預先選定同一種更新政策。

**時序要能覆蓋交錯事件。**例如「舊背景工作固定輸入後，員工才提出更正」：須分別追蹤原話保存、A 下一次可見內容、舊背景可合法發布什麼、新背景何時涵蓋更正、何時才可解除暫時提醒。不能只寫「稍後會整理」而略過兩者之間的使用者體驗；也不能在此範例中假設已存在可靠的偵測／恢復程式。

### 資料保存與使用的共同審查順序

**已確認的是審查方法，不是儲存分配表。**功能、使用方或生命週期改變時，以同一順序重新審視；不從「外部會用」直接推導新增 DB 副本，也不從「只在 Graph 內使用」推導可以忽略正式版本或長期保存需求。

1. **用途與保證：**資料用來做什麼、何時有效、需保存多久、中斷後須恢復什麼；先區分不可遺失的正式結果與容許重新計算的工作。
2. **內容與變更責任：**誰產生、誰可以修改、由哪個來源判定真相；不要讓另一份表示取得獨立且矛盾的權威。
3. **使用介面：**其他使用方需要讀取介面、交接結果、特定快照或固定引用中的哪一種；外部查看進度不自動要求另一份保存。
4. **既有機制是否足夠：**核對框架、業務保存與讀取能力的實際契約及失敗情境，不能只因用了 checkpoint 或資料庫就宣稱已滿足保證。
5. **必要的新增表示：**只有具體需求無法由既有機制滿足時，才增加儲存、副本或投影；若有多份表示，交代用途、判定依據及更新、失效、重建與刪除規則。

各功能文件只記錄自己套用此方法的理由、結果、限制與未決事項，引用本節，不各自維護第二套共同規範。這不要求所有資料雙寫、全部搬出 checkpoint，或每類資料各建一個服務／資料表；也不因能重建就忽略不可接受的恢復時間或重新執行成本。

## 5. 文件如何分層，避免一份文件塞下所有細節

| 文件 | 讀者需要的答案 | 不放什麼 |
|---|---|---|
| **架構導覽／map** | 產品目的、系統邊界、主要資料流、責任 owner、各詳細文件入口、現行與目標差距 | 整份 API schema、完整 prompt、所有歷史討論與逐行程式 |
| **領域／跨層設計** | 來源真相、物件與引用契約、共通不變量、為何跨子系統一致 | 每個子系統重複抄一份不同版本的規則 |
| **元件責任設計** | 單一 owner 的職責、入口、資料形狀、限制、與其他層的契約 | 偷改其他元件 authority；把假設寫成現行事實 |
| **生命週期／runtime view** | 代表性正常、交錯、失敗、恢復場景；觸發與提交邊界 | 只有靜態方框、沒有時序和終局 |
| **ADR／決策紀錄** | 重大取捨、替代方案、理由、後果、狀態、successor | 完整操作手冊或不斷改寫的設計草稿 |
| **施工計畫** | 已核准設計如何分段改、驗證及停止 | 補決產品語意或隱藏未決問題 |
| **runbook／操作手冊** | 操作者如何啟停、診斷與恢復現行系統 | 將目標設計描述成目前可執行程序 |
| **證據／驗收紀錄** | 實際跑了什麼、哪層通過、環境、費用、限制、失敗與反例 | 把離線 mock 當 provider／完整產品成功 |

導覽保持短，詳細設計以連結深入；同一權威概念只在一處完整定義，其他文件引用。文件保留迭代歷史與 supersedes 關係，但現行入口須能帶讀者找到有效版本。圖依問題選用：C4 式靜態圖回答「有哪些邊界與責任」，runtime／時序或狀態圖回答「事情如何隨時間發生」。不要求畫滿 C4 四層，也不要求每個情境都畫圖。

### 全產品導覽如何逐層展開

這套文件本身也要有架構。讀者從**單一全產品入口**出發，先看產品與外部的邊界，再選擇要深入的能力或責任；每一層說明自己的範圍、下一層入口及與相鄰範圍的契約。可由 App 全局深入 Agent 執行，也可由同一全局深入 JD 業務或資料保存；不能要求讀者先知道某個歷史檔名，才找得到責任文件。[C4 的不同縮放層次](https://c4model.com/diagrams)及 [arc42 building-block view](https://docs.arc42.org/section-5/)提供這種逐層閱讀的公開方法；本案不把圖中的方框直接當成已選定的程序、服務或資料表。

逐層放大的**靜態視角**，須能指出全產品邊界、主要能力／責任、重要內部組成及其依賴；跨越多個方框的**流程視角**，則沿真實使用者旅程追蹤命令、資料、來源、版本、保存／發布與錯誤回傳。兩種視角互相連結：例如記憶子系統的內部導覽可帶讀者找到資訊層、整理責任與資料契約；訪談到 JD 的時序圖仍須顯示它如何與顧問、App 後端及使用者互動。只有方框、沒有跨邊界時序，不算完整架構；只有長流程、找不到每步的責任文件，也不算可維護。

入口不複製所有細節。每個重要節點至少連到其唯一責任說明、相關流程／資料契約、決策與已知狀態；細部選型、API／tool schema、資料庫與恢復規則在討論收斂後由對應責任文件說清楚。**先定閱讀路徑及文件責任，不預定新目錄名稱、Agent 數量或程式切分；**實際分檔和資料夾隨全產品覆蓋清單與責任邊界核對後決定。

當目標是整理**整份產品架構**時，先做一張覆蓋清單，再逐題深入：啟動與文件建立；訪談與 A 的工作狀態；模型上下文與壓縮；背景 B1／B2 與 Memory 發布；原話、案例、理解與 JD 的版本／引用；人與 AI 的 JD 編輯及撤回；資料庫、收據與重開恢復；Web 呈現、失敗告知與最終 JD 品質。每項只標「已有責任文件／需核實現況／目標待設計／不適用」，**不是先替每項設計新功能**。缺口從具體使用者情境進入，而不是按資料夾名稱分工後各自設計。

文件至少標明**目的／範圍、狀態、Owner 或決策者、最後核對日期、依賴的有效決策、未決與相關連結**；複雜方案再列 goals／non-goals、替代方案、風險與驗收。資料契約、時序、錯誤處理等細節依受影響風險深入，避免空填模板。

### 討論完成的「可直接產圖」門檻

**討論收斂到哪一層，就應能直接產出並維護那一層的圖，不靠日後回憶補畫。**整體概念收斂後，先有使用者旅程、能力關係與概念性資訊流圖；資料契約和生命週期收斂後，才形成精確資料流、狀態與時序圖；責任和技術方案收斂後，才形成元件／部署圖。不能用概念圖假裝已選定實作，也不能因尚未選框架而不畫概念圖。圖在討論中逐步成形，用來暴露漏掉的邊界與分歧。[C4 的動態圖](https://c4model.com/diagrams/dynamic)用靜態模型中的元素表示執行互動；[arc42 runtime view](https://docs.arc42.org/section-6/)則以相關正常、啟停與異常情境描述行為。這是本案的分階段產圖門檻，不是聲稱外部方法規定固定張數。

| 預期圖稿 | 該層討論收斂前必須清楚的內容 |
|---|---|
| **整體概念／能力關係圖（先做）** | 使用者從訪談到 JD 的目的、各項能力如何接力、資訊如何逐步轉化與延續；方框代表能力／資訊，不暗示 Agent、服務、資料表或框架 |
| **系統邊界／責任圖** | 使用者、產品、外部依賴與信任邊界；主要執行單位、資料 owner、誰呼叫誰；現行與目標分開 |
| **端到端資料流與來源鏈** | 每種重要資料從哪裡來、誰讀寫、暫存或持久、候選或正式、何時可見；身分、版本、引用、回查與最後去哪裡 |
| **主要使用者流程／時序圖** | 觸發者、步驟先後、同步或背景、每條跨邊界呼叫與回傳、持久保存／原子發布點、使用者何時看見結果 |
| **重要物件與工作生命週期圖** | 有意義的狀態、轉換事件與責任者、允許／拒絕條件、重試／恢復／取消／失敗／終局；並行時何者先發生會改變結果 |
| **部署／程序與恢復圖（若相關）** | 啟動與外部依賴、資料落點、程序停止／重開後由哪個持久事實恢復；不需要為尚未選定的基礎設施虛構節點 |

一張圖不必承擔所有用途；同一生命週期若狀態與跨元件互動都複雜，可以用狀態圖加時序圖，但兩圖須指向同一契約。**概念圖**中的節點表示能力或資訊，箭頭表示意義上的延續、轉化或依據，不要求標出尚未選定的程式責任者。進入**責任與實現圖**後，節點與箭頭才需能說明責任者、方向、傳的是資料還是命令／通知、是否寫入、是否正式生效；重要箭頭需標出觸發或條件。版本、引用、提交邊界與失敗路徑在其對應的詳細圖中不可只藏在文字敘述。圖應有範圍、層級、現行／目標標籤、日期或版本、必要圖例與詳細文件連結；以可版本管理、可在專案中重產／修改的來源保存，不只留一張無來源的圖片。

**圖稿就緒檢查分層進行。**概念階段，沒有參與討論的人應能從圖回答：「使用者要完成什麼？系統須具備哪些能力？資訊如何延續、轉化與回查？哪些判斷還未決？」此時**不要求**回答框架、資料表或誰持有某個 state。進入詳細架構階段後，才要求回答：「誰擁有資料？從哪裡到哪裡？何時算保存／發布？失敗或重啟會怎樣？版本與來源如何回查？」答不出該階段應回答的問題，就回到討論補足。若未決事項會改變該圖的實質關係，**不可把候選圖標成已定架構**。

整份產品最後要能從導覽連到各圖與其責任文件，並用覆蓋清單核對重要流程都已說明；不規定一定幾張圖，也不把小型重複圖當成完整性。圖、文字、決策與實作證據在後續變更中一同維護，彼此矛盾時必須修正或標記狀態，不能只更新其中一處。

### 從零接手的文件驗收

最終以**未參與討論的工程師或 Agent 能否在不猜 Caliburn 專有規則的前提下實作**為檢查，而不是以文件數量或圖數量判定完成。選一條代表性端到端旅程，從入口逐層追到產品效果、名詞、責任、資料真相、輸入輸出、正常／失敗／重啟與並行時序、技術選型、操作及驗收；再選一個跨層反例，檢查能否找到唯一判斷依據。已選用的框架、資料庫或外部服務須記錄適用版本與官方契約入口，但不用把第三方手冊整份抄進本專案；秘密與本機環境值也不寫入架構文件。若某個 Caliburn 特有決定仍須靠猜，標出具體 `OPEN`、它阻塞的實作與下一次討論題，不能用舊程式或示意圖暗中補決。

此門檻是**整套架構文件完成時**的目標，不要求目前僅收斂概念的章節回答尚未討論的資料表或 API。每輪只對本輪收斂層級做相應檢查，並在全產品入口更新已具備／仍缺的閱讀路徑；不能把局部記憶導覽或現行程式鳥瞰宣稱為完整新架構。

## 6. 作為持續維護的架構與開發文件

新架構文件應和程式一樣進版本控制、可由正式入口找到、由受影響範圍的責任者審核。文件不是「每次迭代複製一份最新完整稿」：**穩定的導覽與責任文件持續更新；重大改變另留可追溯決策；舊研究與實驗保留原貌**。讀者應能同時回答「現行產品如何運作」「未來目標是什麼」「何時、為何改變」，而不必在數十份日期檔中猜最新答案。

**Owner 已確認：架構文件必須能隨功能新增、修改與退役而維護。**每次先從全產品導覽找到受影響能力及唯一責任文件，再沿實際跨層關係檢查相關圖、資料／介面契約、正常與異常生命週期及驗收；只改受影響處，不把同一規則複製到多份文件。這是架構相關變更的維護要求，不表示每次局部程式修字都要重畫全產品架構。

每種變動有相應的文件更新觸發：

| 變動 | 應核對／更新的內容 |
|---|---|
| 新增功能／能力 | 從全產品導覽可找到其責任者、與既有能力的關係及詳細入口；補受影響的流程、契約、資料真相、失敗／恢復路徑與驗收。不因新增功能自動新增文件層級或通用元件。 |
| 修改功能／能力 | 從唯一責任文件追到受影響的上層導覽、跨層互動、生命週期、契約與驗收；更新已變的敘述及圖，不重寫無關文件或保留相互矛盾的現行說法。 |
| 退役功能／能力 | 從現行導覽、責任與流程圖、正式介面、操作說明及驗收入口移除或標明取代者；保留歷史決策、研究與實驗並標記適用階段，不把舊功能誤畫成仍在運作。 |
| Owner 決定產品效果或取捨 | 目標設計、重大決策紀錄、導覽中的狀態與未決項 |
| 介面、資料 authority、版本／引用規則、生命週期改變 | 唯一責任設計與受影響的互動／失敗情境；必要時決策紀錄 |
| 目標設計落成正式程式 | 現行架構圖、程式入口、操作說明及驗收狀態；移除仍把它標為「尚未實作」的文字 |
| 測試或真實使用發現反例 | 證據、受影響的設計假設與未決問題；先確認是否足以翻案，不直接改寫已確認決策 |
| 框架、provider、資料庫版本或部署方式改變 | 對應的契約與相容性聲明、運作／恢復程序、受影響驗收 |

維護採**同一變更、同一責任範圍**：程式或決策真的改了，相關文件就在同一工作單位修正；不要求每次重新審閱整套文檔。審查時至少核對：標題與狀態仍正確、圖和文字指向同一權責、生命週期中的觸發／提交／失敗仍成立、連結可找到、驗收主張沒有超過實際證據。暫時無法核實的段落標成「待核實」及原因，不裝作已驗證。

每一份持續維護文件要有明確責任範圍與維護者或維護角色；多人可貢獻，但**同一概念只指定一份現行權威說明**。其他文件以連結引用。新決策改變舊決策時，保留原記錄及 successor 關係；歷史快照不改成好像當年就知道新答案。過時入口要標明取代處或移離現行導覽；不刪除研究、實驗與失敗經驗。

這套維護方式是本案對 [Google 的文件維護與受眾原則](https://abseil.io/resources/swe-book/html/ch10.html)、[Microsoft 的架構規格狀態與交叉連結](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-design-specification)及[可追溯 ADR 歷史](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)的實務映射；不是要求導入額外文件平台或自動化工具。

## 7. 研究、審核與收斂規則

- 查**所討論層的第一手來源**：框架／SDK 用鎖定版本官方文件與必要原碼，資料庫用官方 PostgreSQL 文件，產品架構方法用其原始出版來源。可跨 OpenAI、Anthropic、Google、Microsoft、AWS 等公開資料找共同原則；不得把一家的特例或未公開底層實作宣稱為「全業界共識」。
- 每項會改變方案的主張分開標示：**官方明文／框架實測／跨來源共同原則／Caliburn 產品取捨／尚未驗證的推論**。記查閱日期、適用版本、穩定程度與限制；來源互相衝突時列出差異。
- 先找既有能力與反例，再比較是否沿用、薄接線或替換。可以變動現有架構，但需說出它無法達成的產品效果與替代方案代價；「改動最小」不是凌駕效果的目標。
- 只要新資料不再改變選項，或未知可由有界實驗回答，即停止廣泛搜尋。未驗證就標未驗證；不能用猜測施工，也不因追求「最新」而無限換方案。

## 8. 每輪結束與下一輪承接

每輪結束留下**簡短、可續接的結論**：

```text
議題／決策 ID：
這輪確認的產品效果與不變量：
現況證據與目標差距：
Owner 已裁決／仍屬候選／明確 OPEN：
本輪未決問題及其阻塞範圍：
影響的唯一責任文件與交叉連結：
可證偽的情境／下一個 gate：
```

若已形成產品裁決，將結論與理由記入**新架構的決策紀錄**；重大、難逆的取捨用 ADR 或等效可追溯決策紀錄，變更決策時另留 successor，而非覆寫歷史。若只是討論稿，保持討論稿狀態，不把它當作已批准施工。下一輪先看這份摘要與相應責任文件，**不重開已決問題，也不依歷史文件中的舊「下一步」直接動工**。需要翻案時指出新證據與受影響決策。這裡定義文件應如何分工，不強制沿用 Caliburn 舊文件目錄、既有 gate 編號或舊系統的切層。

## 9. 本規範與外部方法的關係

這不是某一家公司的完整模板，也不是聲稱存在唯一「2026 最新標準」。它選用多個公開、互補的方法：

- [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html)：架構描述的共通框架；不指定 Caliburn 必須採用某一套圖形工具。
- [C4 diagrams](https://c4model.com/diagrams)：不同縮放層次的靜態架構與支援圖；只畫有助回答問題的層次。
- [C4 dynamic diagram](https://c4model.com/diagrams/dynamic)：用靜態模型中的元素呈現重要執行互動；不要求為每個流程都畫圖。
- [arc42 runtime view](https://docs.arc42.org/section-6/) 與 [crosscutting concepts](https://docs.arc42.org/section-8/)：代表性時序、啟停、異常，以及跨層共同概念；不求包辦所有情境。
- [Kubernetes KEP 範本](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md)：目標／非目標、風險、替代方案、測試與實施歷史的提案紀律；Caliburn 不照抄其發版儀式。
- [Microsoft architecture design specification](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-design-specification) 與 [ADR guidance](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)：清楚的契約、營運／恢復、取捨與不可改寫的決策歷史。
- [Google Software Engineering：Documentation](https://abseil.io/resources/swe-book/html/ch10.html) 與 [Diátaxis](https://diataxis.fr/)：文件要有受眾、維護責任與用途，不把解釋、參考、操作與證據混成一份。

上述來源支持**分視角、用代表性情境揭露風險、記錄決策與取捨、維護可找得到的文件**。本文件的討論順序與分類欄位，是針對本產品討論需求作的明示取捨，不冒稱外部標準的逐字要求。
