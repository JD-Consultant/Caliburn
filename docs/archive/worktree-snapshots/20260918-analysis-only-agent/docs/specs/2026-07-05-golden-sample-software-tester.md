## 2. 工作摘要

負責公司 SaaS 產品「進銷存雲」各版本的**測試規劃、案例設計、執行與回歸**,配合雙週 sprint
節奏交付;同時負責**客戶問題單的重現與回報**(公司無獨立客服工程師,此職責由 QA 承擔)。
🗣「我一半時間在跑 sprint 的測試,另外很大一塊其實是幫客服重現客戶回報的問題。」

## 4. 核心任務深描(core 才有 12 槽全套;淺掃任務只留總表列)

### 4.1 任務 1.2 測試案例設計 📘T1.2

**公版深描(引用區)**:📘行為指標 P1.2.x(測試分析與設計)· 產出 O:測試計畫 ·
K:測試設計技術、測試層級、黑箱/白箱測試技術 · S:測試工具與技術使用能力、分析與解讀能力。

**客製細項(12 槽)**:

| 槽位 | 內容 | 出處 |
|---|---|---|
| 頻率 | 每 sprint(雙週)一輪 | 🗣 |
| 工作比重 | 20% | 🗣 |
| 單次耗時 | 約 2–3 個工作天/輪 | 🗣 |
| 數量批次 | 每輪新增或修訂 40–80 條案例 | 🗣「大 feature 那種一次就要寫五六十條」 |
| 觸發條件 | PM 開出 sprint backlog、需求評審會後啟動 | 🗣 |
| 準備材料 | 需求規格(PRD)、UI 設計稿、上一版缺陷清單 | 🗣 |
| 工具系統 | TestRail(案例庫)、Figma(對稿)、Jira(需求單)| 🗣 |
| 協作對象 | PM(需求釐清)、開發 Lead(可測性確認)| 🗣 |
| 等待瓶頸 | **等 PRD 定稿,常延遲半天到一天**;期間先寫框架後補細節 | 🗣「最卡的就是等 PM 改完規格」 |
| 例外處理 | 需求中途變更 → 在 TestRail 標記受影響案例、整批重審 | 🗣 |
| 完成標準 | 案例經 QA 組長審查通過;覆蓋該 sprint 全部驗收條件 | 🗣 |
| 產出 | 📘測試計畫 + 案例庫更新(TestRail)| 📘+🗣 |

### 4.2 任務 2.2 手動測試 + 版本回歸 📘T2.2

**公版深描**:📘P2.2.x(測試執行)· 產出 O:測試事件報告 · K:測試層級 · S:測試工具
與技術使用能力、資料備份和還原能力。

**客製細項(12 槽,節錄關鍵)**:頻率=每日零星 + **每雙週四上線前密集 2 天**🗣;比重 25%;
數量=回歸套件約 300 條(自動化跑 200、手動 100)🗣;觸發=每日 build 完成通知(Slack bot);
材料=回歸清單、測試環境帳號、上版 diff 說明;工具=staging 環境、Postman、自寫 pytest 腳本;
協作=開發(缺陷單來回)、DevOps(環境重建);**等待瓶頸=staging 環境被開發佔用時要排隊,
平均等 1–2 小時**🗣「環境只有一套,搶起來很痛苦」;例外=擋版缺陷(blocker)→ 立即通報
QA 組長 + 開發 Lead,當日修復重測;完成標準=回歸 100% 執行、無未解 blocker 才簽核放行;
產出=📘測試事件報告(Jira)+ 放行簽核紀錄。

### 4.3 任務 4.1 客戶問題單重現與回報 ⊕(無公版——純訪談產物,示範「公版外」寫法)

| 槽位 | 內容 | 出處 |
|---|---|---|
| 頻率 | 事件驅動,每週約 5–8 件 | 🗣 |
| 工作比重 | 15% | 🗣 |
| 單次耗時 | 30 分鐘–半天/件(能否重現差很多)| 🗣 |
| 數量批次 | 一次處理一件;客服月結時會集中湧入 | 🗣 |
| 觸發條件 | 客服在 Zendesk 升級(escalate)問題單指派給 QA | 🗣 |
| 準備材料 | 客戶操作錄影/截圖、該客戶的環境資訊(版本、瀏覽器)、匿名化測試資料 | 🗣 |
| 工具系統 | Zendesk、staging 環境、DB 查詢(唯讀帳號)| 🗣 |
| 協作對象 | 客服(補問客戶細節)、開發(確認是否已知缺陷)| 🗣 |
| 等待瓶頸 | **等客服向客戶要重現步驟,常等 1–2 天**;期間單子掛著 | 🗣 |
| 例外處理 | 無法重現 → 附詳細嘗試紀錄退回客服,請客戶提供更多資訊 | 🗣 |
| 完成標準 | 能重現 → 開 Jira 缺陷單附重現步驟;不能 → 退回紀錄完整 | 🗣 |
| 產出 | ⊕重現報告(Jira 缺陷單/退回紀錄)——**非公版產出** | 🗣 |

> ✏️ 註:此任務在職能面向上仍消耗 📘S「問題解決能力」「溝通協調能力」——公版 K/S 可引用,
> 即使任務本身是公版外的(**K/S 引用與任務客製是兩層,互不綁死**)。

## 附:本樣張同時示範的四個機制(給架構用)

1. **公版/客製兩層分野**:📘目錄引用(零幻覺區,受限解碼保證)與 🗣訪談客製內容
   (溯源+人審區)在同一份文件裡並存、標記可辨——顧問稽核時一眼分清哪句話有出處。
2. **抓漏實績**:R4 整條職責是「還有沒有沒提到的?」追問挖出來的(§3 註)。
3. **深問預算**:7 任務中 4 條 core 全套 12 槽、3 條淺掃——訪談時間花在刀口。
4. **覆蓋率自檢**:core 任務 12/12 槽、淺掃任務 4 槽(頻率/比重/產出/標準)——
   可機器檢查的完成度門檻雛形。
