# 職務說明書欄位與寫作指南

本指南提供 JD-R001 的**內容設計建議（Working recommendation）**，不是已核准的資料結構。Owner 於 2026-09-09 授權自主研究並完成建議與樣稿；不再逐項等 C01–C05 回覆，也不把這項授權當成每個細節均已核准。研究基準、決策效力及閱讀路由見 [研究入口](2026-09-09-job-analysis-and-jd-content-research.md)；完整來源見 [證據表](2026-09-09-job-analysis-international-evidence.md)。

**2026-09-10 最新格式裁決：**Owner大致同意[完整格式](2026-09-10-jd-format-review.md)，並固定成果、要求在任務底下兩組並列，不配對、不互為父子、不與任務敘述合併；以下同步此WORKING規則。「工作執行要求」為替代原「工作要求」的名稱推薦，未視為Owner已選定新名稱。其他內容研究與保存缺口見[整體核對](2026-09-10-jd-format-quality-and-storage-review.md)，其中舊合併呈現建議不再適用。

## 1. 文件要描述什麼

描述員工目前職位承擔的實際工作，而不是職業百科、每天工作日誌、理想組織設計或招募廣告。穩定指「可代表目前責任」，不是永遠不能修改，也不排除每年一次或有事件才發生的工作。

建議成品正文六章為：職務基本資料、職務目的、主要職責與工作任務、所需知識總覽、所需技能總覽、工作條件與責任邊界。成果及工作要求就近呈現在適用任務中，不另外重抄一章；不能由六章直接推出六張表或六個工具。O／P／K／S 只作既有研究的對照語言，不要求員工看到縮寫。

## 2. 內容總覽

「核心」指成熟文件應能回答的問題，不代表第一輪必填或不完整時禁止保存。「條件式」指有真實資訊且增加辨識力才單列；不靠 AI 為了填滿而補內容。

| 內容 | 意義／要填什麼 | 建議呈現 | 應避免 |
|---|---|---|---|
| **職務名稱** | 組織或員工使用的職位稱呼，必要時補足容易誤解的範圍 | 核心表頭 | 擅自升成主管、資深、策略職位；把員工姓名當職務 |
| **職務目的** | 替誰、透過哪類工作、達成什麼持續價值 | 核心短段落 | 廣告口號、年度成長目標、逐項重抄所有任務 |
| **主要職責** | 按工作目的／責任範圍組成的主要工作領域 | 工作多時分組；少時可直接列任務 | 只按案件名稱、工具或月份分組；無必要的多層樹 |
| **工作任務** | 本人對什麼採取什麼行動，達成什麼有意義的結果 | 核心完整敘述，可含必要條件 | 工具名稱當任務、無關工作塞一條、每個案例各立一項 |
| **工作成果／產出** | 執行工作形成、交付或維持的結果，可有多項；必要時交代具體交付物及接收用途 | 任務底下獨立分項；原研究 O | 為填滿而硬造報告；把整段任務原句機械重抄 |
| **工作執行要求（名稱推薦）** | 適當執行、完成或持續維持工作所需的品質、條件與異常處理，可有多項 | 任務底下另一組獨立分項；原研究 P；不與敘述合併 | 只看終點交付而漏執行中限制；憑空創造 KPI、時限、錯誤率 |
| **所需知識** | 做這些工作要理解的概念、原理、規範、領域內容 | 相關知識列表，可附必要範圍；原研究 K | 員工全部學歷、所有興趣、百科條目傾倒 |
| **所需技能** | 如何運用方法與專業完成工作、解決問題 | 相關技能列表；原研究 S | 把所有 Task 加上「具備……能力」重抄一次 |
| **責任／協作邊界** | 本人決定什麼、要交接什麼、誰核准、哪些事不由本人負責 | 有必要即呈現，可融入職責／任務 | 「我們做」直接寫成「本人全權負責」 |
| **工作關係與重要條件** | 實際單位／匯報關係、工作地點與環境、輪班／出差、重要觸發或限制 | 已知且有影響才寫 | 未知組織圖、職業常識推定的工時／體力要求 |
| **必要資格／授權** | 此職位確實需要的資格、許可或授權，不等於這名員工剛好擁有的證照 | 條件式，須有可靠依據 | 自動推定學位、年資、證照或法定要求 |
| **文件識別與日期** | 文件版本、檢視日期等管理資訊 | 系統／人工管理，不是分析內容 | 要模型猜 ID、版本號、完成時間或批准狀態 |

這張表是本研究的選擇，不是十二個國際統一欄位。可比的官方內容包括 OPM 的主要責任敘述、SAP 的責任／技能／條件內容，以及 O*NET 的工作活動與工作情境；它們沒有共同規定相同的 UI 或資料表。[OPM USA Class](https://support-class-usadata.opm.gov/hc/en-us/articles/51115834989843-Major-Duties-Statements-Overview)、[SAP Job Profile Builder](https://learning.sap.com/courses/sap-successfactors-platform-advanced-and-talent-intelligence-hub-academy/managing-job-architecture-with-job-profile-builder-jpb_ba59a2d8-e04d-41d9-812e-eea5a8387995)、[O*NET Content Model](https://www.onetcenter.org/content.html)

### 2.1 基本資料與職務目的（JD-R001/C01）

狀態：**依授權形成 Working recommendation，已用於完整樣稿**。只決定成品內容，不決定必填驗證、資料表、AI 編輯權限或 UI 控制。

本研究建議採「簡短識別＋職務目的＋必要時補工作定位」，而非完整人事表頭：

| 內容 | 建議與邊界 |
|---|---|
| 職務名稱 | 使用真實職位稱呼；必要時用範圍補充辨識，不由 AI 自行升成資深／主管或替公司改職稱 |
| 單位／工作定位 | 真有資訊且有助於理解職位時呈現；接案或無正式部門者不硬造部門 |
| 匯報關係 | 有需要且已確認才列對應職位／角色；協作對象不自動當主管，也不由職稱推定組織圖 |
| 職務目的 | 一段短文交代服務對象、主要工作範圍與持續價值；不重抄全部任務，不寫未確認的未來績效目標 |
| 文件管理資料 | 與工作內容分開；如要顯示版本／日期，不能讓 AI 捏造。具體保留哪些管理資料及怎麼產生，後續再議 |

員工姓名是文件歸屬資訊，不能代替職務名稱；是否在成品表頭顯示姓名，本題不強制。學歷、年資、薪資、職等也不是為了表頭完整就全部必填；真正必要的職務資格留到 C05 依工作用途討論。

兩種可行呈現：僅「名稱＋目的」最精簡，但可能分不清同名職位的實際定位；**按需要補單位／匯報角色**較能界定範圍，因此優先建議後者。這些仍是內容建議，不是要求新增組織管理功能。

沿用本研究的虛構接案前端職位作短例：職務名稱為「接案前端工程師」；職務目的為「依客戶確認的需求交付可使用、可維護的網站前端，並處理約定範圍內的交付與維護事項。」沒有已提供的部門或主管就不補。A／B 網站名稱、某次逾時處理及所有細項任務不擠進目的段落。

**寫在前面不等於訪談第一輪就必須定稿。** 目的要能概括已理解的整份工作；後來發現其他有效責任時可修訂，不能反過來用早期的一句目的排除新工作。這是為符合完整工作分析而提出的產品取捨，不宣稱官方規定固定句長或撰寫順序。

官方依據：SAP JPB 將 Headers、Short／Long Descriptions 及 Job Responsibilities 列為不同內容，並允許按模板配置。它支持識別、概述與詳細責任可以分開呈現；**不證明每家都採同一表頭，也不要求 Caliburn 引入其工作族、職等或物件模型**。[SAP 官方教材：Job Profile Content Types／Dependencies](https://learning.sap.com/courses/sap-successfactors-platform-advanced-and-talent-intelligence-hub-academy/managing-job-architecture-with-job-profile-builder-jpb_ba59a2d8-e04d-41d9-812e-eea5a8387995)。其餘分析原則仍沿用 [研究證據表 US1–3](2026-09-09-job-analysis-international-evidence.md)。

本題審查標準：讀者看完開頭能知道這是什麼職位、主要為誰做什麼；沒有虛構組織關係、案例堆砌或未確認目標。完整樣稿另採「受雇於網站服務公司的前端工程師」，組織與權限均由明示的虛構情境提供；不是從上面短例猜出部門與主管。新責任無法被目的涵蓋，或樣稿顯示資訊不足時可重開。

## 3. 職務目的、職責、任務：同一份工作的不同縮放程度

以下均為虛構示例。

**職務目的**：「依客戶需求交付可使用、可維護的網站前端，並處理約定範圍內的上線及維護事項。」

**主要職責**：「網站前端開發與交付」。說明不是必須；只有名稱無法交代範圍時才補一句。另一項明確不同的責任可為「約定範圍內的維護與問題處理」。

**工作任務**：「依確認的需求與設計稿實作網站頁面及互動，串接約定的資料介面。」另一項可為「檢查主要操作情境並修正前端缺陷，配合客戶完成交付確認」。這是示例切分，不是規定所有前端職位都一定兩項。

### 任務句怎麼寫

先回答「做什麼、對什麼」，再加入缺了就容易誤解的目的、結果、方法或情境。不是每句都得包含所有成分。O*NET 寫作附錄明確允許簡單的動作＋對象，也允許較完整的句子；其 2025 更新方法仍以這些語意比較新工作和既有工作。[寫作附錄 pp.7–8](https://www.onetcenter.org/dl_files/GreenTask_AppB.pdf)、[2025 更新方法 p.10](https://www.onetcenter.org/dl_files/EmergingTasks_RevisedApproach.pdf)

**閱讀版的短標題不等於完整任務。** [樣稿 r2](2026-09-09-frontend-engineer-jd-sample.md)把較長的敘述分成標題、說明及就近要求；這些共同承載任務內容，不能後續只保留標題就聲稱已保留完整工作。這是閱讀選擇，不是要求新增「標題／說明／執行時機」三個必填欄位，亦不指定底層保存方式。

| 不理想 | 較好的方向 | 理由 |
|---|---|---|
| 使用 Excel | 核對進出貨資料與庫存紀錄，追查不一致項目 | 工具不等於工作；具體內容仍須訪談支持 |
| 處理客戶的事 | 受理客戶產品使用問題，釐清原因並提供可行處理方式 | 能辨識對象、處理及結果 |
| 開發 A 網站、開發 B 網站 | 依委託需求開發網站前端；特殊差異保留於相關條件或案例 | 不是每個客戶一個永久任務 |
| 執行採購並管理社群 | 分別描述採購與社群工作 | 無共同成果的工作不硬併 |
| 開會、寄信、打電話 | 若都是同一協調責任的方法，可寫協調對象、事項與目的 | 相同手段可服務不同任務，不能只憑動詞決定 |

拆分判斷看能否分別辨識工作目的、成果、責任與變動範圍；不要因一句有「並」就自動拆。合併也不是只算字詞相似度。O*NET 2025 區分「已涵蓋的重複」與「相似但帶來新細節的重疊」；本產品可學此區別，但不照搬其職業資料庫的收錄門檻。[更新方法 pp.7–10](https://www.onetcenter.org/dl_files/EmergingTasks_RevisedApproach.pdf)

**不逐案立任務，不等於刪除所有產品／系統名稱。** 本人長期負責的固定平台或服務範圍若是辨識責任所必需，應依實際資訊保留；單次案件則通常作分析佐證。此區別及 HDR UK／LEGO／Central Saanich 實例集中見[雇主比較§4](2026-09-09-employer-job-document-comparison.md#4-橫向比較共同可學與不可硬湊的差異)，不能靠名稱本身判斷是否成為獨立任務。

**同一最終目的不代表同一任務。** 釐清需求、估算、開發、交付、維護都可能為了交付網站，但合成一長句會遮蔽責任。檢查方式是：其中一部分若取消或改由別人負責，還能清楚看出剩餘工作嗎？不能時考慮分項。這是樣稿審查判準，不是官方固定拆分算法；O*NET 寫作附錄允許多動作，也建議複雜行動／目的組合考慮拆分。[US4 pp.7–8](https://www.onetcenter.org/dl_files/GreenTask_AppB.pdf)

### 何時開始寫、何時修正

2026-09-09 Owner 補充的 WORKING 原則：**先把某項任務大致理解清楚，資訊足以支持工作敘述時才寫；不是每輪訪談都改 JD。**零碎線索與案例可以先累積，重述或新增佐證不必造成改稿；實質補充或更正影響責任、條件、例外或完成要求時，再修正受影響內容。

這不要求固定輪數、填滿欄位或等整份訪談結束。已能說清的內容可先寫，重要未知仍保留；最後再做全份雙向核對。此節是本產品的撰寫節奏，不宣稱跨廠有統一的成熟度分數，也不更動既有 Memory 生成時機。App 接線及效力見[JD 編輯器候選 §2.1](2026-09-09-jd-editor-framework-decision-candidate.md#21-訪談理解與改稿節奏)與 [register](../current-decisions.md)。

## 4. 成果／產出與完成標準，不是同一件事

**成果／產出**回答「形成或維持了什麼」；**完成標準**回答「怎樣才算適當完成」。可一起閱讀，但不應只是同義重複。

| 工作 | 成果／產出示例 | 完成標準示例 |
|---|---|---|
| 法規影響分析 | 制度影響與修訂建議 | 涵蓋受影響制度、說明依據及待確認事項 |
| 設備修復 | 恢復可運作的設備；需要時有維修紀錄 | 完成適用的安全／功能檢查；未排除風險不得交付使用 |
| 客戶諮詢 | 問題獲得解答或轉入適當處理 | 先確認需求；不能處理的部分清楚說明並適當轉交 |
| 網頁交付 | 可操作的前端頁面 | 符合已確認的主要操作與錯誤情境，未解限制有說明 |

以上是示例，**不能不經訪談就寫成某員工的既定要求**。服務結果、維持狀態也有意義，不一定每項工作都有獨立檔案、報告或物件。

即使參考 iCAP，其規則也不是每項任務必有獨立 O：僅有行動／操作性成果時可不列，官方「建議」在 P 描述成果。這不等於沒有成果，也不限制我們只能輸出 iCAP 版型。[iCAP 職能相關概念 §2](https://icap.wda.gov.tw/ap/knowledge_introduction.php)

另須分清「這次實際怎麼做」與「合理完成的要求」。案例中曾經漏檢、趕工或逾期，不可自動被整理成正常完成標準；要求不明時應釐清，不能由 AI 替組織制定或認證標準。這是本研究建議的事實／要求分界。

UK NOS 的 performance criteria 描述達到合格表現所需的行動與條件；澳洲也區分工作表現與證明能力的評量證據。這支持釐清「合理完成」，不支持把評量次數直接當工作量。[NOS §5.7](https://ukstandards.org.uk/media/kqppvuwl/sds-nos-quality-criteria-update-13-05-2024.pdf)、[澳洲 TPOF Appendix A](https://www.dewr.gov.au/download/16680/training-package-organising-framework-effective-1-july-2025/39042/training-package-organising-framework/pdf)

### P 的建議名稱與數字邊界

2026-09-10 Owner續問更合適名稱，本輪推薦「工作執行要求」。相較「執行要求」明說是工作履行，相較「工作標準」較少統一規範／考核門檻的暗示；這是本案命名判斷，不是已驗證員工偏好。原「工作要求／工作完成要求／完成要求／完成標準」均對應同一概念，不是新增另一種P；歷史樣稿保留原標籤。此中文名稱未經Owner另行選定，也不宣稱國際統一譯名。內涵包括執行中條件、成果品質、交付檢查、異常轉交及持續維持，不只終點驗收。[NOS §5.7](https://ukstandards.org.uk/media/kqppvuwl/sds-nos-quality-criteria-update-13-05-2024.pdf)

**依Owner裁決固定分開呈現，不再按重複程度決定是否合併。**任務敘述交代工作，成果列形成或維持的結果，要求列應符合的條件；寫作避免機械重抄，但不因此省掉某組。未知可先缺，不假填或堵住草稿保存。頻率及條件不可跨範圍套用：「特定案件每月維護」不能變成「所有案件每月維護」。NOS 區分影響表現的範圍條件與一般例子，支持保留差異，不規定本案排法。[NOS §5.10](https://ukstandards.org.uk/media/kqppvuwl/sds-nos-quality-criteria-update-13-05-2024.pdf)

**數字不是一律禁止，也不是 AI 可以自由創造。** 若員工明確說明本職位有一項已確認的固定期限或品質要求，數字可能是必要工作條件；若是下一季成長率、個人目標或考核權重，則屬下游績效設計。OPM 的績效標準指引允許數量、品質、時效等衡量，也允許可觀察而非數字的描述；其管理核准與評等程序不是本產品自動取得的權限。[OPM Performance Standards](https://www.opm.gov/policy-data-oversight/performance-management/reference-materials/articles/developing-performance-standards/)

例：「每月 5 日前交付月報」若是確認的責任期限，可以記錄；「錯誤率必須小於 0.1%」若未被提供，不可為了專業感補上。單次月報恰好 5 日完成，也不代表固定期限。

### 多項成果、要求與條件的適用位置

一任務可以有多個成果及多項要求，兩組均在任務底下並列，不一對一、不互為父子、不與任務敘述合併。要求可以約束執行過程、單項或多項成果，以及持續維持；需辨識對象時在要求文字中明說，仍保留在任務的要求組。

時機／頻率、適用條件／例外、分工／權限依實際範圍表達：整項任務的限制寫在任務敘述；成果說明列內容與接收用途，約束成果的品質／期限等要求仍列在任務的要求組，文字明指該成果。某項要求的適用條件與該要求寫在一起；確實是本職位跨任務共通的條件才集中。不能靠位置自動繼承，也不設三個固定通用值。必要輸入、本人判斷、成果接收者及交接仍須讀得出來；減欄不等於刪掉這些資訊。既有r2的月檢、查詢／訂單例外及交付案例對照見[內容核對附件](evidence/2026-09-10-jd-content-scope-quality-audit.md#4-適用範圍的正反例)。

## 5. 知識與技能如何寫

知識是需要理解的內容，技能是將專業用來完成工作或解決問題的能力。ESCO 的 skill 定義包含運用知識與方法，並不限於手工操作。[ESCO Skill](https://esco.ec.europa.eu/en/about-esco/escopedia/escopedia/skill)

| 工作情境 | 知識的適當方向 | 技能的適當方向 |
|---|---|---|
| 網站前端 | 網頁結構、瀏覽器行為、資料介面與錯誤處理概念 | 實作互動頁面、診斷前端與介面整合問題 |
| 設備配修 | 設備構造、故障機理及適用安全要求 | 判讀測試結果、定位故障、調整及驗證設備 |
| 法規諮詢 | 適用法規、組織制度及解釋限制 | 比較規範差異、分析制度影響、清楚溝通建議 |

寫到足以辨識專業範圍，避免「資訊知識」「溝通能力」無所不包，也不列出用不到的全部技術名詞。工具名稱在確實構成職務要求時可以保留，但「曾用某工具」不自動證明該工具是所有接任者的硬門檻。

同一知識或技能可支援多項工作。**本輪樣稿採職務層級的知識／技能總覽，說明必要的用途及適用範圍**，避免每項任務重抄一份。按「內容、用途、範圍」去重，不只比名稱；必要的任務特有專業仍可在當處補明。用途一眼可知時不必固定加一欄。這是閱讀取捨，不是已決定 UI 或多對多資料表。

2026-09-10 Owner大致同意[整份格式](2026-09-10-jd-format-review.md)，包含任務↔知識、任務↔技能兩組明確對應，作可修訂WORKING方向。同一項正文保留一份，反向對應由同一組關係呈現，不要求模型再填第二份清單；不用空白連結假裝已完成專業核對。現行技術契約的項目識別、首次建立與引用缺口見[保存核對](2026-09-10-jd-format-quality-and-storage-review.md#64-採-a-時仍必須補齊的效果)。

這不是宣稱各家都集中 K／S：iCAP 將其連到任務，新加坡 Media 的示例則在職位頁呈現技能清單。兩種方式都能表達工作與專業的關係，樣稿優先選少重複的方式，再檢查有沒有丟失用途。職業參考庫只能提醒追問，不能證明員工實際需要其中每一項。[iCAP 指引 pp.37、73](https://icap.wda.gov.tw/ap/get_file.php?c=%E8%81%B7%E8%83%BD%E5%9F%BA%E6%BA%96%E7%99%BC%E5%B1%95%E6%8C%87%E5%BC%95.pdf&e=20221026143138.pdf&t=download)、[SF Media PDF pp.11–12](https://www.imda.gov.sg/-/media/imda/files/how-we-can-help/media-manpower-plan/skills-framework-for-media-2025.pdf)

### 態度、級別、資格

本候選不另外設 A 或能力級別欄位。這不是說安全、倫理、協作不重要：若直接影響工作，寫成具體責任、完成要求或技能，例如「在授權範圍內使用客戶資料」，而不是無法驗證的「品格良好」。

另須區分縮寫：iCAP 的 Attitude 與 O*NET 的 Abilities 不是同一概念。不設 A 欄，不代表略過工作確實涉及的體力、操作、感官辨識或持續注意要求；有必要時在工作條件或任務中具體說明，而不是評斷員工身體狀況或新增能力分數。[iCAP 概念](https://icap.wda.gov.tw/ap/knowledge_introduction.php)、[O*NET：Abilities](https://www.onetonline.org/find/descriptor/browse/1.A)

主管是否有決策權、工作是否複雜，應理解並如實描述；不自動轉成六級、七級或八級量表。將來若要能力評量，需另選適用體系及判定依據。

資格、技能與決策權分別核實：持有證照不等於職位必須持有，具備技能也不等於有簽署、採購或人事核准權。資料未知不能寫成「不需要」。任務特有的限制留在任務，真正共通的條件再集中；必要的短句重述比為去重而造成誤導更合理。SAP 將 Certification、Education、Employment Condition、Physical Requirement 分列，能支持概念區分；其中 Employment Condition 比工作環境更廣，不能僅因名稱相似就一對一套用。[SAP Job Profile Content Types](https://learning.sap.com/courses/sap-successfactors-platform-advanced-and-talent-intelligence-hub-academy/managing-job-architecture-with-job-profile-builder-jpb_ba59a2d8-e04d-41d9-812e-eea5a8387995)

## 6. 什麼留在分析，什麼進 JD，什麼留待下游

| 資訊 | 分析／Memory | JD | 下游文件 |
|---|---|---|---|
| A 案處理了哪個逾時情境 | 保留可辨識的重要情境與處理 | 只在能界定職務時提煉其要求 | 可作甄選或訓練案例，但需另設題目 |
| B 案另約定每月維護 | 保留 B 的適用範圍 | 描述約定維護責任，不套到所有案件 | 可延伸維護能力訓練 |
| 後端規則不由本人決定 | 保留，避免誤分析 | 必要時呈現責任邊界 | 招募可據此避免要求全端責任 |
| 員工今年想學某技術 | 保留為意願，不能當既有工作 | 通常不進 | 個人發展另談 |
| 一次成功降低成本 20% | 保留案例事實與條件 | 不自動變成每年降 20% 的責任 | 經確認可作績效案例；新目標另訂 |
| 一位接任者必須持有的法定許可 | 待可靠核實 | 必要時列真實要求 | 招募應再核實最新法規 |

JD 描述工作的要求，不是判斷員工本人已達到所有要求。個人能力缺口、評分、訓練課綱、考核週期、薪資福利，以及與實際職務無關、未核實或僅供招募篩選的門檻，不要混入核心文件。已核實且執行工作真正必要的資格或授權，仍可列為職務要求，不能因它也會用於招募就一概排除。特定法域的必要揭露應在實際用途與法域明確後另行核查；本指南不作跨國合規模板。

## 7. 最後讀一遍時要看什麼

不用檢查每個格子有沒有字，而是檢查：讀者能否知道做什麼、為什麼、負責到哪裡、怎樣算完成、需要什麼專業；全份是否漏工作或重複；每項是否有真實根據；有沒有把案例、願望、他人工作或未確認目標寫成這個職位。

可以有不同職位的不同長度。責任少的職位不必為了整齊造 Duty；責任多的職位也不能為了固定「八項」上限刪工作。格式精簡與範圍完整應同時達成，不能互相取代。

客製化不能只改職稱與公司名。省去某項已知差異會讓人誤解工作對象、判斷、權限或條件時，就應在適當位置寫清楚；未知不能補造，單次案例也不必逐案入JD。具體三種深度及研究限制見[客製化校準§5](2026-09-09-customized-jd-depth-and-interview-calibration.md#5-樣稿三種深度對照)，不是再加一組固定欄位。
