# 接案前端網站開發與維護

## 工作角色與共同做法
- 員工自述為接案前端工程師，依不同客戶需求開發與維護網站，並非只負責單一固定網站。
- 工作流程包括了解客戶需求、製作畫面、串接後端 API，以及進行上線前測試；在青禾案例中，開始製作前也會確認畫面、會員功能、API 回傳狀態與驗收條件，遇到不清楚之處會回問。
- 青禾與雲岸採共同的開發與驗收方式：先對照已確認需求與重現步驟，判斷驗收問題是否屬於原定範圍內的缺陷。前端呈現或狀態處理錯誤由員工修正；API 回應不符合文件時，員工整理請求、回應及操作步驟交後端釐清，再做畫面回歸測試。修正後員工先自行測試相關正常與失敗流程，更新測試站，再請客戶產品負責人重新驗收。若屬新增需求，員工會先確認工作範圍，不自行承諾全部處理。
- 維護期間每天排查客戶回報的問題，通常收到當天先確認影響範圍，但沒有保證當天修完；每週五彙整所有專案的未結問題、原因、接手者及下次追蹤點。正式上線後，員工會依問題收集發生時間、帳號代碼與操作步驟，在測試環境重現並查看瀏覽器主控台與網路請求；前端問題由員工修正，API 問題則提供請求與回應交後端處理，不自行判定扣款失敗或代客退款。修正先上測試站驗收，客戶確認後由員工部署前端正式版並記錄版本與回退步驟；後端 API 修正由後端部署，員工做畫面回歸。客戶確認原問題未再發生且相關功能正常後結案。
- 每案員工會把已確認的畫面清單、API 串接項目、包含與不包含的功能、驗收情境及客戶指定的確認窗口整理在同一份交付說明中，先請客戶確認，再作為測試與驗收依據；需求經核准而變動時同步更新整份文件，不只修改報價或工時。
- 每個案子都會交接前端操作與維護資訊，包括啟動方式、環境變數名稱與用途、部署與回退方式及已知限制；文件不放真正的密碼。每案首次交付做一次操作說明，重大變更時才另行追加說明，但文件只要受變更影響就會更新。這項交接範圍是前端操作與維護資訊，不包含接手後端維運或客戶後續全部客服工作。
- 套件升級曾被提及，但一次實際升級的觸發原因、影響評估方式，以及如何驗證升級後仍可交付，尚未回答。
- 扣款、退款核准及後端維運不在員工責任範圍。

## 個別案例
- **青禾／會員訂閱網站**：客戶產品負責人彙整需求交給員工。員工開始製作前確認所需畫面、會員可使用的功能、API 回傳狀態及驗收條件，不清楚時回問；依客戶設計稿製作響應式畫面與操作狀態，串接會員權限 API 及付款狀態 API。測試依清單涵蓋手機、桌機、正常流程與失敗提示；完成後先放測試站，由客戶產品負責人驗收，對方確認後員工配合上線。首次交付時，員工會示範一般會員與付費會員的操作差異、付款成功後的畫面變化，以及發生問題時客戶需要提供的資訊；這不表示員工承接後續後端維運或全部客服責任。
- **青禾的驗收問題與責任界線**：驗收發現問題時，員工先依已確認需求及重現步驟判斷是否為原定範圍內的缺陷；前端呈現或狀態處理錯誤由員工修正，API 回應不符文件時整理請求、回應及操作步驟交後端釐清，之後做畫面回歸。修正後員工自行測試正常與失敗流程、更新測試站，再請客戶產品負責人重新驗收；若是新增需求，先確認範圍，不自行承諾全部處理。扣款由後端執行，員工沒有扣款或退款核准權。需求由客戶產品負責人彙整，但需求變更由客戶營運主管核准。正式上線後，曾遇到客戶回報已付款卻看不到會員內容：員工收集發生時間、帳號代碼及操作步驟，在測試環境重現並檢查瀏覽器主控台與網路請求，判斷該次付款成功但前端收到成功狀態後未刷新權限畫面；員工修正更新流程，測試成功、失敗及逾時狀態，附截圖與重現步驟交產品負責人確認。若 API 本身錯誤，提供請求與回應交後端，不自行判定扣款失敗或代客退款。修正先上測試站，客戶確認後由員工部署前端正式版並記錄版本與回退步驟；後端 API 修正由後端部署，員工做畫面回歸。客戶確認原問題未再發生且相關功能正常後結案。員工每天排查客戶回報，通常收到當天先確認影響範圍，但沒有保證當天修完；每週五彙整所有專案的未結問題、原因、接手者及下次追蹤點，不限於付款問題。
- **雲岸／課程報名網站**：只做課程報名、不做金流；員工負責串接報名 API、製作報名表單與送出狀態。員工依測試清單檢查手機、桌機、正常流程、錯誤流程及重複點擊，完成後放到測試站交由客戶驗收。雲岸與青禾採共同的開發方式；兩案差異須保留：青禾有會員權限與付款狀態，雲岸沒有付款或退款功能。曾遇到使用者連點報名鍵導致前端送出兩次：員工以測試帳號重現，從網路請求確認送出時按鈕仍可持續點擊，加入送出中狀態、停用重複觸發，並在成功或失敗後恢復操作；同時將重現步驟與請求記錄交後端，因後端仍需做冪等防護，員工不以按鈕停用保證永不重複。雲岸維護同樣先在測試站驗收，客戶確認後由員工部署前端正式版並記錄版本與回退步驟；後端自行部署服務，員工測試相關畫面。客戶確認原問題不再發生且其他功能正常後結案。客戶內部退款最終核准者未知，且不屬員工權限；雲岸本案不含金流，該未知不影響員工排查前端。雲岸交付說明會明載本期不包含候補名單與金流；候補名單雖曾討論與估算，但未列入本期交付。兩案前端維護分工大致相同，但青禾付款成功未刷新權限畫面與雲岸連點重複送出是不同案例。
- **雲岸／開案與新增範圍估算**：每個新案開始或新增範圍時進行，不是每週固定估算。員工先釐清使用者、主要操作、所需畫面、要串接的 API、驗收條件及不包含項目，再將畫面製作與 API 串接拆開，確認依賴、風險與預估時間；API 文件不清楚時先列問題詢問後端，不自行假定 API 具備某項能力。估算交給客戶決定範圍與時程，員工沒有核准追加預算的權限。範圍縮減或追加獲核准後，員工會更新畫面清單、API 串接項目、驗收條件與估算，並與指定核准窗口確認，不只調整工時數字。雲岸後來討論候補名單，員工確認涉及候補畫面與 API 並另行估算；因本期時間不足，客戶決定不做，因此目前已交付範圍不包含、也尚未開發候補名單功能。交付說明會把已確認的畫面清單、API 串接項目、包含與不包含功能、驗收情境及客戶指定確認窗口整理在一起，先由客戶確認，作為測試與驗收依據；因此候補名單與金流會明載為本期不包含項目。

- **雲岸／課程報名網站**：只做課程報名、不做金流；員工負責串接報名 API、製作報名表單與送出狀態。員工依測試清單檢查手機、桌機、正常流程、錯誤流程及重複點擊，完成後放到測試站交由客戶驗收。雲岸與青禾採共同的開發方式；兩案差異須保留：青禾有會員權限與付款狀態，雲岸沒有付款或退款功能。曾遇到使用者連點報名鍵導致前端送出兩次：員工以測試帳號重現，從網路請求確認送出時按鈕仍可持續點擊，加入送出中狀態、停用重複觸發，並在成功或失敗後恢復操作；同時將重現步驟與請求記錄交後端，因後端仍需做冪等防護，員工不以按鈕停用保證永不重複。雲岸維護同樣先在測試站驗收，客戶確認後由員工部署前端正式版並記錄版本與回退步驟；後端自行部署服務，員工測試相關畫面。客戶確認原問題不再發生且其他功能正常後結案。客戶內部退款最終核准者未知，且不屬員工權限；雲岸本案不含金流，該未知不影響員工排查前端。雲岸交付說明會明載本期不包含候補名單與金流；候補名單雖曾討論與估算，但未列入本期交付。兩案前端維護分工大致相同，但青禾付款成功未刷新權限畫面與雲岸連點重複送出是不同案例。
- **雲岸／開案與新增範圍估算**：每個新案開始或新增範圍時進行，不是每週固定估算。員工先釐清使用者、主要操作、所需畫面、要串接的 API、驗收條件及不包含項目，再將畫面製作與 API 串接拆開，確認依賴、風險與預估時間；API 文件不清楚時先列問題詢問後端，不自行假定 API 具備某項能力。估算交給客戶決定範圍與時程，員工沒有核准追加預算的權限。範圍縮減或追加獲核准後，員工會更新畫面清單、API 串接項目、驗收條件與估算，並與指定核准窗口確認，不只調整工時數字。雲岸後來討論候補名單，員工確認涉及候補畫面與 API 並另行估算；因本期時間不足，客戶決定不做，因此目前已交付範圍不包含、也尚未開發候補名單功能。交付說明會把已確認的畫面清單、API 串接項目、包含與不包含功能、驗收情境及客戶指定確認窗口整理在一起，先由客戶確認，作為測試與驗收依據；因此候補名單與金流會明載為本期不包含項目。
