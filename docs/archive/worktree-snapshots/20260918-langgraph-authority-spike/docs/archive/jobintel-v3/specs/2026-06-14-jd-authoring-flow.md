# JD 撰寫流程（完整版）

> 使用者撰寫職務說明書的完整步驟流程。本文件只談**使用者流程**，不談內部實現（graph/元件留待實現討論）。
> 狀態：流程已收斂。
> 互補：[schema v3](../../../jd-ocs-indexer/docs/superpowers/specs/2026-06-14-schema-v3-design.md)（資料）、[整合設計](2026-06-14-jobintel-ocs-integration-design.md)（角色分工）、[決策紀錄](../../../jd-ocs-indexer/docs/superpowers/specs/2026-06-14-v3-decision-log.md)。

---

## 目標與分工

- **目標**：產出**完整（滿分）的職務說明書**，同時**控制時長**。
- **分工**：`jd-ocs-indexer` = 無狀態知識服務；`jobintel-ai` = 流程 + 使用者狀態 + LLM 顧問 + 產出。
- **OCS 永遠是參考 + 完整度標尺，不是模板**；最終 JD 用使用者自己的編號/排序。

---

## 貫穿全程的兩個模式

**① 可選 + 可編輯清單**：除了 O/P，每個「選」的階段都同一套——
```
給選單（從 OCS 來）→ 勾選 → 進可編輯清單
   可：排序 / 改名 / 改內容 / 新增 / 刪除 / 改代號
   可：跟 LLM 討論，LLM 幫忙新增或修改
```
共 4 個選單套這個：**任務、K/S、態度、建議條件**。

**② 每個使用者項目的狀態**（jobintel-ai 管）：
```
{ 來源: (ocs_code, 原始id) | null(自訂),
  內容改過?: bool,
  使用者自己的: { 編號, 排序, 名稱, 內容 } }
```
→ `來源 + 內容改過` 決定後續「by-id 取 vs 向量找」。

## 完整流程

```
1. 描述工作 → 選職位（1 主 + N 副）
2. 任務選單（合併）→ 勾選
3. 自訂任務清單  ← 建立「有哪些任務」（廣度）
        ▼
4. 細節訪談（T/O/P）  ← 深入「每個任務怎麼做」（深度）
        ▼               依序逐任務、共享上下文、可暫停
5. 每任務 level + K/S 選單  ← 全部談完後批次列
        ▼
6. 態度選單
7. 說明與補充（建議條件選單 + 補充參考）
8. LLM 白話覆述 → 確認完整 / 回頭優化
```

### Step 1 — 描述工作 → 選職位
- **做**：使用者一兩句描述工作 → 列候選職務 → 選 **1 主 + N 副**（1-3 個 OCS）。
- **資料**：profile 向量搜尋（embed 含職務描述+工作內容+技能，tool 詞命中）。
- **LLM**：可選——描述太模糊時引導補一句。

### Step 2 — 任務選單（多職位合併）→ 勾選
- **做**：合併選定職位的任務做成表格讓使用者勾「我做哪些」。**輕量顯示：task 名 + 1-2 句活動（秒認）**。
- **資料**：撈選定 ocs_code 的所有任務（完整、含無能力區塊的任務），按單元分組。
- **state**：勾選的任務記下來源 `(ocs_code, task_id)`。

### Step 3 — 自訂任務清單（廣度：有哪些任務）
- **做**：勾完進可編輯清單——排序/改名/改內容/新增/刪除。**也可跟 LLM 討論工作，LLM 幫忙新增或修改任務**。
- **資料**：自訂/LLM 新增的任務 → 向量找最像的標準任務（標來源、繼承候選 K/S 給後續用）。
- **state**：自訂任務 `來源=null`；改過內容的標 `內容改過=true`。
- **性質**：快速、選單式。**只決定「做哪些」，不決定「怎麼做」**。

### Step 4 — 細節訪談（深度：每個任務怎麼做）→ 產 T / O / P
- **做**：LLM 顧問逐任務深問，產出每個任務的 **T（任務）/ O（產出）/ P（行為指標/流程）**——使用者自己的真實內容。
- **方式**：**依序逐任務，但全程共享上下文**——
  - LLM 心裡一直有「全部任務 + 已累積的回答」→ 能問跨任務連結（「T2 整理的資料是 T3 在用嗎?」）、不重複問（「T1 提過 Python，T2 也是?」）、產出連貫的工作流。
  - **任務之間是自然停點**，可暫停、下次接續（疲勞友善、控時長）。
- **OCS 的角色**：task 的 `activity_examples`（P 參考）、`output_pairs`（O 參考）當**訪談背景 + 補漏提示**（「OCS 這任務通常產出 X，你有嗎?」），**不是選單**。
- **LLM**：顧問式追問（5W2H 精神：情境/目的/協作/工具/步驟/產出/品質/時效），引用 OCS 原句對照但不逼照唸。

> **O / P 不做選單**：它們是細節訪談的直接產物（問「怎麼做、產出什麼」就得到）。只有 **K/S 要選單**，因為 K/S 是「對應到標準命名的能力代碼」、要從標準清單選。

### Step 5 — 每任務 level + K/S 選單 → 勾選 → 可編輯
- **做**：全部細節談完後，**批次**列每個任務的 **能力級別 + K/S 選單**讓使用者勾。勾完進可編輯清單（刪/增/改名/改內容/排序/**改代號**）。
- **為什麼批次 + 放最後**：此時 LLM 有完整上下文，K/S 建議更準；使用者一次看全部好比較。
- **資料**（依任務狀態）：
  - 有來源且**內容沒改** → **by-id** 取該標準任務 → K/S + level。
  - **自訂或內容改過** → **向量**（用當前內容）找最像標準任務的 K/S 當建議。
  - 向量是保底（永遠對）；by-id 是沒改時的捷徑。
- **state**：使用者的 K/S 用自己的代號（JD-local）。

### Step 6 — 職能內涵（A 態度）選單 → 勾選 → 可編輯
- **做**：列態度選單讓使用者勾，可新增/刪除/自訂/排序。
- **資料**：合併選定職位的態度池（態度是職務級）。

### Step 7 — 說明與補充事項
- **7a 建議學歷/經驗/能力條件**：**選單**（勾選 + 自訂）。資料 = 合併選定職位的建議條件。
- **7b 其他補充說明**：**參考**（給 LLM 當背景 + 使用者要引用再貼，不做硬選單）。

### Step 8 — LLM 重看 + 完整度確認
- **做**：LLM 把使用者全部內容**用白話講一遍**（這份工作實際在做什麼）→ 使用者覺得**完全符合、沒缺** → **完成**；有漏 → 回對應步驟**繼續優化**。
- **完整度**：深度（每任務 T/O/P/K/S 齊全）+ 廣度（對標準覆蓋、漏的都確認過）。

## 流程裡的「選單」總覽

| 選單 | Step | 為什麼是選單 |
|---|---|---|
| 任務 | 2 | 從標準任務清單勾「做哪些」 |
| K/S | 5 | 對應標準命名能力，要選/認 |
| 態度 | 6 | 從標準態度池選 |
| 建議條件 | 7a | 從標準建議條件勾 |
| ~~O 產出~~ | — | ❌ 細節訪談直接產出，不做選單 |
| ~~P 行為指標~~ | — | ❌ 細節訪談直接產出 + 從內容生成 |

## 各步的 indexer 存取

| Step | indexer 能力 | 機制 |
|---|---|---|
| 1 找職位 | profile 向量搜 | 向量 |
| 2 任務選單 | 撈 task（by ocs_code） | 結構化 |
| 3 自訂任務找對應 | task 向量搜 | 向量 |
| 4 細節訪談參考 | 讀 task 的 activity_examples/output_pairs | 結構化 |
| 5 任務 K/S（沒改） | by-id 取 task | by-id |
| 5 任務 K/S（改過/自訂） | task 向量搜 | 向量 |
| 6 態度 | 讀職位態度池 | 結構化 |
| 7a 建議條件 | 讀職位建議條件 | 結構化 |
| 7b 補充 | 讀職位補充說明 | 結構化 |

> indexer 全程**無狀態**；「使用者選了/改了什麼、排序、代號」都是 jobintel-ai 的 state。

## 完整度模型（滿分定義）

| 軸 | 意思 | 怎麼量 |
|---|---|---|
| **深度** | 每任務 T/O/P/K/S 齊全 | 逐任務檢查 |
| **廣度** | 該職務「該有」的任務/K/S/產出都涵蓋或明確排除 | 對標準覆蓋率 |

- **完整度儀表**：使用者看得到離滿分多遠 → 給滿分動力 + 分段心理錨。
- **完成 gate**：深度齊 + 廣度缺口都解決，或使用者明確接受「夠了」。
