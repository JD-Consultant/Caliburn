# 0052. JD 完整度評估的歸屬與兩種「代碼」的權責分界

- 狀態：Accepted
- 日期：2026-08-02
- 依據：[`docs/specs/2026-08-02-icap-2026-quality-manual-form-authority.md`](../specs/2026-08-02-icap-2026-quality-manual-form-authority.md)
  （2026-01-27 版官方手冊，2026-08-02 自 icap.wda.gov.tw 下載逐字核對）
- 延續：[0040](0040-professional-consultant-engine-and-r1-validation-contract.md) 決定 33–34（公版匯出措辭）、
  [0048](0048-opks-evidence-axes-and-document-level-competencies.md)（Attitude 預設留空）
- 審查：外部審查者第六輪（2026-08-02）

## 脈絡

Task、OPKS、訪談與人工編輯都已接通，但公版版型的表頭幾乎全空——`DocumentMetadataWrite`
目前**只有 `title`**。此時直接做 Excel／PDF 匯出，只會得到格式正確、內容大量空白的殼，
還會在欄位語意未定之前先鎖死匯出契約。

三件事因此需要先裁決。

**其一，完整度規則放哪裡。** 直覺是放進 `packages/job-analysis-contract`，讓 UI 與匯出共用。
但 `app/job_analysis` 目前對該套件**零 import**（只有 `app/api/*` 這層 transport 邊緣用它），
把產品政策放進 wire schema 會讓 transport 反過來支配 domain，也違反六邊形的依賴方向。

**其二，兩個都叫「代碼」的東西被混為一談。** 官方手冊把 `職能基準代碼` 標為「（免填）」，
體例格式進一步標明「（iCAP 計畫執行單位提供）」——`職類別代碼` 亦同。
而 `T1`／`T1.1`／`O1.1.1`／`P1.1.1` 是表格上的位置編號（同表註明「表格列數請自行調整」）。
前者是別人發的身分，後者是排版排出來的位置。混寫的後果是把官方身分碼做成可生成欄位，
正是 0040 決定 34 禁止的事。

**其三，「缺漏」不能機械認定。** 2022 指引 p37 明文：任務僅有行動或操作性質之工作成果時
**不必列出工作產出**，成果併入行為指標。官方也把態度列為「視需求納入考量」。
把「沒有 O」「沒有 A」一律判成缺漏，等於用我們自訂的標準否定官方允許的寫法。

## 決定

### A. 完整度評估的歸屬

1. **readiness 規則是 `app/job_analysis` 的純函式**（domain／application），
   不依賴 transport contract、不碰 IO。
2. **transport contract 只承載結果**：一個 `DocumentReadinessView` 與一組固定的 issue code；
   契約描述形狀，不描述政策。
3. **Web 直接呈現 API 回傳的結果，不自行重算**完整度。
4. **未來 exporter 呼叫同一套 assessment**——UI 與匯出共用同一份真相，
   但真相住在 domain，不住在 wire schema。

### B. 提示的性質

5. **只提示，不阻止**：未填欄位不阻止保存、不阻止繼續訪談、**也不阻止匯出**。
   匯出永遠放行，因此缺漏必須在成品上看得見是缺的——不自動補、不由 LLM 生成、不靜默省略。
6. **不存通用 `missing`／`not_applicable` 三態欄位**，也**不做完成百分比**。
   只有依現行官方規則能確定的缺漏才發聲；無法確定的一律不提示。
7. 措辭為「iCAP 版型欄位尚有 X 項未填」。**不得使用「不完整」「不合格」「未通過」**
   ——我們產出的是 0040 決定 33 定義的客製 JD，不是送審的職能基準。

### C. 兩種代碼的權責分界

8. **`職能基準代碼` 與 `職類別代碼` 由 iCAP 計畫執行單位配發**：
   不開輸入欄、不列入 readiness 缺漏、**AI 與 application 都不得生成**。
   未來只能由可信官方 reference source 帶入，不得推導。
9. **`職業別`／`行業別` 的名稱與代碼是分類資料**，依中華民國職業標準分類與行業統計分類填寫，
   **與第 8 條的 iCAP 配發代碼分開處理**——它們可由員工填寫或由分類資料帶入。
10. **`T1`／`T1.1`／`O1.1.1`／`P1.1.1` 是匯出時的版面位置碼**，依 Duty／Task／O／P 的排序
    決定性產生。**不是官方識別碼，也不是持久 identity**，不落庫、
    不取代 `duty_id`／`task_id`／`entity_id`。

### D. 本切片範圍

11. 本切片只做：**公版 header／metadata 欄位、nullable 基準級別（1–6，員工手選）、
    說明與補充事項、readiness 純函式、UI 編輯與缺漏提示**。
12. **基準級別不由 LLM 推論**，未填只提示不擋。每個 Task 的職能級別不在本切片。
13. **Duty（主要職責）與 Task 職能級別另開獨立結構切片**，但
    **export-ready v1 必須完成**——不得永久省略，也不得用 `ResponsibilityRole` 冒充，
    更不得自動合成假的 T1。該切片中 **OPKS 繼續引用 `task_id`**，identity 不重做。
14. **正式匯出為 deterministic，不讓 LLM 參與。本 ADR 不實作匯出。**

### E. 官方允許的空值

15. **工作產出可合法缺省**（操作性質任務將成果併入行為指標），
    readiness **不得**把「沒有 O」一律判成缺漏。
16. **Attitude 依官方「視需求納入考量」與 0048 維持可空**，同樣不列機械缺漏。

## 後果

### 正面

- 完整度只有一個實作，UI、API 與未來 exporter 都讀它；wire schema 改版不會改變產品政策。
- 官方身分碼在架構上不存在生成路徑——沒有欄位、沒有 issue、沒有推導點。
- 員工在任何時刻都能保存、訪談與匯出；表單完整度不會變成流程關卡。
- Duty 被明確標記為 export 前的必要工作，不會因為本切片跳過而悄悄消失。

### 負面／代價

- 匯出永遠放行，意味著可以匯出一份大量留白的文件。**這由成品上的可見缺漏承擔**，
  不由阻擋承擔。
- readiness 規則保守（只提示能確定的缺漏），因此**不會**涵蓋所有品質問題；
  它是版型欄位檢查，不是內容品質評估。
- 未做 Duty 之前，成品無法對齊官方的三段位置碼；內部呈現須誠實顯示「未分組」。
- 分類資料（職業別／行業別）第一版靠員工填寫，正確性不由系統保證。
