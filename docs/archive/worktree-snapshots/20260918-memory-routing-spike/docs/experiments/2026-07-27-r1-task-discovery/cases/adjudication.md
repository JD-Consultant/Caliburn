# 八案人工裁決理由

- experiment revision：**1**（與 `FROZEN_SUITE_HASH` 同批凍結）
- 用途：記錄每案的 `required_behaviors`／`forbidden_behaviors` **為什麼**是這樣裁的。
  `case.json` 說「要什麼」，本檔說「憑什麼」。
- 專業判準來源：O\*NET Task Writing Guidelines（Task = 具 meaningful outcome 的最小活動單位；
  工具與方法屬 Enabler）、OPM Job Analysis（先建立工作，再檢查能力連結）、
  iCAP 職能基準（工作任務／工作產出／行為指標分層）。逐條對映見
  [R1 深入研究 §3.1](../../../specs/2026-07-25-professional-consultant-r1-task-discovery-deep-research.md)。

> 凍結（ADR 0041 決定 15）：本檔的裁決理由不得為了配合模型輸出而改寫。

## TI-R1-01 工具不是 Task

Java／HTML／Python 在 O\*NET 的結構裡是 **Enabler**，不是 Task。句中沒有對象、目的或結果，
連「開發什麼、交付給誰」都不存在，因此**沒有任何 Task 可以成立**——不是「暫時不確定」，
是證據根本不足以構成一個工作。

正確結果是 0 個 Task ＋ 誠實說明不足 ＋ 一個能補上 outcome 的追問。
這也是前一版產品最主要的失敗模式，所以三個工具名稱各自列進 `forbidden_behaviors`。

**邊界**：本案不測「工具永遠不能成為 Task」——那是 TI-R1-02 的事。

## TI-R1-02 工具相關工作可成 Task（locked regression anchor）

與 01 的差別**不在有沒有工具，而在有沒有 outcome 與責任**：這裡有主責（本人）、
有週期（每季）、有可辨識結果（服務相容且可用）。依 O\*NET 判準它就是一個 Task。

相容性驗證、排停機時間、確認服務恢復是**同一個 Task 的步驟**，不是三個工作：
它們沒有各自獨立的交付對象與結果，拆開會踩到 OPM 提醒的過度拆分。

列為 anchor 的理由：這是八案中**唯一的正向案例**。若迭代把 prompt 調成「看到工具就排除」，
只有這一案會抓到。它防的是退步，**不證明 unseen generalization**。

## TI-R1-03 一故事多工作，但不是見動詞就拆

「查 log、重現、修復、部署」是同一次故障處理的連續步驟，共享同一個結果（服務恢復），
因此整併。「根因報告」有獨立產出與明說的獨立責任（獨立完成），可另成工作單位。

「主持每月改善追蹤」刻意留在灰色地帶：有頻率、有動詞，但**責任邊界與產出都沒講清楚**。
正確反應是追問，不是建立 Task —— 這測的是模型會不會用 `clarify` 而不是硬湊。

**邊界**：本案不預設「正確答案就是 2 個 Task」。合理範圍是 2–3 個；紅線是 6 個（見動詞就拆）。

## TI-R1-04 多故事一 Task

三段故事的結果是同一個：把門市交易資料正確地放進系統。日常匯入、月底去重、
改版調驗證規則是同一責任的**不同情境與條件**，不是三個工作。

依 OPM 的過度拆分／過度合併檢查，這裡的風險在拆分側：把情境當成工作會讓 JD 膨脹，
而且三個 Task 會互相重疊，後續的 Output／Indicator 全部要重複寫。

整併後**三個來源都要保留**：情境是證據，不能因為併了就丟掉兩段。

## TI-R1-05 過去工作不進現況

「前一份工作」是明確的時間標記。管理伺服器因此不支持任何現行 Task ——
這條在專業上沒有灰色地帶。

灰色地帶在另一邊：「現在只負責應用測試」是現行工作訊號，但缺產出與範圍，
所以**不應該直接定案成 Task**。正確反應是收下訊號並追問範圍或完成標準。

`forbidden_behaviors` 特別列「因技術經驗把過去責任帶入現在」，是因為這是自述資料最典型的污染路徑：
員工提到會某件事，系統就把它寫成職責。

## TI-R1-06 他人責任與交接

「正式部署是他們做」是明確的責任歸屬陳述，維運的工作不得進本人 JD。

本人這一側有兩個訊號：產出測試報告、部署後確認核心功能。它們**可能**同屬一條測試責任
（測試→交付→驗證），所以允許 merge；但也允許分開，只要邊界說得清楚。
這裡不設唯一正解，只擋「把維運責任收進來」。

下一問必須朝**本人的完成標準**。追問部署細節列為禁止，因為那是在挖不屬於這份 JD 的工作。

## TI-R1-07 一次性支援（locked regression anchor）

三個訊號同時成立：明確的一次（做過一次）、明確的原因（同事請假）、
明確的否定（平常不是我負責）。依穩定性判準，這不是 Task。

正確反應是 `no_change` 或 `clarify`，而且**不該繼續深挖** —— 深挖一件已被否定的事
是在浪費員工的注意力，也容易誘導出不存在的責任。

列為 anchor 的理由：一次性事件升格是 K/S/A 膨脹的上游來源，一旦這裡漏掉，
後面每一層都會把錯誤包裝得更完整。

**邊界**：正式的低頻責任（例如每季一次的正式職掌）**可以**是 Task。本案否定的是
「一次代班」，不是「低頻」。

## TI-R1-08 更正壓過舊說法

turn-002 是對 turn-001 的明確更正，且同時做了兩件事：撤回本人部署責任、
指出正確責任人（維運）。**後說的更正優先**。

共同語意的要求是：最終 Task 語意集合裡**不得含本人負責正式部署**。
A1 看不到 `task-existing-001` 這個 ID，但光靠兩段逐字稿就能滿足這條 ——
`proposed_tasks` 是「目前應成立的完整集合」，不是本輪 delta（設計 §6.1）。

`state_change_targets_existing_task` 是**只有 full arm 適用**的機械維度：
必須把 state change 指向 `task-existing-001`。A1 結構上做不到，記 `not_applicable`，
**不是 fail**，而且這條不得用來宣稱 A6 的 Task 邊界優於 A1。
