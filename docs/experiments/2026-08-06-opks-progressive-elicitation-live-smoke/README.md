### 1.1 成本估算的教訓：token 數不可跨 provider 換算

跑 Opus 前用 Luna 實測 token 推估 US$1.07，實際只花 US$0.243（差 4.4 倍）。原因是
**prompt token 數本身就差很多**：同一份 packet，Luna 報 18,164 tok、Opus 報 6,725 tok。
tokenizer 不同，數字不可搬。

| | Luna in/out | Opus in/out |

| t1 specialist | 6,891 / 3,160 | 1,457 / 682 |
| t2 主顧問 | 22,258 / 10,629 | 7,501 / 2,021 |

順帶：Luna 的 completion 多次超過 `max_output_tokens=4096`（10,629／10,771），**再次證實

在上限內，符合其「`max_tokens` 涵蓋 thinking」的明文。

## 2. 場景（跑之前凍結，兩次相同）

單一 Task「每月彙整門市營運月報」直接種進 Current JD，**只有一句依據**：

> 我每個月初要做一份門市營運月報給區經理。

這句證明「有這份產出」，但沒說怎麼做、資料哪來、到什麼程度算完成。**工作產出站得住，其餘軸
站不住**——模型若把其餘軸也編出來，是可歸因的 grounding 失誤。

三回合員工原話預先凍結：①換話題（讓 pre-gate 的 `next_question` 條件放行）②閒聊（看主顧問
怎麼問缺口）③講出做法。

## 3. 觀察點結果（以 Opus 為準）

### 3.1 觀察點 1：證據薄時真的回 `uncertain` —— **成立，而且比 Luna 保守得多**

Opus 從那一句話只提了 **1 條候選**，開了 **4 個缺口**：

| 軸 | decision | 內容 |
|---|---|---|
| 工作產出 | `add_new` | 每月初完成並提供給區經理的門市營運月報，使其掌握各店營運狀況 |
| 行為指標 | **`uncertain`** | 缺乏可判斷月報品質的依據，例如交付時點是否被要求、是否曾發生資料錯誤或被退回補件、區經理收到後的使用與追問情形 |
| 知識 | **`uncertain`** | 未說明月報須涵蓋哪些營運項目或指標、其定義與判讀基準 |
| 知識 | **`uncertain`** | 未說明資料來源，如各門市回報方式或所使用的系統、報表 |
| 技能 | **`uncertain`** | 未說明彙整月報的實際操作步驟，包括如何取得各店資料、如何整併與檢核數字、以何種形式產出 |

對照 Luna（2 條候選、2 個缺口）：

| 軸 | Luna | Opus |
|---|---|---|
| 工作產出 | `add_new` | `add_new` |
| 行為指標 | `add_new`「每月初完成一份門市營運月報並提供給區經理」 | **`uncertain`** |
| 知識 | `uncertain`（1 個） | **`uncertain`（2 個，互相獨立）** |
| 技能 | `uncertain` | `uncertain` |

**兩處實質差異：**

1. **Luna 生出的行為指標其實是把 Task 重述一次**（「每月初完成一份月報並提供給區經理」＝
   工作本身，不是可判斷品質的指標）。Opus 判定「缺乏可判斷月報品質的依據」而不出候選。
   這正是 §8.2 記錄的那條分界線的另一個實例：**便宜模型會把站不住的東西講成站得住的**。
2. **Opus 在同一軸開了兩個獨立缺口**（涵蓋範圍與定義／資料來源）。這是 commit `0b261fc`
   那條 prompt 修正（「同一軸缺好幾件不同的事就分開寫」）的第一筆實測證據——當初 owner 用
   「不知道交出什麼文件」與「不知道要達到什麼狀態」是兩件事否決了我提的
   `DUPLICATE_GAP_AXIS` verifier 規則，**這次生產模型的行為證實那個否決是對的**。若當初加了
   那條規則，Opus 這一輪會被整批退掉。

### 3.2 觀察點 2：缺口摘要是陳述句 —— **成立，但有一處要盯**

機械檢查：0 則以問號結尾（兩次 run 皆是）。

**要盯的**：Opus 的指標缺口寫成「⋯⋯例如交付時點**是否**被要求、**是否**曾發生資料錯誤或被
退回補件⋯⋯」。形式仍是陳述句（在列缺什麼），但那幾個 `是否` 已經很接近把問題材料寫進摘要。
決定 16 禁的是 gap **帶問句**，這一則沒有越線；但若日後看到摘要開始長出問號或第二人稱，
就是這條線在鬆。**照原樣記錄，不改判準去換一個好看的結果。**

Luna 的摘要則偏公文（「缺乏⋯⋯之必要性依據」），資訊量明顯低於 Opus。缺口摘要員工看不到，
所以這隻影響 specialist 下一輪的自我記憶品質，不影響產品文案。

### 3.3 觀察點 3：K/S 問行為不問認領 —— **成立**

Opus 三題原文：

1. 請講一個最近店長臨時問庫存的實際例子：他問的是什麼、你當下去查了哪些資料或系統、最後回覆或處理到什麼程度（只是給數字，還是你要決定調撥、補貨之類）？
2. 回到每月初的月報：各門市的數字你是從哪裡拿到的（是門市自己回傳表單，還是你自己從某個系統或報表匯出）？拿到之後你實際會做哪些整併或核對動作，最後交給區經理的是什麼形式的檔案？
3. 你說「都對上了才填進月報」——這份月報你實際是填在什麼東西上（門市既有的 Excel 範本、系統直接產出的報表，還是你自己做的表）？填完之後你用什麼方式交給區經理，通常要在每月幾號前交出去？

**沒有任何一題是「你是否具備⋯⋯能力」。** 第 2 題正面打知識缺口（資料來源）與技能缺口（整併、
核對動作），全部問**做法與產物**；第 3 題把員工上一句原話引回來再追具體載體，並順手探指標
缺口的「每月幾號前交出去」。ADR 0048 決定 14 要的形狀成立。

Luna 三題也都沒有問成認領題，但明顯較泛（「這些數字通常怎麼確認、判讀」）。

### 3.4 觀察點 4：`issue_resolutions[]` 沒有被當偷懶出口 —— **成立**

Opus 全程只送出一筆：turn 3 的 `{open_issue_ordinal: 3, resolution: answered}`（技能缺口）。
它通過了 verifier 的機械前提——同一輪確實有一筆 `support_only` 把員工那句話掛成 task-1 的依據：

```
task-1 support_links（turn 3 之後）
  我每個月初要做一份門市營運月報給區經理。
  月報我是先把各店 POS 的日結資料抓下來對過，數字對不起來就打電話問店長確認，都對上了才填進月報。
```

**沒有出現 `employee_unknown`。** ADR 0054 後果段承認 verifier 擋不住那條，兩次 run 都沒撞上。
而且 Opus 只關了技能那一個，沒有順手把另外三個也宣稱答完——雖然那句話其實也帶到了部分資料
來源（「各店 POS 的日結資料」）。**保守，不是偷懶。**

### 3.5 觀察點 5：沒有走後門 —— **未觸發，不等於已證明**

兩次 run 共 6 個主顧問回合，0 rejection，模型一次都沒有嘗試用 `resolves_open_issue_ordinal`
關缺口（`RESOLUTION_OPKS_GAP_NEEDS_ISSUE_RESOLUTION` 未觸發）。這條規則是 `a013d3b` 才加的。
**未觸發只代表這 6 回合沒走那條路。**

## 4. 這兩次 run 揭露的真問題：多缺口把再分析鎖死

**specialist 兩次都只被呼叫 1 次。**

| | 缺口數 | turn 3 關掉 | 仍 active | 第二次 specialist |
|---|---|---|---|---|
| Luna | 2 | 1（技能） | 1（知識） | **沒有** |
| Opus | 4 | 1（技能） | **3**（指標、知識 ×2） | **沒有** |

決定 3 的 pre-gate 明列「無 active 的 OPKS gap」。所以：

> **一個 Task 上有 N 個缺口時，員工答掉其中一個不會觸發再分析；要 N 個全部關掉
> （`answered`／`employee_unknown`／`not_applicable`）才會重跑一次。**

行為完全照 ADR，但 **ADR 沒有算過這筆帳**：決定 3 寫那條的理由是「缺口未解時再分析沒有新輸入」，
前提是缺口數量小。Opus 這種保守的生產模型從一句話就開 4 個缺口，於是：

- 員工在 turn 3 已經交出了新依據（POS 日結、對帳、打電話確認），digest 也變了，
  **但 specialist 永遠看不到**——它被 3 個還沒關的缺口擋在門外。
- 最快要 4 輪追問全部命中才會有第二次分析。真實訪談裡員工隨時可能結束，
  **這條線很可能一次都跑不到第二次分析**。
- 諷刺的是：模型越誠實（缺口開得越細），再分析被鎖得越久。

這不是 Luna run 看得出來的規模（2 個缺口尚可接受），**是 Opus run 才暴露的**。

**本篇不裁決怎麼改。** 選項至少有三個方向（放寬 pre-gate 讓有新證據就重跑／限制 specialist
一次開幾個缺口／讓 `answered` 觸發該 Task 的重新分析而不管其他缺口），各有代價，要照 AGENTS
規則 1 先寫研究紀錄再開 ADR。

## 5. 誠實邊界

- **各一次 trial。** 不宣稱穩定品質；Luna vs Opus 的差異是這兩次的事實，不是統計。
- **場景不完全忠實**：種下的依據不在 transcript 裡（主顧問看得到 Task 與引文，看不到員工何時
  說的）；員工回合預先凍結，接不上主顧問當下真正問的那一題。Opus 的第 3 題恰好接得上第 3 回合，
  是設計運氣不是保證。
- `quality_eligible=false`：兩次共 8 筆呼叫都不符合既有歸因判準。
- **成本估算不可跨 provider 外推**（§1.1）。
