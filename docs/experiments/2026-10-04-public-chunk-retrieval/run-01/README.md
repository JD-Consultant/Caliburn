## 本輪切法與搜尋單位

同一805份凍結公版、八個不改字的whole查詢。五份既有合成需求F01–F05，另三份歷史真A／合成員工完整訪談H01–H03；不同来源分開解讀。沒有新真人或Memory輸入，不加rerank、不改員工分段。

|---|---:|---|
| 整份D | 805 | 原概述＋工作單元／任務名稱＋O/P正文，一公版一向量。 |
| 任務T | 8,068 | 7,265任務節點＋803獨立概述；每任務含所屬單元名稱與對應O/P。 |
| 工作單元U | 3,661 | 2,858單元群組＋803獨立概述；一單元包含底下任務及O/P。 |

20個task節點有多個任務碼；保留同一節點的所有名稱與定位，不複製成多個point。T/U各自所有chunk的聯集均保存D全部非空正文行，沒有因切細捨棄概述，沒有把概述重複貼到每任務。K/S不加，公版職稱／OPKS代碼表頭不額外拼入向量；必要名稱正文保留。原正文自然出現職位詞不做全文刪除。原始JSON的語意及逐字品質仍沿既有解析限制，結構保存不等於PDF全文已驗收。

同版本機BGE-M3／FP16／1024維；11,064唯一文字中1,604逐字hash重用既有向量、9,460新算，最長新chunk1,315tokens，未截斷。346批新embedding HTTP時間共114.396秒，整體批次122.996秒；八query向量與舊whole原文完全相同。新Qdrant三collection共12,534points，父公版數各805；建庫合計約10.618秒，不是新增12,534個職位。

## 公版合併方法

真Qdrant exact cosine按parent_id分組，**每次先取得20份不同父公版，各最多3個最佳chunk**。grouping原生按最高point分數排序；本輪另建parent keyword索引，24個真查詢與全chunk离線分數核對，最高誤差小於1e-6。

- max：父公版分數是最高chunk cosine，保留前五。
- 前三均值：只重排**相同max初搜20份候選**，平均最高min(3,該父chunk數)個cosine，再留五份；不足三個不補零，不按命中數相加。不是全805父的mean3搜尋。

同一父命中多個chunk仍占一份。整份D只有一point，所以只列D-max。T/U各max與mean3，共五方法；同分按父ID，不設相似度門檻。前三均值不保證三chunk互補，也未消除chunk數量／長度差異的影響。這些cosine聚合和下面0–3分評審是兩件事。

## 仍不能定案的原因

同批八小樣本，只測whole輸入、manual public結構及兩種聚合。未比較員工分段×公版切法的交互作用，未測整份＋chunk混合搜尋、rerank或相似度門檻。原五案主要領域粒度、跨工作對象1/2分界，以及H03孤立通知给2／公版額外責任降級仍有疑義。

新H03「資材人員」給3時允許公版有員工未負責的庫存／專案責任；既有「採購人員」給2卻以額外招標／議約等責任作降級理由。同一規則判讀是否一致仍需獨立標註／評審校正；本輪不改原分來製造贏家。F04冷氣中的跨對象維修公版仍有模型2，也不把同名維修動作當已驗收的代表性。

因此可用這輪定位哪些表示會漏掉既有代表、哪些會新增較合適候選，**不選一套正式最佳方法**。下一個有限比較可以保留整份候選，再補工作單元候選並合併；這是未測方向。評審有效性須繼續補，不能用模型分級代替全庫Recall、真人、Memory或JD/PDF收尾驗收。
