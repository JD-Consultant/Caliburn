回覆：

以下依你原始訪談中的說法核對，兩案分開整理。

## 1. 青禾：付款後看不到會員內容

### 原因

這次**不是實際扣款失敗**，而是：

- 前端已收到付款成功狀態；
- 但會員權限畫面沒有跟著刷新；
- 所以使用者看不到原本應該看到的會員內容。

你後來特別補充：「**青禾這次沒有真的發生扣款失敗，只是畫面沒更新**。」

### 你做了什麼

你當時的處理順序是：

1. 請客戶提供發生時間、帳號代碼與操作步驟。
2. 在測試環境重現問題。
3. 查看瀏覽器主控台與網路請求。
4. 確認前端收到成功狀態，但權限畫面沒有更新。
5. 修正前端的權限畫面更新流程。
6. 測試成功、失敗、逾時三種情況。
7. 提供截圖與重現步驟給客戶確認。

### 後端負責什麼

青禾的後端責任包括：

- 實際處理扣款；
- 如果會員或付款 API 沒有回傳正確狀態，由後端修正 API 並部署；
- 你則整理請求與回應交給後端，修正後再做前端畫面回歸測試。

你沒有負責：

- 判定是否真的扣款失敗；
- 扣款處理；
- 退款核准或執行。

你的原話是：

> 「我現在可以補維護了。青禾曾有一筆客戶回報『已付款卻看不到會員內容』。我先請對方提供發生時間、帳號代碼和操作步驟，再在測試環境重現，看瀏覽器主控台和網路請求。這次是前端收到成功狀態後沒有刷新權限畫面，我修正更新流程，測試成功、失敗和逾時三種情況，附截圖與重現步驟給客戶確認。API若沒有返回正確狀態，我整理請求與回應交給後端，不能自行判成扣款失敗或替客戶退款。」

另外，你在較早的訪談中也說明：

> 「實際扣款是後端處理，我沒有扣款或退款核准權。」

---

## 2. 雲岸：報名重送

### 原因

這次不是付款問題，而是：

- 使用者快速連點報名鍵；
- 請求送出期間，前端按鈕仍然可以再次點擊；
- 因此前端送出了兩次報名請求。

### 你做了什麼

你當時的處理是：

1. 使用測試帳號重現問題。
2. 確認請求送出時按鈕仍可重複點擊。
3. 增加「送出中」狀態。
4. 在請求處理期間停用重複觸發。
5. 請求成功或失敗後恢復按鈕可操作。

### 後端負責什麼

後端不能只依賴前端按鈕停用，仍須自行做：

- 報名 API 的冪等防護；
- 即使收到重複請求，也要避免建立兩筆報名資料。

你原話是：

> 「再補雲岸的維護案例：使用者連點報名鍵出現兩次前端送出。我用測試帳號重現，確認請求送出時按鈕還可重複點擊，就加上送出中狀態與停用重複觸發，成功或失敗後恢復可操作；後端仍要自行做冪等防護，不是只靠我按鈕停用就保證不重複。這跟青禾的付款狀態刷新是不同案例。我們兩案都先測試站驗收再部署，沒有把雲岸加金流。」

你也曾明確說：

> 「雲岸只做課程報名，不做金流。」
