# 原生 Compaction 與長訪談資料管理的組合比較

狀態：四組方法與資料已確認；先導完成，主執行的停止、修正與結果見 [實驗入口](README.md)及[執行計畫](main-plan.md)。「完整歷史」採全部保存、模型按需回查；主案例涵蓋足以形成可用 JD 的完整職務訪談，包含跳題補答、指涉、更正與精確數值。本頁不修改正式產品、不覆寫既有實驗，也不提供尚未完成的四組成效結論。

## 1. 研究問題

Caliburn 同時使用 OpenAI 原生 Compaction 與三層 Memory。這次要問的是：在相同 Luna/high、訪談資料與 JD 任務下，原生接續經過實際壓縮後，不同訪談資料管理方式對早期事實、更正、補充、精確數值與 JD 編輯有何影響？此外，直接按序號回查原話，與沿工作理解 → 工作情境 → 原話關聯讀取，能否在相同資訊目標下減少不必要閱讀、保持正確指涉與來源支持？

上一輪[45 段訪談比較](../long-interview-memory-2026-10-04/README.md)刻意排除原生歷史，回答 Memory 捕捉與取用的問題；只有 7,459 字元，未發生 Compaction。它不能代替本次完整組合比較。原件、判準及結果保持不變。

## 2. 比較組別

比較四種組合，不把相同方法重列為第五組：

| 組別 | 原生接續 | 額外的訪談資料表示 |
|---|---|---|
| `compaction_hierarchical_memory` | 保留自身有效歷史，依門檻呼叫原生 compact | 現行 B1 → B2 → 發布；導覽與正文按需讀取，來源原話仍可回查 |
| `compaction_flat_summary` | 同上 | 相同來源分批自然生成、持續更新的一份摘要；不手工填入標準答案 |
| `compaction_raw_history` | 同上 | 完整保存原始訪談；按正式序號／範圍回查，不預載全歷史，不提供 Memory 關聯導覽 |
| `compaction_recent_history` | 同上 | 固定規則的近期原始訪談，不提供三層或單層整理產物，也不開放更早原話回查 |

四組不是共用一個最終 compaction blob。各自的導覽、工具觀察及模型輸出不同，必須沿自己的合法歷史接續、壓縮，完整承接自己的 `compacted.output`；不能將三層組讀過的資訊複製進其他組。

「只有近期」仍有原生 Compaction 中可能保存的早期資訊，不是完全不知早期內容的負對照。它用於觀察沒有額外整理產物時，原生接續與近期原話的表現。

### 原話按需回查的比較邊界

「完整歷史」指全部原始訪談有保存、可按需查閱，不是每次將全部原文放進 Context。因此改用 `compaction_raw_history`，報告寫作使用「Compaction＋原話按需回查」，避免讀者以為它是全文預載。

- 原話組允許模型自行選擇有效訊息或區間、向前後補讀，以取得必要語境；不強迫從頭掃描、不刻意遮住可讀範圍，也不加一個較差的提示詞製造低效。這是**序列式原話回查**與**關聯式分層回查**的比較，不把「無腦查閱」當成實驗操作要求。
- 三層組可沿理解／情境導覽與來源關係定位，也保留同一契約的原話工具。單層組可使用摘要中的自然來源線索回查相同原話。原話組沒有這兩種整理產物，但有相同的正式序號、說話者、原文及有效讀取範圍；不另外新增搜尋系統或讓模型選版本。
- 三層、單層、原話組共用相同近期預載規則與歷史回查上界。只有近期組不取得超出近期範圍的原話；否則會和原話按需組重疊。這個限制只用於研究組裝，不縮減產品工具權限；近期組仍可能從自身原生接續／Compaction 得知更早資訊。
- 全部原文一起預載只作容量計量的反事實對照，不是第五個付費組，也不把超量的生成失敗算成原話組輸掉。

共同資料供給及工具範圍在執行前固定；不根據結果更換組別名稱或把原話補救偷偷算成 Memory 正文保留。

## 3. 共用條件與實際 Context

- 固定產品使用的 `gpt-6-luna`／high、角色分析方法、JD 任務、輸出契約、容量與有界執行條件。方法需要的 Memory／摘要工具差異另列，不假裝四組工具 schema 完全相同。
- 主實驗保留合法的跨輪及跨 Step 原生 items，包括 reasoning、message、phase、工具呼叫與配對結果；不使用上一輪的 fresh-context 隔離方式清空它們。
- 固定 `store=false`，由 App 管理接續，不另加 `previous_response_id` 或 server-side 自動壓縮。外送沿現行 SDK／Runtime；不建立另一套產品執行或保存引擎。
- A 起始以原生歷史／完整 C → user-role App 資料 → 當次員工原文的順序接續。同輪不重加起始資料，不刷新固定 Memory 基準。JD map 維持按需讀取，不能為測試擅自改成每輪預載。
- 各組使用共同的 JD 讀寫能力與初始稿，包含讀 map、讀任務／關聯資料、編輯、引用及差異核對。主實驗保留真實工具 trace；不是只給模型問卷，或把工具定義移除以降低 Context。
- 三層／單層／原話組共用的歷史回查能力、近期組的限制，以及各組額外可取得的摘要／Memory 資料，依 §2 列明權限。正確回答、實際讀取及來源支持分開觀察，不因資料庫存在原話就宣稱 Memory 正文已保留。

背景整理使用相同有效來源邊界與事前固定的比較批次；只整理新取得正式資格的資料，不把尚未完成／取消的 A 輸入交給 B1。這是控制比較來源的方法，不改產品原有通知政策。三層的自然產物、B1／B2 私有歷史與壓縮用量均保存；單層也逐批更新，不在最後才取得超長全文一次摘要。

### 3.1 主案例是完整職務訪談，不是加長問卷

從空白 JD 開始，合成員工逐步說明主要工作，顧問依資料追問、按需查閱與編輯；涵蓋例行工作、週／月／年度週期、事件型工作、重要低頻例外、成果與執行要求、本人及協作者的責任、必要知識／技能和工作條件。依 [工作分析指南 §6](../../../../guides/2026-09-09-complete-work-analysis-guide.md#6-如何檢查整份工作已被適當涵蓋)及[訪談校準 §6](../../../../guides/2026-09-09-customized-jd-depth-and-interview-calibration.md#6-怎樣才是整份工作被理解而非只問透一案)，事前列出該合成職位的有效工作範圍及足以成稿的重要事實；不把它直接交給顧問當答案。

主案例應從基本範圍訪談、各項工作與例外釐清，走到可用 JD，再以回提早期內容檢查修改與引用。長度由這份職務所需的資訊廣度與深度決定，不以固定輪數、填滿欄位、模型說「完成」或單純 token 數判斷。細節應具有辨識工作、支持分析的用途，不用無關文字灌水。

四組共用員工事實、變動時間線與已固定的測試訊息；可允許顧問選不同讀取路徑與問法。若採自然互動，澄清回答只能從相同的隱藏員工事實提供，並保存各組實際得到的資訊與時點。用於直接配對的查閱任務須具有相同可用事實與目標；資訊供給不同的自然旅程另列，不能冒充單一變項受控比較。

完成後以「工作 → JD」檢查主要工作是否涵蓋、重要例外是否保留，再以「JD → 工作」檢查每項主張是否有依據，另看重複、粒度及精簡程度。這是研究者對成品的評估，不新增暫緩中的全稿審核 Agent，也不把合成範圍完整等同真人所有工作已被發現。

## 4. 容量壓力如何證明

每次計量實際待送完整請求：instructions、工具 schema、原生 items、App 資料、JD 導覽／正文、工具結果和當次輸入；依現行容量檢查保留輸出空間，推理使用 output 預留，不重複加算。不能以純訪談字數、磁碟大小或上一輪 usage 當本次容量。

現行產品輪前門檻為 128,000 tokens，完整 Step 交界保險為 160,000 input tokens。它們是主動壓縮政策，不是模型硬上限。核對的 [Luna 官方模型頁](https://developers.openai.com/api/docs/models/gpt-6-luna)列出 1,050,000 context window、922,000 max input、128,000 max output；實際請求仍須符合自身設定及輸出預留。不同資料管理方式可能在不同交界達門檻，不強迫同一輪壓縮來製造表面相同。

完整 JD 訪談與容量壓力分開記錄；自然完成一份 JD 並不保證累積資料必超過模型硬上限。分開證明兩種壓力：

1. **實際壓縮壓力**：有工作內容的訪談、分析及 JD 工具往返，使有效窗口真的達現行門檻。記錄壓前／壓後完整請求計數、採用位置、完整 output 的保存與後續使用；實際經過多次壓縮後再核對早期細節。不用只降低測試門檻或重複無意義文字冒充正式容量情境。
2. **完整歷史無法預載**：累積有效原始資料與共同請求材料的計數超出同模型可用容量。這與「超過 128K」不同。先用反事實完整請求計數證明，不發必定超量的生成請求。自然完整職務訪談未達此規模時，先呈現實際壓縮與 JD 結果；硬容量擴展另列有意義的持續訪談資料與用量，不為跨上限而把一份已完成的訪談無限拖長。

依 [OpenAI standalone Compaction 契約](https://developers.openai.com/api/docs/guides/compaction#standalone-compact-endpoint)，compact 輸入本身仍須容於模型窗口；完整返回 output 原樣承接。故要在超量前按合法交界逐步壓縮，不能先塞入超長全文再期待 compact 補救。壓後不重貼被替代的原生歷史，也不把 JD／Memory 工具結果偷偷裁短。

## 5. 事前案例與精確判準

資料是合成訪談，不使用私人員工資訊。把主要事實分散在前、中、後段，跨段以自然問答回提、更正及補充；不把測試題目或標準答案送入 B1／B2。原話、事實預期與來源序號在執行前固定。

| 類型 | 合成例子 | 核對重點 |
|---|---|---|
| 早期精確時間 | 每天 08:35 核對退貨，09:10 前交差異表 | 不交換任務與時間，不把開始時間當截止時間 |
| 嚴格門檻 | 不良件數占本批驗收件數「超過 5%」才提報主管 | 百分比、分母、適用批次與 `>` 都正確；恰等於 5% 不自行改成需要提報 |
| 區間與單位 | 每日 15–20 張進貨單 | 不改成每週，不捏造平均 18 張或精確固定數量 |
| 早期更正 | 後段更正週一改為 08:50，其他工作日仍為 08:35 | 更新限定範圍，保留未變部分，不全盤覆蓋原規則 |
| 早期補充 | 後段補充只有冷藏退貨需另查溫度 | 添加新條件，保留原工作與責任，不把局部例外套到全部商品 |
| 近似但不同的數值 | 另一項工作有 5% 備品率、不同截止時間 | 不跨主題混用相同數字 |
| 跳題後補答 | 盤點尚有未答問題，先談退貨；後來說「回到前面盤點那件事，月底才需要主管簽核」 | 接回正確工作與未解問題，不把月底簽核套到目前退貨主題 |
| 近期指涉 | 「剛剛說的 5% 是每批，不是整個月」 | 核對可唯一辨認的前文，修正統計範圍，保留未變的門檻及其他工作 |
| 早期指涉 | 壓縮後回提「之前說的月底那張表，改成次月第一個工作日交」 | 找回正確表單、工作與原要求，不改到另一張有相似截止日的表 |
| 省略主語的回答 | 明確前問詢問特定盤點工作，員工只答「每個月，特殊情況再加一次」 | 利用前問／原話語境，不把答覆錯掛到相鄰工作，也不因不是完整句子而丟失 |
| 指涉不能唯一判定 | 已談兩張表，員工只說「之前那張改成每週」 | 先釐清目標，未確認前不選一張直接修改；合理追問不算失敗 |
| 未知與矛盾 | 員工未說金額門檻，或更正範圍仍不清楚 | 保留未知／追問，不從常識或顧問前問捏造事實 |

後續題目包含詢問早期數值、請整理更正後規則、依補充調整既有 JD。工作大意符合但數值、單位、責任、條件、時間或更正範圍不符，不能算精確保留正確。等價表述可接受，例如 5% 與 0.05；不接受自行四捨五入或改變比較關係。

指涉案例在尚有原文、經過一次壓縮及多次壓縮後分段檢查；區分可以由語境唯一定位、補讀後可定位、及仍須詢問員工的情況。「剛剛／之前」不是固定指向上一則訊息，也不因一則新回答晚出現就重寫所有舊規則。各題預期的主題、目標、適用範圍與可接受澄清路徑在生成前固定。

## 6. 判讀與對比

主結果以端到端行為為準，分開記錄：

- **產物保留**：三層／單層產物是否保留題目需要的事實、最新更正及可回查來源。
- **顧問取用**：回答是否正確、是否查到需要的資料、是否使用已更正基準。模型可能從原生 Compaction 得知資訊，不能一律歸功於 Memory。
- **對話指涉**：跳題補答是否接回正確工作，省略回答是否有適當前問，早期回提是否定位正確；不明指涉是否合理澄清，及是否誤改無關 JD 項目。
- **JD 效果**：指定項目的修改是否採用正確事實與引用、保留未受影響內容；需要核對時是否實際提交，而不只看過 diff。數值不一定都要寫進 JD，但寫入的數值與適用條件必須正確。
- **來源支持**：依據是否真的支持這項結論；正文正確與引用正確分開計分。原生 opaque compaction 不當作正式來源。
- **用量與失敗**：計數、生成、Compaction、背景整理、工具往返及重試全部記錄；分開起始與累計 input、output／reasoning、快取用量、呼叫數、讀取次數和容量受阻。不只比較第一個請求，不把限流等待當方法速度差異。

先保存未加分輸出，再依事前事實單位複核。更正題同時看新規則是否成立、舊規則是否仍被錯用；補充題看新條件是否加入及舊內容是否不必要流失。結果既可支持組合有效，也可能指出工具取用或產物整理的缺口，不以三層一定優勝作驗收門檻。

若需另做 fresh-context 診斷，另列結果，用於區分產物缺漏、取用失誤與原話補救；不能與保留 Compaction 的主實驗合併分數。

### 6.1 查閱效率與證據充分性

以相同查閱／編輯目標，對照序列式原話回查與關聯式分層回查，保存實際路徑及每次工具結果。每項至少記錄：

- 查閱呼叫數、讀回訊息／物件數、工具回傳 tokens、全部模型往返累計 input，以及已讀內容的重複範圍；不是只數最後一次閱讀。
- 首次取得足以回答的資料的位置、完成前補讀次數、無效定位與未完成原因。必要的前問和相鄰語境算有用資訊，不將它們一律當成無關回傳。
- 取得的資料是否足以支持全部事實單位、所選來源是否相關，以及最終回答／JD 是否正確。不同來源組合可以支持同一結論，不指定唯一正確查閱順序。

全部任務的成功／失敗和用量完整呈現；另列在同樣正確且來源充分的任務中，各方法需讀多少資料。少查但答錯不是效率改善，多查卻能找回漏項也不能只憑呼叫數判輸。三層整理的事前用量須另列，再看端到端總量，不能只比顧問查閱階段就宣稱總成本下降。

方法依據：[OpenAI Memory Evals](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization#memory-evals)強調時間關係、選擇性再用與完整記憶管線的比較。本案據此評估任務與來源支持，不把「只用較新內容」當成一律覆蓋舊資料的規則；更正仍按適用主題與範圍判斷。

## 7. 外送前的最小準備

1. 依已確認的原話按需組固定共同資料供給、各組工具權限及近期範圍；不再把全部原文預載當成主比較組。
2. 完成足以形成可用 JD 的合成員工資料、跳題／指涉／更正測試訊息、標準答案與離線完整請求計量；據此確定可執行的資料規模、批次、檢查點及重複次數。單純增加輪數不取代範圍與深度。
3. 使用現行產品 Runtime／工具與真 PostgreSQL 隔離範圍，保存程式、角色指引、資料及判準雜湊。不改正式資料或正在使用的職務檔案。
4. 固定本批生成、Compaction、輸出、累計輸入、重試、時間及費用界線；Compaction 和工具回傳的基礎設施拒絕必須納入即時停止，不沿用上一輪只保護生成請求的腳本缺口。standalone compact 沒有 create 的輸出上限，不宣稱估算是遠端硬帳單上限。
5. 有界執行後保存各組完整證據、失敗與分析。沒有實際發生壓縮、沒有達到完整原文不可預載，或沒有完成 JD 任務時，分別說明，不以縮小條件偷偷補成通過。

上述規模與預算未固定前不啟動生成或 Compaction。資料準備可另作最多五次 `input_tokens.count` 預檢：只送合成原文、現行指引與工具 schema，單次 60 秒、整批 180 秒、無重試，任一失敗即停止。它不生成答覆，不整理 Memory，也不宣稱計數服務必定免費。主實驗的總用量、時間與費用另行固定。

它是實驗護欄，不是恢復產品金額攔截；本頁只記錄研究方法，不新增產品要求。
