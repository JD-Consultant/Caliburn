# 導覽讀取與短定位：事前比較方法

狀態：執行前固定的方法，不是結果。原始資料、程式及執行 manifest 一起保存；產品程式、Prompt 與正式資料不變更。

## 目的與範圍

1. 長篇工作資料：比較相關工作事實、後續更正及原話來源的取得，並量測「全文直接投入」與「導覽＋按需閱讀」的累計輸入量。
2. 工具定位：比較相同目標集合下的 UUID 長定位與短定位，檢查首次選取、完整任務成功、錯誤後修正及 tokens。

這是受控子任務，不冒充整套訪談、自然 Memory 生成或專業 JD 品質驗收。導覽與 Memory 是事先整理的同一份合成資料；本實驗檢查資料已正確整理後的讀取效果，不證明背景整理本身不會漏資料。單層摘要、真使用者省時、專家盲評及未接入的 RAG 不納入本次模型比較。已有來源 diff 與訪談指引比較沿用原件，不重寫其評分。

## 固定條件

- 模型 `gpt-6-luna`、`high`，OpenAI 直連；SDK retries=0，`store=false`、`all_turns`、truncation disabled。
- 每次試驗獨立上下文，完整原生 output items 接回，不以自寫摘要取代 reasoning。公開紀錄只保留加密項目的 SHA-256 與長度。
- 兩次重複；第二次反轉組別順序。全部結果納入，不挑成功試驗；provider 錯誤、incomplete、上限退出獨立標示。
- 回傳欄位與判準一致；標準答案不提供給模型。只計最終輸出及實際工具效果，不因未走指定工具路徑判錯。

## 長資料比較

36 個不同工作主題，按順序各含顧問問題、員工陳述、顧問釐清及員工更正／補充，共 144 則正式合成訊息。各主題保留不同數值、條件、責任界線及來源序號；正文不靠無意義文字重複填長。從前、中、後各選一個主題形成三個題目，兩組各重複兩次，共 12 次。

- 全文組：36 項情境正文、同一導覽及 144 則原始訊息直接提供。
- 按需組：同一導覽，透過現行 `read_work_situation` 與 `read_interview` schema 取得同一正文／原文。工具執行只讀 fixture，不讀寫產品資料庫。
- 每題判準：最新頻率、執行者、核准者、期限、適用範圍、權限界線六項精確值，以及支援這六項事實的兩個員工訊息序號。允許來源順序不同，不允許多引無關來源。
- 比較累計 input/output/cached tokens、讀取次數、生成請求數、時間、每項正確率與全項通過率。效率不只計初始資料；兩組享有相同工具，全文組也可再次讀取。

## 定位比較

相同 48 個任務、相同標題與工具說明，只替換 `read_ref` 表示。長定位使用產品內部 `task_<UUID hex>`；短定位使用 `task_<正整數>`。六種題目：單一目標、多目標順序、相近標題、跨輪記住先前定位、引用定位、工具拒絕後重新選取。各組各重複兩次，共 24 次。

定位結果回傳實際選到的物件位置，依獨立答案核對；格式合法但指到另一物件仍算錯。拒絕案例兩組都收到同樣的可改進訊息，故意失效的定位不計為模型原生錯誤，另計修正成功。未採用正式寫入 schema，是為了讓只有定位表示不同，而非混入 JD 分析品質。

## 執行界線與停止條件

生成請求最多 108 次，每次 output 上限 4096；每次 input count 不超過 125,000、全批 admitted input 不超過 4,000,000；60 分鐘總時間上限。按標準 Luna 價格，上界約 US$0.63（不計快取折扣），留在 US$1 以內；這是實驗控管，不是新增產品金額攔截。任何 provider 例外立即停批、不自動重跑。fixture／計分先離線驗證，run 目錄禁止覆寫；manifest 先於付費請求寫入。

## 工作順序

### 首次中斷後的續跑修訂

`live-01` 完成第一對後於下一題遇到 `RateLimitError`，原請求、輸出與分數保持原樣。首次程式只保存例外型別，因此不能判定該次是速率或帳務原因。續跑在新目錄中連結原 manifest／results 雜湊，只跳過已有 outcome 的兩次試驗，沿用原六次 admitted 生成與 249,384 input 預算；未完成的題目才重新開始，不重跑成功案例。資料、題目、Prompt、判準及組別順序不變。

續跑加入白名單的 HTTP 限流數值與正式錯誤分類，不保存任意 headers 或錯誤正文。依 [OpenAI Rate limits](https://developers.openai.com/api/docs/guides/rate-limits) 的 remaining／reset 先等待可用容量，再發下一次生成，單次等待不超過 180 秒；缺少 headers 時大輸入至少隔 60 秒，小輸入隔 10 秒。錯誤仍立即停批，不自動重送。本修訂只改研究流量控制，不改產品或事後計分。

首次按需組 authority 的額外正確說明造成精確字串失分；保留原分數並在結果另註語意觀察，不為提高通過率改答案或判準。

`live-02` 完成中段配對後，後段全文題第二次生成收到 429／`rate_limit_exceeded`，headers 顯示限額 200,000 tokens/min、剩餘 54,752、reset 43.574 秒。已完成的中段兩筆結果保留；該後段題已返回的第一次回應及其用量也保留，但尚無最終答案。先前成功回應的 remaining 接近滿值，不足以預約下一個大型請求。

`live-03` 只接續剩餘題目，繼承所有四筆 outcome 與全批 14 次准入、660,110 input；新增依實測 TPM 的保守間隔（本次 input＋output 保留量 ÷ TPM × 72 秒），並仍遵守 remaining／reset。後段未完成題需從獨立視窗重開，因公開 trace 不保存可重播的加密內容；中止嘗試獨立列出，不隱藏其生成用量。這次修訂只調整發送節奏，原結果與評分不變；若再次遭 provider 拒絕，仍停止、不無限續跑。

## 方法依據

[OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 支持先定任務目標、資料與指標再比較；[Anthropic Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 區分 task、trial、trace 與 outcome，建議以確定性判準檢查可明確判定的結果並保留重複試驗。本案採小型配對比較，不宣稱單一廠商的內部做法或統計顯著性。費率依 [Luna 模型頁](https://developers.openai.com/api/docs/models/gpt-6-luna)。
