# 導覽重讀與回答細節保留：局部提示候選（2026-10-05）

兩個候選各自完成獨立對照：一個只改兩項 Memory map 工具的說明，另一個只改顧問的單一細節回答指引。[五對真模型結果](../reading-probe-01/README.md)顯示局部支持：缺導覽時少讀一份情境 map，細節題補回確認者；已有導覽時兩邊都未重讀。正式產品與原始實驗未改，以下保留假設、離線檢查及施測方法。

## 1. 為什麼只改這兩處

[事後路徑核對](organized-work-sufficiency.md)已區分一般工作、歷史追溯與新資訊。c01 的 map 重讀與 c06 的確認者漏說，都發生在資料已可取得的情況，不能用增加原話閱讀來解決，也不足以支持全面重寫 B1／B2。

| 觀察 | 已有規則 | 本次待驗假設 |
|---|---|---|
| c01 起始已有完整理解 map，模型仍再讀一次 map | 研究提示已寫「不重讀導覽或正文」 | map 工具本身只說回傳什麼，未交代何時需要它；將使用條件放在選工具的位置，可能減少多餘呼叫 |
| c06 已讀理解保存換算確認者，回答只留下數值及適用品號 | 單一細節指引只概括說保留必要限定；完整工作指引才明列角色 | 在單一細節指引說明「省略是否改變適用或確認權責」，可能改善保留，又不迫使每題帶入整份工作 |

這是可測假設，不宣稱已知道模型內部為何選擇該路徑。相同的簡短規則在系統提示中已存在，因此不再追加一段泛稱「少讀工具」的要求。

## 2. 借鑑的官方方法與候選內容

[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)要求清楚表達工具目的、參數、輸出，以及何時使用或不使用；也提醒範例不一定改善推理模型。本次不塞入題目答案或特定案例，保留現有 schema，只把 map 的用途說完整。

[GPT-6 提示指南](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)建議明確指定所需的輸出方式，並檢查不同指引間是否有衝突。該頁的行為觀察主要針對 Astra，只能作 GPT-6 家族的起點，不能代替 Luna／high 的實測；本次不更換模型。

### 導覽候選：只改工具說明

使用條件是目前 Context 沒有可用導覽、或 App 明示可見集合改變。已有完整且仍適用的導覽時，直接選 `target_title` 讀正文。說明同時保留「只回標題與描述」「App 管理範圍」「不刷新本輪固定 Memory」及資料不是指令的界線。

這不是撤掉 map 工具，也不是程式拒絕第二次讀取；導覽真的不在 Context 時仍可取得。候選轉換本身保留原請求的正文、情境、原話及 JD 工具，輸入、回傳及權限未改。本次真模型探針另將兩邊共同限定為五項 Memory 唯讀工具，範圍與原因見下節。

### 細節候選：只替換一段回答指引

> 回答一個細節時，將數值與解讀它必要的單位、適用範圍、時期及已知確認者／決定者一起表達，來源未提供的限定不要補造。完成答覆前核對：省略這項限定，是否會讓員工誤用數值，或誤認誰能確認／決定？若會就補回，不延伸無關工作。

這段只替換原本的單一細節子句，完整工作整理、JD 修訂與來源規則仍沿用原文。角色只有影響所問事實時才帶出，不要求每次列所有人名、全文或固定欄位；它也不要求模型輸出內部檢查過程。

兩項候選由 [reading_prompt_candidates.py](reading_prompt_candidates.py)分別產生。沒有合併版本，避免把兩種改動一起測而無法判斷成因。

## 3. 離線做了什麼

從原始 `live-01/trace.jsonl` 讀取 Memory 組 c01、c06 的第一筆生成請求，直接套用候選；不從持續變動的正式程式重建控制組。

- 導覽候選只改兩個 map 工具的 `description`；其他工具、schema、排序、`tool_choice`、輸入資料、原生接續、模型與推理設定不變。
- 細節候選只替換 `instructions` 中唯一的目標子句，前後文及整份 tools 不變。
- 工具缺少／重複、提示片段找不到／重複，以及把候選再次當控制組時，明確拒絕。
- 產生及修改候選不會改動傳入的原始請求；沒有 SDK 呼叫、資料庫寫入或讀取憑證。

[測試](test_reading_prompt_candidates.py)先在僅複製原請求的骨架上出現 16 個行為失敗，再完成轉換後通過。這些斷言檢查研究請求改動是否越界，不用字串存在與否宣稱模型懂得新規則。Ruff 檢查通過後，格式檢查曾指出兩檔需排版，已用 formatter 修正；最終檢查另記執行結果。

```powershell
apps/api/.venv/Scripts/python.exe -m pytest docs/experiments/product-validation/data/early-interview-recall-2026-10-05/analysis -q -p no:cacheprovider
```

不重跑未修改的產品交易或全套後端；依[開發規範](../../../../../implementation/development-standard.md#31-依風險配置驗證與交付粒度)只驗本次研究轉換與同目錄既有分析測試。

## 4. 真模型比較的最小範圍

使用者已批准新增最多 US$0.05／15 分鐘，計入原累計 US$2。兩種候選各自與控制組配對，不套用另一候選；固定 Luna／high、原始資料與 16,384 輸出上限，沿用既有 HTTP 用量護欄，不操作正式職務檔案。

| 對照 | 主要題目 | 必保留的反例 | 判斷方式 |
|---|---|---|---|
| 原版 vs 導覽候選 | 起始已有 map 的早期事實題 | 沒預載 map 時仍可取得；歷史追溯仍可查原話 | 核對答覆與已讀來源，再看重複 map、正文讀取與整段 token；不硬定唯一工具序列 |
| 原版 vs 細節候選 | 數值、範圍及確認責任的組合題 | 明確未知不補造；窄題不帶入無關工作 | 逐項核對必要條件、是否新增猜測及無關內容，不以答覆更長算改善 |

c01、c06 屬已看過失敗的開發題，改善後不能當未見案例泛化。控制與候選都重跑，原有分數只作歷史證據。更廣的超容量比較另案處理。

### 執行前修正：不重建已遮蔽的原生歷史

trace 的 `encrypted_content` 已替換成雜湊與長度，並非可傳回 API 的原件。c06 的轉換單元測試只證明修改邊界，不代表其歷史可重播。本批因此改採新窗口的配對唯讀問答，不刪除舊 reasoning 再冒稱接續：

- 五個情境各一對，共十個獨立 episode；組別順序交替。起始資料共用原 c01 的近期訊息 101–105 與固定導覽，沒有任何舊的 reasoning 或工具歷史。
- 導覽三題是 c01、移除兩層預載 map 後的 c01、及 c04 歷史追溯。反例只移除 map，不刪工具或員工資料。兩邊共有說明允許缺導覽時讀 map，以免原提示「起始已有 map」造成矛盾。
- 細節兩題是 c06 與「只問每日進貨單張數」。兩邊都預載完整理解正文，隔離回答保留問題，不把檢索差異算成回答指引的效果。這不是模型先前真的讀過 c01–c05 的原生接續。
- 兩邊共同使用五項原 Memory 工具 schema，只讀完整凍結來源；本批不給 JD 工具，不測 JD 保存、引用更新或正式執行恢復。純研究讀取 adapter 沿既有生成契約投影來源，無資料庫寫入，無關鍵字答案表。所有 105 則歷史原文仍可按需取得。
- 原生延續只發生在本次每個 episode 內：保留完整 response output items，按原順序附上 function results；不抽掉 reasoning、phase 或其他項目。最多八次模型呼叫，錯誤不重試。
- `criteria.json` 只供事後評分，不送模型；材料、請求、判準、程式與來源雜湊在外送前保存。資料建構與選讀邊界的六案先失敗再通過，連同原候選與既有分析，共 24 案通過。

這個範圍調整讓本次能獨立驗證兩項局部假設，但結果不等於完整產品或原 c06 故障的重播驗收。

離線準備時累計估算占用 US$1.425661625；後續已完成十次唯讀問答，新增占用 US$0.016609010，累計 US$1.442270635。正式 Prompt 未切換；模型結果、逐项判讀、啟動問題及驗證命令見[結果頁](../reading-probe-01/README.md)。
