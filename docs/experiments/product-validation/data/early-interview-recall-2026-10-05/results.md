# 早期訪談找回與更正：比較結果

**Memory 組能在未放入早期原話的起始 Context 中，選讀理解後答出早期數值與責任；當問題涉及已被更正的舊說法，也能沿情境來源查回原話。**三組都完成後續 JD 局部更新，沒有破壞原有責任條件。本批支持的是按需找回與延續修訂能力，不是 Memory 在所有情況下更省 token 或優於摘要。

## 1. 比較什麼

使用同一份合成庫存與物流訪談的第52段完成狀態：105則正式訊息、13項 JD 任務、80項任務明細、207筆引用；既有 Memory 為12個情境與1個理解。三組各自接續八段，固定 Luna／high，每組一遍，不重跑挑結果。

| 組別 | 起始提供 | 共用能力 |
|---|---|---|
| R 完整原話 | 105則正式訪談 | 可查歷史原話、按需讀寫同一起點的 JD |
| S 單層摘要 | 既有摘要＋近期101–105 | 同上 |
| M 分層 Memory | 情境／理解導覽＋近期101–105；正文按需讀 | 同上，另可沿理解、情境與來源查閱 |

沒有把舊模型的加密歷史放回任一組；本批新產生的原生訊息與工具結果照契約延續。既有 JD 仍保存許多答案，不刻意刪去來增加 Memory 優勢。摘要與 Memory 皆沿用既有產物，生成與維護成本不包含在本批 token 中。

八段涵蓋早期到貨數量與入帳期限、5%邊界、收貨異常權責、帳齡表舊新日期、再次修改期限、包裝換算與未知年限、跳題後回問退貨，以及最終 JD 複核。題目、來源與判準在外送前已[凍結](protocol.md)；[逐項評分](analysis/grades.json)由工程代理檢查正式答覆、實際請求與保存產物，關鍵來源及 JD 項另經獨立代理交叉核對，不宣稱是真人顧問盲評。

### 早期細節確實從理解取得

c01 的四項判準，R與M均完整符合：每日15–20張進貨單、已確認項目通常到貨當天下班前入 ERP、月份歸屬由財務判定、不自行回填日期且保留實際時間／未決原因。最初來源是員工第2及第5次發話（#4、#10）。S答對財務權責，但把「超過截止或有疑義的單據」縮窄成「月底截止後才到或歸屬月份有疑義」，該複合項判部分符合，其餘三項完整。這個範圍差異由獨立語意核對指出，沒有另增評分項。

M 首次請求只含近期資料與導覽，沒有上述完整答案，也沒有舊 opaque item。它先重讀理解導覽，再讀「庫存與物流行政的作業核對、追蹤與支援」。15–20張、當天下班前及月份歸屬規則，直到讀回理解正文後才出現在該組請求中；本題沒有查原話或 JD。可核對 trace 第20／26／32行（request 7／9／11）及[正式答覆](live-01/exchange-memory-c01.json)。題目本身問「能不能回填日期」，不能把這個問題文字算成答案洩漏。

之後 c02、c03、c07 能沿用已讀理解，無須每題重新讀取。這是延續分析的效果，不是多次獨立冷啟動成功。c07 的09:10及客服窗口本來就在近期#105，這兩項只算答對，不算早期找回；08:35與08:50也在較後面的#94再次出現，不能全部說成只來自最早那輪。

### 摘要漏項不等於員工沒有說過

S 的 c03 正確回答兩／四工作日期限、雙結案條件及不保證交期，卻說退貨或補貨的決策者尚未說明，再問員工。原話#6與 JD 明細其實都保存「由採購決定」。

逐一比對發現：既有摘要保留一般訂貨／補貨數量權責，但缺少「異常時是否退換貨或補貨由採購決定」這個明確分工；S 在c01–c03沒有讀任何工具，便把摘要未寫到的部分當成尚未確認。因此判錯的是這項未知宣告，不是它捏造了另一個決策者。證據為[答覆](live-01/exchange-summary-c03.json)、[當時 JD](live-01/product-summary-c03.json)與 trace 第86–87行。

這次觀察可用來區分兩種情況：資料明確標示尚未確認時，不需無目的地向下找；整理內容只是沒有涵蓋時，仍可先查指向的來源，再決定是否詢問員工。

### 歷史更正可以沿關係查回

c04 問帳齡表「最早／後來」的交付日。舊日期只在原話#42；目前摘要、理解、情境與 JD 正文均保留新版，不含舊日期。

| 組別 | 實際取用 | 結果 |
|---|---|---|
| R | 起始完整原話已含#42、#98 | 直接答對 |
| S | `read_interview` 讀#42、#98 | 答對 |
| M | 讀「庫存報表」情境，再按其引用讀#2、#42、#44、#48、#98 | 答對 |

三組均區分「原當月最後一工作日」與「現次月第一工作日」，並保留依月底庫存狀態取數；沒有把 JD 改回舊規則。M 這次是有來源方向的查回，不是讀遍105則原話；但它比 S 多一次情境讀取，也多取了三則訊息，不宣稱查閱效率最佳。詳見 trace 第105–132行與三組 `exchange-*-c04.json`。

### 回答仍可能漏說已讀的細節

M 的 c06 正確回答一箱12件、僅限該品號、年限未知及向財務確認，但沒有點出換算經「資料窗口」確認。凍結判準將此列為同一複合項，因此該項算部分符合，而非事後放寬成滿分。這是輸出涵蓋度問題，不是錯報數值或找不到全部原始資料。見[正式答覆](live-01/exchange-memory-c06.json)。

## 3. JD 更新與來源是否真的保存

c05 明確將下一筆收貨異常起的提醒／回報改為三／五工作日。三組保存的 JD 都只改了同一項期限明細，其餘13項任務、80項明細中的其他內容保留；引用總數維持207，原39筆待核對狀態未被無關地解除。

- 新期限明細直接引用本次員工更正#114，不拿舊 Memory 當新事實。
- 補貨或退貨完成「且」帳物相符、採購決策與不保證交期仍在，原依據#6、#12保留。
- 缺貨追蹤仍以補貨入庫、ERP更新及訂單已有安排為終點，沒有套入新期限。
- c08 複核後 JD 與引用均和c05相同，沒有把最後核對指令#120拿來替換事實依據。

可直接查看六份 `live-01/product-{raw,summary,memory}-{c05,c08}.json`；新期限在 `work.tasks[0].details[14]`，實際來源身分可對回同檔正式訪談#114。這部分核對的是保存後的資料，不只模型聲稱「已修改」。

| 累計 output tokens | 4,597 | 4,409 | 5,067 |
| 其中 reasoning tokens | 3,058 | 3,025 | 3,396 |
| 生成請求／計數請求 | 13／21 | 13／20 | 17／24 |
| 工具呼叫 | 7 | 7 | 10 |
| 本批估算占用 USD（含計數行政估占） | 0.011667000 | 0.010189115 | 0.012105495 |

M 起始請求比 R 少 **45.93%**，但這批累計 input 反而比 R 多 **7.32%**、比 S 多 **30.49%**。原因可以從路徑確認：M 初次讀理解多兩次模型接續，其中一次是重讀已提供的 map；查舊日期又比 S 多一層讀取。不能用起始較小推論整段一定節省。工具總數也包含必要 JD 讀寫，不全是 Memory 成本。

累計 input 是各次請求的加總，含重播與快取，不是任一時點的 Context 長度。output 已包含 reasoning，兩者不能再相加計費。模型 usage 估算合計US$0.027461610；65次計數各保留US$0.0001行政估占，合計本批US$0.033961610。累計估算占用 **US$1.425661625**，沒有未結算外送預留；這是本機固定單價估算，不是供應商帳單。

## 5. 能支持什麼，下一步做什麼

這批提供了可追溯的機制證據：早期原話不在目前輸入時，理解可以支援精確作答；理解不含歷史舊值時，可以沿情境來源查回；新資訊可以接回既有 JD，保住責任條件與來源。

**尚不能據此宣稱超容量下勝出。**本批105則原話仍能全部放入128K預算，三組均未觸發截斷或原生 compaction。它驗的是換窗後接續，不是原話本身超量；不使用重複填塞、刻意降低門檻或刪答案來製造超量優勢。

下一步先處理已有證據指出的讀取成本：減少已在 Context 的 map 重讀、讓整理缺項與明確未知能被區分。真正超容量比較需另備自然累積、帶有效工作事實及工具使用的受控長訪談材料。若要提出三層優於摘要的普遍結論，還需更多訪談與重複樣本；本批不追加付費、不依成績補跑，也不直接改正式產品。
