## 離線檢查

先建立測試與最小資料組裝替身。第一次有效測試為 3 failed／1 passed：整份 13 項任務誤入本應只含一項的 Context、去重格缺少指定任務／改稿、數值格混入無關的人工錯稿，均被測試辨認。這是資料組裝行為的 Red，不是模型品質結論。

實作限定一項任務、個別初稿變體及預載固定理解正文後，四項測試通過；原始訪談與 Memory 不被改寫，評分判準未進入模型 Context。Ruff 格式與檢查通過。`offline-01` 凍結 20 格的預備資料，零 provider 外送；後續 `live-01` 另行凍結其實際執行版本，不覆寫離線原件。

第一次 `uv run` 只遇到本機預設 cache 存取拒絕，沒有執行測試或外送；改用本專案已存在的 `apps/api/.venv/Scripts/python.exe`，不另安裝／更新依賴。第一次 pytest 的 cache 權限警告只影響快取，後續關閉本次 pytest cache，未刪除既有快取。

## 配對與判讀邊界

兩版只差 JD 撰寫區的 161 字元指引；同格的初稿與理解正文相同，不把讀取差異混作指引效果。兩次去重格從已更正常溫／冷藏分工的初稿出發；數值格僅注入成果的清點責任錯誤，避免把其他人工錯稿的修正混入本題。期限格保留實際匯出中的「描述舊期限／要求新期限」反例。

執行先固定語意判準。逐格品質由提交後整項任務與已取得來源判讀；期限跨欄合理去重可通過。空修改只在已正確格符合目的；其他格不能用不改來逃避所要求的更正或精簡。

## 獨立方法審查

配對材料審查確認：兩版只有指定指引不同，初稿與理解正文相同，未見判準洩漏或變體偏袒某版。審查只讀方法、資料與指引，不先讀模型結果，與主流程的語意判讀分開。

審查指出 `already_correct` 初稿寫「主管指定的品項」，來源更具體寫「主管指定的高周轉或容易出錯品項」。提交空修改與合法補明品項特徵都可能合理；原第1判準未排除後者，不能只憑非空修改判成亂改。此格保留原件與判準，另外標為有歧義，不作新舊指引勝負依據。

去重第1判準允許「改善可讀性」，單看分數不能證明去重；結果另列同格前後文字量與跨欄資訊配置。四項判準各含多個條件、彼此可能重疊，不把它們當成獨立品質指標。五類案例只屬同一合成職務，數值題是八個相關欄位的局部控制，不能外推成整份 JD、真人或跨職務改善。
