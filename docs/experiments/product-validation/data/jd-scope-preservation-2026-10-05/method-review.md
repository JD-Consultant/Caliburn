# 評分適用範圍的獨立核對

本批執行期間，另一位只讀審查者在未讀本批模型結果、未得知 Prompt 組別的條件下，依工作分析與 JD 指南評估 `shared_authority`。它只看事先提供的示意稿與來源條件，沒有重評任何模型樣本，也沒有改判準。這是助理的方法複核，不是真人顧問盲測。

## 凍結分數與產品含義分開

凍結規則要求客戶確認需求、員工約定前端、同事後端規則及部署都可辨識。漏一部分仍記 partial，不因本次討論改回 complete。

但這項判準衡量的是較強的「單項任務可獨立還原分工」。[JD 指南 §3](../../../../guides/2026-09-09-jd-field-and-writing-guide.md#3-職務目的職責任務同一份工作的不同縮放程度)並不要求每句包含所有成分；[§4](../../../../guides/2026-09-09-jd-field-and-writing-guide.md#4-成果產出與完成標準不是同一件事)及 [§7](../../../../guides/2026-09-09-jd-field-and-writing-guide.md#7-最後讀一遍時要看什麼)要求必要輸入、權限與交接讀得出來，且省略不能造成誤解。

因此，僅寫「前端維護」不能可靠告訴讀者部署由誰負責；另一方面，若全份 JD 的鄰近、明確適用內容已交代分工，也不必在每條機械重抄。本批沒有提供這種其他欄位，不能假定已交代；也不能反過來從本批漏項推定正式產品所有精簡寫法都錯。

## 後續驗證應回答什麼

必要限定的作用是避免讀者誤判，而不是增加角色名稱數量。若日後比較完整 JD，可事先加入三種反例：

1. 同一適用範圍的鄰近欄位已清楚交代分工，省去任務內重述後，讀者是否仍能正確辨識權責？
2. 只讀「前端維護」時，讀者能否不用猜測辨識誰部署、誰確認需求？
3. 三方分工都列齊，卻把未知的變更核准人推成「客戶」，其他準則是否能抓住錯誤？需求確認與變更核准不是同一件事。

這些尚未執行，不加入本批分母。當前仍按已凍結規則比較，另觀察越界帶入其他工作與無依據擴張；不以較多文字或較少 token 單獨選擇 Prompt。
