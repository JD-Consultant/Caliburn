# 研究程序審查

本頁保留獨立工程審查的問題與處理，不修改事前方法、模型輸出或評分答案。審查使用唯讀程式檢查與純記憶體反例，不是工作分析專家的盲評。

## 已發現的接縫

1. **壓縮未納入通用預算護欄。** 原腳本只限制 `/responses`，沒有在 `/responses/compact` 前套用同一界線。因此約 US$1 是一般生成的保守估算，不是任意壓縮情況的上界。本輪不改正在執行的凍結程式；離線核查一旦看見 compact，拒絕將該批列為已核實預算的結果。未來若重跑此腳本，須先補齊外送護欄或明確禁止此比較觸發 compact。壓縮後發布已有另一次獨立實驗。
2. **工具拒絕不一定拋出例外。** `scope_not_allowed`、`source_not_available`、`target_stale` 及單物件容量失敗可能以工具回傳表示。若忽略它們，最後成功提交不代表資料讀取有效。離線核查會檢查起始導覽及所有已保存的模型／工具往返；任何這類失敗都排除整批有效結果。模型選錯標題等行為錯誤仍保存，不假裝所有模型呼叫都正確。未來重跑須在即時迴圈收到這類拒絕時停止。
3. **五萬元端點的判準文字。** 凍結檔同時寫「五萬元以下」與「正好五萬元未知」。評分時明示：確定的是未達五萬元可自行下單；恰等於五萬元保留重疊待釐清。這是釐清判準的端點含義，不改員工原話，也不把最新未確定說法當成已授權。

`analysis.py` 是事後加入的離線核查與用量計算，未參與生成。它不改原始 trace，先核對執行前檔案雜湊，再確認八份完成答案、兩批發布、起始 Context 隔離、零 compact、讀取資格、完整 usage 與實際生成界線。`test_analysis.py` 的九項反例檢查用量、拒絕、語意分數加總與報告表格；`test_support.py` 的九項檢查來源與隔離。報告驗證另故意把 26／27 改成 27／27、把累計輸入改成起始輸入，兩種錯誤都應拒絕。

## 結果如何判讀

事實正確與來源支持分開。列在 `cases.json` 的來源是核查線索，不是唯一可接受的序號集合；同一事實可能在後續原話再次出現。回答承認資訊未知可以是正確答案，但在未讀過任何依據的負控制中，不等於有來源支持。單一題目的引用只能支持部分事實時，不能算完整引用充分。

比較依固定模型答案進行語意複核，不用字串相等自動評定。凍結標準答案與未加分原結果均保留；複核紀錄說明每項得分與爭議。這份研究不因回應成功就宣告完整 JD、真人效益或容量極限通過。

來料題的第三項，原話未明示「接受」對象。嚴格判讀要求接受處置方案，三層兩次均不加分（26／27）；採共同接受權限的解讀則為 27／27，另記為歧義，不修改原判準。來源完整支持另要求沒有無關序號或顧問轉述，因此即使內容符合，三層仍只有各 3／8 題完整支持。這是直接選原話序號的研究診斷，不直接等同正式 JD 引用 Memory 物件的流程。
