# 完整原話下的 Memory 附加價值：結果

**本次沒有觀察到 Memory 的穩定額外收益。** 在完整訪談與既有 JD 已可容納的條件下，兩組均通過核心更正、責任邊界及未知保留判準；原話＋Memory 組累計輸入多 37.3%，引用也未穩定改善。

這個結果支持先區分兩個問題：原話要保存與可回查；Memory 是否值得作為某次分析的額外材料，需要由使用效果決定。它不支持直接刪除 Memory，亦不代表超容量或跨次訪談已不需要整理。

## 比較條件

同一合成庫存／物流行政職位，取第 52 段成功後的 105 則正式訊息及 13 項任務、93 個可編輯文字欄位。兩組都取得完整對話（包括既有顧問答覆）、同一 JD 及相同核對題；Memory 組另有自然整理成的 12 個情境、一個理解，其導覽與正文可按需讀取。

使用 Luna/high、全新 Context、無 Compaction。兩道複合題各重複兩次，第二次交換組別順序，共八次分析。五個人工錯誤在兩組相同位置植入，不改訪談原件。判準在外送前保存，不由結果反推。詳細方法見 [實驗設計](README.md)、[方法審查](review.md)。

## 核心內容結果

逐項檢查底稿加提案後的相關欄位及追問，不只核對最後的文字結論。由工程代理判讀、另由代理獨立複核；目前沒有真人顧問評分。

| 題目與重複 | 原話 | 原話＋Memory |
|---|---:|---:|
| 更正／第一次 | 12／12 | 12／12 |
| 更正／第二次 | 12／12 | 12／12 |
| 責任與未知／第一次 | 9／9 | 9／9 |
| 責任與未知／第二次 | 9／9 | 9／9 |
| 合計 | **42／42** | **42／42** |

兩組都能分清週一 08:50 與其他工作日 08:35，保持 09:10 交表期限；驗收比例以每批實際驗收件數為分母，嚴格區分超過 5% 與剛好 5%，不混用設備備品比例。帳齡表改為次月第一個工作日交付，但仍採月底狀態；召回決策權回到品質窗口，保存年限與溫度門檻保持待確認。

這些是 42 個固定判準的通過數，**不是整份 JD 的完整性或滿分評定**。不少項目在底稿已正確，本次檢查它們是否被錯改；個別未受試的跨欄位問題仍另列於[語意判讀](semantic-review.md)。

## 引用與工具使用

依每個提交欄位的完整新文字核對直接來源：原話組 9／11 個欄位完整支持，Memory 組 7／10。漏引主要發生在修正一個時點時，保留其他舊句子卻沒有選回支持那些句子的早期來源，例如核准調帳及核准單號出自訪談 18、帳齡核對入庫日期／調撥出自 44、週報收件對象出自 46。

兩次結果有波動：更正題第一次原話組較完整，第二次 Memory 組較完整。因此不能據此宣稱任何一組普遍改善引用。所有提案均直接引用訪談，沒有以 Memory 作直接來源；案例與缺漏位置見[引用逐欄核對](semantic-review.md)。

Memory 組四次分析中，只有一次真的讀 Memory 正文：讀三個情境及一個理解；另一次只重讀訪談，兩次沒有使用讀取工具。原話組四次中，一次重讀訪談。可用工具與實際使用是兩件事，不把「有提供 Memory」當成「答案來自 Memory」。

Memory 導覽與額外工具定義讓首次請求多 1,586 tokens，約 7.5%；加上實際閱讀與接續，總輸入多 40,025 tokens，約 37.3%。沒有單次請求超容量；最高生成請求為 32,279 tokens，未達 128K 輪前門檻。

快取沒有清除，等待按回應標頭調節。費用、耗時只說明這次實際執行，不當成排除供應商快取及網路後的純效能比較。逐次 usage、快取寫入、讀取及用量見 [metrics.json](live-01/metrics.json)。

### 已有 Memory 並非免費

素材中的 Memory 原本由四批整理產生。重讀舊 trace 得到 46 次生成、52 次計數，生成輸入合計 2,370,081 tokens、輸出 74,774 tokens，依產品已保存的定價規則估算生成費用 US$0.114234600。這筆已在前次執行支付／占用，**沒有再加入本次新增費用**，也不攤到每道題宣稱每次都要重建。

這是當時 Context 組裝下的歷史成本，包含已查明會累積舊 App 參考資料的流程；不代表精簡後的 Memory 必然需要同樣用量。原件、各批次及快取見 [前處理重算](live-01/memory-preprocessing.json)。這裡列的是生成估算，計數管理預留與舊 Compaction 的其他成本未併入，不能叫供應商帳單或全生命週期總成本。

本次新增占用 US$0.024165235，其中生成估算 US$0.023065235，11 次計數各保留 US$0.0001 的未知費用額度。整批 5.66 分鐘，原累計占用更新為 US$1.024756355；沒有為補數據追加外送。

## 對設計的意義與下一步

1. **先精簡 Context，不以 Memory 填補重複資料問題。** 原話本身在本案例可容納，先前約 15 萬 tokens 的負擔不能直接歸因於員工資訊太多；每輪 App 資料與工具讀取的累積應分開處理。
2. **目前不要強制每輪讀 Memory 或改用 Memory 引用。** 額外正文可能只是原話及 JD 的重複分析，本次沒有品質收益足以支持固定增加閱讀。
3. **把整理價值與引用機制價值分開。** Memory 的導覽、跨次整理、來源鏈及換版差異仍有產品用途，但不是本次已證明的分析增益。引用漏選早期依據仍需單獨改善。
4. **下一個有鑑別力的比較應測替代，而非只測附加。** 可先離線設計「完整原話」對「近期原話＋Memory 按需查閱」的同題比較，檢查正文是否真的減少、精確事實與引用是否保留；再視結果決定是否值得另行授權付費。不要只是再跑同一個已接近上限的題目。

以上是研究建議，沒有據此停用正式 Memory、改 Prompt、改工具或實作新的輪前摘要。超容量、更長職務、多職位及持續訪談的效果仍應用相應條件測試，不能由這一次短核對直接外推。
