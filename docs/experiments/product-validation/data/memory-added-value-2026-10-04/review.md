# 方法、原件與腳本審查

## 實際執行

八次分析全部完成，11 次生成與 11 次遠端計數均取得 HTTP 200；生成回應的狀態全部為 `completed`。沒有 provider 失敗、工具選取拒絕、SDK 重試或 Compaction。整批耗時 339.77 秒，估算占用 US$0.024165235，連同原有占用為 US$1.024756355，低於本次 US$0.20／30 分鐘及原累計 US$2 的界線。

本次使用產品的 Luna/high 直連 adapter、現行顧問指引及 Memory 讀取契約，但不接正式執行程序或資料庫。它比較獨立核對提案，不是八輪真人訪談、八次正式 JD 保存，也不是完整產品交易驗收。

## 公平性與來源邊界

已逐一核對四個配對截面（兩題、兩次）：兩組的完整訪談、JD、當次題目完全相同；Memory 組只增加兩層導覽及四個讀取工具。共同指引相同，兩組都有原話讀取與同一提交工具。判準與標準答案不放進請求。

每格初始 Context 只有兩則新 `user` 訊息：App 資料及本次題目。沒有復用先前格的 reasoning、工具結果或原生接續；同一格後續模型呼叫則保留 SDK 回應的完整原生項目。公開 trace 對 opaque 內容只留長度與雜湊，不把展示投影當成真正送回模型的項目。

來源是第 52 段成功後的 105 則正式訊息：52 則員工、52 則顧問及一則 App 開場。Memory 是原流程自然產生的 12 個情境、一個理解，處理上界為序號 104；未把後續回提題或本次判準填入 Memory。52 段主要訪談已有相當完整的 JD，底稿大部分欄位正確，另植入五個相同錯誤供更正。

**這是刻意容易容納、已有分析成果的條件**：完整對話包含既有顧問分析，JD 的其他欄位也保留部分正確答案。它適合檢查「額外注入 Memory 是否值得」，但對從空白辨識工作、超容量訪談及跨次持續分析的鑑別力有限。

## 找到的兩個腳本問題

### 失敗回應沒有停止整批

只讀審查發現：若 SDK 回傳 `status != completed` 且仍有可計價 usage，原程式只跳出本格的 Step，還會開始下一格。這不符合既定「第一個 provider 失敗停止整批」。

離線反例以同一 runner 執行兩格，將 provider 邊界替換成帶有效 usage 的失敗回應。修正前觀察到兩格都外送；修正後只允許第一格的一次計數、一次生成，保存停止原因、已知 usage 與未知計數的占用，第二格不開始。現行研究腳本改為交由整批停止處理。

修正發生在 live 完成後。live 的 11 個生成均為 `completed`，沒有觸發此分支，因此**不為修正這個未觸發分支重跑八次付費分析**，也不將新程式冒充當時執行碼。

### 舊 trace 批次欄位讀錯

第一次離線成本重算出現 `KeyError: event_id`。逐行投影舊 trace 後，確認真正欄位是 `after_event`，不是來源檔缺漏。另設兩批 trace 的離線反例，修正前失敗、修正後能正確分組 e012／e052；沒有改原 trace 或生成新的 Memory。

離線反例 Red 階段：2 failed；修正後連同原有素材／護欄測試：10 passed。Ruff 檢查與格式檢查通過。測試不讀實際金鑰、不連資料庫或模型。最初 sandbox 對 pytest 暫存目錄拒絕存取，改為經核准的本機離線測試環境；那兩次環境錯誤不算行為測試的 Red。

## 其餘觀察與限制

- 核心判準另由只讀審閱者獨立複核，未讀主判讀稿：八格的 93 個合成後欄位均對得上底稿與提案，更正題各 12／12、責任題各 9／9。複核未涵蓋完整引用支持，後者由主判讀另逐欄記錄；不將代理複核稱為真人評測。
- 等待邏輯在計數前用保守的 25,000 tokens 初值，而實際加讀後單次輸入最高 32,279。這不解除費用、次數及時間界線，但未重新依計數後的速率標頭精確排程。本次沒有速率錯誤，先保留為研究腳本的後續改善，不延伸成產品改造。
- 反轉第二次兩組順序，不等於清除供應商 prompt cache；已記錄各回應的讀取／寫入快取用量。費用與耗時含快取及等待，不能當成純 Memory 演算法效率。
- 內容與引用需要語意判讀；離線測試及結構接受只證明來源存在與資料隔離，不代表分析正確。具體判讀見 `semantic-review.md`。
- 本次沒有實作輪前摘要，也沒有測輪中 Compaction。不能拿此結果宣稱新的摘要設計已驗證，或覆蓋之前停止的長訪談比較。
