方法見[執行前方案](README.md)，原件見 [manifest](live-01/manifest.json)、[用量與選讀分析](live-01/analysis.json)、[逐項語意判讀](semantic-review.md)。本批使用 18 則合成訊息、三批整理、四題顧問選讀，每組一次；兩組同為單一理解集合，只改維護指引。不是雙層與單層勝負，也不是超容量實驗。

## 2. Token 與成本

API usage 按每次 HTTP 回應累加，包含接續重播與工具結果；cached 是 input 的子集，reasoning 是 output 的子集，不能再相加。工具字數是序列化回傳的字元，不是 token。

| 階段／組別 | input | 其中 cached | output | 其中 reasoning | 模型回應 |
|---|---:|---:|---:|---:|---:|
| 整理／原方法 | 48,920 | 38,196 | 5,082 | 2,945 | 11 |
| 整理／候選 | 35,147 | 26,211 | 2,860 | 874 | 8 |
| 顧問／原方法 | 24,451 | 18,419 | 2,421 | 1,387 | 13 |
| 顧問／候選 | 15,777 | 12,673 | 2,365 | 1,426 | 9 |
| 合計／原方法 | 73,371 | 56,615 | 7,503 | 4,332 | 24 |
| 合計／候選 | 50,924 | 38,884 | 5,225 | 2,300 | 17 |

候選本次顧問 input 少 **35.48%**，讀回字元少 **52.22%**，含維護總 input 少 **30.59%**。原方法維護階段有兩次 patch 拒絕，其重讀和修正已計入，不能把全部差額都歸因於內容組織。每組只一次，亦不作顯著性或穩定收益宣稱。

41 次生成估算合計 US$0.010915415；另保留 41 次 token count 的 US$0.0041 本機預留，**本批占用 US$0.015015415**。加前批 US$1.270089235，累計 **US$1.285104650／US$2**。82 次外送皆收到回應，`pending` 只是 count 尚未結算的保守預留，不是還有程序在跑，也不是實際帳單。

14 個單元全部完成，589.87 秒（約 9.83 分鐘），低於 20 分鐘；無 provider 重試或補跑。請求 input 最高 7,108 tokens，沒有 Compaction，因此本批不能回答超容量下的保存問題。

## 3. 對設計的判斷

可以保留的方向是**輕量導覽 → 相關理解正文 → 只有具體缺口才查原話**，以及**先定位受影響內容，再局部撤換／補充**。本批確有選讀及增量修訂成功例，且沒有靠多塞完整原話完成。

還不能採用「新版已更好」的結論。兩組保存都完整，差距出現在顧問將已讀內容寫成 JD 時；候選沒有通過「品質等價後才談省量」的門檻。共同限定重述也有成本：候選最終正文 574 字元對原方法 517，導覽 429 對 355。

下一步先把問題分開：以固定 Memory 檢查顧問如何保留必要限定、避免跨工作混入，再用未見職類與較多工作單元驗選讀；最後才做超容量的摘要／Memory 比較。這些是後續方向，不是本批剩餘額度的自動續跑。正式產品、資料表、索引與模型均未變更。
