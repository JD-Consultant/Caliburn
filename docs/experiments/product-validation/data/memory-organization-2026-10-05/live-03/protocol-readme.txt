# Memory 組織方法：候選指引與對照準備

狀態：**候選，尚未套用正式產品。**第一批完成一對產物，發現細節保留改善及引用支撐缺口，見[首批結果](results.md)。第二批已補強來源與導覽，兩組輸出上限改為 16,384，但原版第一格碰到實驗的 16 steps 限制；新候選尚未執行，見[第二批停止紀錄](source-navigation-results.md)。正式產品為 64 steps，不能把這次停止當成產品或新提示失敗。配對重複及 A 效果仍未完成。

內容方法以[工作分析指南 §10–12](../../../../guides/2026-09-09-complete-work-analysis-guide.md#10-從碎片訪談到可延續的工作理解)為準；方案、文獻與控制理由見[組織粒度研究](../../../../research/work-analysis/2026-10-05-memory-organization-and-incremental-analysis.md)。這裡不另定義角色權限、資料保存或發布契約。

| 材料 | 候選的重點 |
|---|---|

以下維持原樣：Luna／high、B1 不讀理解、B2 不改情境、B1 → B2 → 發布、不回交、正式訪談範圍、候選工作稿、V4A 修改、來源綁定、App 執行及恢復機制。A 提示及工具不在本次修改範圍。

## 工具與參數審查

候選工具說明只按**該角色原有工具名稱**覆蓋 description，不能將整份檔案當成 B1 可用工具清單。B1 仍只有情境導覽、情境正文、訪談與情境寫入工具；B2 才能讀理解並修改理解。首階段對照不使用這份工具候選。

名稱、參數、strict schema、回傳、錯誤碼及合法下一步均不改。`target_title` 仍是目前導覽上的精確標題，訪談序號仍由 App 提供，版本及範圍不交模型填。Create／Update／Delete 原說明已有候選效果、完整欄位、局部修改、歧義拒絕及刪除關係的交代；何時新增或拆合留在角色指引，不再複製一份到各寫入工具。

參數 description 延用正式契約，不另外手改生成檔。這輪沒有發現必須改參數結構或工具錯誤格式才能表達整理意圖的缺口。

## 分開比較，避免不知道哪裡有效

| 階段 | 唯一主變因 | 固定的部分 | 可回答的問題 |
|---|---|---|---|
| 1：B2 整理 | 原 B2 指引／候選 B2 指引 | 同一份 B1 情境、起始理解、變更資料、可讀訪談範圍、工具及模型設定 | 組織方法是否保留有效資訊、形成可獨立查用的理解？ |
| 2：A 使用結果 | 第一階段兩組產生的 Memory | 相同 A 提示、工具、問題、JD 起點及歷史可見範圍；每組獨立起跑 | 整理結果是否改善實際回答、JD 與閱讀效率？ |
| 3：B1 增量維護 | 原 B1 指引／候選 B1 指引 | 相同分批訪談與起始情境、工具及設定 | 碎片是否接對、拆合是否保留舊資訊及來源？ |
| 4：工具說明 | 原 description／候選 description | 已選定的角色指引、相同材料與起始工作稿；不改正文、schema 或 A | 何時讀／不讀的說明是否減少不必要閱讀，且不漏掉必要下查？ |

第一階段沿用[前次固定材料](../memory-summary-capacity-2026-10-05/live-02/materials.json)的 12 項情境與 1 項理解，不覆寫原件。原資料含 105 則正式訊息，但快照處理邊界是第 104 則員工輸入，因此兩組只准讀取 1–104，不混入第 105 則顧問答覆。先以隔離副本做 B2 重組比較，兩組都被明確告知這是全範圍重組評測，不能把同一快照偽裝成新一批 diff。這測的是既有內容的重組；增量 diff 另用[案例卡](cases.md)準備合法前後工作稿。

第一階段可直接沿用前次[19 項事實判準](../memory-summary-capacity-2026-10-05/live-02/cases.json)，並檢查整份產物是否丟掉其他仍有效內容。這 19 項不是整份 Memory 的完整性上限。已知材料瑕疵須在判讀註記，不能偷偷修原件或把既存錯誤當正解。

每階段至少做配對重複，若費用不足以支持約定的重複數，先縮小研究問題或記為未完，不把一格成功包裝成穩定提升。各付費批次開始前才凍結實際請求、材料、版本、預算及停止界線；本輪不沿用已結案批次的付費授權。

## 怎樣才算值得採用

先逐項標記完整、部分、遺漏、錯誤，附產物文字與來源；新造職責、數值或權限混淆列為重大錯誤，不讓平均分抵銷。可接受不同合理組織；來源只相關、不支持正文，不能算正確引用。

品質沒有退步後才比較：B1／B2 建立與維護成本、導覽大小、A 讀入正文量、無關內容、回讀原因、輸入／快取／輸出 token、時間及工具錯誤。必要下查不是失敗，沒有下查卻回答錯也不是節省。

「理解已有，A 沒讀到」「情境已有，理解漏掉」「已讀到，改寫又漏掉」分開記錄。若主要退化不在組織方法，依證據修正相應責任，不繼續堆疊 B2 指令。

## 首批本地驗證與限制

2026-10-05 本批已獲授權：新增最多 US$0.10／20 分鐘，計入原累計 US$2；開始前估算占用 US$1.198955810。順序為原版 1、候選 1、候選 2、原版 2。只改角色指引，工具說明仍用正式版。每格最多 16 個模型 step；全批最多 64 次外送（含容量計數），遇到上限或 provider 失敗即停，不補跑。

[執行器](study.py)使用正式 B2 runtime、讀寫工具與候選交易，在 55441 的測試 PostgreSQL 新增獨立 schema。四份職務檔案互不干擾，模型仍可按需查閱有界原話；不發布到正式產品。初始物件 ID 在造種子時固定，以排除正式導覽按 UUID 排序造成的閱讀順序差異；模型開始前即恢復正常 ID 產生，不替換工具結果。四格起始導覽、正文及來源須逐一相同才准外送。原件、提示、工具及程式雜湊由 manifest 保存。

本地檢查只驗角色工具集合、schema 不變、完成 JSON 可由現行 consumer 接受，以及既有角色接線／工具契約是否仍正常。純文字方法沒有假裝成 TDD，也不以關鍵字存在判斷內容品質。

候選文字與離線契約驗證見 [verification.md](verification.md)；本批隔離資料庫、審查及停止過程見[執行紀錄](execution-notes.md)。兩份完成產物已逐項語意核對，尚未經真人顧問複核；正式指引與工具未替換，原實驗 trace／manifest 未變更。累計估算占用更新為 US$1.222543940。

第二批條件、原件與停止原因另見[來源與導覽修訂結果](source-navigation-results.md)。前兩批腳本均按各自 manifest 原雜湊保存於 `live-01/study-source.py.txt`、`live-02/study-source.py.txt`。截至第二批停止，累計估算占用為 US$1.236537370。

## 第三批：對齊正式執行能力

2026-10-05 使用者另批准新增最多 US$0.10／20 分鐘，計入累計 US$2。先跑原版、來源與導覽修訂版各一次；本批不足以判斷穩定性，不與不同上限的前批合併計分。材料、B2 文字、工具及判準與第二批相同，不再次修改候選提示。

執行能力由正式 `ModelSettings` 取值，避免在實驗裡抄一組較低的限制：每格 64 steps、每 step 32 個工具呼叫、16,384 輸出 token、每請求 120 秒。正式每格 512 次外送之外，實驗全批也共用 512 次外送上限，包含 token 計數。實際設定隨 manifest 凍結，若執行時不一致就拒絕開始。

實驗刻意較嚴的部分是：失敗不自動重試、整批付費階段最多 1,200 秒及估算占用 US$0.10。這次只研究固定材料的 B2 組織方法，不測 compaction；輸入達 128K 或請求壓縮即停止。正式 compaction 能力雖保留於設定，不代表本批有執行壓縮。初始兩份工具 view 必須完全相同，正式產品不改動。執行與審查紀錄繼續寫於[同一份紀錄](execution-notes.md)。
