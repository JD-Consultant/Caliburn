# B2 重組對照：細節保留改善，但來源與輸出容量仍須處理

2026-10-05。本批完成原版與候選各一次；候選第二次因單次輸出達上限停止，原版第二次未開始。**不能視為已完成兩次重複比較，也尚未採用候選到正式產品。**

## 3. 來源支撐仍有缺口

候選 1 的 12 項理解各引用一項情境。這次的工作範圍大多可以如此分開，但正文若帶入別項工作的條件，就不能只留下同名來源。

| 候選理解 | 正文帶入的內容 | 實際綁定 | 缺少的支持 |
|---|---|---|---|
| 收貨異常週報 | `案件的兩／四工作日提醒與結案條件屬收貨異常追蹤本身` | 只有「收貨異常週報」 | 該情境沒載兩／四工作日；條件在「到貨驗收、ERP 登錄與收貨異常追蹤」 |
| 退貨核對、狀態登錄與差異處理 | `與盤點使用核准庫存調整單的程序不可混為一談` | 只有同名退貨情境 | 盤點調整單的依據在「庫存盤點與差異查核」 |

這些不是憑空編造的員工事實，而是**分析讀過其他情境，寫入結論後卻沒帶上支持關係**。資料庫能確保綁定合法，不能代替語意支撐判斷。後續可選擇補來源，或避免在本項重複寫出不必要的跨工作規則；不能規定每項必須只引一個來源。

另有兩個保留問題：

- 已知初始理解把退貨的「前一天」寫成「前一工作日」；兩組都沿用了這個說法。原情境及員工原話沒有相同限定，不能因兩組一致就算改寫正確，也不能把這個既存問題說成候選新造成。
- 候選將保存年限放在「收貨異常週報」、工作條件放在收貨理解，導覽卻沒有完整提示這些跨工作資訊。正文存在不代表 A 一定選得到；下一階段仍需測實際選讀。

## 4. 組織與 token 的取捨

| 指標 | 原版 1 | 候選 1 |
|---|---:|---:|
| 模型回應次數 | 6 | 8 |
| 累計輸入 token（含快取命中） | 94,755 | 133,094 |
| 其中快取命中 token | 70,174 | 106,677 |
| 累計輸出 token（含推理） | 7,154 | 8,025 |
| 其中推理 token | 2,669 | 1,749 |
| 單次最大輸入 token | 24,566 | 26,396 |
| 整理後理解正文總字元 | 3,643 | 5,040 |
| 理解 map JSON 字元 | 651 | 1,336 |
| 只查退貨時，對應理解正文的字元 | 1,863 | 512 |
| provider 回報用量換算的生成費用估值 | US$0.007350915 | US$0.008380795 |
| 執行秒數（包含速率等待） | 128.48 | 154.65 |

輸入是每次 API 請求的累計，不是單次 Context 超過 128K。字元也不是 token。兩組都讀了起始理解及全部 12 項情境，均未呼叫訪談原話工具；初始已有的兩層 map 仍被重讀，候選「不必重讀有效導覽」尚未消除這個行為。

原版把收貨、退貨、調撥、缺貨與週報放在同一項，查退貨便要讀 1,863 字元。候選退貨理解為 512 字元，這是**靜態產物的選讀潛力**，不是 A 已實測節省約 73%。候選 map 與總正文反而較長，建立階段的 token 也較多；跨工作題還可能需要更多物件及來源。是否能靠後續重用抵回建置成本，需另測，不能只報單項變短。

## 5. 為何停止

候選 2 第三次模型回應的 `status` 是 `incomplete`，`incomplete_details.reason` 是 `max_output_tokens`；輸出恰為本批 **8,192 token**，其中推理 2,410。回應內包含 13 個建立理解呼叫，最後一個參數截斷。正式 runtime 在準備工具前拒絕整個不完整回應，因此這 13 個呼叫不列為已執行修改，不將其文字評成正式產物。

這是本批容量設定的限制。**現行產品的 `ModelSettings.max_output_tokens` 是 16,384，本批為有界試驗設成 8,192。**兩組雖用同一上限，但候選較細的重組更容易在一次輸出產生多個長正文；本次失敗不能直接推論正式產品也會失敗。沒有在途中提高上限或改指引續跑，以免混用條件。

全批耗時 380.22 秒，生成用量估算 US$0.021888130，加上 17 次容量計數各 US$0.0001 的保守預留，共占用 **US$0.023588130**；原累計更新為 **US$1.222543940／US$2**。這是本機估算與預留，不是帳單。停止不是費用或 20 分鐘上限造成，原版第二次也沒有另送請求。

## 6. 下一步

1. 先處理候選的引用支撐與跨工作資訊導覽，不要求固定項數，也不增加新工具或資料層。
2. 下一個獨立批次將兩組單次輸出上限對齊正式產品的 16,384，保留分 step 寫入能力，完成約定的配對重複。要重新記錄版本、預算與授權，不能把此次未用完的額度當成自動補跑許可。
3. B2 內容與來源達標後，再固定 A，測「找到正確理解 → 內容足夠便使用 → 有具體缺口才下查」。只有這一步完成，才能判斷實際 JD 品質及閱讀成本。
