## 方法與判讀範圍

依[事前規程](live-01/executed-protocol.md)和[固定判準](live-01/cases.json)，三種條件各重複兩次，第二次反向排列；各格皆是新 Context。使用 `gpt-6-luna`／high、OpenAI SDK 3.20.0、前批同一 candidate 指引與工具。只預載對應完整任務、Memory 導覽及近期序號 105，完整 1–105 可按需回查。

控制素材人工移除部分已知事實，原話與來源關係保留；這不是自然遺漏率。原 JD 的退貨 requirement_7 已含正確常溫／冷藏分工，因此本題可驗跨欄修正及停止深讀，不能單獨歸因為 Memory 帶來新知。兩個缺口題的完整任務同時含另一項污染，補讀須按實際目的判斷，不以深度本身判錯。

執行成功、成品語意與閱讀負擔分開判讀；API 200、研究工具接受，都不是全面品質通過。語意核對見 [semantic-review.md](semantic-review.md)。

可成立的觀察是：模型沿相關情境的來源清單要求取回原話，但先重讀導覽，再分批查較晚序號，造成多次往返；尚未證明這一類缺口能在本研究界線內完成成品。完整成品正確性、必要原話引用及取得充分資料後的停止行為，都不能由這兩格評定。

## 下一步的有界方向

優先檢查已知資料的使用方式，而不是提高模型或另造檢索框架：明確區分已預載導覽與需要補取的正文；相關情境缺少細節時，利用既有 `read_interview` 的多序號查詢，減少無內容線索的逐批試讀。保持「理解足夠即停止、具體缺口才下查」不變，不要求每次掃全部來源。

這是依本批軌跡提出的待驗假設，**尚未改 Prompt／工具、尚未證明能提高完成率**。OpenAI 指南建議在工具指引明說何時與何時不該呼叫，並把程式已知資訊的負擔留給程式；它不保證上述本案假設必然有效。[Function calling](https://developers.openai.com/api/docs/guides/function-calling)。

局部改寫則需另驗「保留有效舊條件」：在改分工時，同時保留仍正確的期限、狀態與適用範圍。不與讀取策略同時改動後直接比較，以免分不清改善來源。這次沒有改正式產品或再送付費請求。
