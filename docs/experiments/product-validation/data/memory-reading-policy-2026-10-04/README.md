## 比較問題

在完全相同的近期原話、Memory 與 JD 底稿上，明確要求「理解足夠就停止；具體缺口才向下讀取」，是否能保留判斷品質，同時減少原話回查與累計輸入？

前次[替代價值比較](../memory-replacement-value-2026-10-04/results.md)觀察到 Memory 與原話雙重閱讀。其[診斷及提示審核](../memory-replacement-value-2026-10-04/review.md)已修正 A 指引；本次只比較這項改動，不重製 Memory 或放寬執行上限。

## 凍結內容與處置

兩組均使用 `memory-replacement-value-2026-10-04/live-01` 保存的 `materials.json`、兩題原始輸入及相同 Memory 讀取／研究提交工具。起始只含訪談序號 105、情境與理解導覽、共同 JD 及當次題目；訪談 1–105 與固定 Memory 正文均可按需查閱。每格都是新 Context，同格內保留原生接續。

| 指引組別 | 唯一改變 |
|---|---|
| `original` | 前次 `instructions.json` 的原指引，不重新從現行程式生成 |
| `candidate` | 使用本次 A 顧問指引；隔離研究的共同補充與原指引保持相同 |

兩題各做兩次重複，共八格。第一次先 original、後 candidate；第二次交換順序。模型固定 Luna／high，每格最多六次模型回應；整批最多 32 次生成／64 次外送，最多 8,192 output tokens。工具、材料、題目、21 項核心判準及共同研究補充保持相同；只改產品顧問指引。準備時驗證來源、工具與輸入指紋，保存程式、兩組完整指引及本協定，不修改前次原件。

這是既有 JD 的更正與責任核對，不是從空白訪談到完整 JD，也不驗證新輪前摘要或壓縮後行為。題目沿用原件，不因已知結果重新挑題；同任務欄位一致性與完整修改欄位的直接來源支持，沿前次輔助審查另列，不加入原 21 項分數。

## 指標與判讀

先依原判準人工語意核對套用後 JD、提案、未知與來源，再比較工具讀取類型／範圍、重複讀取、回傳字數、起始與累計 input、output、reasoning、cached tokens，以及用量估算。新組只讀更少但漏掉例外或不交付，不算成功；API 接受與來源形式合法也不等於內容有據。

交付數以預定四格為分母；核心判準分開列出通過、未交付與錯誤。保留原話回查的理由與 Memory 已有內容，檢查是否真正使用理解／情境作直接引用。對同素材兩次重複只作局部比較，不作統計顯著性推論。Memory 的既有前處理費用不重算本批新支出，也不因此說它沒有成本。

## 界線與紀錄

單一共用護欄管理兩組，不因切換指引重置費用或時間。先計數、預留，再生成；SDK 自動重試關閉。首次 provider 失敗、未知 usage、費用、時間或次數到界即保存並停止，不重送結果未知的請求。正式產品、DB 與他人程序均不變，不 commit／push／merge；只外送既有合成資料，不輸出金鑰。

`policy_study.py --run offline-01` 僅凍結素材，零外送；`--run live-01 --live` 才讀既有明確指定的憑證並執行。新目錄拒絕覆寫。公開 trace 遮蔽加密內容，同格接續仍用完整原生 items；manifest、原始 trace、提案及失敗保持為原件，離線 metrics 與語意判讀另外保存。

方法借鑑 [OpenAI Memory Evals](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization#memory-evals)的同 harness／判準、完整 trace 與 A/B 指引比較；本次僅驗 Memory 的使用策略，不宣稱已完成整條整理管線評估，也不照搬個人偏好記憶的「最新勝出」到員工事實。
