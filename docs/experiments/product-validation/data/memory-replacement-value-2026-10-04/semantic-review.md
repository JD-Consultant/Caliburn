# JD 內容、直接依據與閱讀路徑判讀

## 判讀範圍

本頁是工程代理離線逐項判讀，不是另一次模型打分請求，也尚未經真人複核。判準沿用前批外送前凍結的 `cases.json`；判讀完整的提案後相關欄位與結論，不只看關鍵詞或回應狀態。原話、當時 Memory 正文、初始錯誤 JD、提案與套用結果都在 `live-01` 可查。

八格中七格交付提案。近期＋Memory 的責任題第一次到六次模型回應上限，沒有提案，不以原本草稿的正確子項、工具返回或中間文字冒充交付。本頁將該格九項內容判準標為**未交付**，不計入已交付的品質分母。

## 三、額外發現：同一任務的欄位一致性

原底稿 `task_2.outcome_2` 一般化寫成「退貨狀態依倉庫同事確認結果登錄」。正式原話 96 已分清：常溫依倉庫、冷藏另交品質判定。原稿 `requirement_7` 已保留這個冷藏例外，問題是同任務的欄位沒有對齊，而非整份 JD 完全漏掉冷藏規則。

- 完整組兩次都修正描述，也額外對齊 `outcome_2`。這個額外修改有來源與理由，不視為無關改稿。
- 近期組第一次已讀 Memory 正文及原話 96，描述仍沒有冷藏例外；第二次描述有修正，但兩次都保留原 `outcome_2`，沒有對齊受影響的同任務欄位。

跨欄對齊未列入外送前凍結的 21 項判準，不事後追加扣分。原有責任題仍有「冷藏門檻未知、向品質確認」的判準，兩者不可混淆。這個反例顯示，指定錯誤被修正不等於整個任務已一致；後續可據此檢查核對指引，不必增加全稿審核 agent。

## 四、閱讀失敗不是資訊沒有保存

近期責任題第一次讀七項 Memory 資料（兩個已預載導覽、四個情境、一個理解），再查閱六次原話，仍未交付。後段讀了驗收比例 92、98–103 以及 80–90，未取到保存年限的原話 56。第二次從 36–58 區間取到 56，在第六次模型回應提交。

但資訊並未從 Memory 消失：

- 「收貨異常週報」正文與來源含 56，明記保存年限待財務確認。
- 工作理解正文也寫明保存規則及未知；四個近期分析都讀過該理解正文。
- 其情境導覽只說明週報、未結案、供應商回覆及時間戳記，沒有提示保存規則；理解的回查指引把該標題定位為週報。

因此本次支持的診斷是：**讀取路徑沒有充分利用已整理資訊及其來源導覽，並出現 Memory 與原話雙重閱讀。**不能說是原話太長、模型容量不足、OpenAI 壓縮失敗，或 Memory 已漏掉 56。導覽語意及顧問引用／停止閱讀策略是後續研究候選，尚未修改正式 prompt。

第一個近期責任題到 Step 上限不能證明「多一個 Step 必然成功」，第二次完成也不能撤回第一次結果。六次模型回應是本研究的有界設定，不是正式產品的執行上限；未測放寬該界線的行為。
