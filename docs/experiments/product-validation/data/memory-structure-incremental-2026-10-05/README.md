先看[結果](results.md)、[逐項語意核對](semantic-review.md)及[執行紀錄](execution-notes.md)。以下保留執行前協議，未完成部分不改寫成完成。

事後另有[局部選讀離線核對](reading-coverage-audit.md)，只分析保存位置與字元量，未新增模型結果、未修改原判準或補跑。

目的：比較「情境→理解」與「直接維護工作理解集合」，哪一種較能保留工作脈絡、接續更正並讓顧問按需使用。依據為[表示方案研究](../../../../research/agent-systems/2026-10-05-interview-memory-representation-alternatives.md)與[工作分析指南](../../../../guides/2026-09-09-complete-work-analysis-guide.md)；本次同意的是先比較，不是直接取消正式 B1／B2。

本批先做一組配對、每組三次整理，再各做三個獨立顧問選讀題。這是可行性先導，不能宣稱穩定優於另一種架構。先完成維護內容的核對，才判讀讀者效果及成本。

## 1. 兩組比較什麼

| 組別 | 持久分析內容 | 三批各自執行的工作 |
|---|---|---|
| `two_layer` | 工作情境及工作理解；情境引用原話，理解引用情境 | B1 先更新情境，再由 B2 根據情境差異與目前內容更新理解；不回交 |
| `one_collection` | 一套工作理解；直接引用原話 | 同一維護角色釐清指涉、整合既有理解及支持來源；不先取得另一模型整理的情境 |

兩組都從空白開始，原話、批次及事實權限相同。共同分析方法一致，角色差異只表達各組的職責與來源路徑；不給單層額外的正解、來源分類或手工理解。雙層以先前[候選 B1](../memory-organization-2026-10-05/b1-instructions.md)及[候選 B2](../memory-organization-2026-10-05/b2-source-navigation-instructions.md)作方法基礎，不混稱為現行正式 Prompt。

這是兩個方案整體的先導比較：分工、引用路徑與內容層數一起改變，**不是只改層數的純因果消融**。工具能力盡量等價，但不硬把單層理解塞進正式 B2 只能引用情境的契約。

## 2. 固定材料與更新順序

[materials.json](materials.json)只有合成訪談、批次及讀者問題；[grading.json](grading.json)另放預期事實、錯誤反例及最低來源支持。模型永遠不得讀取評分檔。

前兩批取自分析指南 §11 的虛構前端案例，改排為有顧問問題及員工回答的正式順序；第三批是本研究新增的合成延伸。不是實際員工個資，也不是獨立於教材的泛化測試。傳給模型的是指定訊息投影，不包含本協議、指南完整案例、教材來源說明或評分檔。

| 批次 | 可讀訪談上界 | 新增資料與目的 |
|---|---:|---|
| `initial` | 10 | 兩個專案的前端逾時、交付後修正、例行維護、分工及未知；包含跨案指涉與跳回早期專案 |
| `corrections` | 14 | 甲的誤述更正，乙自特定時期改變周期；其餘有效資訊須延續 |
| `extension` | 18 | 乙的核准人由未知變已知；新增低頻且尚無既有引用的甲案工作 |

序號是本資料包預先分配的訊息順序，不是 Agent turn，也不以奇偶數判定角色。員工發話才支持其工作事實；顧問問題只提供對話脈絡。每批依上界限制所有讀取入口，不能藉索引、來源關係或檔案讀到未來訊息。

## 3. Context 與工具的比較界線

### 整理角色

- B1 與單層維護者收到相同本批原話及相應工作稿導覽，原話按需可向前讀取。B1 不得讀理解。
- B2 收到情境及理解導覽、本批情境 diff；可讀本階段固定情境及合法原話，只能改理解。
- 單層維護者收到自己的最新理解導覽，不收到雙層組情境、產物或任何人工答案。
- 每批用新執行 Context，只接回該組已保存的資料；不保留前批模型推理、tool trace 或答案作額外記憶。這是刻意隔離持久 Memory 的研究條件，不宣稱等同正式跨批執行。
- 共同具備導覽、讀正文、讀指定訊息／區間與局部維護能力；名稱及參數沿既有風格。版本與可讀範圍由執行器處理。保留完整工具請求、回傳、拒絕及最終產物。
- 不新增 embedding、reranker、摘要樹或關聯生成 Agent；本批先看集合組織及來源維護，不同時比較檢索技術。

### 顧問讀者

每題從新 Context 開始，只收到同一讀者方法、題目與該組對應發布狀態的導覽；不帶原始訪談全文、生成 trace、另一題答案或評分。

雙層可讀理解→情境→原話；單層可讀理解→原話。不是強迫依序讀到底，已有足夠正文可直接使用。讀者可指出未知，不因少讀就猜答。三題均產出一項 JD 任務草稿及採用的來源定位，不操作正式 JD；來源定位以各組實際產物為準，由分析時回溯到原話核對。

兩個題目使用 `corrections` 快照，一題使用 `extension` 快照，見材料中的 `probes`。前者即使在第三批整理完成後執行，也不得看見第 15–18 則或其產物。

執行器只放此實驗資料包，使用隔離記憶體工作稿並輸出 JSON 快照，不修改正式 Schema、Prompt 或工具。`workspace.py` 重用正式工具 Schema；單集合以情境的「直接引用訪談」契約改名為理解，並重用正式 V4A 正文編輯器。`episode.py` 用正式 Responses request／序列化元件延續完整原生 items；`study.py` 共用前批費用及速率觀察機制。這是內容方案驗證，不是正式 runtime／PostgreSQL 整合驗證。

## 5. 判讀與量測

每項標記完整、部分、遺漏或錯誤，附產物摘錄與來源。不要求固定標題、物件數、字數或呼叫順序。評分檔的 `minimum_support` 表示須能由引用鏈回查的必要員工說法，不要求完全相同來源集合；單層可直接連原話，雙層可透過情境連到原話。

關鍵錯誤包括：把初判期限當修復承諾、把乙的周期套到甲、只留下「每季」而漏掉第一個工作日、在更正批次猜出未來才提供的核准人、把客戶的文案工作歸員工。不能用其他通過項目抵銷。

分開看三類問題：沒有存進理解；有存但顧問找不到；已讀到卻在寫 JD 時丟失或改錯。判準之外發現的問題另列，不事後修改分母或掩蓋。

用量分為建立、兩次更新及顧問閱讀，記錄 input、cached input、output／reasoning、外送次數、工具回傳、原話展開與等候時間。字元數只用於正文／導覽大小，不冒充 token。雙層兩個角色的成本都納入；API 成功、物件變多或總 token 變少都不獨自代表改善。
