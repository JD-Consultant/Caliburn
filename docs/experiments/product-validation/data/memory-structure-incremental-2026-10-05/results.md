# 雙層與單集合：三次增量整理先導結果

**單集合已展現接續維護工作理解的可行性，但還不能據此切換架構。**本例中，它保留了三批要求的事實與條件，維護輸入 token 比雙層少 35.92%；但顧問只讀一項理解後，漏掉存於另一理解的分工。雙層則在第三批出現「已確認核准人」與「核准人未知」並存。需要改善的是更新與選讀的正確性，不是單純增加或減少層數。

2026-10-05，Luna／high，一組配對。研究範圍、教材來源及凍結判準見 [協議](README.md)，逐項證據見 [語意核對](semantic-review.md)。這是隔離內容方案試驗，不是正式產品／PostgreSQL 整合驗收，也不是超容量長訪談實驗。

## 2. 能看見的效果與問題

### 不需要兩套永久正文，也能完成本例的增量維護

單集合沒有先讀雙層組的情境或產物，也沒有接回前批的模型執行歷史。它依本批原話及自己的既有理解，保留了訂單／查詢的不同逾時要求、24→48 小時更正、初判與修復期限的差別、維護周期的適用時期、核准權限，以及低頻素材工作。這支持單集合繼續作為候選，不支持跨職務或大規模穩定優勝。

### 多一層分析不自動保證更新後一致

雙層第三批 B1 已把核准人更新正確；B2 卻用追加 patch 把新版接在舊版後。問題在更新操作，而不是來源缺失。只檢查工具成功、引用可達或正文出現新資訊，都會漏掉這種矛盾。由一次操作不能推論「雙層必然比較差」，但它指出真正需要驗收的反例。

### 少讀必須以資料足夠為前提

交付後缺陷題中，兩組都只讀一項理解並以它為依據，未回查原話。雙層讀者得到完整分工；單集合將共同分工放在另一項理解，讀者未取用。**保存完整與局部選讀完整，是兩個分開的品質要求。**必要的責任界線要在相關工作內讀得到，或有明確且能實際被採用的關聯導覽；不是強迫把所有來源再讀一次。

## 3. 可公平比較的維護用量

以下只比兩組都完成的三批整理；雙層包含 B1 與 B2，單集合包含其維護角色。輸入含快取命中，輸出含推理；不是將字元數當 token。

| 指標 | 雙層 | 單集合 |

| 模型回應次數 | 17 | 12 |
| 累計 input tokens | 82,846 | 53,084 |
| 其中 cached input | 59,301 | 42,918 |
| 累計 output tokens | 7,672 | 4,271 |
| 其中 reasoning tokens | 3,827 | 1,933 |

單集合維護 input 少 35.92%、生成費用估值少 47.98%。這包含少一個持久層、少一個角色階段及不同生成／讀取路徑的整體效果，不能只歸因於層數。單集合第三批用了六次回應，包含修改後回讀；雙層兩角色合計也是六次，並非每一批單集合都少呼叫。

雙層最後有 2 項情境、3 項理解；單集合有 3 項理解。兩組沒有被要求固定數量。所有模型請求都遠低於 128K，本批沒有原生 compaction 或自訂摘要，不能由此推論超容量能力。

## 5. 格式失敗與實驗設計修正方向

`read-maintenance-one_collection` 的 Response 已完成，並非輸出上限或 provider 錯誤；但 task 物件未關閉，`json.loads` 拒絕。當時只在 Prompt 要求 JSON，沒有給最終文字輸出 `text.format` 的 JSON Schema。工具參數的 strict Schema **不等於**最終回覆也受相同格式約束。

這是本實驗完成契約的設計缺口，不能算成 Memory 無效。下一批應依 [OpenAI Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs) 以宣告式 schema 約束需解析的最終結果，並先核對 Luna、SDK 及容量計數入口的支援。保留本批為停止原件，不以人工修復 JSON 或新增重試來重寫成功率。此處只是下一批修正方向，尚未外送驗證。

## 6. 費用與可支持範圍

本批 523.28 秒，35 次模型回應及 35 次容量計數。模型生成費用估值 **US$0.012598195**，加容量計數每次 US$0.0001 保守預留，估算占用 **US$0.016098195**；累計 **US$1.270089235／US$2**。pending 只留下容量計數預留，不表示仍有模型請求在跑；數字不是帳單實付。

數值由 [analyze.py](analyze.py) 從未修改的 trace 投影，保存於 [analysis.json](live-01/analysis.json)；每次實際工具執行只計一次，不重複計算原生歷史重播。原始提示、工具、材料、判準與來源雜湊已在執行前固定，停止後 verify 通過。正式產品、DB 與服務未變，未 commit、push 或 merge。

目前可採取的下一步是：**保留單集合候選，先處理更新時撤換失效說法，以及局部工作理解的必要分工是否自足，再補足尚未完成的閱讀驗收。**不因單次小例直接移除正式 B1／B2，也不先造新的向量、圖或多代理系統。不同職務、重複配對及長訪談仍屬後續驗證。
