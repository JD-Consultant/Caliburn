# 三批工作理解的語意核對

依執行前凍結的 [grading.json](live-01/grading.json) 評分，不能把工具成功、關係存在或出現新數值當成語意正確。前兩批各 10 項、第三批 13 項，是同一批事實在不同更新階段的 33 次檢查，不是 33 個獨立樣本。

核對範圍為每批**完成後的工作理解正文**；情境及原話用來檢查支持鏈。相同事實可分布於多項理解，不要求物件數或標題一致。顧問選讀另評，不以整份 Memory 保存完整推定一項任務已完整。

### 雙層的矛盾如何產生

延伸批 B1 的乙情境已正確替換未知狀態。B2 也收到差異並寫出了新核准人，但提交的 diff 把舊兩行標成保留上下文（空白前綴），再用 `+` 新增同名小節，沒有 `-` 移除舊段。因此編輯器正確執行「追加」，正文同時出現：

- 「由客戶哪一位核准尚未確認。」
- 「超出約定範圍的需求須先經客戶產品負責人核准。」

這不是定位到錯誤物件、不是來源版本無法解析，也不是原話不在 Context；是模型的更新操作沒有撤換已失效的說法。**唯一定位與原子更新可以保證按提交內容修改，不能保證提交內容的語意正確。**原操作見 `trace.jsonl` 中 `cell=extension-two_layer-b2`、`event=tool`、`name=update_work_understanding`；結果保留在延伸快照，不人工修正。

## 3. 完成的顧問選讀配對

兩組讀者均使用 `corrections` 快照，該快照的核准人本來就尚未確認；不套用延伸批產物評分。

|---|---|---|
| 更正後的 48 小時初判 | 完整 | 完整 |
| 初判不是修復承諾 | 完整 | 完整 |
| 甲沒有固定月維護 | 完整 | 完整 |
| 客戶／本人／同事的工作界線 | 完整 | **部分**：有前端修復範圍，但未交代客戶確認需求、同事負責後端及服務端部署 |

兩組各讀一項理解、直接引用該理解，沒有讀情境或原話，沒有重讀 map。雙層 D4 本身含完整分工；單集合 S2 沒有，而分工存於 S1。單集合的導覽已把 S1 的「工作界線」列為選讀線索，但讀者未選讀 S1，也未把這些界線寫入任務。

因此單集合這格不是 Memory 沒保存、不是引用了沒讀的物件，也不是已寫內容捏造；是**相關資訊保存在另一理解，讀者過早判定已足夠**。目前引用支持它實際寫出的內容，但不足以涵蓋預定的完整責任範圍。不能把回傳較短或少讀當成較佳答案。

雙層 `maintenance`、兩組 `infrequent_work` 尚未執行。第三批低頻工作雖已在兩組 Memory 保存，**不能因此宣稱顧問已成功選讀這些工作**。
