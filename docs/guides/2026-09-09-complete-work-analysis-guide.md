# 完整工作分析與訪談指南

本指南是 JD-R001 的分析方法研究建議。它先回答「顧問需要理解什麼」，再說明如何轉為 [JD 成品](2026-09-09-jd-field-and-writing-guide.md)。**以下資訊面向不是必填 schema、固定問卷或新 Memory 資料層。** 決策狀態見 [入口](2026-09-09-job-analysis-and-jd-content-research.md)，原始依據見 [證據表](../research/work-analysis/2026-09-09-job-analysis-international-evidence.md)。

閱讀順序：§1–3 說明訪談要取得什麼；§4–9 說明內容取捨、JD 銜接及深度；[§10](#10-從碎片訪談到可延續的工作理解)定義 B1／B2 的整理方法，[§11](#11-整理與修訂的完整演進範例)示範同一批資料如何演進，[§12](#12-如何審查整理是否有效)提供可檢查的反例。後三節為 2026-10-05 確認的內容方向，尚不代表正式提示已調整或模型效果已驗收。

## 1. 分析的對象是完整工作，不是這一回合的答案

顧問需要累積對員工工作範圍的理解，分清楚實例、經常／有條件承擔的責任、他人角色及尚未確定的內容。員工可能先說工具、困難、成果或一段案例，不必先說出 Task 或 Duty。

職業標準與一般知識是追問及比較的參考，不是員工工作事實。OPM 將工作與所需能力及其關係作為分析核心；O*NET 將活動、情境、知識技能等分開描述。本指南把這些面向轉為訪談觀察方向，沒有把官方職業分類直接當成個人工作的答案。[OPM](https://www.opm.gov/policy-data-oversight/assessment-and-selection/job-analysis/)、[O*NET](https://www.onetcenter.org/content.html)

## 2. 要完整理解哪些資訊

下表是開放式分析清單。只問會改變工作理解、責任辨識、品質判斷或 JD 撰寫的資訊；不逐列拷問，也不要求每個案例都具備所有內容。

| 分析面向 | 應理解的內容 | 有用的追問示例 | 漏掉可能造成的錯誤 |
|---|---|---|---|
| **職務定位與目的** | 目前角色、服務對象、為何需要這份工作；實際而非想像的範圍 | 「別人通常為了什麼事找你？」 | 職稱相同就套同一 JD |
| **全工作範圍** | 日常、周期、專案、事件觸發、維護、收尾、正式低頻及支援性質 | 「除了最近這案，平常還有哪些事？月末或特殊情況呢？」 | 最近／常談工作蓋掉其他責任 |
| **觸發與輸入** | 什麼使工作開始，誰提供何種資料或需求；何時拒收或補件 | 「你收到什麼才開始？缺資料時怎麼辦？」 | 任務起點與對象不明 |
| **本人行動** | 真正做了哪些處理；哪些只是工具／步驟，哪些有獨立成果 | 「你親自做哪一段？可以說一個實際例子嗎？」 | 把團隊結果全歸本人；按動詞碎切 |
| **判斷與選擇** | 怎麼辨識問題、比較方案、決定下一步；需要什麼專業 | 「什麼情況要換處理方式？你看什麼判斷？」 | 只記錄機械流程，漏掉專業工作 |
| **成果與接收者** | 交付或維持什麼，誰使用，何時算交接完成 | 「做完後誰會用？什麼改變了？」 | 只知道忙什麼，不知道工作價值 |
| **合格完成要求** | 正確性、安全、合規、完整性、時效；實際檢查與返工原因 | 「哪些狀況會被退回？交付前一定確認什麼？」 | 用『做好』代替品質；自造 KPI |
| **責任與權限** | 主責、協作、建議、執行、核准；人員／資源管理及升級邊界 | 「你能自己決定到哪裡？最後誰確認？」 | 把協助升格全權負責 |
| **頻率與負荷** | 常態周期、事件條件、旺季、範圍、典型耗時；數值確定程度 | 「每月是指所有案件，還是只有維護合約？」 | 個案時間變成通則；聊天次數變頻率 |
| **情境、負荷、風險與例外** | 哪些環境／規範／限制會改變做法；相關的搬運、姿勢、感官辨識及持續注意要求；失敗後果及少見但必要責任 | 「最不一樣或最容易出問題的是什麼情況？實際操作或持續監看有什麼要求？」 | 只用辦公工作視角；抽象共同模式吞掉重要差異 |
| **知識、技能及必要工具** | 理解哪些原理、能運用哪些方法；工具是否可替換、資格是否真的必要 | 「新人最容易判斷錯哪裡？為什麼？」 | 列通用工具而不懂專業要求 |
| **協作與工作前後關係** | 與誰協調、輸入／輸出交接、他人依賴、外部限制 | 「你交出去之後，對方接著做什麼？」 | 丟掉交接、溝通與整合工作 |
| **時間及適用範圍** | 現在／以前／未來；全部案例／特定類型／一次性；例外條件 | 「這現在還由你負責嗎？只有那次，還是遇到都會做？」 | 早期責任或單案被當現在通則 |
| **未知、矛盾與更正** | 哪裡未說明、哪句只是印象、更正影響哪段、是否需要回查問答 | 「你是修正那個案例，還是所有這類工作的做法？」 | 模糊升成肯定，新一句覆寫全部舊資訊 |

觀察面向相似不代表底層都該有欄位。英國 NOS 強調會影響表現的條件與所需理解；澳洲現行框架也表達情境、自主性、責任及問責。它們支持不要只蒐集動作清單，並不替本產品規定上述十四列。[NOS §5](https://ukstandards.org.uk/media/kqppvuwl/sds-nos-quality-criteria-update-13-05-2024.pdf)、[TPOF §2.2](https://www.dewr.gov.au/download/16680/training-package-organising-framework-effective-1-july-2025/39042/training-package-organising-framework/pdf)

也不能漏掉非辦公情境。例如設備檢查可能涉及移動部件、辨識細小刻度或持續留意異常訊號；只有確實相關時，才追問頻率、持續時間、實際負荷及可用輔具。O*NET 分別描述注意力、體力、操作與感官能力；這支持分析不能只看知識與軟體操作。**本指南的映射是描述實際工作要求，不是替員工作健康／能力診斷，也不憑職稱推定資格門檻；不因此新增 A 欄或能力量表。** [O*NET：Abilities](https://www.onetonline.org/find/descriptor/browse/1.A)

## 3. 如何訪談，不變成冗長表單

建議循環：**先看全貌 → 選有價值的工作情境 → 深入一個案例 → 比較其他情境 → 確認目前理解 → 回查全範圍。** 這是訪談策略，不是單向 wizard，更不是固定六次模型呼叫。

1. **先建立範圍而不急著定欄位。** 用職務目的、工作來源、平常／周期／特殊事件取得粗略全貌；不知道還有什麼本身就是需要繼續探索的訊號。
2. **選一項值得深問的事情。** 優先處理會影響責任或結論的模糊處；也可先談員工容易具體描述的案例建立脈絡。沒有必要每回合編輯 JD。
3. **問實際行動與判斷，不只問感受。** 「很複雜」後面要能說明何處複雜、哪些選擇與限制；不是要求員工背專業術語。
4. **用對照找到通則與例外。** 「另一個案也一樣嗎？哪裡不同？」比直接宣布兩案是同一任務更安全。相似不代表所有條件都相同。
5. **確認重要理解，不朗讀全部記憶。** 短句確認範圍、責任或更正即可；已說清楚的不反覆追問。未回答的有影響問題仍須保留。
6. **新線索不必搶走當下焦點。** 先辨識並保留；除非會導致當前分析錯誤，否則可在當前問題告一段落後再談。

Anthropic Interviewer 公開採訪談目標／rubric、可適應追問及後續分析；支持「固定研究目的，問題路徑可變」。其跨受訪者研究和約 10–15 分鐘測試，不是本產品的模型分工、時間上限或完成保證。[Anthropic Interviewer：How it works](https://www.anthropic.com/research/anthropic-interviewer)

**客製化補查：**具體缺口→中立追問→問後能區分什麼，以及答不出來時怎麼處理，見[校準文§3](2026-09-09-customized-jd-depth-and-interview-calibration.md#3-顧問怎麼取得資料而不是靠公版補齊)。實際雇主的取證方法支持例子反查與補漏，但不因此加入主管簽核／文件上傳。現況、已確認要求與單次表現的衝突另看該文§4，不能把公版視為員工工作的答案。

## 4. 案例、工作理解與 JD：如何取捨而不丟失

| 內容位置 | 要保留的重點 | 不是什麼 |
|---|---|---|
| 原始訪談 | 員工與顧問實際問答，可回查當時語境 | 不能直接把每句當正式工作結論 |
| 工作情境（B1） | 按工作脈絡整合及拆合情境，保留各輪的本人處理、判斷、成果、限制、重要差異與不確定性 | 不是閒聊逐字重抄；不是一批訪談一物件，也不必一個專案永遠只放一物件 |
| 工作理解（B2） | 依工作意義重組相關情境，寫出目前能成立的工作範圍、模式、責任、條件、例外及有影響未知 | 不是每案永久新增一個 Task；不是整份工作持續膨脹的一篇摘要 |
| JD | 某項工作已有足夠理解即可逐步寫成清楚、適當粒度的職務內容，之後再做全份核對 | 不必等整場訪談結束，也不是所有案例和分析過程的合集 |

這裡沿用已討論分工說明內容用途，**不新增物理儲存層或規定每層各呼叫一次模型**。目前 Memory 流程不因本指南改動。[既有資訊取捨研究](../research/work-analysis/2026-09-07-work-case-and-understanding-information-selection.md)

### 具體取捨

- **相關細節不可因少見就丟。** 有責任意義的年度／危機工作應能回查；不是只保留高頻內容。
- **新批次未提不代表撤銷。** 補 A 的資料不能順便刪 B 的有效責任；可以去重、改寫，不能縮窄工作範圍而沒有依據。
- **通則不能偷吃案例差異。** 共用「處理逾時」可以，但兩案不同的行為、核准方式或維護承諾仍要保留在適當位置。
- **案例實例不等於執行次數。** 說過五個案例不代表固定每週五件；做過一次也不代表永遠不再負責。
- **更正看語意範圍，不只看時間新舊。** 「剛才說錯了」依問答理解；新舊不一致但未明確更正時，先釐清，不能自動認定最後一句必真。
- **確定性不能變強。** 「印象中每月」不能整理成「每月」；「還沒確定」不是「不需要」。
- **保留可辨識及回查線索。** 人名、日期、產品名稱、數值只要會影響工作判斷或區分案例就有價值；不是全部刪，也不是全部升入正文。
- **分清長期工作對象與單次案例。** 固定負責的平台／產品可能要出現在 JD；「案例不等於任務」不是禁止具體名稱。是否保留與如何表達沿[欄位指南§3](2026-09-09-jd-field-and-writing-guide.md#3-職務目的職責任務同一份工作的不同縮放程度)，不在分析端先一律抽掉。
- **無關瑣事不強留。** 寒暄、重複修辭、與工作判斷無關的偏好不必膨脹語意記憶。這不改原始訪談保存政策。

以上是本產品的內容取捨，不冒稱 OpenAI／Anthropic 逐條採同一職務分析規則。Anthropic 官方支持用提示指定記憶的主題相關性及維持一致組織；哪些工作資訊重要，仍由職務分析方法決定。[Memory tool：Prompting guidance](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool#prompting-guidance)

## 5. 完整示例：接案前端工程師

以下是**虛構、已補齊範圍的教材**，不是實際員工資料，也不是完整測試驗收。

### 已取得的訪談資訊

員工說明目前接前端委託：先釐清需求、估算本人工作與變更影響；依客戶提供的視覺設計開發頁面、串接後端介面；檢查主要操作和錯誤情境、協調交付。後端工程師負責業務規則與服務端部署；客戶決定需求及驗收。本人另處理合約明訂的前端維護與交付說明，不帶人、不制定客戶的商業策略。

A 電商案送出訂單逾時，前端需避免重複送出；B 預約案查詢逾時需保留已選日期，且只有 B 已約定每月前端維護。員工說 A 的客服是客戶自己的工作。後來補充 A 也有交付後缺陷修正，但沒有固定每月維護。

### 案例詳記與共同理解

詳記保留 A／B 各自的需求、逾時處理、責任及維護差異。共同理解不是「A 開發、B 開發」兩條，而是需求釐清與估算、前端實作與整合、交付檢查、約定維護等工作；另保留適用條件及詳記引用。新增 A 的缺陷修正，不讓 B 的每月維護消失；也不能把每月維護套到 A。

### JD 可整理的工作範圍

| 職責分組示例 | 任務敘述示例 | 沒有因此被升格的資訊 |
|---|---|---|
| 需求與交付規劃 | 釐清前端需求及驗收範圍，估算工作與需求變更對交付的影響 | 不代表決定客戶商業策略或全部專案預算 |
| 前端開發與整合 | 依確認的需求與設計實作頁面、互動及資料介面串接 | 不代表本人設計後端業務規則 |
| 品質確認與交付 | 檢查主要操作及錯誤情境，修正前端缺陷並完成交付說明 | 不必把每個測試按鍵列一個任務 |
| 維護與問題處理 | 依約定維護範圍處理前端問題及變更 | B 每月維護不是所有案的固定周期 |

是否將第二項再拆成頁面實作與介面整合，取決於實際責任與閱讀粒度；兩種都可能合理，不是由教材替所有職位定死。正式 JD 還要補實際目的、必要完成要求及 K／S；不是此表一出就宣稱完整。

完整成品另見 [前端工程師 JD 樣稿](2026-09-09-frontend-engineer-jd-sample.md) 與 [情境依據及雙向核對](2026-09-09-jd-sample-basis-and-review.md)。成品示例另明示受雇情境與完整工作資料；上面短例只是分析示範，不應把尚未提供的組織關係當成從短例推論出的事實。

### 下游文件還需要新增什麼判斷

- 招募：可由前端工作與專業需求設計甄選情境，但年資、薪資與聘用門檻另定。
- KPI：可從交付與維護責任辨識衡量方向；目標值、周期、權重、控制範圍須另行確認。
- 訓練：可用 A／B 差異設計錯誤情境練習，但課程、評量方法與個人缺口不是由 JD 自動確定。

## 6. 如何檢查整份工作已被適當涵蓋

**日常續談不必每回合讀完全部資料；全面製作／收尾檢查才需要回顧全範圍。** 目的是核對每項有效工作資訊有適當去處，不是每筆 Memory 都變成一條 JD，也不是必須一次塞完 prompt。

建議做兩個方向的語意檢查：

1. **工作 → JD**：每個有效工作領域，是否被某段 JD 適當涵蓋？如果只是案例佐證、方法細節或不屬此職位，是否有合理原因不單列？重要例外有沒有被過度抽象吞掉？
2. **JD → 工作**：每項聲稱的責任、標準或專業，有沒有實際根據？是不是混入他人工作、未確認推論、過去責任或新編目標？

再檢查重複與粒度：同一工作是不是在兩個職責重抄？不同案例被合併後是否失去邊界？有沒有同樣工具但完全不同目的的工作被錯合？

這是品質檢查方法，不是要求新增 exact manifest、coverage ID、分數或第二個 verifier。O*NET 的人工比對與修訂提供參考，但其「職業級」收錄過濾不能用來刪除這名員工真實且較特殊的工作。[2025 更新方法 pp.7–10](https://www.onetcenter.org/dl_files/EmergingTasks_RevisedApproach.pdf)

### 什麼情況值得說「可以收尾」

建議的可觀察條件：主要工作領域及重要低頻工作已檢視；責任／完成要求已足以寫清；影響結論的矛盾已釐清；跨工作重複與遺漏已核對；員工看過目前範圍並有機會補充。這是本產品候選收尾標準，不是 OPM 或任何模型供應商核發的滿分證明。

不能用輪數、字數、欄位填滿、讀過所有 Memory 或 AI 自稱完成作唯一依據。員工可隨時停止聊天，與分析是否完成是兩件事；本輪不新增暫停操作。

補充的廣度、深度、一致性及員工核對機會見[客製化校準§6](2026-09-09-customized-jd-depth-and-interview-calibration.md#6-怎樣才是整份工作被理解而非只問透一案)。只問透一案、或確認樣稿涵蓋作者給定情境，都不能當成真實員工整份工作已完整理解的證明。仍有會改變結論的未知時明說，不用漂亮措辭掩蓋。

## 7. 後續怎麼用於提示與 Skill

## 9. 工作理解正文要寫到多清楚（2026-09-25 研究補核對）

本節說明工作理解正文的資訊取捨，供[產品概念](../product-concept.md#核心概念與資訊關係)引用。B2 的資料結構、提示、角色權限與發布流程依[現行規格](../specs/README.md)；模型是否達到這些內容目標，另以實測判定。

### 來源能支持什麼，不能支持什麼

2026-09-25 核對的第一手來源：[OPM Job Analysis](https://www.opm.gov/policy-data-oversight/assessment-and-selection/job-analysis/)把工作分析建立在實際任務、所需能力及兩者關係；[O*NET Content Model](https://www.onetcenter.org/content.html)區分一般、較詳細的工作活動及工作情境；[英國 HSE 的 Understanding the Task](https://www.hse.gov.uk/humanfactors/assets/docs/understanding-the-task.pdf)以工作目的組織步驟與決策，特別提醒低頻但重要的工作不應只因不常發生就忽略；[UCSB Job Description Basics](https://www.hr.ucsb.edu/hr-units/compensation/job-description-basics)要求職務內容能辨識實際工作、責任及結果，而非只剩籠統動詞。這些共同支持**描述不能空泛、抽象層與具體層應互相連得上、條件與責任不能被無據泛化**；但各來源服務的是職業資料、任務分析或 JD 撰寫，**沒有任何一份規定本產品 B2 的 Memory 正文長度、欄位或三層架構**。本節以下是 Caliburn 對個別員工長訪談需求的映射，不冒稱外部標準。

[OpenAI Codex 公開的 consolidation 提示](https://raw.githubusercontent.com/openai/codex/main/codex-rs/memories/write/templates/memories/consolidation.md)將簡短導覽與較具體、可用於後續工作的記憶內容分開，且不主張固定項目數；可借鑑「導覽不是正文、正文不必複製全部原始材料」的資訊分層。該 `main` 文件會變動、服務的是程式開發而非職務分析，不能用它決定哪些員工工作可以刪除。本節沿用已有的[資訊取捨研究 §3–4](../research/work-analysis/2026-09-07-work-case-and-understanding-information-selection.md)，不重建另一份 Memory 原則。

### 三種深度比較與結論

| 做法 | 會發生什麼 | 判斷 |
|---|---|---|
| 只留標題或職業級通用句，例如「負責前端」 | 不知道本人實際做哪段、哪些條件才適用，顧問每次都得盲找情境，也容易把某案推成全部工作。 | **過淺**；只能作導覽線索，不足以作理解正文。 |
| 把每個情境的過程、對話及結果再抄成理解全文 | 表面完整，卻出現兩份可修訂的具體敘述；個案更正後易不一致，且共同工作與重要差異被大量經過淹沒。 | **過深／重複**；詳情留在工作情境，原話沿引用回查。 |
| 寫出有據的工作認識與不可省略的邊界，附可回查的情境依據 | 不讀全部情境也知道本人做什麼、做到哪裡、哪些條件或未知會改變判斷；需要過程時再下查。 | **建議**；不是固定長度，也不預填 JD。 |

實際取捨用**反事實省略檢查**：若刪去某資訊，後續顧問是否更可能誤判「做什麼、誰負責、何時適用、是否已確認」？若會，正文保留**足以避免該誤判**的有據內容，包括會改變工作判斷的精確數值與期限。與本項判斷無關的個案經過及完整問答留在下層，透過分開的來源資料回查；來源列是可用入口，不是正文要求顧問逐項閱讀的清單。工作理解可依**一項或多項**情境形成；只有一項情境時可寫清其限定範圍，不因尚未觀察第二例就刪除，也不能據此宣稱通則。工作理解反映這名員工目前的工作，不等同 O*NET 的職業平均或 JD 的職責分組。

以下都是**虛構的內容審核反例，不是員工事實或已通過的模型測試**：

- **相似工作但條件不同：**A、B 網站都涉及本人處理前端逾時互動；理解正文可指出 A 要避免重複送單、B 要保留已選日期，且僅 B 已確認每月維護。每案觸發、實作與更正經過回查各自情境；不能把 B 的月維護寫成所有網站都要做，也不能因 A 有補充而刪掉 B 的責任。
- **例行工作與少見例外：**假設員工說明日常教室收尾及一次特殊活動後的窗戶清理。理解應使顧問知道兩者是否屬本人、是否同一適用範圍；若只知道一次，不能寫成每日清窗，也不能因低頻而讓有責任意義的工作消失。清理順序與現場細節仍在情境。是否構成持續職責要以後續訪談核對。
- **僅有部分資訊：**假設只知道員工「使用 Excel」，尚不知用來處理什麼工作。下層可保留已知原話及缺口；理解不能造出「負責報表分析」或填滿一套知識技能。若線索影響工作範圍，應標明目前只知道什麼、還缺什麼並保留回查入口，供顧問追問。

**驗收方法不是字數或欄位數。**用不同職位、舊情境後來被更正、低頻高影響工作、本人與團隊責任不清，以及只掌握部分事實的對照，檢查正文能否支持正確的初步理解與向下回查；再看情境與原話是否保留了更細的證據。這些判準檢查已取得資訊的整理品質，不能單獨證明完整訪談範圍，也不增加驗證器、資料層或 B2 審核 B1 的職責。

## 10. 從碎片訪談到可延續的工作理解

**B1 按具體工作脈絡整合碎片、拆分或合併情境；B2 按工作意義拆分或合併理解。**兩者都能新增、修訂、拆分及合併自己負責的物件，差別在組織依據，不是「B1 只合、B2 才拆」，也不是「先寫長摘要，再縮成短摘要」。原話保留事實與脈絡，情境保留具體工作的來龍去脈，理解減少後續顧問反覆重做相同分析。

整理方法借鑑任務分析的活動／目的辨識、質性研究的情境內與跨情境比較，以及按需 Context 的組織方式；來源、比較及適用限制見[本輪研究](../research/work-analysis/2026-10-05-memory-organization-and-incremental-analysis.md)。2026-10-05 的後續討論確定以既有分層收斂優化：保留原話、情境與理解，改善每層的內容組織、局部修訂及選讀方法；資料系統的借鑑見[研究收斂 §9](../research/agent-systems/2026-10-05-demand-loaded-memory-and-incremental-updates.md#9-收斂採用既有分層改善內容組織與選讀)。以下是內容方法，不新增工具或流程；正式提示的套用及效果另行驗證。B1／B2 權限及單向發布仍依[背景生命週期](../specs/2026-09-25-b1-b2-information-gap-lifecycle.md)。

### 10.1 先分清組織單位

整理判斷收斂到既有研究指南，不另立一套工作分類標準：

- **哪些資訊值得保留：**依本指南 §2、§9 與[客製化深度 §2](2026-09-09-customized-jd-depth-and-interview-calibration.md#2-什麼細節不能被抽掉)，看資訊是否影響本人工作、判斷、責任、成果或適用條件，而非只看出現次數或文字長短。
- **哪些工作宜分開或合併：**用[欄位指南 §3](2026-09-09-jd-field-and-writing-guide.md#3-職務目的職責任務同一份工作的不同縮放程度)的工作目的、對象、成果、責任與變動範圍校準。共同的最終目的不代表同一工作，使用同一工具也不代表應合併；這是語意判斷依據，不是把 Memory 預先做成 JD 欄位。
- **結論能說到哪裡：**依[客製化校準 §4](2026-09-09-customized-jd-depth-and-interview-calibration.md#4-實際工作完成要求與個人表現不混用)，分清實際承擔、已確認要求與單次表現。不能將一次成功、失誤或暫代直接寫成永久責任或標準。

通過上述校準後，再依各層用途決定內容的承接位置；不以增加物件數作優化目標。

| 層次 | 組織依據 | 一項內容應能回答 |
|---|---|---|
| 工作情境 | 同一具體案例、反覆發生的工作流程或問題處理脈絡 | 在什麼情況下，這名員工怎麼處理、根據什麼判斷、結果與界線是什麼？ |
| 工作理解 | 有內在關聯的工作目的、責任及適用條件 | 這名員工實際承擔哪一類工作，做到哪裡，哪些差異與未知會影響判斷？ |
| JD | 供人閱讀及管理的職責、任務與相關要求 | 這份職位主要負責什麼，需達成什麼，以及需要哪些已確認的專業與條件？ |

工作情境不必是一件偶發事件；例行盤點也能有持續維護的情境。工作理解接近撰寫 JD 所需的工作認識，但比成品保留更多條件與不確定性，不照 JD 欄位預切。最後如何形成職責與任務，由 A 依[欄位指南](2026-09-09-jd-field-and-writing-guide.md)處理。

一項情境可能同時支持逾時處理、缺陷修正等不同理解；數項情境也可能共同支持同一理解。物件數不由訪談輪數、案例數或 JD 任務數決定。

### 10.2 B1：以工作脈絡整合，不以訊息順序分袋

1. **辨認這段話在說哪件工作。**結合說話者、前問、指涉、時期及對象，區分員工事實與顧問的提問／假設。必要時回查合法歷史；不能因相鄰發話就假定屬同一案。
2. **先找既有情境的承接位置。**同一流程的後補、例外或明確更正通常修訂原情境；不同工作脈絡即使同用 Excel、ERP 或「核對」一詞，也不因此合併。資訊不足以定位時，保留不確定，不任意歸案。
3. **整合有用事實，不累積問答殘片。**重述已知事實可合併表達；新增判斷、期限、角色或例外則補進相關位置。保留問題如何發生、本人如何處理及重要結果，使正文離開訪談順序仍可理解。
4. **維護而非覆蓋。**只修正被明確更正的範圍，保留其他有效內容；拆合情境時也要保住仍有效的事實及其原話依據。標題與描述隨內容調整，不把每次補充另立一項。

一個專案可以包含多個相對獨立的工作脈絡；若正文已混入不同對象、目的及流程，讀者需要整篇才能找到其中一件事，就應考慮拆開。反之，同一流程中的收件、判斷、追蹤與結案，不能只因是不同動詞就機械切成四項。

B1 拆分時，把各段有效事實及相應原話依據放到正確情境；共同且必要的背景可在各項簡要保留。發現既有兩項其實是同一工作脈絡的重述時，也可以合併。這些判斷不需要讀取理解層；B1 維護自己的情境，拆合造成的下游影響由 App 交付變更，再由 B2 接續分析。詳細例子見 §11.5。

去重以「同一對象、適用範圍、時期與事實含義」為準。例如兩次說「月底盤點」可以整合；後來補「月底最後一個工作日，由主管核准調整」則補進周期與權限，不視為重複刪除。這是閱讀時的比對方法，不新增四個必填欄位。

### 10.3 B2：按工作意義重組，不逐篇縮寫

B2 從本批情境變更與目前導覽辨認應處理的工作，包括尚未被理解引用的新情境。它比較相關情境及既有理解，判斷共同工作、補充與差異；不預設每次全讀全改，也不只檢查原有引用清單。

拆合時先問三件事：這些內容是否服務同一工作目的？責任與適用條件能否清楚放在一起？顧問需要其中一部分時，是否經常得一併讀入無關工作？這是語意判斷，不是三個必填欄位。

| 情況 | 處理方式 | 應避免 |
|---|---|---|
| 相同工作、相同範圍，只是另一種說法 | 合併重複敘述；按實際支持關係維護來源 | 因多一個案例就多造一項理解 |
| 同一工作增加條件、判斷或細節 | 補進既有理解，必要時調整標題與描述 | 把有新訊息的重疊當成完全重複而刪掉 |
| 共同工作但存在局部差異 | 在同項內標明各自範圍；若差異已形成獨立工作，再拆開 | 把其中一案的周期、權限或承諾套到全部情境 |
| 一項情境包含不同目的與成果的工作 | 將相關內容分別整理進適合的理解；同一情境可被多項引用 | 一情境一理解，或讓一篇理解包住整份職位 |
| 同一工具／動詞，卻是不同工作 | 按實際目的分開，例如 ERP 收貨核對與出貨缺貨追蹤 | 因關鍵詞相同就合併 |
| 新舊說法不同 | 區分明確更正、不同時期、不同條件或未解矛盾 | 無條件採用最後一句，或同時寫成兩條現行通則 |

工作理解宜有清楚、可按需選取的主題，但不是越碎越好。期限、比率、核准者通常是某項工作的條件，不各自變成一個理解；否則每次分析仍須讀一串碎片。來源也不是只追求最少：選擇真正支撐這項理解的情境，不把整份職位的所有情境都掛上去。正文若另用其他案的事實作比較，來源也要涵蓋該案，不能讓文字有依賴、來源關係卻缺漏。

### 10.4 小範圍、足夠深：理解應能直接使用

每項理解在自己的適用範圍內，應足以辨認工作、本人責任、重要處理原則及仍未知之處。涉及工作判斷的期限、時間、比率、單位、例外及結案條件，不因上層稱為「理解」就只能留在原話。

例如「每日 09:30 前匯出前一工作日差異報表；本人只記錄與回報，不核准庫存調整」若有依據，就不能縮成「定期處理報表」。保留這些規則不等於複製每次匯出經過。兩項理解若都須短句提醒同一權限邊界，可以必要重述；不要為了零重複而造第四層，或迫使讀者跳轉才能正確理解其中一項。

`title` 命名工作主題，`description` 區分適用範圍並提供選讀線索，`body` 承載可用的工作認識，來源關係另列。不只寫「詳見情境」，也不在正文列一串「必須回查」命令。

閱讀停止點沿[Memory 讀取契約](../specs/2026-09-27-memory-read-and-source-navigation-contract.md#a-顧問的閱讀與停止條件)：理解足夠就用理解；需要具體工作脈絡才讀情境；情境足夠就用情境。來源關係保留查證入口，不是一份必讀清單。

**已完成整理的工作，其現行事實應能由理解或情境支持一般分析。**B1 須把分散的有效事實接回正確工作，B2 須保留理解所涵蓋工作必要的精確值、責任與條件，不能要求 A 每次再從原話重做分析。若一般問題仍須靠原話補回已提供的重要事實，應追查整理缺漏或導覽問題；A 當次答對，不等於整理品質已通過。

這不要求上層重抄所有原文或已被取代的舊說法。查原句、追溯更正前的歷史、核對原始指涉或具體矛盾，仍可按需回查原話。尚未整理的新訪談也不受此充分性要求限制。原話入口不移除，不以禁止下查或一律引用理解來取得好看的成績。

### 10.5 未寫進理解與尚未取得，是兩種不同缺口

- **整理時未收進上層：**理解未交代某項有關期限，相關情境可能有，按來源線索讀取有意義。B2 若發現它影響此項工作判斷，應補足自己的理解；情境也漏掉已確認的必要事實，則須追查 B1 的整理。當次可查原話確認缺漏，但不能把這種補救當作一般閱讀方式。
- **已有分析明確指出尚未確認：**在來源未增加、未出現矛盾或指涉疑義時，重讀同一批下層不會憑空取得答案。保留未知；若影響當前 JD，由 A 中立追問，不讓 B2 替員工回答。
- **有新資料或具體疑點：**可能使原先未知變成已知，也可能需要回查確認。不能把「已寫未知」當成永遠禁止下查；根據實際線索處理。

B2 已能依情境完成判斷時，不重做 B1 的全量原話分析；需要查原話時仍在原權限與批次上界內。查出不足或矛盾可如實保留於理解，不修改情境、不回交 B1。這不是要求新增未知狀態欄位或讀取證明。

### 10.6 增量修訂保留已完成的分析

新批次不是重寫整份工作：B1 更新相關情境，B2 依實際變更與工作關聯修訂相關理解。對未受影響部分沿用既有分析；對有影響部分，不只貼上新句，還要檢查原結論是否仍成立。

- 補充不撤銷其他工作；新的適用條件不能默默擴大到其他案。
- 明確誤述更正，修正對應內容；從某時起改變的工作，則保留新舊適用時期，不混為同時有效。
- 分拆或合併理解時，逐一安置原有有效責任、細節、例外與來源，再移除冗餘表達。不能以重組為由只留下新資訊。
- 情境被移除或改動後，依現存依據重新判斷理解；引用關係變動不自動代表正文仍正確。
- 有意義的新情境須分析，但不必強迫每項情境產生一項理解。暫不足以形成工作認識時，仍可留在情境供後續讀取。

這些是內容責任，不要求 B1／B2 逐條確認引用換版；候選綁定與正式快照沿既有契約。若判斷無須變動，也不為了展示處理過而重寫正文。

### 10.7 收斂後的整理與選讀準則

**以「可定位、可直接使用、可局部修訂」決定理解的粒度。**這裡的「單元」就是既有工作理解物件，不另建資料類型。單項理解承載一項有意義的工作認識；若判斷本來就跨數項工作，可按需讀多項。

| 檢查方式 | 整理時的做法 | 預期使用效果 |
|---|---|---|
| 看導覽能否選對工作 | `title` 明說工作；`description` 指出對象、適用範圍及足以區分鄰近工作的重點 | A 可由導覽選正文，不必先逐篇試讀 |
| 單讀正文能否正確使用 | 本人行動與成果連同必要責任、條件、精確值及未知放在一起 | 讀理解即可處理其涵蓋的問題，來源保留為深入入口 |
| 某部分改變時能否局部更新 | 可獨立辨認的工作目的與成果分開；同一工作的期限、權限與例外就近保留 | 修訂能定位，也不把必要條件拆成一串必讀碎片 |

B1 的工作順序是「定位脈絡 → 區分重述、補充、更正或新工作 → 整合／拆合情境 → 同步導覽與原話依據」。B2 則是「由變更及導覽定位相關工作 → 比較情境與既有理解 → 維護共同工作與範圍差異 → 同步導覽、正文及情境依據」。這是每批分析的思路，不規定工具呼叫順序或次數。

**必要的短脈絡可以就近重述。**例如客戶確認需求、同事負責後端，若都適用於缺陷修正與合約維護，兩項理解各保留這個短限定；只讀其中一項也能辨認本人的權限。不重複整段案例經過，也不把僅適用甲案的條件帶到乙案。共同限定更新時，B2 由情境 diff、既有引用及導覽找出相關理解，一起修訂受影響表述；不另增全域規則層或依賴索引。

**不必要的跨案比較不另存一份數值。**例如乙的期限未提供，寫清乙的未知即可，不必再加「甲的 24 小時不適用乙」；這會把不屬於乙的期限複製成另一份待維護資料。正文、title 及 description 都適用此原則。若比較確實影響本項判斷，須保留適用對象並引用支持兩側敘述的來源，讓來源變更能找到受影響內容，不能借另一物件的引用替本物件補依據。這項校準來自[三批分層比較](../experiments/product-validation/data/memory-layered-value-2026-10-05/results.md)的跨案舊期限殘留；不修改既有實驗產物。

A 使用時先辨認本次範圍：

- **回答一個細節：**取所問事實及解讀它必要的限定。例如問回覆期限，保留「48 小時內初判，不是修復期限」，不必帶入整份維護工作。
- **整理一項完整工作：**從已讀理解取出這項工作的本人責任、行動、成果與必要條件，依 JD 欄位安排；不能只取最近更正的那一句。必要分工不只寫本人不做什麼，也保留已知的決定者或接手者；例如「不負責後端」不等同於完整保留「後端由同事負責」。只補正文未涵蓋、且影響本次整理的資訊。
- **處理跨工作問題：**再選其他相關理解；要具體經過或原始指涉才沿來源深入。這是橫向補齊相關工作與縱向查細節的區別，並非每次都要走兩條路。

讀到足以支持本次判斷就停。已明確記錄「尚未確認」且沒有新線索時，A 保留待問，不把相同來源反覆讀取當成取得新資訊。停止條件、可讀範圍及引用操作以[讀取契約](../specs/2026-09-27-memory-read-and-source-navigation-contract.md#a-顧問的閱讀與停止條件)為準。

## 11. 整理與修訂的完整演進範例

以下是虛構教材，延續 §5 的前端工作，但只分析此處列出的片段，不借用樣稿其他事實。甲、乙是兩個網站專案；「片段」是教材索引，不是正式訪談序號或工具參數。正文與來源分開列示，並非一份新 schema。

### 11.1 原始資訊分散在不同發話

| 片段 | 已取得的員工說法 |
|---|---|
| 一 | 「甲是電商。送出訂單逾時，我要處理前端，避免使用者一直重按造成重複送單。」 |
| 二 | 「乙是預約網站。查詢逾時要保留已選的日期，這個也是我處理。」 |
| 三 | 「剛才兩個案都一樣：後端業務規則和服務端部署由同事負責；客戶確認需求，我負責約定的前端範圍。」 |
| 四 | 「回到甲，交付後的前端缺陷也是我修，接到回報後 24 小時內回覆初步判斷，不是 24 小時內一定修好。甲沒有固定月維護。」 |
| 五 | 「乙合約有每月一次前端維護，檢查頁面操作並修正前端問題。超出約定範圍的變更要先核准，但最後由客戶哪一位核准，我還沒確認。」 |

### 11.2 B1 整合為有脈絡的情境

本片段群可先形成以下兩項；這不是規定每個專案永遠只能有一項情境。

**情境：電商甲的前端逾時處理與交付後修正**

- `description`：本人處理訂單逾時的重複送單風險與交付後前端缺陷；無固定月維護。
- `body`：甲案送出訂單逾時時，本人負責約定前端範圍內的處理，避免使用者反覆操作造成重複送單。需求由客戶確認；後端業務規則及服務端部署由同事負責。交付後前端缺陷由本人修正；收到回報後 24 小時內回覆初步判斷，此期限不是保證完成修復。甲案未約定固定月維護。
- 原話依據：片段一、三、四。

**情境：預約乙的前端逾時處理與合約維護**

- `description`：查詢逾時保留已選日期；每月前端維護；超範圍變更的核准人尚未確認。
- `body`：乙案查詢逾時時，本人處理約定前端範圍，保留使用者已選日期。需求由客戶確認；後端業務規則及服務端部署由同事負責。乙案另有每月一次的前端維護，內容為檢查頁面操作並修正前端問題。超出約定範圍的變更須先取得核准；目前尚未確認客戶端的最終核准人。
- 原話依據：片段二、三、五。

B1 將「剛才兩個案」的角色界線接回兩案，將跳回甲的補充更新在甲，沒有讓乙的月維護覆蓋甲，也沒有猜出乙的核准人。

### 11.3 B2 重組為可按需使用的理解

這裡示範三項合理分組。等價分組也可接受，重點是工作意義、邊界與細節，不是產出恰好三項。

**理解：網站前端逾時互動處理**

- `description`：約定前端範圍的逾時互動；區分電商重複送單與預約日期保留，後端由同事負責。
- `body`：本人依客戶確認的需求，處理約定前端範圍的逾時互動。電商甲須避免反覆操作造成重複送單；預約乙須在查詢逾時時保留已選日期。兩案的後端業務規則及服務端部署均由同事負責，不能將它們納入本人的前端責任。
- 情境依據：電商甲、預約乙。

**理解：電商甲交付後的前端缺陷修正**

- `description`：處理甲案交付後前端缺陷；24 小時內回覆初判，並非修復期限；不含固定月維護。
- `body`：本人依客戶確認的需求，負責甲案約定前端範圍內的交付後缺陷修正。收到回報後 24 小時內回覆初步判斷；不能據此承諾同期限完成修復。此工作不表示甲案有固定月維護，也不擴大到同事負責的後端業務規則或部署。
- 情境依據：電商甲。

**理解：預約乙的合約前端維護**

- `description`：每月檢查頁面操作並修正前端問題；超範圍變更須核准，核准人尚未確認。
- `body`：本人依客戶確認的需求與乙案合約，每月一次檢查頁面操作並修正約定範圍內的前端問題。此處描述乙案約定，不據此推定其他案有同樣周期；維護範圍不包含同事負責的後端業務規則及部署。超出約定範圍的變更須先核准，客戶端最終核准人尚未確認，不能自行指定或視為本人有權核准。
- 情境依據：預約乙。

B2 沒有重抄兩案的全部經過，而是用兩案形成一項共同理解，再保留兩項範圍不同的交付後工作。理解正文直接提供本次判斷需要的條件；來源關係留下查具體經過的入口。

片段三的共同分工在各項必要處簡要保留，讓甲案缺陷修正、乙案合約維護各自足以使用；A 不必為了找需求確認者，再讀另一項逾時處理理解。這是對教材的內容校準，未更動既有實驗輸入或成績。

### 11.4 更正與後補，只更新受影響的內容

後續取得兩個片段：

- 六：「甲剛才說 24 小時是我講錯，應該是 48 小時內回覆初步判斷；其他不變。」
- 七：「乙從 10 月起改為每季第一個工作日做一次維護，之前才是每月一次。檢查和修正的範圍不變，核准人還沒確認。」

| 位置 | 本次應採用的修訂 | 必須保留 |
|---|---|---|
| B1 電商甲情境 | 初判回覆期限由 24 改成 48 小時，納入片段六依據 | 不是修復期限、無固定月維護、前後端分工與逾時處理 |
| B1 預約乙情境 | 保留 10 月前每月一次，寫清 10 月起每季第一個工作日，納入片段七依據 | 維護內容、核准要求與尚未確認的核准人、逾時日期保留 |
| B2 甲案缺陷修正理解 | `description` 與正文中的初判期限同步改為 48 小時 | 不宣稱 48 小時一定修好；不影響乙案周期 |
| B2 乙案合約維護理解 | 寫清新舊適用時期；目前周期為每季第一個工作日 | 不能只留下「每季」，也不能推廣到甲案；未知仍是未知 |
| B2 前端逾時互動理解 | 分析變更後可判定正文不用改 | 兩案各自的逾時需求及角色界線 |

甲案是明確誤述更正；乙案是工作安排自特定時間變動，不能用同一種「刪舊留新」處理。原始片段不改寫，已發布歷史不覆蓋；候選關係由既有物件綁定承接，不要求 B2 重加引用表明讀過。

### 11.5 B1 也可以拆分既有情境

甲案的逾時處理與交付後缺陷修正已有不同觸發與處理範圍；B1 也可以選擇將它們分開維護，而非讓甲案一直包含所有工作。以下是在 §11.4 修訂後的另一種合理整理，未增加新的員工事實：

| B1 操作 | 整理後的內容與來源 |
|---|---|
| 保留原甲情境的物件身分，改名為「電商甲的前端逾時處理」，修訂描述與正文 | 保留避免重複送單、約定前端範圍、需求確認及前後端分工；原話依據為片段一、三。缺陷修正段落移到新情境，不再混在此處。 |
| 新建「電商甲交付後的前端缺陷處理」 | 承接交付後前端缺陷、48 小時內回覆初判而非完成修復、無固定月維護及角色界線；原話依據為片段三、四、六。不能因移轉而遺漏原有條件，也不能將已更正的 24 小時繼續寫成現行期限。 |

B1 不需要知道哪些理解引用了甲案，更不替 B2 修改理解。App 將原情境的改名／內容變動及新情境交給 B2，既有物件綁定依生命週期契約處理。

B2 接手後，前端逾時理解可繼續引用保留身分的逾時情境；甲案缺陷修正理解則須改連到新的缺陷情境，移除已不支持它的原逾時來源。兩項理解的正文若仍正確，可以不改；乙案理解也不因甲案拆分而重寫。這是實際支撐關係的調整，不是逐條確認版本刷新。B1 情境拆分並不必然要求 B2 理解也拆分，反之亦然。

### 11.6 顧問如何直接使用這些理解

- 問甲案交付後責任與回覆期限：讀甲案缺陷修正理解即可取得 48 小時及「不是修復期限」，不必再讀乙案或全部原話。
- 問兩種網站的逾時處理：讀共同理解即可辨認各自要求；若要寫程式實作細節而正文未涵蓋，才按需讀情境。下層也沒提供就不能捏造。
- 問乙案由誰核准變更：理解已明示尚未確認，且沒有新增線索時，由 A 追問員工；不是沿同一來源鏈反覆搜尋姓名。

這些是預期行為與教材，不是模型已達成的成績。來源仍須支持所寫內容，導覽名稱本身不能作為讀過正文的替代。

## 12. 如何審查整理是否有效

依事實與工作意義審查，不比對一套固定標題或物件數。以下是後續 Prompt 對照的測例方向；本次未執行新真模型測試。

| 測例 | 應保留的分析效果 | 失敗反例 |
|---|---|---|
| 跳題後回到早期工作 | B1 正確接回情境，保留前問與角色含義 | 把「每月」接到最近但不同的工作 |
| 同義重述與新增條件混在一起 | 去除重複表達，仍留下新增期限或例外 | 用去重把新條件刪掉 |
| 一案多工作、多案同工作 | B2 能按目的拆合，保留限定範圍 | 每案一項，或全部追加進「工作管理」 |
| 同工具但不同工作目的 | 各項工作可辨認、可選讀 | 都用 ERP 就合成一項空泛理解 |
| 單一案例或低頻重要工作 | 有據保留、適當限定，不捏造頻率 | 因只有一次就丟棄，或升格為每天 |
| 明確更正與時期變動 | 更新正確對象、保留適用時間及未受影響事實 | 新說法覆蓋其他案，或抹掉仍有意義的時期差異 |
| 精確值、狀態及權限 | 保留數字、單位、期限性質、結案條件及責任人 | 48 小時初判寫成 48 小時修好，前一工作日寫成前一天 |
| 已知未知與上層遺漏 | 前者無新線索時保留待問，後者查明整理或定位缺口 | 把整理漏項說成員工沒說，或靠每次回查原話掩蓋漏項 |
| 已整理的現行工作 | 理解或情境足以支持所問範圍，沿用已讀內容 | 已確認的重要條件只留原話，A 每次重做分析 |
| 原句與更正前歷史 | 按來源回查，區分舊說法與現行規則 | 把必要歷史回查當作 Memory 失效，或把舊值寫回現行 JD |
| 尚未整理的新補充 | 依近期資料及當次輸入處理，不受舊 Memory 限制 | 把新資料尚未入 Memory 誤判為整理遺漏 |
| 情境新增／移除／改來源 | 分析語意影響，必要時修訂正文及支撐關係 | 只看舊引用清單，或只改關係不看結論 |
| 理解拆分／合併 | 有效舊資訊有去處，各項可獨立正確使用 | 重組後遺失責任，或拆成必須全讀的一串條件碎片 |

先核對整理內容，再評估 A 的回答、JD 及讀取路徑。記錄「B1 整理時遺漏」「情境有但 B2 遺漏」「已整理但未定位／讀到」「讀到但改寫時遺漏」的不同成因，不把它們都歸為 Memory 記不住。整理缺漏在當次被原話補救時，回答品質與整理品質分開記錄；不因答對就把缺漏算成已解決。

現行工作、歷史追溯與新資訊接續分開觀察，不把必要歷史回查混入一般工作閱讀成本。相同品質下較少無關閱讀才是效率改善；建立與維護 Memory 的成本、map 變長的成本也要計入，具體對照控制見[研究協議](../research/work-analysis/2026-10-05-memory-organization-and-incremental-analysis.md#4-後續比較先確認整理品質再看讀取成本)。這是分析與驗收方法，不新增強制工具順序、自動完備性檢查或發布門檻。
