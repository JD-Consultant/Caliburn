# JD 編輯器：研究、討論與設計執行計畫

狀態：Owner 已要求執行；2026-09-09。Topic：JD-R002/C03，連動 C01／C02。這是研究到設計交接的計畫，不直接授權 production 改碼或付費模型測試。

## 1. 目標與有效前提

員工透過聊天室持續訪談，AI 專業職務說明書顧問承擔主要撰寫，持續完善同一份有結構的客製 JD；員工主要閱讀與補充，保留直接編輯能力。修改正確、差異可理解、可核對、可保存，出錯後能恢復。多份文件各自保存對應完整職務的訪談與 JD，供真人顧問後續核對或修改。LLM、Memory、訪談與來源回查已有成果，本計畫研究它們與 JD 編輯器的接點，不重做 Memory。

- 沿 R001 的 JD 內容／樣稿方向與 C01 的有意義結構＋完整敘述。
- 人與 AI 接續同一份最新工作稿；實際變更可查，局部修訂保留其他有效內容。Owner 後續已採持續工作稿，個別 pending 接受／取消不列本版功能，效力見審閱稿 §7.7。
- Owner 於 2026-09-10 釐清不接受「目前稿／請 AI 更正後」兩個頁面：聊天與同一可編 JD 在同一工作畫面，AI 原地更新，實際差異及唯讀歷史在原畫面查看。
- 編輯器及必要擴充只考慮免費開源；商業產品可作契約及行為參照，付費功能不能混入採用組合。
- 開源能力不足時先列證據、替代方案與代價，再與 Owner 決定，不默默降低效果或自造通用引擎。
- 本機單一員工與 AI，不擴張多人協作；新設計不受舊產品、舊架構與舊格式限制，不搬舊資料。
- **執行中補充：**Owner 表示「人改待審內容仍待審，如果不是共識的話也可以改」。該項改為依原生能力及跨產品證據重新比較的政策，不再是候選硬淘汰條件；尚不等於已同意人工編輯自動接受。
- **後續方向已同意：**訪談主導、AI 持續主寫、多份文件與真人後續核對，詳見主稿 §6.2；不以員工逐批接受為預設主流程。持久逐項修訂是否必要重新對照此效果；不默認 AI 有最終核准權，也不將「滿分」當成已被保證的模型能力。
- **Owner 隨後釐清：**員工仍能審閱寫錯、理解錯及是否符合自己工作；產品不假定他能評估專業寫作品質。AI 的實際新增、刪除及改寫須可見且可查前後內容，不能用摘要代替完整差異或靜默改動。這不等於已指定逐筆接受規則，與底層 pending 模型分開決定。
- **Owner 再次同意並限定：**核對工作事實是概念，不指定按鈕或強制 UI 操作。真人顧問後續核對不增加權限需求；本輪維持單機、單人、本地，不做登入、員工／顧問角色權限或多人協作。多文件隔離不等於多使用者系統。
- **撰寫節奏補充：**先理解某項任務，資料足以寫成有根據的敘述時才寫；有實質補充或更正時再修訂。每輪訪談與每次 Memory 更新都不必改 JD，不設固定輪數／填滿欄位觸發；局部可先寫，整份收尾仍依既有完整性要求。

## 2. 研究方法

六條工作線：LLM 使用 App；App 執行與錯誤結果；結構化 JD 與文件模型；人機共同編輯；保存與資料庫；專業顧問整合。

**2026-09-10 Owner 全面補充：**研究者主動覆蓋整個 AI 專業職務說明書顧問，不限 Owner 提及的例子。所有影響產品效果或正確性的重要選擇，都要有責任歸屬、現行官方證據／版本／授權、需求映射及驗證界線；模型參數須區分語意判斷與 App 已知／可推導資訊，錯誤須分清誰修復、實際副作用、重試與停止，資料關係由真實保存需求與 DB 正式約束推導。內容品質涵蓋忠實、完整、責任條件、未知與更正，不用品牌或模型自評滿分代替驗收。技術問題由研究者處理，不等 Owner 指出；既有有效證據直接重用，不因「最新」無限廣搜或重建 Memory。[本輪責任與證據稽核](../specs/2026-09-10-jd-responsibility-and-evidence-audit.md)發現的共用契約缺口先有限補正，再依六切片接線，最新狀態依 register；下方 S5／直接施工敘述為先前結論。

先讀官方現行文件，再追重要 API 的原始碼、測試、release／migration／deprecation。分清 Official fact、Inference、Caliburn mapping、Unknown；每項採用依據記查閱日、適用版本、成熟度及授權。較早但仍有效的官方契約可以使用；已被取代的做法只留沿革。不得猜測閉源產品內部實作或把單家政策稱為跨廠共識。

**Owner 補充的必查來源：OpenAI（Codex、ChatGPT）與 Anthropic（Claude）。**兩家都要涵蓋產品如何共同編輯，以及公開工具／執行契約；不能用只讀某一家 API 或其他廠商的產品頁代替。Microsoft、Google 及 OSS 官方資料用來交叉核對差異與採用能力。無公開資料的部分明記 Unknown，不為補齊比較表而猜測。

**按概念與效果研究：**先列員工情境與失敗，再找大廠用什麼能力處理同類問題，最後核對原生接點與限制；不要求相同名詞，不從 Owner 的概念直接推定按鈕、格式或引擎。官方公開的設計理由與研究者推論分開。必查不代表每次新增頁面都要廣搜；版本仍有效的依據可沿用，新版本或矛盾才定點追查。

調查起點為 Plate、ProseMirror／Tiptap 開源核心、Lexical。逐套件及必要擴充核對免費開源與本機條件，最多保留三個實質方案；只有一個或沒有可行方案也如實交付。對會改變選擇的主張補足證據；來源不再新增決策分支、剩餘 unknown 可用有限實驗回答時停止廣搜。

## 4. 共用驗證情境

| 類別 | 必須觀察的效果 |
|---|---|
| 定位 | 繁中、標點、換行、重複文字、貼上後結構改變、讀後目標被人改；無法定位需如實回報 |
| 內容／結構 | 未完整任務、改名、移動與拆分；未改內容、條件及必要 metadata 保留 |
| 持續審閱 | AI→人→AI 的最新版接續；每次實際差異可查，聊天／手改更正保存新版，不誤動獨立內容；個別 pending 接受／取消已取代 |
| 保存／恢復 | 部分套用、保存失敗、保存成功但結果遺失、關頁重開；不重複新增、不誤報完成 |
| 文件視圖 | 最新工作稿、某次修改與歷史版本可區分；舊刪除文字不冒充現行工作；不需 accepted projection |
| 顧問品質 | 案例與責任區分、未知不補造、更正保留其他有效工作、工作→JD 與 JD→來源雙向核對 |

固定操作只證明文件能力。後續真模型驗收須另列資料與預算，含短情境、持續訪談及未用於調整的新職位案例，評估誤改、漏改、資訊保留、修復、延遲與成本。r2 與 CT49 接案者不是同一職位，不合併為同一測試真相。
