# 保存恢復 安全 維護性與交付的演進材料

回到[演進入口](README.md)。本頁追查已成立結果的查回、來源邊界、效能診斷、重構範圍與交付驗證。

前七節整理基準：2026-10-02，`target-rebuild@2c70f0ef`；後續另按日期接續。以下數字為原紀錄結果，這次文件整理未重跑產品、模型或安全測試。

## 1 分層名稱存在但依賴方向仍然相反

**問題與變化（6/28）。**早期 API 已有 Protocol、adapter 與 Repository，但 `LlmPort` 放在 Graph 裡，五個應用 use-case 反向 import Graph；`services` 又混合資料存取與業務工作。研究不是建議再加一套框架，而是移動既有 port／adapter、保留組裝點與既有訪談行為。

**證據與界線。**[原診斷 §2](../../research/engineering/2026-06-28-api-hexagonal-untangle-research.md)、[ADR0008](../../adr/0008-api-hexagonal-layering.md)記錄 move-only 與86 passed／61 skipped，並明列 tracing 的容忍依賴及暫緩的 domain 抽取。本次沒有原執行 log 重驗；測試覆蓋範圍內的行為回歸，不足以證明所有行為完全等價。不能把「用了六邊形」本身當改善證據，也不能說一個檔案就能無條件更換任何供應商。

**可用之處。**說明抽象、目錄名稱與真正的依賴關係是不同事情；早期做法不是要求新版沿用同一樹狀結構。

## 2 已接受的輸入不應因模型暫時不可用而無法核對

**問題與定位（9/30）。**FastAPI 的 readiness dependency 在進 route 前就拋503；同 command 的輸入明明已存，App 卻到不了核對原結果的 workflow。臨時替測試補可用模型設定能繞過問題，卻沒有修正產品的查回能力。

**修正與結果。**改為先查原 command／原文是否已接受，只有新輸入才受模型可用性限制；原交易內仍重查，避免併發重送各自新增。原測試觀察3個行為失敗，後續真 PG／合成 HTTP 回歸43項通過。查回原結果不重新啟動模型，也不復活取消的 Turn。

**原件：**[T08 原結果核對](../../history.md#source-c77481f575e2c33b8e1e)，含當時另外遇到的 Host guard 測試環境問題。這是保存與准入分責，不是「所有503都可重送」；沒有真模型品質結論。

## 3 取消不能吞掉已取得的結果也不能偷偷繼續工作

**問題與定位（9/30）。**共用保存邊界已握有完整模型結果，保存時遭取消，原程式只傳出普通取消例外，沒有把原件交回；另有串流 terminal 已取得、close 階段才出錯的情境。原診斷核對 Python 取消例外與框架包裝，不把取消當一般可重試錯誤。

**修正與結果。**沿既有 typed handoff 與 checkpoint 接回原件，同時保留取消分類；沒有新增第二份結果庫或自動續跑權限。最初5個真 `Task.cancel()` 反例失敗；後續 terminal 接縫另有4個失敗，再補實際取消與保存故障組合，該批離線83項、真 PG18項通過。這些是不同切片的數字，不相加成新的一次驗收。

**原件：**[T06 原件交接](../../history.md#source-ed77b0aa0b39ca48fa6c)。只涵蓋仍握有完整原件與明確交接，不保證 process 被殺後找回未存內容，也不把使用者取消當成准許自動恢復。真事故的安全退出與續跑另讀[案例集第二例](../research-casebook.md#案例二-長訪談中斷後如何避免重複與假成功)。

## 4 開發代理轉送不能偽造可信來源

**問題與定位（9/30）。**第二組 Vite 為了使用既有後端，把所有 Origin 改成受信任的5173。真 Vite → 臨時 HTTP server 的探針發現：不允許的9999、實際5174、沒有 Origin，全部被改寫成5173。這損害後端的來源判斷，不是畫面能開就算接線正確。

**修正與結果。**保留原請求來源，由啟動設定明確增加一個合法 loopback Origin，不用代理假冒。三個原始標頭案例先失敗、後通過；另外找到預設80埠的 Origin 正規化差異，再補3個反例。原記錄連有 OWASP／WHATWG 契約及實際測試方法。

**原件：**[T15 來源保留修正及獨立審核](../../history.md#source-0e25c675694e9744582f)。Demo 沒有啟用該 override，不是已被攻擊的證據；Fetch Metadata 仍有另一層拒絕，不能誇大為所有跨站請求都可通過。這也不是完整滲透測試。

同檔的「憑證不進接續歷史與公開資料」是另一類**事後驗收**：用合成 key、MockTransport 與真 PG 查成功／401回顯路徑，並非修復已發生的真金鑰外洩；不把它包裝成 TDD 或全面隱私保證。

## 5 先量測再決定不優化

**問題與方法（10/1）。**擔心長歷史使讀取、保存與 context 變重，因此重用既有合成資料，以唯讀查詢分開量 token、relation 配置空間、logical payload、workflow 耗時及輸出 bytes，沒有為量測再付費生成大量資料。

**結果與取捨。**最大樣本完整狀態含中間訊息的中位讀取約279ms，業務狀態單獨約3ms；輸出僅857 bytes。追到慢點在遍歷 saver history、還原 response 後投影 commentary，而不是看見 checkpoint 大就直接怪資料庫索引。既有索引已生效；當時不阻塞核心編輯，決定暫不加 cache 或另一份進度庫。

**原件：**[T15 容量量測 §1–5](../../history.md#source-b565f2701598469ee5b0)。三個 thread 中兩個屬同一職務檔案；單機暖快取、每筆五次、無並行負載，不是SLA或通用效能基準。約267MiB是整組診斷資料的 checkpoint relations，不是單一請求傳輸量。後來更長旅程與新門檻的證據另見T16／T17，不混在本次樣本內。

## 6 Lint 全過仍可有結構問題但不必為行數重構

**問題與方法（10/1）。**以實際 import 圖與同段邏輯的共同修改需求審查，而不是只設檔案行數上限。原基準 lint／型別檢查乾淨、模組級環為0，套件級仍有 `adapters ↔ settings`、`transport ↔ workflows` 兩個環。

**修正與結果。**移回角色組裝與資料設定的合理責任位置，抽出兩個 runner 逐字相同的開頭；沒有建立 BaseAgent。原量測的套件級環由2變0，並用違反依賴方向的反例測試固定規則。恢復狀態機雖長，但缺乏新的行為需求，先保留，記下觸發後續拆分的條件。

**原件：**[T15 程式組織審查](../../history.md#source-e980f8e50d0556586ed2)，看「判準與方法」「發現與處置」「保留的已知債」。靜態指標是描述性代理，不是維護工時下降的實測；不同切片測試可能重疊，不加總成品質分數。原文的費用預留等寫法只代表當時程式，不從報告恢復已撤去的產品金額攔截。

## 7 開發環境能跑不代表套件裝好能跑

**問題與定位（10/1）。**從固定 Git 匯出、建立新非 editable venv，遷移成功後用真正安裝的套件啟動，卻得到 `No 'script_location' key found in configuration`。原因是程式沿 `__file__` 往上找 checkout 的 `alembic.ini`，wheel 的 site-packages 沒有同樣目錄。

**修正與結果。**依 Alembic 套件資源契約，將唯一 migration 放進 package，CLI／程式共用同一資源定位，19份revision與DDL不變。移出checkout的反例先失敗，相關30項回歸通過；再實際build wheel、安裝、啟動，用HTTP保存JD並重開讀回同一修訂。沒有加另一套遷移系統或自動升級。

**原件：**[T18 乾淨安裝與套件化 migration](../../history.md#source-25de60a3e4266687fd86)。這是同機、共用系統工具與PG的固定Git匯出，不是另機／容器／網路clone驗證；手動JD保存也不算AI產稿品質。PDF的字型與文字層問題見[JD與交付沿革](jd-authoring-and-delivery.md)。

## 8 Docker 交付補上容器與資料保留的實機證據

**交付進度（10/3）。**在 Windows 主機的 Docker Desktop Linux containers 建置正式 App，實際驗空資料庫啟動拒絕、明確 migration、同源 Web／API、中文 PDF，以及容器重建後保留原 JD 修訂與文字。App 與 PostgreSQL 分開，由 named volume 保存資料；沒有搬移原資料庫。這補上第 7 節當時未驗的容器交付，仍限本機環境與合成 JD。

**更新接續（10/5）。**原容器未掛載原始碼，重新啟動仍是舊映像；比對實際程式後才重建與替換 App，沿用同一 PostgreSQL 與 volume。映像已含公版角色工具，但該示範 App 尚未設定 RAG URL，不能將已打包寫成已啟用。稍後刪檔功能另有自己的映像與 migration 紀錄；依各次建置辨認實機版本。

**原件：**[Docker 交付](../../experiments/product-validation/2026-10-03-docker-delivery.md)、[示範站更新](../../experiments/product-validation/2026-10-05-docker-demo-update.md)、[刪檔實機版本](../../experiments/product-validation/2026-10-05-job-file-deletion.md#docker-實機檢查)。上述交付未新增真模型訪談或品質評測。

## 9 取消已提交仍須等真正保存結束

**新反例（10/6）。**整份檔案刪除初版只檢查資料庫的執行狀態；取消交易雖已提交，監督程序與原生 Saver 仍可能收尾。事件控制反例先重現顧問取消、顧問完成及 Memory 完成時過早准許刪除；真 PostgreSQL 另重現官方 `aput`／`aput_writes` 在刪除後重建 checkpoint。

**修正與邊界。**先沿既有監督程序的派送鎖與任務清單拒絕尚在收尾的刪除，再核對鎖定版框架的實際 exit／executor 行為。最終在 checkpoint Adapter 借用官方 Saver，將根檔案的 `FOR KEY SHARE` 與原生寫入放在同一連線、同一交易：先寫入則刪除等待；先刪除則遲到寫入找不到根記錄而拒絕。取消及重複取消須等實際保存交易結束後才交回，未修改框架私有實作或產品取消語義。

**驗證與部署。**原件記錄定點反例、真 PostgreSQL 競態與相關回歸，以及完整 `pnpm check` 通過；沒有新增真模型或瀏覽器 e2e。最終程式保存於 `6750be5d8`，尚未建入上節最後一次 Docker 映像，不能把程式回歸當重新部署。

**原件：**[刪檔與取消保存競爭](../../experiments/product-validation/2026-10-05-job-file-deletion.md#取消與保存競爭的接續驗證2026-10-06)。這是第 3 節之後另一個保存邊界反例，不表示先前的原結果交接測試已涵蓋此競態。

## 本頁能支持與仍不能支持的主張

這些材料支持診斷、責任分離、有限修正與相應回歸。真人時間／學習負擔、跨平台完整交付、部分原始執行 log 與成員貢獻仍需另補證；官方契約的查閱經過由各原件持有。
