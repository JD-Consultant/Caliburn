## 共用敘事與證據結構

每個案例依下列順序表達。簡單問題可以合併成一段，不為形式增加文件。

| 段落 | 必須回答的問題 | 避免的說法 |
|---|---|---|
| 問題與影響 | 哪個使用情境失敗？影響什麼結果？ | 只列功能或框架名稱 |
| 發現與重現 | 從哪份輸入、輸出、日誌或反例發現？ | 只說「覺得效果不好」 |
| 原因與取捨 | 排除哪些原因？參考什麼？為何採用或放棄方案？ | 把相關性、推測當成根因 |
| 修正 | 改了哪一層？哪些條件保持不變？ | 用大量重構代替解釋 |
| 驗證 | 與哪個基準比較？樣本、環境、判準與結果？ | API 200、測試全綠等於產品品質 |
| 限制與接續 | 哪裡沒解決？沒有測到什麼？下一個可驗證問題是什麼？ | 把單次合成結果寫成普遍成功率 |
| 團隊工作與協作 | 團隊完成哪些決策、設計、實作及判讀？成員與 AI 工具如何參與？ | 用 repo 提交數推定實際分工，或將 AI 協助寫成全部手寫 |

涉及成員署名或具體分工時，另依團隊可核實資料確認。現有 repo 能支持系統與實驗經過，不能單獨證明每個步驟由誰完成；缺少結果的部分保留未驗證，不補造成功敘事。

## 案例一 訪談能進行但 JD 的資訊密度不足

**問題。** 顧問能完成對話，不代表問到了重要工作條件；也可能把多個工作壓成過長任務，或在成果／要求欄重抄任務。目標不是填滿欄位，而是取得足夠且精簡的工作資訊。

**查證與取捨。** 以工作分析指南提出指引候選，固定 Luna、兩種合成人設與每份最多 12 輪，依預先登記的條件比較。保留 c0 基準、c1、c1b 與 c3，沒有只展示成功版本。c1 增加填寫能力的指示後，知識技能有 54% 近似任務改寫；收窄成 c1b 又幾乎消失，因此 c3 移除該條，保留有改善依據的其他要求。

**驗證。** 每批 6 份，Q3 的 72 個顧問 Turn 完成。Q1 → Q3：被引導說出的隱藏面向由平均 0 到 2.17／份；職務目的有內容由 3/6 到 6/6；成果／要求近重抄由 38% 到 20%。這些指標都有操作型定義，不等於人類專家的完整品質分數。

**限制。** 只有兩種合成人設、每批六份，並非真人試驗、隨機化大樣本或普遍改善保證。知識技能仍不穩定，Q3 仍有一個經逐筆核對原文確認的輕微漏引；不能寫成「全面解決幻覺」。

證據：[T14 的完整比較與未解問題](../history.md#source-d3293e9b28c75bbb6616)、[原始輸出、逐字稿、指標及算法](../experiments/product-validation/data/instruction-experiments-2026-10-01/README.md)。

本例可用來說明如何把領域方法轉為可測假說，並連同改善與副作用決定採用範圍。

## 案例二 長訪談中斷後如何避免重複與假成功

**問題與發現。** 採購合成人設長旅程完成前 24 輪後，資料庫程序非預期停止。後端持有的連線失效，狀態讀取回 500，評測 harness 也退出。不能把「不知道結果」當成「可以再送同一句」。

**原因與取捨。** 檢查 execution、正式訪談、checkpoint、日誌與 PostgreSQL／LangGraph 契約，區分環境事故、產品恢復邊界與 harness 缺陷。資料庫遭停止的外部原因未查明；不能用事件時間接近就認定是某程式造成。沿既有 App 重啟及安全退出設計，沒有臨時增加一套熱重連或選主平台。

**修正。** harness 補上依原職務檔案／execution 續接、事件逐筆保存、已知重啟期間的有界唯讀重試，以及絕對截止時間。一般 5xx、逾時或查不到結果不授權重新提交。已遺失的兩筆早期事件只作明示的事後重建。

**驗證。** 原旅程續完 45 輪、3 批 Memory，匯出 4 頁 PDF。第 25 與 30 輪的兩個原執行均安全失敗，確認後才新送；其候選皆 discarded，45 個完成輪次的候選皆 adopted，取消／失敗原輸入被 Memory 引用為 0。這證明本例的安全收尾分支，**不是兩個原 execution 都從中間成功續跑**。

**限制。** 仍有 10 筆 JD 依據待核對，本例也沒有自然產生 JD → Memory 的引用換版；B1／B2 未自然觸發壓縮。不能以長旅程完成宣稱所有品質／容量 gate 已通過。重建事件、缺少的完整接續原件及不完整耗時均需保留註記。

證據：[T17 事故、原因核對、A2 修正與實測](../history.md#source-98d840caa9eed7fb2840)、[四份長旅程原件及保存限制](../experiments/product-validation/data/instruction-experiments-2026-10-01/README.md#採購長旅程原件)。

本例可用來說明如何核對原結果、界定恢復責任，並保存事故與續跑的證據。

## 案例三 來源已提供但模型仍漏選引用

**問題。** JD 跨輪彙整資訊時，文字可以正確，引用卻沒有包含提供該事實的早期員工原話。

**查證。** 對照模型已取得的 Memory、舊 JD 來源與寫入結果，發現來源已提供，後續讀到原話仍未補引。已排除「App 沒保存／沒把資料交給模型」作為該觀察的解釋；但尚不能證明更深層的模型原因。

**試驗與狀態。** 曾調整來源選項說明、參數順序、推理設定、壓縮與提示候選，尚未可靠解決。Q3 的 169 個檢查項目有一個輕微真漏引，另有一個自動標記經原文核對是誤報。

**未來研究問題。** 是否由 App 提供有依據的候選來源，能比自由選序號減少漏選？需固定資訊，比較引用支持率與額外成本；目前沒有這項方案的效果結論。

證據：[T14 診斷與「已知不足」](../history.md#source-d3293e9b28c75bbb6616)。

本例支持來源選擇仍有缺口的判斷，尚沒有可靠修復結果。

## 案例四 額外分析階段是否真的值得

早期 R1a 用八個凍結案例比較 A1、A6、A2，共 24 observations。A2 的兩階段作法有局部追問改善，但未滿足預先設定的實質改善門檻，且每案多一次生成；因此當時暫留較簡單的 A6。此比較涉及整個 harness bundle，不能歸因於單一資料結構，更不能推出兩階段永遠無效。

後續由 Codex 按凍結期望逐案核對，還發現 model grader 漏掉任務過早建立與錯誤拆分；該審查不是人類領域專家驗證。這是「評測器也需要檢查」的材料，不是盲評 plumbing 跑通就已證明品質。

證據：[R1a 結果與未通過項目](../experiments/2026-07-27-r1-task-discovery/r1a-results.md)。部分原始 capture 仍是本機 ignored 資料，不能宣稱僅靠 Git 即可完整重播；歷史模型、費用與當時決策不作現行架構規範。

## 編成報告時的取捨

依報告要說明的問題與設計取捨選材；正文保留必要的反例、方法、結果及限制，逐次輸出與完整數據連回原件。

產品與資料責任沿[系統架構報告](system-architecture/README.md)取材。每個數字須能回查具基準與限制的原證據；完整 API 清單與 log 留在其責任文件。

團隊報告以共同成果為主；成員姓名、指導者、具體分工及 AI 協作方式，另依可核實資料與送件要求填寫。
