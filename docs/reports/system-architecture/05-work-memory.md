# 五、長訪談如何累積工作記憶

[報告目錄](README.md) · 上一章：[訪談執行](04-agent-execution.md) · 下一章：[JD 與恢復](06-jd-and-recovery.md)

## 三層不是三份同樣的摘要

「受訪者工作記憶」保存 AI 對員工工作的理解及其依據。這些資料獨立於 JD 格式；即使欄位或寫法改變，顧問仍可使用原有工作資訊重新撰寫。

![圖五：三層工作記憶與 JD 的依據關係](diagrams/05-evidence-layers.png)

圖五以同一個 JD 任務甲說明三種可併用的來源：工作理解、工作情境與訪談對話。從任務甲出發的箭頭是 JD 的直接引用；標示「既有來源」的箭頭則屬於來源本身的引用鏈。箭頭由產物指向依據，並非模型執行順序。理解可引用多個情境，情境可引用多則原話，同一來源也可支持多個下游物件。

JD 通常直接引用工作理解，再沿既有引用鏈回查情境與原話，不必將鏈上資料逐筆重複列為直接來源。例如任務甲引用「課程執行資料管理」，便可回查情境甲、乙及對話 1、2，因此圖中不另畫任務甲指向這些物件的箭頭。

任務甲另引用情境丙及對話 4，補充上述理解鏈未涵蓋的依據；情境丙之下的對話 3 仍可沿鏈回查。這是避免重複引用的通常做法，不是程式禁止重複引用，也不要求每個任務選滿三種來源。圖中的對話編號僅供合成示例辨識；原話可以尚未整理為情境，情境也可以尚未形成理解。

| 層次 | 合成案例 | 保留的意義 |
| --- | --- | --- |
| 原始訪談 | 「每個上課日整理簽到表」；後來補充「每季統計並交主管」 | 實際發話、角色與順序；更正另成新訊息，不改原話 |
| 工作情境 | 「出席紀錄彙整」的頻率、輸入、處理、成果、例外與未知 | 把分散敘述整理為可理解的具體工作脈絡 |
| 工作理解 | 「維護課程執行資料，支持主管追蹤出席狀況」 | 跨情境形成較穩定的責任、範圍與能力理解 |

工作理解透過引用保留細節，無須重抄所有情境。資料不足或互相矛盾時，保留未知與矛盾，供顧問繼續追問；B1／B2 負責整理這些資料，如何撰寫 JD 仍由 A 判斷。

## 為什麼導覽與正文分開

情境與理解物件具有 `title`、`description`、Markdown `body`，以及獨立於正文的引用關係。Map 是目前範圍的導覽，提供標題與範圍描述，讓模型先找值得讀的物件；正文再按需取得。這避免每個 Step 都重送所有長文。

模型以 App 提供的 `target_title` 等工具參數定位物件，App 再依角色權限解析成資料庫身分，標題本身不是主鍵。A 讀取本 Turn 固定的快照；B1／B2 讀取正在修改的候選工作稿。

正文使用 V4A diff 編輯，修改範圍限於指定物件。即使使用模糊匹配，也必須找到唯一合格位置；若定位有歧義或多區塊修改失敗，就不採用部分結果。標題、描述與引用則以型別化欄位操作管理。模型因此能修改長文，但沒有任意修改檔案系統的權限。

## 背景整理如何開始與交接

![圖六：B1／B2 的背景批次](diagrams/06-memory-batch.png)

圖六呈現背景整理的單向流程，省略故障與恢復的細節。A 可在工作中提出整理要求，但只有該 Turn 成功完成後，要求才具備啟動資格。App 固定本批原話上界為觸發輪的最後一則員工輸入，不讓稍後訪談或已取消輸入混入本批。

B1 先在候選工作稿整理情境。完成後，App 保存結果與變更，由 B2 接手整理理解；此時 B1 不再修改本批情境，讓 B2 能依固定的上游資料分析。現行流程為 **B1 → B2 → 發布**，B2 不修改情境，也不回交 B1 返工。

B2 透過差異資料得知哪些情境新增、刪除或修改，包括尚未被任何理解引用的新情境。差異協助定位需要重新分析的範圍；分析時仍可按需讀取最新版全文及原話，不能只因讀過 diff 就視為完成。

B2 完成後，App 發布整份 Memory 快照。資訊不足或矛盾須如實保留，不藉猜測補齊，也不因此啟動 B2 → B1 的回圈。Memory 是由系統管理的背景工作，使用者不能暫停、取消或重試。

## 可變工作稿與固定快照

![圖七：物件修訂重用與發布快照](diagrams/07-memory-snapshots.png)

圖七的線表示快照選用與固定引用，為了閱讀省略部分重複的選用線。**快照涵蓋原始訪談、情境、理解三層，不是只保存理解入口。**合成例子中 M1 選用情境 S1-r1、理解 U1-r1；後來情境修改為 S1-r2，M2 選用重新整理的 U1-r2。未改的情境 S2-r1 可被兩版重用。`r1`、`r2` 是說明用修訂名稱，不是工具要求模型填的參數。

候選工作稿的引用綁定物件身分：理解引用某情境後，即使該情境改了標題或正文，仍連到同一物件的目前狀態。刪除情境會解除候選中的相關綁定，但保留理解及已發布歷史。App 在每次操作時維持結構合法，發布時再以交易固定整組物件修訂與關係，不將資料格式檢查交給模型補做。

發布後，同一版 Memory 對同一情境或理解身分只選一個修訂，無論從 Map 或任何引用路徑抵達，都得到相同正文與下層引用。不同物件不必有相同修訂號。正文沒改而下層引用修訂改變時，上層的固定修訂也要反映該變動。

B1／B2 完成語意整理後，App 將候選與關係一併固定、發布，無須 B2 逐條呼叫「確認刷新引用」。這與第六章 JD 的逐項核對不同。程式保證的是快照與引用結構一致，模型是否正確理解員工工作仍須另外評估。

所有已發布快照及沿引用可達的物件、原話都須保留，讓 JD 的歷史依據可回查。中途失敗的候選則不要求永久保存；執行恢復紀錄與正式歷史有不同的保留需求。

## 整理失敗，不等於訪談必須停止

尚未發布的候選不提供給 A。背景整理最終失敗時，A 繼續使用已發布 Memory、近期原話及訪談讀取工具；App 提供整理未完成與已知原因，不能宣稱 Memory 已更新。系統有界處理故障，不能無限重跑。

背景整理失敗後，現行程式會等待正式訪談進度增加，再允許一次新批次：正式序號比失敗時前進 6（一般為三輪完成的訪談）才解除阻塞，再失敗便重新阻塞；舊失敗紀錄若未存當時前緣，不會自動解除。等待三輪是否適合作為產品政策仍未定案，也未在真模型長旅程中觸發驗證。
