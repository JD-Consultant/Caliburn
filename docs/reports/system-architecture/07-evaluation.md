## 分層分析的設計取捨

長期分析由三個角色分工：A 決定當前訪談與 JD 工作，B1 整理具體情境，B2 形成跨情境理解。程式負責固定資料範圍、保存版本、執行工具與安全提交。分層記憶和差異讓模型不必每次重讀全部資料，需要細節時仍可回查原話。

本專題的貢獻在於上述工程整合，未提出新的基礎模型或演算法，也尚未證明多角色設計優於所有單角色方案。

| 選擇 | 得到什麼 | 承擔什麼／目前不做什麼 |
| --- | --- | --- |
| 模組化單體 | 同一套業務規則、部署及交易較簡單 | 不先拆微服務、加入訊息佇列平台 |
| App 管理原生 Context | 可控制提供範圍、接續與壓縮採用點 | 需自己驗證格式、容量與恢復；不自製 reasoning |
| 分層 Memory＋Map／按需讀 | 大量事實可逐步整理與回查 | 檢索可用不保證模型選對來源 |
| 候選與正式快照分開 | 預覽、取消、固定歷史可以共存 | 需維護正式化邊界，不把 DB 寫入都當正式發布 |
| 差異引導重新分析 | 重點檢查變動，避免全文重讀 | 差異不是專業判斷，也不是品質證明 |
| Luna 作產品模型 | 符合目前成本選擇 | 來源與提煉品質仍需優化，未以更換高價模型取代問題處理 |

## 一個重要的品質反例：資料可見，模型仍可能漏引

既有合成課程行政旅程中，早期訪談第 8 則描述每個上課日整理簽到紀錄；本次輸入補充統計方法，完成後成為第 10 則。模型建立結合兩次資訊的任務，卻只選 `current_input` 作來源。

建立任務前，模型已讀到相關情境、理解及舊 JD 的早期來源；建立後又讀到第 8 則原話，仍未補引。App 保存的就是模型選取的來源，沒有證據顯示引用在保存途中遺失。因此，目前能確認的是來源選擇不完整，不能歸因為 Context 缺漏；模型為何漏選仍未查明。

這個反例說明，資料能回查，仍須另外驗證模型是否正確使用必要依據。增加來源索引、得到 `needs_recheck=false`，或直接複製全部來源，都不足以證明漏引已解決。詳細分析見 [T14 品質紀錄](../../plans/2026-09-29-target-rebuild/evidence/t14-job-analysis-quality.md)；第一章的示意案例並非這項問題的測試證據。

## 這份專題可以主張什麼

目前已完成的成果，是將 AI 引導訪談、分層工作記憶、可追溯的 JD 編輯與安全保存接成可驗證的流程。分析角色各有職責，模型與工具的執行機制則共用，避免各角色重複實作。

尚未證明的包括：普遍達到專業顧問品質、零幻覺／零漏引、所有長訪談均能完成、跨平台交付，以及實際節省的人工時間。後續應依既有工作分析指南，評估事實涵蓋、責任邊界、來源正確性、資訊精簡度與訪談負擔；目前不另建評測平台。
