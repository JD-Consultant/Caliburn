## 技術上的重點是組織分析，不是增加 Agent 數量

本系統把長期分析拆成幾種互補責任：A 決定當前訪談與 JD 工作；B1 整理具體情境；B2 整理跨情境理解；程式提供範圍固定、版本保存、工具執行及安全提交。三層記憶與差異降低每次重新閱讀全部資料的需要，但不把任何一層摘要當作原話替代品。

這是一項工程整合設計，不是宣稱發明新的基礎模型、演算法，或已經證明多 Agent 優於所有單 Agent 方案。

| 選擇 | 得到什麼 | 承擔什麼／目前不做什麼 |
| --- | --- | --- |
| 模組化單體 | 同一套業務規則、部署及交易較簡單 | 不先拆微服務、加入訊息佇列平台 |
| App 管理原生 Context | 可控制提供範圍、接續與壓縮採用點 | 需自己驗證格式、容量與恢復；不自製 reasoning |
| 分層 Memory＋Map／按需讀 | 大量事實可逐步整理與回查 | 檢索可用不保證模型選對來源 |
| 候選與正式快照分開 | 預覽、取消、固定歷史可以共存 | 需維護正式化邊界，不把 DB 寫入都當正式發布 |
| 差異引導重新分析 | 重點檢查變動，避免全文重讀 | 差異不是專業判斷，也不是品質證明 |
| Luna 作產品模型 | 符合目前成本選擇 | 來源與提煉品質仍需優化，不用更貴模型掩蓋未解問題 |

## 一個重要的品質反例：資料可見，模型仍可能漏引

既有合成課程行政旅程中，早期訪談第 8 則描述每個上課日整理簽到紀錄；本次輸入補充統計方法，完成後成為第 10 則。模型建立結合兩次資訊的任務，卻只選 `current_input` 作來源。

這不是已證明的 Context 遺漏：建立前，模型已讀到相關情境、理解及舊 JD 的早期來源；建立後又讀到第 8 則原話，仍未補引。App 保存了模型實際選的來源，沒有證據顯示 App 吞掉引用。**已知的是來源選擇不完整；模型內部為何漏選仍未證明。**

因此，「資料可以回查」與「AI 正確使用所有必要依據」是兩個驗收問題。只增加來源索引、看到 `needs_recheck=false`，或把所有來源機械地複製上去，都不能直接證明問題解決。完整定位在 [T14 品質紀錄](../../plans/2026-09-29-target-rebuild/evidence/t14-job-analysis-quality.md)。本報告的第一章案例是解說用合成情境，不能拿來取代這個實測反例。

## 這份專題可以主張什麼

目前可以主張：Caliburn 已將 AI 引導訪談、分層工作記憶、可追溯的 JD 編輯與安全保存接成可驗證的核心流程，並用角色權責與共用執行機制控制複雜度。

尚不能主張：AI 已普遍達到專業顧問品質、保證零幻覺／零漏引、所有長訪談都完成、正式產品全面交付，或已實證節省多少人工時間。後續評估應沿既有工作分析指南，對照事實涵蓋、責任邊界、來源正確性、資訊精簡度與實際訪談負擔，而不是再堆一套評測平台。
