## 1. 建議：一套可維護內容，多個輕量入口

本節記錄候選探索時的建議：優先驗證「**不可變原話＋可局部修訂的工作理解集合＋按需導覽**」。每項理解以一段能正確使用的工作認識為單位，帶齊必要責任、適用條件及精確細節；較深的經過與其他工作再按需取得。不先增加圖資料庫、向量服務、固定分類樹或另一套長摘要。後續已改以既有分層收斂，見 §9。

這不是主張單層已勝出。先導中單集合維護輸入少 35.92%，但局部選讀少了另一項中的分工；雙層則追加新核准人後留下舊未知。兩個反例要求一起處理**保存、更新、找回與使用**，不能只用 token 下降選架構。

本題 `MEM-REP-02` 處於證據與候選比較階段：在不損失事實、來源、發布快照及按需讀取的前提下，什麼組織與修訂方法最適合延續職務分析？正式層數、資料表、工具 schema、Agent 數量及輪前摘要的實作均不由本研究直接切換。

## 2. 大數據方法可以借鑑，但不能代替語意判斷

以下為本次核對的公開來源；表中「映射」是 Caliburn 的設計推論，不是廠商對本產品的品質保證。

| 公開來源 | 可核對的機制／發現 | Caliburn 映射與界線 |
|---|---|---|
| Google [BigQuery 增量 materialized views](https://docs.cloud.google.com/bigquery/docs/materialized-views-use#incremental_updates) | 符合追加等條件時重用快取；更新、刪除或特定 JOIN 來源變動時，增量路徑不適用，回退原查詢。 | 延續已有分析，只重新分析受影響部分；不符合假設時擴大重看。**訪談只追加，不代表工作理解也只追加**：新話可能撤換舊結論。語意分析不像 SQL 可精確推導增量。 |
| Databricks [Change Data Feed](https://docs.databricks.com/aws/en/tables/features/change-data-feed)與 [MERGE](https://docs.databricks.com/aws/en/delta/merge) | 前者提供變更類型、前後值及提交版本，但受保留期限限制；後者依匹配條件更新、刪除或新增，多來源競爭同目標可能歧義。 | 先定位，再決定修訂；diff 告訴模型改了什麼，不等於已處理。原話與發布歷史另保留，不能把暫時變更紀錄當永久證據。資料列匹配不等於兩段話語意相同。 |
| Microsoft [Azure AI Search index projections](https://learn.microsoft.com/en-us/azure/search/search-how-to-define-index-projections) | 父文件可投影成子文件；建議單索引重複必要父欄位，分開索引時沒有查詢期跨索引 JOIN。 | 可搜尋單位與完整閱讀內容分開；必要脈絡可有限重述。這不是自動把某一工作的條件套到同類所有工作。 |
| Elastic [parent/child join](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/parent-join) | 父子查詢有成本，官方不建議用多層關係模擬關聯模型，建議優先考慮去正規化。 | 不追求每句只存一處，也不因需要關聯便先建圖。複製的必要限定仍有同步成本，須納入修訂測試。 |
| Anthropic [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 切塊可能丟失所屬對象／時期；在檢索表示加入片段特定脈絡，並在其資料集比較混合搜尋與重排序。 | 索引不能只有失去主語的「48 小時」；正文需交代誰、哪項工作、什麼期限。不照搬其 chunk 長度、Top-K、模型或成效數字。 |
| Microsoft [Memora](https://arxiv.org/html/2602.03315v2)及 Google DeepMind [ReadAgent](https://proceedings.mlr.press/v235/lee24c.html) | 前者分開豐富內容與輕量查找；後者由概要定位後按需回看原文。 | 借用「入口不是完整內容」。不把每項理解變成必須再讀原話才能使用的目錄，也不新增必走的摘要層。 |
| [LongMemEval](https://arxiv.org/html/2410.10813v2)，§3–5 | 將記憶分成索引、檢索、閱讀；涵蓋更新、時間及未知題，並指出正確取回仍不保證正確使用。 | 分開量測整理保真、必要內容進入 Context、最終 JD 使用及引用；不能把某一階段成功代替完整效果。 |

這些方法的共同啟發是「儲存不等於每次全讀，索引不等於內容，變更不等於重新寫全部」。它們沒有共同規定最佳 Memory 層數，也沒有證明關聯鏈能自動解決長訪談分析。

## 3. 本地證據：缺的是可使用的閱讀單位

[離線核對](../../experiments/product-validation/data/memory-structure-incremental-2026-10-05/reading-coverage-audit.md)追到具體正文：單集合的交付後單元為 170 個 UTF-16 code units，共同分工在另一個 134 單元。要從當前完整理解單元取得這題全部依據，就需讀兩項，共 304，也就是此快照的全部理解。雙層實際讀一項 259，已有四項必要內容，但也讀入乙案維護。

這支持兩個診斷，不是新模型成績：

1. 只補「相關項目」或要求 A 多讀，可能只是把全讀分成多次工具呼叫。
2. 只減少單項篇幅，也可能讓責任與條件碎裂；需要一起檢查適用範圍與必要脈絡。

內容邊界仍由[工作分析指南 §10–12](../../guides/2026-09-09-complete-work-analysis-guide.md#10-從碎片訪談到可延續的工作理解)及 [JD 指南 §3](../../guides/2026-09-09-jd-field-and-writing-guide.md#3-職務目的職責任務同一份工作的不同縮放程度)收斂：按工作目的、對象、責任、成果及變動範圍組織，不按固定字數、訊息數或動詞切。

## 4. 候選的三個責任

```text
有效訪談原文 ──新增／補充／更正──→ 找到受影響工作
     ↑                                  ↓
  來源回查                       局部修訂理解與來源
     │                                  ↓
     └──────── 工作理解集合 ─────→ 固定發布快照
                     │                       │
              輕量導覽／必要關聯          顧問按需讀取
                     └───────────────────────┘
```

圖為候選能力與資訊流，不表示新增三個服務、三張資料表或三個 Agent。

### 4.1 內容：範圍適當，局部足以正確使用

`title` 區分工作，`description` 提供範圍及查閱線索，Markdown `body` 承載可用的理解，來源另列。第一版不增加通用標籤、每句 claim ID 或強制十四欄資料表。

- 一項不必回答整份 JD，但應帶齊使用它時不可缺的限定。48 小時必須跟「接報後、回覆初判、不是完成修復」一起出現；本人與他人的必要責任也不能只藏在別項。
- 適用於多項工作的短責任界線，可有來源地重述。只有經常被獨立使用的共同知識才另成單元；不為零重複增加一層。
- 相關入口回答「缺哪方面可看哪裡」，不是來源證明或必讀清單。第一版先用既有描述選讀；若另加結構化關聯，須另定更新、刪除與版本契約，不能偷偷把關聯當引用。
- 原話不變成 atomized facts 的唯一替代品，完整原話仍可查。尚未完整的線索可以帶明確未知保存，不因不能寫成完整 JD 就丟棄。

以本例說明，甲案交付後缺陷與乙案例行維護可分開；前者正文同時帶甲的責任與初判期限，後者帶乙的周期、核准範圍及未知。這是示意，不要求所有資料都按案件切，也不提供固定標題或物件數作答案。

### 4.2 修訂：先判斷新舊關係，再改正文

維護時以「新來源＋相關舊理解＋必要原話」形成局部分析。先用既有來源關係找受影響項，再以工作範圍找可能尚未建立引用的項；全新工作與跨工作補充不能因沒有舊邊就被漏掉。來源關係是候選定位，不是完備的語意依賴圖。

| 新舊關係 | 當前理解如何改 | 不應發生 |
|---|---|---|
| 重述 | 必要時整合表達與來源，其他沿用 | 每次新增同義單元 |
| 補充 | 加入所屬工作，保留其他有效限制 | 只留下最新資訊 |
| 明確更正 | 撤換同一範圍的舊說法；舊原話與快照保留 | 24 與 48 同時作現行期限 |
| 自某時改變 | 保留前後適用時期 | 把過去規則當錯誤刪掉 |
| 未知被確認 | 在相同工作／條件內用已知內容取代舊未知，描述同步 | 舊未知與新答案同時作現況 |
| 不同條件或未解矛盾 | 分開範圍、保留待釐清 | 無條件採最後一句 |

這些是分析方法，不先新增 `classify_change` 工具、持久規劃表或第二個審核 Agent。沿用局部編輯與原子保存；提交 patch 前比較預期的新正文，確認失效說法是否真正撤換，而非合法地追加同一小節。必要時回讀受影響物件核對，不要求每個無關項都重讀。

若共通分工在多項重述，補充該分工時要重新評估這些項；一般相關連結不自動複製正文，也不自動宣稱完成核對。雙層若保留，同一方法亦適用於 B2 維護，不限單集合。

### 4.3 讀取：小入口、完整局部內容、缺口導向補查

1. App 固定職務檔案、可見範圍與快照；模型不選資料庫版本。整理端讀自己的最新工作稿，顧問端讀固定發布版，不能混用。
2. 小集合仍用完整精簡 map。模型已能從現有 Context 正確定位且內容仍適用時，不強制重新讀 map。
3. 讀所選單元的完整正文與來源導覽。內容不足時指出具體缺口：另項工作的界線、細節、原始指涉或更新衝突，才選擇下一入口。
4. 補查相關理解或原話；保留原始角色、序號及足夠前問。不存在的答案不能靠反覆查同批來源補出。
5. 停止以當前任務是否已有足夠依據判定。到用量／時間界線、沒有新命中或相似度高，都不代表分析完成；必要缺口仍須保留或向員工確認。

充分性依問題而不同：只問回覆期限，需期限及性質；要整理工作任務，還需相關本人行動、責任、條件與成果。不要為每題強制填相同清單，也不要為減少工具呼叫而省略關鍵限定。

## 5. 資料多時怎麼擴展，不把全部 map 永久塞入 Context

先比較現有資料下的組織；只有量測顯示 map 膨脹或漏選，才進入索引實驗。大規模候選為：

- 保留可列舉的主題／工作入口，每項正文可直接按標題定位；跨主題搜尋作補充，不限制每項只能屬一個分類。
- 查找可使用標題、描述、員工用語及正文；找到後回傳定位及簡短命中理由，正文仍按需取。不能只搜一句 description 就斷定沒有資料。
- 若字詞差異造成實測漏召回，再比較語意＋字詞候選及必要重排序，不先決定向量產品或通用 Top-K。
- 搜尋受同一快照與權限限制；索引是可重建的派生表示，不能把最新索引指向舊快照不存在的內容。新修訂不可讓舊發布版查回不同正文。
- 未命中時可換表述或擴大入口；整份職務盤點須可列舉全部工作，不能用相關度前幾名代替完整工作範圍。

單一集合不代表只能有一份平坦 map。多種查找投影也不等於多套可獨立修改的長正文。第一版不導入圖資料庫、Kafka、完整事件溯源平台或查詢規劃 Agent；這些不能解決已知的語意漏改與漏讀。

## 6. 用什麼實驗選，而不是先宣告最好

### 先排除測法問題

既有批次的最終 JSON 未受輸出 schema 約束而停止；下一批先依 [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 核對模型、SDK 及容量計數契約，約束需要機器解析的最終結果。兩組用同一修正，格式仍不通過就如實記失敗，不人工補括號。格式正確不算事實正確。

### 分段比較，避免把多項變因揉成一個結論

| 階段 | 對照與凍結項 | 要回答的問題 |
|---|---|---|
| A．閱讀邊界診斷 | 固定原話事實，以既有產物為對照；人工重組只作可行性上限，清楚標記，不當成模型成果 | 所需事實是否能在少量內容中完整供讀，而不需要全讀？ |
| B．模型增量維護 | 單集合原方法／本研究候選，同來源、空白起點、批次、Luna/high、工具與限制；兩組都由模型建置 | 模型能否自行形成自足單元、撤換舊說法，且保留未受影響內容？ |
| C．顧問選讀 | 固定相同讀者、題目、JD 起點及原話權限；只換兩組生成的 Memory | 實際選到、讀到、用對了哪些資料？少讀是否仍完整？ |
| D．方法消融與規模 | 候選有穩定效果後，分開關掉自足限定／關聯入口，並比較全量原話與已保存雙層；超容量另控制接續方式 | 改善來自哪項機制？加入索引的收益是否足以抵銷維護成本？ |

B 階段比較的是內容組織與維護方法的組合，不宣稱只有某句 Prompt 造成效果；D 再拆因。既有雙層結果只作歷史參考；若要正式宣稱優於雙層，須用相同完成契約與資料重新配對，不能混用不同批次用量。

既有前端案例用來回歸，另加未出現在教學範例的倉庫／設備工作。資料事前固定答案、必要限定、來源及容許路徑，題目可跨句、跨期或改用員工簡稱；同一資料的改述不是獨立樣本。評分資料不送給模型，不按輸出重寫分母。

必要反例包含：未知轉已知、誤述更正、未來才生效、兩條件只有一條已知、相同工具不同工作、共通分工更正、跳題後「剛剛那個」、5% 的分母、每日 09:30 的時區／工作日語義、低頻重要工作，以及根本沒有答案。時間、分母等只按材料保存，不自造員工未提供的值。

### 指標和判定

- **保存保真：**每項必要事實完整／部分／遺漏／錯誤；精確值、限定、責任及未知分開。查新舊說法是否同時被當成現況。
- **更新一致：**應變更項、未受影響項及仍有意義的歷史適用期；來源可達與正文真受支持分開。重複輸入不產生無意義重複。
- **選讀完整：**題目所需、且 Memory 已有的事實，多少實際進入讀者 Context；另列 Memory 原先就缺的事實。以整題全部滿足率補充逐項率，不能讓一項嚴重責任錯誤被平均掩蓋。
- **使用與引用：**取得後是否正確寫入 JD；引用是否支持整段。分開「沒保存」「有但沒讀到」「讀到但沒用對」。
- **效率：**分列建立、各次更新、導覽、查閱、重播與輸出 token；另記工具數、重讀、延遲、失敗及費用。字元數只描述文字量，不代替 API usage。

小批次准入先要求已知關鍵反例沒有錯誤／缺漏、來源支持成立、局部選讀沒有假裝足夠，再比較用量。通過只表示值得擴測；跨職務重複與超容量尚未完成前，不宣稱通用最佳。總效益按「建立＋更新＋後續使用」計，不只挑單次最省的讀取。

## 7. 目前收斂與下一步

當時建議保留單集合為優先候選，同時把「可獨立正確使用」與「明確撤換失效說法」加入下一批比較。以下保留這批結果；後續依 §9 改以既有分層優化，不再優先推進單集合。

多方研究與既有產物離線核對後，完成了[自足理解單元配對](../../experiments/product-validation/data/memory-coherent-units-2026-10-05/results.md)：兩組保存均 33／33；候選顧問讀取由 7 次減為 4 次，reading input 少 35.48%，但 JD 判準為 14 完整／2 部分，原方法 15 完整／1 部分。部分項均是正文已讀到、最終未完整保留，不能以增加資料量處理。

本批已結案，估算占用 US$0.015015415，累計 US$1.285104650／US$2。這是每組一次的已知反例回歸；尚不符合品質等價的採用條件，候選指引不替換正式產品。跨職類與超容量另驗，不能把未用完的單批額度當自動補跑授權。

這份候選的採用條件是品質與成本的配對證據，而不是層數或技術名稱。若必要限定在多處重述後難以一致維護，或單集合仍頻繁回查全部原話，就重新比較雙層及有明確依賴的讀取投影；不要為了維持本輪建議而降低判準。

## 8. 從查詢與增量系統進一步借鑑

本節補核資料建模、按需掃描及增量處理，回應「資料量大時如何找得到、只讀相關內容、持續修訂」。下列都是可借鑑的機制，不是要把 JD App 改成資料倉儲，也不以資料庫效能推定語意品質。

| 可借鑑方法 | 官方／論文的實際主張 | Caliburn 的用途與限制 |
|---|---|---|
| 經常共讀的資料就近組織 | [BigQuery nested／repeated fields](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-nested?hl=en)建議對經常共同查詢的階層資料適度去正規化，減少 JOIN 與資料協調；也明說部分 schema 不會因此更快。 | 工作正文帶齊使用時必要的短責任、條件，減少為拼回語意而跨項全讀。不是把整案全部黏成一項；共同限定若多處重述，要一起納入修訂範圍。 |
| 只讀查詢所需部分 | [DuckDB Parquet partial reading](https://duckdb.org/docs/current/data/parquet/overview#partial-reading)把欄位選取及過濾下推至讀取端，依可用統計略過無關資料。 | map 選工作、read 取正文是類似的分工。模型判斷語意相關性不像 SQL 條件可精確執行，不能把「看起來不相關」當成可證明安全的刪除；也不新增任意截斷正文工具。 |
| 有條件的增量維護 | [Databricks materialized views](https://docs.databricks.com/aws/en/ldp/dbsql/materialized#incremental-refresh)依來源／查詢及成本選增量或全量更新。[Enzyme 論文 §4.5、§5](https://arxiv.org/html/2603.27775v1)進一步討論沿資料依賴圖考慮總更新成本，而非每個 view 各自最省。 | 評估「整理＋修訂＋顧問查閱＋最後 JD」，不只挑 B2 token 最低者。新訪談雖只追加，卻可能使舊理解失效；引用只能幫忙找受影響候選，未涵蓋所有語意依賴。本文不移植其成本模型或套用論文效能數字。 |

上述方法可收斂成三個研究問題：**一項資料要帶哪些必要脈絡、什麼變動會影響哪些已分析內容、這次任務實際需讀什麼**。資料分層只是一種組織答案，不先決定層數、固定切塊長度或索引服務。

### 已讀到與使用正確，須各自驗證

自足單元實驗已顯示有必要分開這兩個階段：內容正確取回後，顧問仍可能在縮寫時漏掉分工。資料系統提供的是可定位、可更新的內容，不會自動替 LLM 保證輸出含義。

[固定 Memory 比較](../../experiments/product-validation/data/jd-scope-preservation-2026-10-05/results.md)已完成 16 次，不重做整理：兩組讀相同 Memory，只改顧問如何依任務範圍取捨。原指引完整任務 21／25 項完整，候選 24／25；局部片段兩組皆保留必要條件且不過度展開。候選輸入少 12.36%，但生成費用估算多 5.46%，仍有一次讀後漏分工與一處責任推論風險，未替換產品。兩組還各有兩份完整任務帶入同案其他工作，顯示共讀組織不能只以專案為界，仍須區分工作目的與適用範圍。接著先離線審查工作單位，再規劃跨職務、更多單元及超容量比較。

「讀到越少越好」不是准入條件；應在回答仍完整、來源支持且沒有混入其他工作的前提下，比較載入量與總處理成本。這是借鑑查詢最佳化時保留問題語義的研究思路，不主張 SQL 的等價轉換保證可直接移植到自然語言。

## 9. 收斂：採用既有分層，改善內容組織與選讀

本次設計方向是讓三層各自提供可用成果：原話保存依據，B1 把分散資訊整理成有脈絡的情境，B2 將相關情境分析為可直接使用的工作理解。A 依目前要回答或編輯的範圍選讀，資訊足夠便停止。層數不再作本階段的比較變項。

### 可直接借鑑的做法

| 來源與方法 | 在既有分層中的用法 |
|---|---|
| [Databricks Medallion architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)：保留原始資料，逐層整理，再形成面向業務用途的資料 | 借用「每層有不同用途」：B1 還原具體工作脈絡，B2 按工作意義重組；不是每往上一層就只能縮短文字。這是概念映射，不把職務理解等同於 SQL 彙總，也不新增 lakehouse。 |
| [BigQuery 共讀資料就近組織](https://docs.cloud.google.com/bigquery/docs/best-practices-performance-nested)：適合共同查詢的階層資料可適度去正規化 | 一項理解帶齊該工作的必要責任、時間、條件；短共通限定可就近重述，長案例經過留在情境。按工作用途決定哪些資訊一起讀，不按整個專案包成一大篇。 |
| [BigQuery 增量更新](https://docs.cloud.google.com/bigquery/docs/materialized-views-use#incremental_updates)與 [Databricks 變更資料](https://docs.databricks.com/aws/en/tables/features/change-data-feed) | 用新增訪談與情境 diff 定位修訂範圍，沿用未受影響分析；更正、時期變動與新工作分別處理。既有引用提供影響線索，再由導覽補找相關理解，包括新情境。 |
| [Anthropic 按需 Context](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：以輕量入口及工具逐步載入所需內容 | `title`／`description` 幫助選讀，正文承載可用認識，來源提供深入入口。A 依具體資訊需求讀取，不把附有來源理解為必須展開全部來源。 |
| [OpenAI GPT-6 提示指引](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra#prompting-best-practices)：清楚表達目標、脈絡、任務與約束，避免指引彼此牴觸 | 將 B1／B2 的指引整理成角色、整理方法、修訂原則及少量完整例子；工具說明負責何時用與回傳意義，不重抄整份分析指南。正式模型維持 Luna／high，效果由相同模型驗證。 |

以上官方來源支持的是各自領域的方法；Caliburn 的拆合粒度、適用範圍及停止判斷由工作分析指南定義。方法集中於[指南 §10.7](../../guides/2026-09-09-complete-work-analysis-guide.md#107-收斂後的整理與選讀準則)，本頁只保留研究依據，不另定一份 Prompt 或工具契約。

### 本階段的最小優化範圍

1. **先校準內容與例子。**理解以可定位、可直接使用、可局部修訂為準；B1 保留脈絡，B2 保留工作意義與必要限定。已補齊指南範例的需求確認者與適用範圍，與正文原則對齊。
2. **下一步調整既有角色指引。**沿用工具、引用、快照與恢復機制；不增加搜尋服務、第四層或新 Agent。只修改分析方法及必要的工具使用說明，保留正式能力邊界。
3. **再用配對結果決定採用。**固定 Luna／high、相同原話與起始資料，比較既有指引與優化指引的 B1 → B2 → A。先檢查更正、共同權限與完整／局部任務，再擴大至長訪談。

驗證沿用既有固定判準，分開記錄事實是否保留、所需內容是否讀到、JD 是否正確使用；同時比較實際讀取量、整理及使用成本。以「同品質、較少無關閱讀」或「相近成本、內容更完整」判斷效果，不強制每題只讀一項、不為低 token 放寬判準。本輪未送付費請求，既有批次與累計用量不變；新的真模型比較另依有效授權執行。

### 後續驗證：分層取用成立，重述範圍仍需校準

上述方法收斂後，使用者另授權 US$0.10／20 分鐘的[分層與完整原話比較](../../experiments/product-validation/data/memory-layered-value-2026-10-05/results.md)。三批 B1 → B2 與四對顧問作答已完成：四個分層題均各讀一項理解、不展開下層；分層 JD 15／16 完整、完整原話 16／16。這直接觀察到按需使用整理成果，不依賴前批對話歷史。

結果也界定了「共讀資料就近組織」的範圍：必要共同分工值得保留，但不相關的跨案期限被複製到另一理解後，會變成未同步的副本。整理應減少這類比較，必要引用則覆蓋所有被陳述的事實。方法校準集中回[指南 §10.7](../../guides/2026-09-09-complete-work-analysis-guide.md#107-收斂後的整理與選讀準則)，不另造全域規則層。小材料的導覽與工具成本仍使 reading input 高於完整原話，不能把正文少讀直接換成 token 節省。該批結案時未替換正式提示；後續局部採用見下節。

## 10. 研究收斂與可重算證據

**保留分層，先讓每層能直接使用，再減少不必要的閱讀與重述。**本次沒有增加索引服務、Agent 或同步機制；採用已有反例及配對證據支持的小修訂。

### 研究如何影響取捨

再次核對 [Anthropic 的 Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：以輕量識別與工具按需取得內容，降低常駐 Context 負擔，但探索本身仍有成本。對本產品的啟發是「理解足夠就使用，有具體缺口才深入」，不是把來源鏈當必讀清單。

[BigQuery 的共讀資料建模建議](https://cloud.google.com/bigquery/docs/best-practices-performance-nested)支持把經常共同使用的階層資料就近組織；它也指出去正規化未必總有收益。Caliburn 因此保留解讀工作所需的短責任、條件與數值，但不複製無關案件的數值作排除比較。這是內容組織上的借鑑，不是把 SQL 的一致性保證套到自然語言。

[OpenAI 的提示建議](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)用來檢查目標、脈絡與約束是否清楚；模型家族指南不是 Luna 的效果保證。新指引仍須在 Luna／high、固定材料及判準下比較，不因文字看起來合理就宣稱有效。

### 已有數據支持哪項設計

重新核對[閱讀策略實驗](../../experiments/product-validation/data/memory-reading-policy-2026-10-04/results.md)原件，八格用量與衍生 metrics 一致，trace／結果 SHA256 亦與原結案紀錄相符。它固定同一份 Memory、近期訪談、JD 底稿、模型與工具，只改顧問指引。兩題各重複兩次，其中三對兩組都完成：

| 共同完成的三對 | 舊指引 | 理解足夠便停止深入 |
|---|---:|---:|
| 生成請求累計 input tokens | 199,594 | 87,353 |
| 讀取工具呼叫 | 23 | 3 |
| 指定核心事實判準 | 33／33 | 33／33 |

輸入降幅為 `(199594 − 87353) / 199594 = 56.23%`。這裡的 input 是各次請求的實報輸入加總，含重送與快取部分，不是單次 Context 大小。共同完成子集用來避免把舊組未交付的消耗當成全部改善；完整四對仍須保留：舊組交付 3／4、新組 4／4，累計 input 分別為 322,388 與 128,762，讀取 37 與 5 次。

**這項比較支持明確的充分性停止規則能減少冗餘取讀，同時保留本次指定事實。**核心判準不含全部 JD 品質；[另列的語意審查](../../experiments/product-validation/data/memory-reading-policy-2026-10-04/semantic-review.md)仍記錄同任務跨欄位不一致及一處候選來源例外問題。本次不是三層與單層的對照，也沒有驗證超容量後的整體優勢。

### 本次採用：避免不必要的跨案數值副本

[局部修訂實驗](../../experiments/product-validation/data/memory-local-preservation-2026-10-05/results.md)另外回答維護問題：網站甲的期限由 24 小時更正為 48 小時後，舊指引修了甲，卻在乙的理解留下「甲的 24 小時不適用」；候選移除了這段不必要的比較。倉庫案例兩組都保留必要條件，候選也移除了多餘跨案比較。這是兩個 B2 配對各一次的局部證據，不把未發生錯誤的倉庫控制組算成失敗。

依此只將兩句規則加入[正式 B2 提示](../../../apps/api/src/caliburn/agents/work_understanding_analyst/instructions.py)：本項不需要他案條件就不複製他案數值；必要比較則核對雙方最新事實及來源，正文、標題與描述一起維護。完整工作本來需要的責任、期限及未知不因此刪除。沒有替換整份實驗提示，A、B1、工具、快照及恢復流程不變。

角色接線、Memory 工具及完成契約共 25 項測試通過；Ruff 檢查與格式檢查通過。它們驗證提示能沿既有接線使用，不能代替語意品質。這兩句與其餘正式提示組合後尚未重跑真模型；本次沒有新增付費請求，也未重啟服務。採用及檢查紀錄見[執行紀錄](../../experiments/product-validation/data/memory-local-preservation-2026-10-05/execution-notes.md#後續採用2026-10-05)。

下一個效率問題先做離線 Context 投影，定位工具契約、導覽及重送的負擔；只有確認具體冗餘才改。需要驗證新效果時再凍結單一變因，不反覆調整所有角色或重跑已回答的題目。
