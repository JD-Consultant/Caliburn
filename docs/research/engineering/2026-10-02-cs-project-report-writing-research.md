# 資工專題報告的內容與證據設計研究

查閱日期：2026-10-02。用途：為 Caliburn 的[專題報告](../../reports/project-report/README.md)選擇內容、敘事及驗證呈現方式，不改產品契約。

本次整理的寫作定位是：以論文的論證方式撰寫系統型資工專題，讓讀者理解問題、關鍵設計、驗證結果與作者判斷；不是將開發文件改成正式語氣，也不把備審專題套成學位論文。來源考察保留在前半部，可直接執行的準則見[文體與章節](#專題與論文的文體及章節)、[段落與成果表達](#段落與成果的寫法)、[格式與引用](#格式圖表與引用)、[整稿與審核程序](#整稿與分面向審核程序)。

## 研究問題與範圍

本次研究如何呈現專題的問題價值、技術貢獻與作者的研究能力，讓讀者能看見設計者如何界定問題、比較方法、完成詳細設計，以及根據實驗作取捨。資料選自臺大、清大、陽明交大、成大、劍橋及 Stanford 的系所公告、課程要求與公開作品。不同文件的適用範圍分開標示；課程要求不是全系共識，專題競賽辦法也不是碩士甄試評分表。

本次取得正式格式與競賽辦法、課程研究要求、專題簡介、附批註作業及課程評選的優秀完整報告。以下是可借鑑的證據，不是各校的統一規則。校名提供來源背景，實際採用仍看內容與 Caliburn 的適合程度。

## 成果呈現的第二輪修訂

初稿將內部審核語氣帶入正文，反覆列出沒有主張過的事情，例如未提出新基礎模型、未證明優於所有方案。這使成果與設計理由被免責式句子打斷。提出者指出問題後，本輪重讀上述作品的摘要與緒論，調整敘事重心。

Ryan 的報告先提出個人化需求、方法及具體結果，評估範圍隨實驗交代。CapNet 也先使讀者理解受益者、問題與方案，再呈現量化及定性發現。兩篇都明確介紹自己的工作，並未用假設中的全能標準評價自己。這裡借鑑的是報告結構與表達方式。

當時的成果呈現修訂採以下寫法；個人分工部分已依後續決定移出正文：

- 摘要先說完成的系統、關鍵方法及代表結果；緒論新增主要貢獻，讓讀者先掌握技術價值。
- 演進案例以「問題、追查、取捨、設計影響」組織。未採用的方案用來說明決策，避免將整段寫成失敗清單。
- 實驗章保留樣本、模型、指標及版本；重要條件貼近相應結果，跨實驗的限制集中於討論，不逐段重複。
- 個人分工材料具體記錄資料庫、資料流、版本、生命週期、Context、工具及恢復設計，另交代 AI 依規格實作；後續依團隊報告定位改由內部編輯紀錄保存。
- 結論收束已完成成果與後續研究問題，刪除與本專題定位無關的自我否定。

修訂沒有調高數字、補造真人成效或刪除已知品質問題。正文保留能力提煉與漏引案例、長旅程採重新發起方式續跑、真模型與替身測試的區別；排程待決及歷史環境追查等維護細節由原證據與架構報告承接。

以下是本次綜合判斷，不是上述學校共同指定的章節。

|---|---|---|
| 動機與問題 | 誰遇到什麼困難，原做法哪裡不足 | 由訪談顧問公司所了解的痛點與需求切入；3–4 小時為該訪談中了解的作業情境。依清大內容要求、交大緒論批註 |
| 相關方法 | 理解了哪些方法，為何沒有直接套用 | 比較職務分析、檢索、Context 與持久 Memory 的用途；不把列框架名稱當文獻探討。依清大格式、臺大研究課程 |
| 設計與技術 | 如何將問題變成具體的系統與資料規則 | 以同一合成案例解釋原話、情境、理解、JD；說明資料流、版本、候選及完成邊界。借鑑臺大教學文章與成大架構要求 |
| 演進與取捨 | 遇到反例後如何改變判斷 | 精選檢索、否定範圍、兩階段評估、提示指引案例；不把每次 commit 當一項研究貢獻。依臺大比較要求、交大程式分析批註 |
| 實驗方法 | 比較條件、指標與資料是否足以支持結論 | 區分歷史實驗、同批合成人設比較、真資料庫及長旅程。說明指標算法與不足。依臺大公平比較及成大測量範例 |
| 結果與失敗 | 哪些觀察支持改善，哪些沒有 | 同時呈現增加指示後 K/S 冗餘、後續收窄失敗、採用版本的改善及殘留漏引；不只報最好的一批 |
| 個人材料與團隊正文的界線 | 團隊成果如何呈現，個人分工另如何說明 | 正文談團隊的問題、設計及成果；已確認的個人詳細設計與開發協作留在編輯紀錄。交大、清大特定課程要求分工，不代表本篇必須設個人章；是否另附依實際送件要求處理 |
| 限制與未來工作 | 知道現有證據不能回答什麼嗎 | 分清工程正確性、模型分析品質及真人效果；提出可測的後續問題，而不是泛稱未來更智慧 |
| 圖表與可讀性 | 不熟悉 repo 的人能否讀懂 | 每圖只回答一個問題；引用已有圖稿，不混入開發修正日誌；數字保留分母、版本與直接來源。依成大簡介及交大批註 |

## 報告組織與不採用的做法

採一篇可連續閱讀的團隊主報告，正文依「問題—方法—設計—實驗—討論—結論」展開；團隊技術貢獻在緒論先說明，再由後文支持。細節由現有架構報告、指南與原始證據承接；另設編輯檢核頁記錄個人分工、未補資料及本次審核，不把待辦混進教授正文。

不新增一套產品規格，不逐頁搬開發文件，不堆測試總數證明模型品質，不把歷史成功片段接成不存在的一次完整實驗。各實驗的基準保留在引用處；更換架構後，舊實驗仍是舊架構的證據。

目前尚缺真人前後對照、專業顧問盲評與完整團隊署名資料。報告可以先完成論證及內容初稿，但不能因此宣稱已符合實際送件格式、所有成員已確認分工，或已證明節省訪談時間。

## 專題與論文的文體及章節

### 先分清交付的是什麼

以下是綜合上述指引後，對本案採用的分類，不是學校統一命名。

| 文體 | 核心任務 | Caliburn 如何使用 |
|---|---|---|
| 系統型專題報告 | 說明需求如何轉成設計、實作與可檢查的成果，呈現取捨與作者能力 | 本次完整主稿的定位；工程設計及實驗分析都是內容，不只列功能 |
| 研究論文 | 圍繞明確問題或技術主張，交代方法及支持它的證據 | 借鑑論證方式；若日後投稿，再收斂為特定研究問題，不以更長或更多術語冒充研究深度 |
| 學位論文 | 完整呈現學位研究，並符合授予學校的程序與格式 | 借鑑章節完整性，不加上不存在的口試審定、學位或校方核定資訊 |

正文的目標讀者是具有資工背景、但未參與本專案的教師。不能要求讀者先讀 repo，才看得懂三層記憶、候選工作稿或一次模型執行。重要概念在首次使用時定義，產品示例採相同資料一路說明，詳細工程契約放附錄或架構報告。

### 先定主張再排章節

Caliburn 可用以下敘事主線組織既有材料：

> 從顧問公司的訪談需求出發，設計能持續累積工作理解、保留來源並支援修訂的 AI 訪談系統；透過反例追查、指引比較與長旅程，檢查設計如何影響分析及交付。

這是報告主線，不是新增實驗結論。每項主要貢獻都要連到「為何需要、如何設計、用什麼材料檢查」；不用每個功能各寫一項貢獻，也不必替套件原有能力宣稱原創。工程設計可由資料行為、實作與測試說明；涉及品質或效率改善的比較，才以相應實驗支持。若未量測時間，不將設計上減輕負擔的目的寫成已量得的節時效果。

本案建議採以下內容配置。章數可隨篇幅合併，章節職責不混淆：

| 部分 | 必須回答 | 本案材料與寫法 |
|---|---|---|
| 題名與摘要 | 做了什麼、為何值得讀、得到什麼結果 | 題名點出職務訪談與關鍵方法；摘要用問題、方法、代表結果及意義形成一段完整概覽 |
| 一 緒論 | 誰的問題、困難在哪、本文完成什麼 | 顧問公司訪談、跨輪語意、長期分析與依據變更；區分產品目標、本文檢視的問題、主要貢獻 |
| 二 背景與相關方法 | 前人提供什麼，本案為何還需要這個設計 | 依工作分析、資訊取得、分析記憶及可追溯編輯分組比較，不逐篇摘要或逐項介紹框架 |
| 三 系統設計與關鍵取捨 | 機制怎麼運作，為何如此選擇 | 先給整體資料流，再解釋分層、Context／工具、快照引用與編輯生命週期；將關鍵反例放在相應選擇旁，完整沿革留在附錄 |
| 四 實驗方法 | 如何檢查前述問題，別人如何核對 | 分清程式正確性、模型分析品質及長旅程；交代資料、人設、模型、比較條件、指標及判讀方式 |

| 六 討論 | 結果對設計有何意義，下一個值得研究的問題是什麼 | 分析效果與代價，集中交代影響解讀的範圍；將未透露工作與訪談收束轉成具體研究方向 |
| 七 結論 | 專題留下了什麼成果與認識 | 回答緒論，收束系統成果、設計認識及代表發現；不在此首次加入新數字，不重抄摘要 |
| 另備的個人材料 | 作者親自決定、設計、判讀了什麼 | 不列入團隊主報告。先於內部編輯紀錄保留已確認的詳細設計、審核與協作事實；後續備審需要時另行撰寫 |
| 參考文獻與附錄 | 方法從哪裡來，細節如何回查 | 外部方法使用正式書目；本專題資料另列有名稱的實驗附錄。核心結論不能只放在附錄 |

這份配置對應 MIT 對[資工方法](https://mitcommlab.mit.edu/eecs/commkit/journal-article-methods-cs/)與[結果](https://mitcommlab.mit.edu/eecs/commkit/journal-article-results/)的區分，再依 Caliburn 的系統型題目調整。並非規定每份專題都要七章，也不因研究範例使用模型訓練，就替本案加入不存在的訓練程序。

## 段落與成果的寫法

### 用可追查的判斷呈現能力

教師能從報告評估的能力，應由具體工作呈現：能否界定問題、比較方法、設計完整機制、追查異常、解讀實驗，以及清楚交代自己的貢獻。這是由清大、陽明交大及 Stanford 上述要求歸納出的編寫重點，不是對個別教授錄取決策的預測。

同一段通常先提出要說明的問題或發現，接著給方法、例子或數據，再說明它改變了什麼判斷。實際行文不必每段都貼「問題／方法／結果」標籤；標籤只用於編輯檢查。不要只寫「發現問題後修改程式」，應讓讀者看懂如何排除其他原因，以及為何選這個修正。

例如部分回答診斷可用下列方式組織；後續整稿已將此寫法用於正文 §3.4，並保留原資料連結及比較條件：

> 在跨輪回答的診斷中，顧問同時詢問兩種工作情境，員工只表示其中一種尚未處理過，記憶整理卻將兩者都記成沒有經驗。回查模型請求可確認八則原始訊息均已提供；再沿抽取與整併結果追查，第一個錯誤出現在抽取階段。這項診斷將修正方向從補送資料轉向回答範圍的解讀，也說明保留可追溯中間結果的必要性。

這段讓讀者看見診斷方法，不需要在句首放日期或自評「具備研究能力」。若接著介紹改動及效果，仍應保留該次比較的條件，不能把單一反例的改善寫成整體問題已消失。

### 摘要與緒論要讓成果先被看見

摘要交代具體問題、核心方法、代表成果及意義；技術名稱只留理解主張所需的部分。緒論再展開需求來源、為何既有做法不足及主要貢獻，而不是複製摘要。[MIT 摘要](https://mitcommlab.mit.edu/eecs/commkit/abstract/)及[緒論指引](https://mitcommlab.mit.edu/eecs/commkit/journal-article-introduction/)都要求把工作價值說清楚，但未要求以誇大的形容詞吸引讀者。

對本案，具體寫出資料層、引用與生命週期如何支援持續分析，比「創新整合多個 AI Agent」更能顯示設計內容。摘要可以放已核實的比較結果；樣本條件用一句話交代，其餘方法留到實驗章，不在摘要放多份任務紀錄的完成狀態。

### 相關工作比較方法而非堆來源

每組文獻先說共同處理的問題，再比較其資訊表示、使用條件或限制，最後說明本案借用及調整的部分。框架官方文件可支持 API 或機制描述，不能單靠框架文件證明整套分析方法的效果。專案內的研究摘要是找來源的入口，正式書目應回到讀過的原論文或官方文件。

後來查到的文獻可以用來比較現有設計，不應寫成當初已依該文獻決策。研究啟發、採用機制與事後對照三者要分清楚。

### 結果先陳述觀察再解釋意義

結果段落說清楚比較對象、指標、數值及直接觀察；若原因尚只是推測，放在討論並以待驗的解釋呈現。工程測試回答規則是否成立，訪談輸出回答分析表現，兩者可以互補，不能用測試總數替代 JD 品質。這是本案依 [CS224N 報告指引](https://web.stanford.edu/class/archive/cs/cs224n/cs224n.1204/project/project-report-instructions.pdf)及已有證據作的評估分工。

採用版本與中間候選要用讀者能理解的名稱，例如「原指引」「加入能力寫入指示」「最終採用指引」。原代號可在方法表附一次，正文不要求讀者記住 c0、c1、c3 或任務編號。長旅程則先說驗證目的和結果，事故修復命令留在原始紀錄。

### 把限制寫成研究判斷

先明確呈現已完成的成果，再交代會影響結論的條件，以及由此形成的下一步。與數字直接相關的條件放在方法或表註；跨實驗的適用範圍集中在討論。不要重複列出從未主張過的能力，也不要刪除會改變結論的反例。這種寫法與 [MIT 討論章指引](https://mitcommlab.mit.edu/eecs/commkit/journal-article-discussion/)一致。

例如能力欄位增加卻接近任務重述，是一項有用發現：它揭露填寫率與內容品質不同，並支持捨棄該提示的決定。可以把它寫成方法選擇的依據，不必包裝成所有嘗試都成功。至於員工從未提及的重要工作，應保留為核心難題；說明目前的探問策略及可觀察成果，再提出如何評估完整性，不將仍在研究的收束條件列成已完成貢獻。

### 日期 用詞與作者聲音

- 日期只有在界定實驗、版本或時間變化時放正文；一般診斷先講問題。原始證據保留日期，並不因正文省略月份而失去可追溯性。
- 團隊正文以「本專題」「系統」為主，需要時以「我們」說明團隊研究行為；不混入個人能力自評。「本人」及開發協作留給獨立個人材料，不把未列出分工改寫為人工獨立完成。
- 專有概念先定義再使用，例如工作情境、工作理解、發布快照；沿用同一名稱，不為避免重複而任意換同義詞。
- 描述設計、已執行實驗及未來工作時，分別使用「採用／由……負責」「在測試中觀察到」「後續將評估」等能辨識狀態的語句。
- 少用未定義的「完整」「高效」「穩定」「顯著」。有衡量時寫出判準；「統計顯著」須有相應檢定，不能只是肉眼看起來改善。

以上是本報告的編輯約定，不是禁止日期、第一人稱或特定詞語的通則。

## 格式圖表與引用

### 格式依用途決定

### 圖表要有閱讀任務

[MIT 圖表指引](https://mitcommlab.mit.edu/eecs/commkit/figure-design/)主張每圖有清楚主訊息。本案的設計圖用來解釋機制，結果圖用來呈現觀察，介面截圖用來展示操作；不能互相當成驗證。

圖表各自連續編號；本稿採表題在上、圖說在下的統一慣例。結果表列比較條件、樣本單位、分母與單位，圖的座標及縮放不得掩蓋差異。若只有少量測次，保留各次值或範圍通常比只有平均數更有資訊；缺少變異量時不得補造誤差棒。表內數字由文字解釋重點，不逐格複述。

### 外部文獻與專案證據分開整理

正式版採一致的數字編號引用，將作者或機構、題名、年份、出版來源、DOI 或網址整理完整。動態官方文件保留必要版本，查閱日期留於內部研究紀錄；依本次偏好，公開主稿不逐筆列查閱日期。若實際模板要求其他格式，再統一轉換。這是本案選擇，並非資工領域只有一種格式。

外部研究引用原始資料；借用或改繪圖片明示來源。自己產生的實驗圖表則說明資料與方法。repo 中的逐字稿、CSV、測試證據與設計紀錄，依主稿主題集中於內部編輯紀錄，不和學術文獻混成沒有分類的連結清單。報告附錄則直接說明必要的示例與實驗範圍。主要論證必須自足，不能要求教授開啟本機路徑才能判讀結果。

引用與書目須逐項核對；不能只因 BibTeX 或網址看起來正式就直接採用。[Widom 的技術寫作建議](https://cs.stanford.edu/people/widom/paper-writing.html)特別提醒書目完整性及圖文的一致呈現。

### 成品檢查

PDF 產出後按實際頁面閱讀，檢查中文、圖中文字、跨頁表格、圖說、頁碼與目次；再檢查文字選取、搜尋及連結。螢幕與列印尺度都要能讀，不把原始 Markdown 通過連結檢查當成排版完成。成大圖書館也要求轉檔後檢查圖表及文字是否移位；本案另保留電子閱讀的檢查。

## 整稿與分面向審核程序

先完成論證再潤飾句子，最後才排版。本案採以下順序：

1. 從原證據整理主要成果、對應問題與可支持的結論，先選代表圖表及案例。
2. 寫出章節各自要回答的問題，去除重複段落；將操作日誌移到原證據，不新增另一套數據。
3. 先寫方法、實驗設定與結果，再回寫緒論及結論，最後精修摘要，使前後主張一致。
4. 分面向審核，再做全文連讀；修正優先序是事實與論證、結構、措辭、版面。
5. 製作送件版本及 PDF，確認正文自足、參考資料可辨識，保留完整稿的證據路徑。

| 審核面向 | 檢查問題 |
|---|---|
| 問題與貢獻 | 讀完緒論能否說出需求來源、真正難點及作者完成了什麼？核心問題是否在後文獲得回應？ |
| 方法與取捨 | 是否說明資料流、關鍵規則與選擇理由？能否分清成熟機制、自己設計及未採用方案？ |

- **分開保存與呈現。**公版全文與候選來源可留在模型視窗之外，模型先取得能判斷下一步的導覽，再取得所選範圍。這是未來公版研究的方向，不改變現行 A 已確認的近期訪談預載規則。

- **以分析效果比較效率。**在相同候選與模型條件下，比較全文、摘要、導覽加按需讀取；同時量必要條件取得、跨輪延續、職責補問、單次及累計輸入量、工具往返與延遲。避免把少送 token 當成唯一最佳化目標。

### 書目與推論修正

1. 早期筆記以 Improving LLM-Generated Follow-Up Questions 稱呼 arXiv:2509.12709，但正式題名是上表的 Harnessing the Power of AI in Qualitative Research。主稿採正式名稱，原始筆記保留作歷史，不無聲改寫。
2. AI Conversational Interviewing 的原文指出某項追問規則的違反有 88% 歸於 AI；這不同於「AI 所有錯誤的 88% 是追問不足」。早期紀錄的分母表述不一致，本次主稿不引用該百分比，也不據此宣稱缺少狀態機是經實驗證實的成因。
3. 早期相似度研究將窄分數帶直接歸因於各向異性，超出本次可核實範圍。正文改為「研究曾參考此議題，實際判斷仍以本地配對與校準為準」，保留有資料支持的前處理與誤合併反例。
4. ALCE 的 citation precision 不要求引用集合絕對最小；它辨認不相關引用。正文不將「不得有任何重複支持」說成該文規範，也不混同引用存在檢查與 NLI 支持度評估。
5. LongMemEval 與 Lost in the Middle 在早期 Context 審查已有紀錄。前節的新增是報告書目整理，不是首次研究；採用的是問題分類及設計考量，未宣稱重現公開基準。

研究對照服務於報告論證，不把每篇論文變成一個產品元件。主稿新增五筆正式書目並按首次引用重排為 [1]–[20]；既有成果、實驗條件與產品狀態不因這次補寫改變。

### 敘事與格式取捨

- **成果先行。**摘要及結論先講已完成的方法、產物與代表數據；不以未曾主張的「全面勝過所有方案」標準反覆自我評價。
- **問題服務於貢獻。**保留能說明診斷方法與設計選擇的反例，用「如何定位、據此作何判斷」組織；一般環境事故及待辦項目留在工程證據。
- **範圍集中交代。**方法說明合成人設、探索式迭代及判準；附錄保留歷史版本與特殊驗證範圍。讀者判斷主要成果需要的差異仍留在正文或表註。
- **團隊技術報告。**維持七章、編號引用、圖表標題及兩份附錄；個人分工、AI 開發協作及內部紀錄不混入主稿。材料的引用路徑由內部 review 保存。
- **先定內容，再排版。**Markdown 是單一主稿；PDF 階段再加入署名、目次、頁碼、交互參照及版面檢查。現階段不產生假頁數或宣稱已符合成大送件格式。
- **包裝落在選材與論證。**刪去重複自辯及無關故障，增加實際成品和有判斷力的取捨；不把歷史探針、合成比較或預期成效改寫成已完成的真人驗證。

本輪新增的寫作來源只留在本頁。主稿的技術書目仍依實際採用研究及後續方法安排，不將寫作指引塞進產品相關研究。

## 前期檢索實驗與 Agent Harness 的取材

本輪按使用者補充，回查相似度、灰區與重排序研究，將「已完成的前期研究」和「尚未整合的訪談完整性方法」連成可閱讀的研究脈絡。寫法沿本頁既定的系統型專題原則：正文呈現發現與設計取捨，附錄交代資料、單位、門檻和數據；不把尚未接入現行 App 的方法寫成產品成果。

- [最終校準紀錄](../retrieval/2026-07-04-similarity-matching-calibration.md)保留三組職類、四類主要內容的高分／灰區配對數；[前期研究](../retrieval/2026-07-02-multi-ocs-candidate-dedup-research.md)另有門檻調整與 20 對重排序試驗。主稿 B.7 說明餘弦分數、高低門檻及候選量，不將配對數當準確率；不同批次間還有身分碰撞修正，故不計單純門檻改善率。
- 主稿 §6.3 把前期研究轉為下一階段問題：檢索到相關職務後，如何讀取尚未談及的面向、確認適用性，再讓員工回答。以「相似」取得候選，與判定員工「確實負責」分開；多份參考、按需導覽及未參與調整資料的評估仍屬後續研究。
