# 公版檢索的輸入、有效輸出與相關性評判研究

日期與來源查閱：2026-10-04。狀態：**研究／候選；五案四組第一輪已執行，正式評分／檢索方案未定，未接 JD App**。

結論：檢索評估的對照答案通常是一組「需求—文件—相關性」標註，不是一個唯一職稱或一份指定公版。標註需要明確的用途、正文證據與評分準則；cosine、reranker 分數或原始生成文件不自行成為語意真值。沒有真人資料時可以做合成案例及 LLM 評判，先比較候選方案；其分數描述固定案例與評審下的表現，不能直接代表真人工作涵蓋率。

本題先解決「如何判斷員工工作搜尋出的公版參考有用、是否保留已知工作支持」。顧問能否藉公版找到未知工作、判斷 JD 收尾與交付 PDF 的品質，仍屬後續驗證。單項 JD 任務完整度機制維持暫緩。本研究不指定新 DB、API、schema 或決策模型。

## 1. 業界的評估基礎與其效力

下表分開官方方法、研究結果與 Caliburn 的映射。官方評估方法不等於所有產品適用的單一規範；歷史 TREC 任務的評分定義也不直接當成今日所有檢索任務的契約。

| 來源 | 直接支持的做法 | 本案可用之處與限制 |
|---|---|---|
| [NIST TREC 相關性定義](https://trec.nist.gov/data/reljudge_eng.html) | 該歷史評測以內容是否對資訊需求有用來判相關，透過 pooling 建立 qrels；文件局部有用也可判相關。 | 公版含一項有用工作，不需要整個職位都適用；但局部相關不能直接升格成整體目錄適用。 |
| [BEIR 官方專案](https://github.com/beir-cellar/beir)、[評分原碼](https://raw.githubusercontent.com/beir-cellar/beir/main/beir/retrieval/evaluation.py) | 分開 corpus、queries、qrels 與檢索結果，計算 Recall、Precision、nDCG、MAP，另支援 MRR 及 holes。 | 可沿用成熟指標與資料分工。通用 benchmark 不能代替 OCS／iCAP 與員工工作之間的業務標註；本輪未安裝或跑 BEIR。原碼為查閱日 main，沒有宣稱已鎖定執行版本。 |
| [Azure Databricks AI Search 評估](https://learn.microsoft.com/en-us/azure/databricks/ai-search/retrieval-quality-eval) | Beta 功能從文件生成查詢，比較 ANN、hybrid、全文與有／無 reranker，由 LLM 逐對給 0–3 分，保存指標與信賴區間。 | 合成與自動評判是公開實務選項，不必等真人資料才能試選。但工具公開能力不保證本案的語意判定正確，也不代表採用其服務或主指標。 |
| [Microsoft Foundry RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators) | 分開有 qrels 的 Document Retrieval 與沒有真值時的 LLM Retrieval 評分；Holes 記錄缺少相關性標註的文件。 | 區分「相對固定答案的找回」與「模型認為回傳內容有用」，同時報未標註率。 |
| [Qdrant retrieval relevance](https://qdrant.tech/documentation/search-evaluation/retrieval-relevance/) | 可由專家、使用者紀錄或合成查詢建標註；提醒來源措辭、重複文件與語料漂移可能扭曲分數。 | 保留公版快照與完整標註來源。從公版生成案例可作基線，但不足以推定真實輸入品質。 |
| [Ragas Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)、[Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) | Recall 需要參考資訊或參考來源；部分無參考答案的內容指標用生成回答作對照。 | 不把「沒有真人」混同「沒有任何對照」；也不以回答自我對照代替員工工作支持標註。該 Context Precision 的排名加權形式不直接當普通 P@K。 |
| [NIST pooling／sampling 研究](https://www.nist.gov/publications/comparison-pooled-and-sampled-relevance-judgments-trec-2006-terabyte-track) | 比較合併候選池與額外抽樣標註；不同標註範圍可能改變系統排序。 | 多方法候選池能減少工作量，但仍可能漏有效來源，宜另查／抽查池外資料。這是方法證據，不是完整召回保證。 |

LLM 評審的公開研究有分歧：[TREC 2024 RAG 資料](https://trec.nist.gov/data/rag2024.html)保留不同人工／LLM 輔助條件；[2024 大規模研究](https://arxiv.org/abs/2411.08275)在 77 個 run、19 個團隊中觀察到自動與人工評分所產生的系統排序高度相關；[Soboroff 2025 論文](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=958495)則指出用模型製造答案會將評估約束到該模型的判斷。後者明示是作者觀點，不是 NIST 或政府的政策。系統排序相關不代表每個員工—公版判斷都正確，兩者均不能作本案已驗證的證據。

## 2. 輸入對應的是可接受參考集合

傳統測試集合包括固定文件、固定資訊需求、相關性標註。對 Caliburn 而言，研究候選映射如下：

- **固定需求**：同一員工快照中的實際工作、本人責任、條件及否定；合成案例由先固定的工作事實表提供依據，真實案例則沿訪談來源核對。
- **查詢表示**：原話、B2 正文或保留脈絡的分段，是傳達同一需求的候選方式。比較表示時不能跟著較差摘要刪掉對照中的工作。
- **可接受輸出**：能支持該工作需求的多份公版與其有效範圍。原始生成來源只是一個已知有效例，不是唯一容許答案。
- **檢索結果**：每步實際取得的來源、排名、分數、查詢邊與正文。相關性標籤與搜尋模型分數分開。

標註評審需看固定工作需求及公版正文；不以職稱、cosine、rerank 分數、另一方法名次或「本案例從這份公版生成」作理由。工具、產業或名詞相同，仍需核對工作目的、動作、對象及責任範圍。兩份不同公版都能支持時，兩份都可以有效。

## 3. 建議討論的正文相關性準則

下表是 **Caliburn 候選**，參考公開的分級方式後依用途改寫，尚未成為正式評分規範。分數評某個工作需求與某份公版的內容關係，不代表整個公版職位是員工職稱。

| 分數 | 候選判準 |
|---|---|
| 3：直接有用 | 正文提供與該工作面向直接對應的任務／動作，可指出相符範圍及證據；不需要靠補造本人職責才能成立。 |
| 2：部分有用 | 正文對其中一部分工作有具體參考價值，但支持範圍有限，需明列支持與未支持的部分。 |
| 1：僅主題接近 | 同領域或名詞相近，尚找不到對該工作有用的具體正文。 |
| 0：沒有有效參考 | 內容無關，或只有不適用的工作、對象／責任關係，沒有可支持的有效部分。 |
| 不確定 | 語意、來源或工作事實不足，或評審有未解分歧；獨立保存，不偷算成 0。 |

2／3 暫作有用候選分級，不是已選定的 cosine 或 logit 門檻，也不直接表示工作面向已完整涵蓋。若一個主題同時含備份與還原，而文件只支持備份，不能拿「2 分」自動證明還原支持也已找到。

每份評判紀錄應能回答：依據哪個固定員工來源、哪項工作需求、公版哪個版本及正文位置、哪些內容有用、哪些責任不適用、給分理由、評審及 rubric 版本、是否有分歧。內部 ID 與版本由程式綁定，評審選既有來源，不讓模型自造。

### 整體參考價值另判

正文能支持一項局部工作，不足以斷定整份職位目錄適合探索員工其他工作。另記錄「值得查整體目錄／目前只證明局部有用／不確定」，附其與主要工作、工作組合及責任範圍的理由。這個用途評判仍待顧問／領域核對，不能只按工作主題數、職稱或分數換算，也不在本輪增加正式 consumer 篩選模型。

公版有一部分被員工否定，其他部分仍可能有用；否定限制適用範圍，不自動排除整份文件。未提到的公版工作保持未知，不宣稱員工有做或沒做。

## 4. 一個示意案例

以下是方法說明，**不是新增實驗案例、真實員工或對實際公版的已完成標註**。

固定事實：員工開發後端 API；每週另作資料庫備份與測試還原；前端介面由同事負責。需要找能支持這些本人工作的公版參考。

| 假設公版正文 | 對哪項工作有用 | 判讀示意 |
|---|---|---|
| A 描述 API 介面實作及測試 | 後端 API | 該工作可給 3，保留支持範圍。 |
| B 描述資料庫備份、復原演練及紀錄 | 備份／測試還原 | 該工作可給 3；是否採其整體職位目錄仍另判。 |
| C 只泛稱「資訊系統維護」 | 尚無具體支持 | 1，不能因同屬資訊工作就當已涵蓋。 |
| D 僅描述前端介面實作 | 本人未負責 | 對此需求為 0；本示意假設沒有其他有效部分。 |

A＋B 可以滿足這兩個已知工作面向；若 E 的正文同時支持兩者，E 也可以，不必指定 A／B 才算正確。只有 A 而漏了所有備份／還原支持來源，表示已知支持漏失；回傳大量 C／D 不能補足。文件是否實際存在、語料是否有合適來源，必須在真實標註時核對。

## 5. 沒有真人資料時的三種評估選擇

| 方法 | 對照如何來 | 能回答什麼 | 主要限制 |
|---|---|---|---|
| A：來源生成案例 | 看過公版後生成工作描述，記錄支持來源。 | 已知來源能否找回；改動是否重現既有漏失。 | 措辭／情境可能接近答案；其他來源標註不完整。 |
| B：只有回傳內容的模型評分 | 固定需求及 rubric，由 LLM 判讀各結果。 | 各方案回傳內容被評審判有用的程度。 | 未取得的文件無法評，不能直接計全庫漏失或宣稱完整 recall；評審可能偏誤。 |
| C：固定案例與參考集合 | 先固定工作事實與原話，再獨立核對來源，凍結標註後比較方案。 | 已知支持涵蓋、已標註來源找回、相關性與成本的對照。 | 標註有成本，合成事實與模型來源判讀仍未經真人／領域驗證。 |

研究初始建議保留 A 作回歸、以 C 建立暫定對照，B 協助擴充與診斷。使用者後續確認先以評分比較，當前採 B 為主要研究方法；最新效力見 §9–10。原比較保留，不要求先完成 C 才能前進。

新案例生成步驟不提供待搜的 805 份公版、既有標註或期待公版 ID；可由獨立工作情境素材建立案例，明記哪些事實是合成。案例固定後才核對公版，不為了讓搜尋通過回頭改原話。模型預訓練可能已見過職業資料，因此「本次未提供公版」不等於證明完全沒有模型知識重疊。

先用少量案例建立較完整的來源標註：可全庫核對，或合併不同方法的候選池後逐份評判，補查池外來源。評審隱藏方法、分數與排名；兩次評判分歧、證據不足及來源含糊另存，不能只以一致投票製造真值。若採模型全庫標註，也仍是模型參考集合，不自稱專家真值。

評審本身先以明確支持、只同名詞、否定／他人負責、部分支持、跨兩份來源的例子測試；保存錯判、修訂及重跑範圍。不同模型或不同代理的同意只能提供一致性資訊，不能自動保證正確。

合成資料可先比較工程方案。真正的員工工作事實與職位目錄效用，後續在試用資料中確認，不能把「缺真人資料」誤寫成「完全不能做任何評估」。

## 6. 如何計分而不把涵蓋偷換成單一文件找回

| 指標／檢查 | 回答的問題 | 使用條件 |
|---|---|---|
| 每員工已標註工作支持保留 | 每個可由公版支持的已知工作面向，是否至少有一個有效來源留在集合？ | 按固定工作範圍與支持邊計數，不要求公版／JD 一對一。屬本案 coverage 指標，不冒充標準文件 Recall@K。 |
| 已標註文件 Recall@K | 預先確認有用的來源，在指定前 K 找回多少？ | 說明參考集合及其完整性；不把缺標文件直接當業務上的無關。 |
| Precision@K／未標註率 | 留下多少有用參考，多少結果仍無法判定？ | 所有回傳結果需有評判，或將未知率及只對已判資料的指標分開報，不能藏掉 holes。 |
| nDCG@K 等排名指標 | 高相關結果是否排前面？ | 需明確的相關性標籤及排名。多查詢合併若只有集合，不虛構全域排名；可先報單查詢與合併集合的不同指標。 |
| 廣蒐→精搜保留 | 初搜漏了，還是 rerank 才丟掉？ | 保存兩階段來源與支持邊，次要／低頻工作另外列出。 |
| 表示完整性 | Memory 相較固定工作事實，是否漏失、擴張或誤認本人責任？ | 與檢索失敗分開定位；不因 Memory 沒提到就縮小評估需求。 |
| 回傳量與時間 | 在相近支持品質下，哪種方式更省？ | 報查詢數、候選／rerank 比較數、去重文件、字元／實際 token、冷啟動／暖機與耗時；樣本不足不稱正式 p95。 |

無合適公版的實際工作另外報告，仍保留在員工事實中；資訊不足、未標註及確認無支持不同。參數在開發案例調整，最後驗收使用未參與調整的員工案例；已觀察的 22 個案例只作回歸。若對新來源補標，另存版本並以相同新對照重算所有被比較方法，不只補有利於某方法的分數。

本案成功標準與風險取捨需要依用途定義。公開資料支持以上評估方法，不提供通用的「cosine 到某值就正確」、固定 K 或所有產業共同的及格分。先保住固定資料中可核對的工作支持，再比較無用參考與成本，是目前已確認的研究方向；正式門檻仍未定。

## 7. 現有實驗可以宣稱到哪裡

本輪唯讀重算[固定案例](../../experiments/2026-10-04-retrieval-input-boundaries/cases-observed.json)中的支持文件 ID：22 個合成案例包含 16 個有支持標註的正例、6 個未評分控制；86 個工作主題的支持來源共 15 份去重公版。原 12 個正例 64 主題使用 10 份；新增 4 個正例 22 主題使用 7 份，兩批來源重疊。這是支持標註來源數，不是全部曾閱讀公版的數量。

[86／86 原結果](../../experiments/2026-10-04-retrieval-input-boundaries/README.md)檢查支持文件是否留在每員工的合併集合。它沒有驗收精準任務段落定位、所有回傳公版的相關性、語料中所有有效來源、真人工作涵蓋或 JD 收尾。原標註、分數、排名與封存原件保留；本研究不回寫它們，也不新增成功數據。

資料庫 ANN 與精確近鄰是否一致、內容檢索是否符合工作需求、顧問與 JD 輸出品質是不同驗證層。前輪 exact 核對不能被當成 ANN 參數已測；相關性支持保留也不能被當成顧問完整度判斷已通過。

## 9. 使用者確認：先以評分比較

2026-10-04，使用者表示「同意，那我們就以評分來評判，因為沒有答案」。目前的研究決定是採 0–3 分的正文相關性及證據判讀，比較回傳公版的有用程度；沒有預先的完整正確文件集合，也不要求先取得真人資料。已準備的[評分協定 v1](../../specs/2026-10-04-public-reference-scoring-protocol.md)保存準則、Prompt 草案、七個最小校準例及比較紀錄要求。

這個確認選定研究評估方法，不代表評審已校準、模型已執行、任一輸入勝出或全庫涵蓋已證明。全庫 Recall、真人職位判對率與 JD 收尾仍不宣稱；舊來源標註及封存回歸保留。評分準則以新協定維護，本研究保留來源、選項與演進。

## 10. 後續確認：代表主要職位、最終前五、不累積評分

使用者接著要求先寫多份固定員工需求並記錄，討論寫法；不同方法最後只比較最高五份公版。這輪目標是能代表主要工作的職位，局部兼任不管；全端工作可以由前端與後端共同代表。使用者並表示「3 > 多個 1」，分數分別列出，不用加起來。
