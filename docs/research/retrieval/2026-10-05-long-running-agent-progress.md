# 長任務 Agent 進度保存與公版核對研究

查閱日期：2026-10-05。狀態：研究／候選，未實作、未接 JD App，沒有新增模型實驗或費用。

接續狀態：上句及以下方案保留本研究當輪脈絡；後續已採用獨立 `excluded_work` 並完成[可選工具接線](../../experiments/engineering/README.md#角色接線)。使用者再次確認 JD 為總目標、工作任務可動態拆合與修訂；當前 state 提供時機與避免重問的候選比較見[接續研究](../agent-systems/2026-10-05-adaptive-jd-task-state-and-repeated-questions.md)。

後續確認（2026-10-05）：使用者將確認紀錄收斂為「確認事項＋員工回答來源」，其餘由顧問判斷，見[最新設計方向](../../specs/2026-10-04-public-reference-completion-design.md#最新確認只記確認事項與員工回答來源)。下文另存結論、接續事項或公版定位等做法保留為研究沿革，不再是第一版要求；有回答來源不自動代表事項已釐清。

**建議保留少量可查回的核對結果，先比較其價值，再決定是否建立專用進度機制。** 公開長任務設計常保存進度、未解問題與依據，但「增加待辦工具必然改善品質」並不成立。最新 Deep Agents 的直接消融甚至沒有發現待辦清單帶來顯著準確率增益。這支持縮小候選方案，不能推論所有進度資訊都可刪除。

## 本輪問題與有效邊界

- 題目：公版參考核對進度是否過重；目前處於官方證據與方案比較，不是施工。
- 使用者最新方向：顧問不確定能否收尾時按需搜尋，透過自然追問確認；取代前輪的員工選答候選。Memory 發布不是自動搜尋觸發。
- 已有邊界：公版只是客製 JD 的參考，公版與實際工作多對多；搜尋結果可改變；已有回答不能因排名變動便重置。單項任務完整度機制暫緩。
- 本輪不決定：新資料表、進度工具 schema、額外 Agent、完整收尾契約或 PDF 品質；獨立 RAG API 的既有實作不因此變更。
- 前輪底稿：[參考處理進度研究](2026-10-04-public-reference-progress-and-context-selection.md)、[收尾用途設計](../../specs/2026-10-04-public-reference-completion-design.md)。前輪選答及廣泛觸發敘述保留為歷史，不能當成本輪有效方向。

## 效果數據與不能混用的結論

### 待辦清單直接消融

[Deep Agents PR 4929](https://github.com/langchain-ai/deepagents/pull/4929) 於 2026-07-23 合併，比較是否啟用 `TodoListMiddleware`。這是待辦 prompt、工具及狀態通道一起有／無的比較，並非「保留所有資訊」對「完全失憶」。下表保留官方 `micro avg@3` 指標名稱，不能解讀為 JD 完成率。

| 模型 | 有待辦 micro avg@3 | 無待辦 micro avg@3 | 有待辦每 trial 費用 | 無待辦每 trial 費用 |
|---|---:|---:|---:|---:|
| GPT-5.6 Terra | 25.5% | 33.3% | US$0.585 | US$0.473 |
| Claude Opus 4.8 | 25.5% | 26.5% | US$1.347 | US$1.510 |
| GLM 5.2 | 3.9% | 5.9% | US$0.467 | US$0.464 |

作者結論是三個模型都沒有待辦帶來的統計顯著準確率增益，兩個模型使用待辦時 token 較多。成本方向並不一致。PR 摘要未充分呈現題數、信賴區間及全部取樣條件；不能宣稱無待辦普遍顯著更好，也不能推論跨天訪談的未解問題不必保存。

### 記憶與上下文整理的組合

[Anthropic context management](https://claude.com/blog/context-management)，2025-09-29：內部 agentic search 評估中，memory 加 context editing 相對 baseline 改善 39%，只有 context editing 改善 29%；另一個 100-turn 網搜評估由 context editing 降低 84% token。原文沒有完整揭露資料集、樣本量及統計。39% 是組合成效，不能寫成待辦增益、39 個百分點，或 Caliburn 可預期的收益。

[Anthropic 2026-03-24 harness 研究](https://www.anthropic.com/engineering/harness-design-long-running-apps)則記錄隨模型能力提高移除 sprint 分解，並主張逐一拿掉元件觀察效果。其早期遊戲開發案例完整 harness 約六小時／US$200，單代理約二十分鐘／US$9；品質觀察伴隨更大範圍與算力，不能當公平的進度機制效益實驗。

## Caliburn 的最小候選

目前 [B1 指示](../../../apps/api/src/caliburn/agents/work_situation_analyst/instructions.py)要求保留工作責任、未知與更正；[Memory 內容](../../../apps/api/src/caliburn/features/work_memory/models.py)沒有公版核對進度契約。工作事實可以已有來源，仍不表示 App 可查詢某次確認事項的狀態。

需要保留的是「哪些工作範圍已釐清、依據在哪、還缺什麼」，未證實需要完整公版任務管理系統。最小候選只在實際核對時保存少量資訊：

| 資訊 | 範例 |
|---|---|
| 確認範圍 | 員工是否負責正式環境部署 |
| 目前結果與依據 | 已釐清，由維運負責；引用員工正式訪談回答 |
| 尚待接續 | 測試環境是否由本人部署，尚未確認 |
| 必要參照 | 引出問題的固定公版位置；正文按需讀取 |

這些是候選資訊，不是正式 schema。App 已知的檔案、ID、版本及保存結果仍由 App 綁定；只保存簡短結果與來源，不重建一份員工事實或私有推理。既有訪談／Memory 仍是回答依據。進度是否採簡短文件、少量結構欄位或既有狀態承載，待驗證及 consumer 契約確認。

為限制負擔，先不為每份公版、每條任務及每一步建立狀態，不要求每次讀取都更新進度工具。搜尋輸入／結果版本屬可回查的執行證據，應先檢查既有保存能否承接，不因此設計第二套搜尋台帳。

下一次公版只換名次不重置回答；新公版可能對應同一已回答範圍，也可能有未涵蓋面向，由顧問依內容判讀。舊公版消失不刪未解問題。新回答若新增責任、更正或改變條件，須核對受影響範圍，即使 Memory 尚未發布或原回答 hash 沒變。App 不靠向量相似度自動宣告兩個問題等價。

按需提供未解事項及必要已釐清摘要，原文可查回。初次驗證不加入依 done 硬性隱藏來源的規則，避免無法分辨品質變化來自保存還是過濾。「此問題已釐清」不等於 JD 已寫入，也不等於整份 JD 已完整。

## 有限比較與退出條件

候選比較 A：現行 Memory、訪談讀取與接續；B：同樣能力加最小核對紀錄。兩組固定模型、檢索結果序列、訪談事實與任務目的，只改核對紀錄能力。採用相同情境及多次重跑，保留逐案結果，不先讓 B 取得 A 看不到的員工答案。

至少覆蓋：同範圍換公版、Memory 無關更新、責任更正尚未發布、部分責任、問題未回答、上下文壓縮／恢復、公版結果消失。更正後有理由的重核不算重問；評分者依固定員工事實及本輪材料判定，不能以 Agent 自填 done 作答案。

主要指標：不必要重問、遺失未解問題、無依據已釐清、錯誤收尾、相關更正後未重核。成本記全流程模型及工具呼叫、實際 token、費用、延遲、維護紀錄負擔；保存案例、版本、輸入、輸出與評分理由。

目前只能推薦 B 作最小候選，不能宣稱其效果優於 A。若 B 沒有穩定降低重問／漏接續，或增加誤結案、漏更正及不可接受成本，就縮減或不採用。若兩者均可可靠接續且成本相近，優先較簡單的方案。完整 JD／PDF 收尾品質仍需獨立驗證。

本輪 finding：公開做法支持保留必要接續資訊，不支持一律增加待辦管理；最新待辦消融是縮小設計的直接反例。下一步是討論最小核對紀錄及有限比較，尚未取得新付費外送或 production 整合授權。模型更新或實測反例可重開此取捨。

## 後續確認：沒做的工作另存，不放入 Memory 或檢索文字

2026-10-05，使用者在[否認輸入反例實測](../../experiments/2026-10-05-negated-work-retrieval/run-01/README.md)後明確指定：**Memory 不保存員工已確認沒做的工作；這些確認另行維護，不放入向量，但 LLM 可以讀取。** 這是已確認的內容分工方向，取代前一步「否認留在 Memory，搜尋時才過濾」的建議。以下尚未成為正式保存／工具契約，也未改 production；原實驗封存保留當時建議。

| 內容 | 保存及用途方向 |
|---|---|
| 員工確認負責的工作 | 由工作 Memory 整理，保留實際行動、工作對象、產出及適用條件；作搜尋來源，仍以主要責任為優先。 |
| 員工確認不負責的範圍 | 從工作 Memory 分離，另存精簡確認紀錄及回答來源；顧問可讀，embedding 與 rerank 的工作查詢皆不拼入這些否認描述。 |
| 原始訪談 | 原話及更正照原保存規則保留，作兩類內容的共同可回查依據；分離整理結果不刪改原始回答。 |

否認紀錄只需承載實際確認的責任範圍與依據，不必先擴充成每份公版的任務進度平台。例如「SEO 策略及排名追蹤不是本人職責」，可以跨搜尋結果沿用；不以該公版 ID 標記整份永遠不適用。是否增加有效條件、更新表示、專用工具或資料表，留待契約設計，不能從此表推成已完成接線。

分離須保留語意：員工說「退不退由採購決定，我只負責備貨和登記出貨」，Memory 保留「依採購已確認的退貨安排備貨及登記出貨」；另存「不負責決定是否向供應商退貨」及其原話來源。不能把整段刪掉，也不能因包含「退貨」就封鎖員工實際負責的退貨作業。

「不確定」「沒有回答」「暫時不想談」不是已確認沒做，不能寫入否認結論。本輪沒有決定所有未知的保存位置，也不把低頻但負責的工作刪除。否認紀錄只對當時確認的條件與範圍有效；Memory 無關更新或排名改變不重開，員工更正相關責任時則更新受影響的肯定／否認內容，不能讓兩邊同時保有互相矛盾的有效結論。

LLM 在判斷是否再次確認某範圍時須能取得對應否認紀錄，但不能把這份紀錄再串回正向搜尋 query。同一公版仍可能因其他工作被召回，因此「沒做的不進向量」不能保證某公版永遠不返回；顧問不應把該已否認範圍重新當未知，公版其他相關內容仍可使用。

下一步的比較對象相應調整：原話控制、既有 Memory 控制、肯定工作 Memory＋獨立否認紀錄候選。須用實際整理產物測主要工作涵蓋與否認干擾，再以顧問旅程測不必要重問及相關更正後是否正確接續；前輪人工已確認文字投影與原文相同，只是控制，不能當作新分工有效的驗收。本輪僅保存使用者確認方向，無新增模型呼叫。

## 再次調整：允許 Memory 保留，隔離搜尋輸入

2026-10-05，使用者隨後放寬為「或是可以保存，但是未影響向量資料庫，要想個辦法如何解決」。因此前節的「Memory 不可保存否認」不再是必要限制；現在的目標是保留顧問需要的確認內容，同時避免否認描述成為正向工作檢索依據。以下為方案比較及推薦，尚未選定正式新格式或實作。

現行[檢索服務](../../../apps/ocs-indexer/src/jd_ocs_indexer/references/service.py)只接收query，該文字同時送embedding與rerank；入庫的是公版向量，並未把員工Memory整份存入公版索引。需要改進的是Memory到query的組裝，不必因本題重建公版索引。Memory完整正文是否保存否認，與哪些字送到模型是兩個可分離的選擇。

| 方案 | 好處 | 成本及限制 |
|---|---|---|
| 顧問讀Memory，按需組出已確認主要工作query | 可沿現有獨立搜尋API，完整Memory保留，無需新增持久內容；顧問原本已有訪談脈絡。 | 抽取仍可能出錯；每次選擇或表述可能漂移，須保存實際query、來源及輸出來驗證。 |
| 同一Memory旁保存衍生的檢索文字 | 可固定文字、重用，容易驗哪段被送進模型。 | 須綁定來源版本，更新後重建；不能允許它和Memory各自手改、變成兩份事實。尚無必要先建立這個快取。 |
| 否認另建獨立紀錄 | 分離的輸入邊界明確，可供後續已確認事項管理。 | 增加跨資料同步及更正責任；既然使用者允許Memory保存，尚不必只為檢索另造保存系統。 |

**推薦先比較第一個方案**：顧問從本輪已讀且有來源的Memory及尚未整理的新更正，組出已確認主要工作的query，沿同一乾淨query完成embedding與rerank。完整Memory仍供LLM讀，包括否認、未知、責任界線；不要在rerank階段又把完整Memory拼回query。RAG服務維持不解讀Memory生命週期的獨立契約。若實測重複生成成本或不穩定性明顯，再評估第二個方案；兩者都不是把LLM抽取當成必然正確。

[LlamaIndex官方文件](https://developers.llamaindex.ai/python/framework/module_guides/loading/documents_and_nodes/usage_documents/#customizing-embedding-metadata-text)提供分別控制LLM與embedding可見metadata的機制，例如excluded_embed_metadata_keys；查閱於2026-10-05。這證明保存、LLM閱讀與embedding輸入可以分開設定，並不保證自動辨認否定。把文字留在body再只排除metadata也不會移除body中的否認；Caliburn無需為這個原則引入LlamaIndex。若未來採同物件分欄，仍須明確只序列化允許的工作欄位，不能將整個物件自動串接進query。

驗證至少區分以下四類：

1. 已確認的工作不變，只新增原本未確認項目的否認：正向工作集合及最終送出的query應不變；固定模型、語料及參數下，另核向量／排名是否在實作容許誤差內一致。
2. 否認原本被視為本人工作的責任：須移除或修正受影響工作，此時query改變是正確行為，不能要求所有否認永遠不影響排名。
3. 混合句「不決定退貨，只備貨登記」：查詢保留備貨登記及必要脈絡，不把否認轉成肯定，也不刪整個退貨工作。
4. 未知、別人負責、低頻有做、跨前後端主要工作：不補造本人責任，也不因抽取變短而漏掉真正主要面向。

機制測試可確認否認欄位／全文沒有被重新送入embedding與rerank；語意測試則要核查query是否忠實、主要工作是否涵蓋。向量仍可能找到含否認任務的混合公版，不能只用「該公版是否消失」判成功。顧問不重問還須單獨驗完整Memory中的確認是否被正確使用。本輪未新增模型呼叫、未改production或原實驗封存。
