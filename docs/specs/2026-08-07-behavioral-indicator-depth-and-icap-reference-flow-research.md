# 行為指標深度與 iCAP reference 流程研究

> **不重做的部分**：AI 輔助 Duty 的機制分辨（暫定框架 vs 歸納）、候選承載形狀三選項、
> reference 存取缺口，已由 [`2026-08-06-ai-assisted-duty-research.md`](2026-08-06-ai-assisted-duty-research.md)
> 處理。本研究只引用其結論，不重新論證。
> 方法論（混合式職務發現）由 [ADR 0055](../adr/0055-hybrid-job-discovery-and-ttop-formation.md) Accepted，亦不重做。

## 1. 為什麼現在做這份研究

owner 於 2026-08-07 提出四項與現行實作不符的觀察：

1. **行為指標（P）沒有被當成產品核心**，它與 O/K/S 平權，但 P 才是「這份 JD 的價值所在」；
2. **AI 提取的工作任務名稱過長**；
3. **缺漏檢查看不到 O/P/K/S**，等於不檢查一份 JD 是否完整；
4. **訪談中沒有進度感**，員工不知道走到哪裡。

並確立產品定位：**產出的是具有企業內部知識體系的職務說明書，公版是版型與下限，不是內容深度的標準。**
P 要具體到「去哪裡找什麼資料、怎麼分析、做成什麼報表」。

## 2. 一手證據：iCAP 全量統計（本 repo 首次）

來源：`apps/ocs-indexer/data/jd-json/` 全量 **908 檔**（2026-08-07 實測）。
先前的 ADR 0048 引用的是香港／新加坡／澳洲／美國 OPM 的資料，**本節是首次針對台灣 iCAP 語料的全量統計**。

重現指令見 §8。

| 指標 | 實測值 |
|---|---|
| 任務總數 | 8,347 |
| 工作任務名稱樣本 | 8,594 條 |
| 行為指標樣本 | 23,804 條 |
| **任務名稱字數** | 中位數 **8**、平均 10.6、90 百分位 16；≤10 字佔 **71.0%**、≤15 字佔 89.4% |
| **行為指標字數** | 中位數 **25**、平均 28.2、90 百分位 45 |
| 行為指標以「能」開頭 | 2,369／23,804 = **10.0%** |
| **行為指標含數值門檻** | 13／23,804 = **0.05%** |
| **沒有任何工作產出的任務** | 1,816／8,347 = **21.8%** |
| 每任務行為指標數 | 中位數 **3**、平均 2.9 |
| 每任務工作產出數 | 中位數 **1**、平均 1.2 |

### 2.1 P 是具體行為描述，不是數值判準

`企劃人員`（BAS1219-002v4，owner 提供的 PDF，2024/12/15）：

```
T1.1 企劃需求分析（工作產出欄空白）
  P1.1.1 蒐集組織產業現況與發展趨勢。
  P1.1.2 蒐集各類企劃類型、規範及注意事項與經費。
  P1.1.3 依組織服務項目定位及需求，分析所需資源及資訊。
```

`智慧製造導入顧問`（MPM2511-001v2）用另一種句式：

```
T1.1 訪談中高主管
  P1.1.1 能夠整合公司營運方向、製造管理需求及智慧製造趨勢，辨識智慧製造關鍵議題，
         發展切題的訪談大綱/問卷。
```

兩者都是**行為描述**，差別只在句式；後者帶質性的品質意涵（「以確保所有的議題資訊皆可完整被收集」），
但**不是數值判準**。全量 23,804 條中含數值門檻者 13 條（0.05%），實質為零——
這與 ADR 0048 決定 23（四個政府體系數值門檻皆為 0）一致，且首次有台灣本地數據佐證。

**直述句是主流**：以「能」開頭者僅 10.0%。

### 2.2 任務名稱與行為指標是 3 倍篇幅差

任務名稱中位數 8 字，行為指標中位數 25 字。兩者職責不同：

| 欄位 | 官方實例 | 字數 |
|---|---|---|
| 工作任務 | `企劃需求分析`／`訪談中高主管`／`材料準備` | 4–9 |
| 行為指標 | `依組織服務項目定位及需求，分析所需資源及資訊。` | 22 |
| 工作產出 | `企劃書`／`企劃資源清單`／`訪談大綱/問卷` | 3–8（名詞） |

### 2.3 五分之一的任務沒有工作產出

1,816／8,347（21.8%）。`裝修木工助理` T1.1「材料準備」只有 P1.1.1，無任何 O。
這與 ADR 0048 決定 19 及 ADR 0058 引用的官方規則（操作性任務可不列 O，成果併入 P 的描述）一致。

**結論：缺漏檢查不得把「任務沒有工作產出」列為缺漏**，否則比官方嚴格，會逼員工為操作性任務硬掰產出。

### 2.4 K/S 是名詞化的能力，不是動作句

`智慧製造導入顧問` T1.1 的 S：`策略管理能力`／`問題/議題掌握能力`／`訪談技巧`／`跨部門/對外溝通能力`。
`企劃人員` 的 S：`資料蒐集及判斷能力`／`資料分析能力`／`溝通協調能力`／`表達技巧`。

形狀是「名詞＋能力/技巧」，**不是**「操作 X 工具」這類動作句。

K 為純名詞：`產業現況與發展`／`組織政策與流程`／`成本概念`／`消費者行為`。

跨任務重用率高：`企劃人員` 的 S02「資料分析能力」出現在 4 項任務、S03「溝通協調能力」出現在 4 項任務
——這是 K/S 文件層平坦編號＋多對多（ADR 0048 決定 5–7）的實證。

### 2.5 語料品質：2.64% 的任務名稱有 PDF 解析黏連

| 問題 | 規模 |
|---|---|
| 《歷史資料》檔（非最新版） | 40／908 = 4.4% |
| 任務名稱疑似跨欄黏連（>30 字） | 227／8,594 = **2.64%** |
| 任務名稱含換行 | 202 條 |

實例（`《歷史資料》專利工程師`，T4.2，363 字）：

```
專利申請程序之管控與處理T4.2.1瞭解專利法規T4.2.2瞭解專利程序審查基準及實務…
```

這是 `apps/pdf-to-json` 的跨欄文字黏連，**不是 iCAP 原始資料的問題**。
配對介面若直接呈現，員工會看到亂碼般的候選項。處理選項見 §6。

## 3. 診斷：現行實作的三個缺陷（皆由 §2 證據直接指出）

### 3.1 `opks_prompt.py` 對行為指標的定義是錯的

```python
# apps/api/app/job_analysis/llm/opks_prompt.py
- 行為指標：能從工作行為或結果判斷是否做好；不得自行補數字…
```

「判斷是否做好」是**品質判準**的定義。官方 23,804 條 P 中，0.05% 有數值、90% 是直述的行為句。
這行會引導模型產生判準而非行為描述，與產品核心價值（P 要具體到可執行）方向相反。

**修正方向**：P 是「這項任務具體要做哪些事」，可含質性條件（依據什麼、為了確保什麼），
不含數值門檻。「不得自行補數字」這句本身仍然正確，予以保留。

### 3.2 `prompt.py` 的 Task 成立條件被當成 statement 寫法

```python
# apps/api/app/job_analysis/llm/prompt.py
## Task 成立條件(四項同時滿足)
1. 可寫成 `action + object (+ purpose/result)` 的單句…
```

作為**成立判準**正確（說不出 action+object+purpose 的東西不成立為 Task），
但模型會照著它寫 `statement`，產出 20–30 字的長句——正好侵佔行為指標的篇幅（§2.2）。

**修正方向**：把判準與寫法分離。判準不變；`statement` 明確要求寫成
**名詞短語（官方中位數 8 字）**，具體行為留給 P、產出物留給 O。

### 3.3 `opks_prompt.py` 對技能的寫法指示與官方版型不一致

```python
- 技能：完成工作必要的可操作技術，以具體工作行為表達；不要寫成『具備……之能力』
```

「以具體工作行為表達」會生出「操作資料分析工具」，而官方全部是「資料分析能力」（§2.4）。
真正該禁的是冗贅句式（「具備資料分析之能力」），不是「能力」一詞。

**修正方向**：S 寫成名詞化能力／技巧；禁止的是「具備……之能力」的贅語結構。

## 4. reference 存取現況

`app/job_analysis` 對 reference 的存取仍是零（2026-08-06 實測，本次未變）。
基礎設施完整可用：

| 端點 | 回傳 | 用途 |
|---|---|---|
| `POST /occupations:search` | `OccupationSearchResponse` | 工作描述 → 候選職類 |
| `GET /occupations/{ocs_code}/tasks` | `OccupationTasks{units[]→tasks[]}` | **主要職責→工作任務兩層**，與本產品 domain 同構 |
| `GET /occupations/{ocs_code}/competencies` | `CompetencyPool` | 該職類 K/S/O/P 池 |

typed client：`app/adapters/knowledge_http.py` 的 `HttpIndexerClient`。
greenfield 慣例是自帶 port（`providers/` adapter），不共用 `app/core` 型別。

## 5. 流程決策記錄（owner 於 2026-08-06～08-07 逐項裁決）

### 5.1 產品定位

| # | 決策 |
|---|---|
| D1 | 產出**企業內部版** JD；公版是版型與下限，**不是內容深度標準** |
| D2 | P 要具體到「去哪裡找什麼資料、怎麼分析、做成什麼報表」 |
| D3 | 文件描述**這位受訪員工的實際工作**，不假裝代表職位標準；多份彙整成職位標準是主管日後的事 |
| D4 | 沒有選 iCAP 基準的文件與有選的**完全等同**，只是少了參考提示 |

D3 與 ADR 0048 決定 27–29 一致；P 具體化後該效度聲明更為必要，不得放寬。

### 5.2 iCAP reference

| # | 決策 |
|---|---|
| D5 | 配對時機：**表頭填完（職能基準名稱＋工作描述）即可配對** |
| D6 | 官方**主要職責可直接採用**成為文件的 Duty（Duty 是結構分組，不主張員工會什麼，domain 本無 evidence 欄位） |
| D7 | 官方**工作任務勾選後只進「待訪談清單」，不進 Current JD** |
| D8 | 官方 K/S **在配對階段不給員工看**（只進顧問 context 當提示）；**O/P 齊備後才可檢索 iCAP 的 K/S 池供員工採用**——見 D16a |
| D9 | 待訪談清單做成**表單**，員工自選一條進行訪談；訪談完成後進入確認環節 |
| D10 | 清單項目**只有「成立為 Task」或「員工明確否定」才消失**；問過但無結論者保留 |
| D11 | 文件層記錄「參考了哪一份官方基準」（ocs_code＋名稱＋版本）作為 **provenance，非認證** |

**D8 的時機分割是刻意的，且與 Morgeson 的建議方向一致。** 配對階段給 K/S 清單＝在員工尚無任何
具體工作可當錨點時就要他認領能力，正是 Morgeson et al. (2004) 測到 d≈.52 膨脹的情境；
O/P 齊備後才給，員工已有自己的行為描述當參照，對應該研究討論段的第二項對策
（給在職者明確的 task–ability linkage）。**但原著未驗證 anchoring 能降低膨脹**（ADR 0048 判準 3-B
第 2 條的更正已載明），故此處只能寫成「依原著建議方向的設計選擇」。

**因此 `evidence_origin: reference` 必須實作**（本研究初稿曾誤判為不需要，依 owner 2026-08-07
對 K/S 檢索來源的裁決更正）。iCAP 的 K/S 一旦可被員工採用進 Current JD，就會出現沒有員工
訪談證據的條目，而現行 `OpksEvidenceLink` 的來源白名單只有 `employee_turn`／`direct_edit`。

**不得以「員工按了採用就記成 `direct_edit`」規避。** 那會抹掉「這條來自官方清單」這個事實，
而清單挑選正是膨脹風險最高的動作；ADR 0048 決定 1 已明定 `evidence_origin` 指**證據來源**
而非文字作者，決定 16 亦明定「不得因員工按確認而升級」。

這不是新設計，是補完 ADR 0048 決定 A 已裁決但未實作的另一半。四種組合屆時全部有用：

| 情境 | `evidence_origin` | `task_linkage` |
|---|---|---|
| 從員工 Task／故事推導 K/S | `employee` | `linked` |
| 員工直接新增、無 Task 依據 | `employee` | `unlinked` |
| **iCAP 候選已對上本職 Task（D16a 的常態）** | `reference` | `linked` |
| 尚未對上本職工作的 iCAP 候選 | `reference` | `unlinked` |

D11 與 ADR 0052 決定 8（不得生成職能基準代碼）的界線：
**記錄「參考了 BAS1219-002v4」是 provenance；宣稱「本文件為 BAS1219-002v4」是偽造認證。**
兩者在匯出檔上外觀相近，措辭必須在 ADR 固定。

### 5.3 訪談結構

| # | 決策 |
|---|---|
| D12 | **兩個對話區分開**：骨架區（主要職責＋工作任務）／內容區（逐項任務的 O/P） |
| D13 | 內容區**每項任務一條獨立子對話** |
| D14 | 子對話結束時回傳主訪談：**結果摘要＋被標記的新線索**（員工順口提到、但不屬於該任務的事） |
| D15 | **O 與 P 一起訪談**（官方語意耦合，見 §5.4） |
| D16 | **K/S 在 O/P 齊備後另一步生成**，不再對話 |
| D16a | K/S 候選有**三個來源並存**：①文件內既有 K/S（重用）②檢索 iCAP 的 K/S 池 ③AI 依該 Task 的 O/P 提建議。**AI 亦可結合檢索結果共同提議** |
| D17 | 員工說不出具體時**追問到具體為止** |
| D18 | K/S **以抽象層為主**（對齊公版的 `資料分析能力`）；**通常不必寫太細**。具體工具例子由 **AI 從行為指標文字提取**當預填，非必要欄位 |
| D19 | 內部系統／資料庫／表單名稱**只寫在 P 的文字裡**，不另建術語表、不另填 enablers |
| D19a | 匯出**照公版版型**，行為指標變多導致儲存格變高即接受，不另設明細表、不改七欄結構 |

**D18 的取捨**：具體工具留在 P（D19），K/S 保持抽象，跨任務重用率才能維持
（`企劃人員` 的 S02「資料分析能力」跨 4 項任務，§2.4）。若 K/S 也寫成
`Power BI 儀表板製作能力`，同一條就無法被其他任務共用，會退回 ADR 0048 決定 6 要避免的重複。

**D19a 的後果**：內部版 P 若達每任務 8 條×40 字，主表單一儲存格約 320 字，
一頁可能只容納一至兩項任務。owner 已確認接受此版面代價，以換取與官方版型完全一致。
`export_xlsx.py` 的既有換行與垂直合併邏輯不需改動。

**D17 需要停止條件。** ADR 0055 負面後果已警示「需防止故事訪談無限延伸」，而 D17 本身無出口。
建議：同一個具體化缺口追問**至多兩次**，仍得不到就收下現況並標記該條 P 可再深入，繼續往下。
此為本研究提出的補充，待 ADR 裁決。

**D16 與 ADR 0048 決定 17 的張力與解法。** 決定 17 要求「確認時使用對比追問
（這是完成該 Task 不可缺少的知識，還是你目前剛好使用的工具／方法？）」，而 D16 取消了 K/S 對話。
**解法：把對比追問移到候選卡片上**——員工檢視 K/S 候選時，卡片本身帶該提問。
ADR 0048 防止照單全收的意圖保留，且追問出現在員工實際下判斷的時點，成本更低。

**D16a 的候選來源必須在畫面上可分辨。** 三種來源的膨脹風險不同：③（AI 依員工自己的 O/P 推導）
有員工證據鏈；②（iCAP 池）沒有，且是 Morgeson 點名的清單認領情境。
員工看不出差別就無法有意義地判斷，`evidence_origin` 也會失去產品意義——
它必須是員工看得到的區隔，不只是資料庫欄位。具體投影方式留給 ADR。

### 5.4 O 與 P 的關係（官方語意，非本產品發明）

兩件事同時成立，皆有全量證據：

1. **任務可以沒有 O**（21.8%，§2.3）；
2. **上一項任務的 O，是下一項任務 P 的輸入條件**。實例（`企劃人員`）：

```
T2.1 統籌及協調資源 → O2.1.1 企劃資源清單
T2.2 管控企劃案執行 → P2.2.1「依企劃資源清單，進行活動前置確認…」
```

這使 D15（O/P 一起訪談）有具體的提問形狀：
**「這項工作你具體做哪些事」→ P；「做完交出什麼、下一步誰拿去用」→ O（可以沒有）。**

ADR 0058〈不在本 ADR 範圍〉已裁定**匯出層不表達 O→P 參照**（公版表格沒有該欄位，
加上去會製造新的非法狀態）。本節不翻案該裁決：O→P 的耦合**只用於訪談提問設計**，不進資料模型。

### 5.5 Duty 歸納

| # | 決策 |
|---|---|
| D20 | AI **提供歸納建議**，重點是讓員工**確認歸納是否正確**；尚未歸入職責的 Task 可輔助歸納或建立新 Duty |

此決策取代了 2026-08-07 稍早的「隨時可重新歸納全部」。**這是重要的風險降低**：
全量重組會打散已採用的官方職責，並使匯出位置碼（`T{i}.{j}`）整批變動，
而第一版無版本歷史（`product-notes.md`）可解釋差異。ADR 0058 決定 5 已為同一理由
把排序切片排在匯出之前。D20 只動未歸類項目，不觸及既有結構。

### 5.6 缺漏檢查

| # | 決策 |
|---|---|
| D21 | 缺漏檢查**必須涵蓋 O/P/K/S**；不涵蓋等於不檢查 JD 是否完整 |

判準直接取自公版空格語意，**不發明「幾條算夠」的門檻**：

| 檢查項 | 依據 | 是否列入 |
|---|---|---|
| 任務沒有任何行為指標 | 公版每列皆有 P | ✅ 列入 |
| 任務沒有連到任何 K 或 S | 公版每列皆有 K 與 S | ✅ 列入 |
| **任務沒有工作產出** | **21.8% 官方任務本來就沒有** | ❌ **不得列入** |
| 職責底下沒有任務 | 現行 `duty_without_task` 已有 | 已有 |

缺漏仍**只提示、不阻擋**訪談／儲存／匯出（ADR 0052 決定 5、ADR 0058 決定 11）。

**新增的副作用**：D6（官方職責可直接採用）會讓員工勾完立刻觸發數條 `duty_without_task`。
建議該情境下的措辭與靜態缺漏區隔（「這 N 項職責還沒有工作任務，接下來的訪談會逐步填上」），
避免員工把正常起始狀態讀成錯誤。

### 5.7 訪談進度

| # | 決策 |
|---|---|
| D22 | 訪談需要**明確的進度指標**，解決「不知道走到哪」的不確定感 |

D9（清單式訪談）與 D21（O/P/K/S 缺漏）合起來已足以構成進度來源，**不需要新增 completion gate**：
骨架區進度＝待訪談清單「N 條中已確認 M 條」；內容區進度＝每項任務的 P／K/S 是否齊備。
兩者都是既有資料的投影，不是新的狀態機。這一點很重要：ADR 0042 與現行 `prompt.py`
明文「第一版沒有完成 gate，模型不得宣稱訪談或 JD 已完成」——進度**顯示**不等於完成**判定**。

## 6. 需要在 ADR 或 plan 處理的實作缺口

1. **「訪談引導進 O/P」不得動 `task_analysis_result_v2`。** 該 schema 是唯一經 Opus 5／Sonnet 5
   付費驗證的契約（ADR 0042 決定 7；2026-08-06 研究 §7 硬約束 3）。
   **解法：判斷「哪些任務可以開始談 O/P」改由 application 端決定性規則處理**
   （已進 Current JD、無未解邊界爭議、尚無任何 P），UI 據此提示；模型的 `next_question`
   本就是自由文字，可自然引導，無須新增結構化欄位。
2. **子對話的儲存形狀。** 現行 `JournalRepository.list_conversation_turns()` 依 `journal_sequence`
   展開為單一 transcript。D13 需要 per-task 子對話，須決定 Journal kind 與投影方式。
2a. **`evidence_origin: reference` 的 domain 落地**（D16a）。至少涉及：`SourceKind` 新增一種
   reference 來源、`_EVIDENCE_ORIGIN_BY_SOURCE_KIND` 與 `OpksEvidenceLink` 的白名單放寬、
   `OpksItem.evidence_origins` 的回傳型別（目前寫死 `Literal["employee"]`）。
   `SourceRef` 存在 JSONB 內，**可能不需要 migration**，須實測確認。
   同時要決定 reference 來源要記到什麼粒度（僅 `ocs_code`，或含 `task_code`／原始 K/S code）。
3. **語料品質防線（§2.5、§7.2）。** 《歷史資料》檔案目前被正規化為 `is_current=True`
   且查詢層不過濾（§7.2 已實測驗證會誤排名第一）——**這是修復，不是加新過濾條件**：
   `normalizer.py` 需修正「無 version_info 且來自《歷史資料》」的判定，
   `app/job_analysis` 呼叫 `search_occupations`／`search_tasks` 時須明確傳入 `is_current=True`。
   2.64% 的黏連任務名稱需在呈現層處理（截斷並標記，或以 `task:search` 的向量相似度降權）。
4. **待訪談清單的「員工明確否定」出口。** D10 只承認「成立」或「否定」，但顧問不綁順序（D9），
   清單可能卡住。清單項目應提供「我不做這個」按鈕作為 D10 的否定路徑。
5. **D17 的追問停止條件**（§5.3）。
6. **D6 觸發的起始缺漏措辭**（§5.6）。

## 7. 待驗證（不得在 ADR 宣稱已成立）

1. ~~**iCAP 檢索準確度未實測。**~~ **已於 2026-08-07 補測，見 §7.1。**
2. **企業內部版 P 的合理條數未知。** 公版每任務中位數 3 條；內部版必然更多，但「多少算夠」

### 7.2 發現的真實缺陷：已退場職類未被過濾，會與現行職類混淆排序

`data/jd-json/` 下 40 個《歷史資料》檔案是**已退場、被取代的職類標準**（整個職類停用，
不是同一職類的舊版本）。這些檔案沒有 `version_info`，而 `normalizer.py:147` 的規則是：

```python
is_current = not versions  # no version_info -> treat as current
```

**沒有版本資訊被當成「就是現行版」**——這條規則的原意是處理「從未有過修訂」的正常案例，
但誤傷了《歷史資料》這個特例。查詢層又完全不過濾：

```python
# api/service.py:156,175
service.search_occupations(..., level="profile", ocs_code=None, is_current=None, limit=top_k)
```

**實測驗證**：搜尋「傳統建築修復小木作技術工匠」，已退場的 `CCM7114-005`
**排名第一、score 1.0**，與現行職類在結果清單上完全無法區分。

**後果**：員工可能配對到一份已作廢的官方基準而不自知，且若成立，該作廢代碼會被記入
D11 的文件層 provenance（「參考了 CCM7114-005」——一份已不存在的基準）。

**這必須在 iCAP 配對切片動工前修**，屬於 `apps/ocs-indexer` 端的小改動：
查詢時排除 `is_current=False`（`search_occupations`/`search_tasks` 已接受該參數，
只是 `app/job_analysis` 尚未實作的 port 需要在呼叫時明確傳入），
或至少要求 API 回應攜帶 `is_current` 供呈現層標示。修法留給 ADR／plan 裁決，
本研究只確認缺陷存在且可重現。

                for it in (cb.get('indicators') or []):
                    npi+=1
                    if it.get('text'): pt.append(it['text'])
            tasks_total+=1
            if nout==0: tasks_no_out+=1
            p_per_task.append(npi)
print('tasks',tasks_total,'names',len(tn),'indicators',len(pt))
print('name median',statistics.median([len(x) for x in tn]))

## 9. 建議走向（供 ADR 引用，本研究不拍板）

- **先修三個 prompt 缺陷（§3）**，它們是目前品質問題的根源，且不依賴任何新基礎設施。
  §3.1 與 §3.2 會改變模型輸出的形狀，依 ADR 0042 的分界屬「判斷層」改動，
  **上線前需補一次 Opus／Sonnet 複驗**，不可只在 Luna-Pro 上驗過就宣稱完成。
- ~~配對切片動工前先補檢索準確度實測~~ **已於 §7.1 完成，準確度足夠、不需縮小範圍步驟；
  但配對切片動工前必須先修 §7.2 的已退場職類過濾缺陷**，否則員工可能配對到作廢基準。
- **缺漏檢查涵蓋 O/P/K/S（D21）可獨立先行**：純函式、零新依賴、無模型參與，
