## 1. 從概念到證據

研究順序是：**員工想完成什麼 → 哪裡可能寫錯／遺失 → 大廠如何處理同類問題 → 正式能力及限制 → 本案映射 → 必要實證**。名稱不同不代表沒有對應功能，名稱相同也不保證相同語意。

- **必查**：OpenAI 的 Codex、ChatGPT，Anthropic 的 Claude；同時查產品體驗與公開工具契約。
- **交叉核對**：Microsoft、Google 的文件／人機介面，及免費 OSS 的正式 API、source、測試、release／migration／license。
- **證據效力**：官方明示理由是 Fact；推論它能防哪類錯誤是 Inference；是否適合員工 JD 是 Mapping；未公開內部或尚未測到是 Unknown。不能把產品 UI 說明當資料庫交易契約。
- **時效**：每項記查閱日與適用產品／版本／成熟度。舊但仍有效的契約可用；退場、過渡及 Preview 分列，不把「今年讀到」當「今年推出」。

本輪的具體時效修正：Canvas 的 2024 發布文已轉介現行 release notes；2026-05-28 公告限定 GPT-5.5 Instant／Thinking 不再支援 Canvas，legacy 僅限時續用。因此不再以舊 Canvas 當現行通用流程，也不推論所有 ChatGPT 平台已全面停止文件編輯。現行 Work 的文件續編另有直接來源，見 [evidence §2.8](evidence/2026-09-09-jd-app-tool-and-review-contracts.md#28-必查補證chatgptcodex-與-claude-的現行文件體驗)。

## 2. 一份 JD 的完整操作情境

以下為**產品映射與驗收草案**。例子是合成情境：員工主要協助需求澄清與介面實作，特殊案件才支援上線，交付責任尚待確認；不是替既有職位樣稿添加真相。既有 r2 與 CT49 案例仍分開。

| 步驟 | 員工與顧問的動作 | App 必須可證明的效果 | 來源接點與限制 |
|---|---|---|---|
| J01 開始一份工作分析 | 員工選擇／建立文件，透過聊天描述工作 | 對話、理解、JD 保持同一文件歸屬；切換另一文件不串用資料 | 本案已同意邊界；外部 Project／Artifact 的同名功能不證明本機資料隔離，也不產生帳號需求 |
| J02 形成初稿 | AI 依已知工作轉寫；資訊不足時追問或保留未知 | 有未完整任務仍能保存；AI 能讀實際目前稿與既有理解／來源 | ChatGPT Work、Claude Artifacts 的對話續編有正式先例；JD 品質依既有內容指南，不由編輯器保證 |
| J03 補充與局部修改 | 員工補充「僅特殊案件支援上線」；AI 改受影響內容 | 保留適用條件及其他有效工作；不靠模型自行數位置決定唯一目標 | OpenAI context patch、Anthropic view／exact match；結構 JD 的操作須再映射入選 editor 原生模型 |
| J04 知道改了什麼 | 員工讀更新後的 JD，查看新增、刪除、改寫與前後內容 | 所有實際修改可查；摘要須能對到真实變更。說「改好了」不是寫入憑證 | Codex 的實際 repository diff／Last turn 是明確參照；不移植 Git 儲存或把某頁未述完整 diff 當已有 |
| J05 用聊天更正 | 員工指出「我只是協助，不是負責核准」 | AI 讀目前稿後修正責任；有效人工內容、其他任務及未知不遺失 | 兩家產品的續談改稿與工具重讀可作接點；局部更正不代表整份專業品質已確認 |
| J06 直接手改再續談 | 員工手動補一個條件；接著請 AI 整理 | AI 讀到人工最新版；人改後的審閱狀態按將來已決政策呈現 | 原生 editor 更新／讀取是必要能力；人工編輯不自動推定全組接受，也不預定永久 pending |
| J07 改名、重排與拆分 | 顧問將一大段整理為兩項任務，移到適合職責 | 完整敘述、條件、來源關係與必要身分不丟失；結構改動也能辨識 | Plate／PM／Lexical 有原生結構能力，但完整修訂追蹤不因此成立；NodeKey、位置與業務身分分清 |
| J08 保存與重開 | 關頁後重新進入該文件續談 | 明確讀到已保存版本、相對應訪談及必要變更資訊；未成功保存不冒稱完成 | Editor serialize／reopen、App 保存與結果回報各需驗證；版本切換 UI 不是本機 crash recovery 證明 |
| J09 全文核對與交接 | AI 核對整份 JD；真人後續讀原始訪談及成品，必要時修改 | 工作→JD 覆蓋、JD→依據可核對；未決事項明示。真人能取得配對內容與可編輯成品 | 依既有 JD 指南與來源契約；取得方式及匯出版本仍待產品選擇，不新增權限或多人模式 |

員工可在正文、聊天、差異檢視或手動編輯中完成事實核對；上述情境不指定「是不是我的工作」按鈕。AI 執行期間是否暫停受影響區域的手改仍待取捨；無論是否同時編輯，都必須處理讀取基準已改變的情況。

## 3. 必須看見的失敗流程

此表定義應避免的結果，**不是自製定位／回退協議**。以入選 framework 的正式行為決定何處能拒絕、回傳什麼及如何恢復。

| 情境 | 有依據的處理方向 | 尚須回答／不得假定 |
|---|---|---|
| 格式錯誤／零處或多處匹配 | App 回傳可行動錯誤，模型依需要重讀／修正；不猜第一處就套用 | Anthropic exact one match 與 OpenAI Invalid Context 是文字例證；rich-text 定位由 editor 能力推導 |
| AI 讀後目標被手改、移動或貼上改變 | 檢查目前基準；無法證明仍有效時不靜默覆盖 | Google 有 revision 拒絕／協調，但不代表 OSS 自帶 Google 的 reconciliation；中文與重複文字需固定反例 |
| 一批操作中途失敗 | 依實際結果判定哪些已動、哪些未動，再修復 | OpenAI 把原子邊界交整合者；PM step 失敗不抹去先前成功；Tiptap chain false 不等於未 dispatch |
| 編輯已套用但保存失敗 | 分別呈現套用與保存結果；保留可恢復的已知狀態 | Browser editor 與 DB 不是天然同一 transaction；不能把一次 tool success 當保存完成 |
| 保存成功但結果遺失 | 先讀可證明的保存／執行事實再決定是否重試 | 兩家 tool call ID 都不是文件副作用去重保證；不得直接重播新增職責 |
| 拒絕早期修改，但後續已有相依與獨立修改 | 呈現受影響範圍；獨立有效修改不應無聲被帶走 | 整份舊 snapshot 回復不能冒充選擇性拒絕；相依項如何處理仍為 S3 產品取捨 |
| 模型把已刪內容當現行工作 | 給模型的目前正文與歷史比較分清 | Plate SkipSuggestionDeletes 的部分支援不證完整 block delete 投影正確；須驗模型實際讀取內容 |

工具錯誤能交回模型，只表示有修復通道，不保證模型一定會重試或成功。何時停止、提示員工、保留未完成，以及一次操作的保存單位，要在候選正常／失敗流程中定義；本輪不加泛用修補 Agent。

## 4. 原生能力如何重排候選

免費開源仍是硬條件。**先核對必要文件能力，再比較修訂政策**；不因先研究了某 suggestion 套件，就反過來要求員工逐項批准。

| 候選 | 能作為起點的原生能力 | 決定性缺口及本輪評價 |
|---|---|---|
| Plate | 結構文件、一般編輯、部分文字／區塊 suggestion transforms 與解析操作 | suggestion／AI helper 不是所有操作的修訂引擎；AI helper 可能清除既有修訂資料。若產品需要內文修訂，可優先有限驗證其原生 transforms；目前仍未採用 |
| ProseMirror／Tiptap OSS 核心 | schema、transactions／steps／mapping、JSON 文件與原生人編輯 | changeset 不保證格式／attrs 完整差異；第三方文字追蹤對程式修改有限制。可作文件核心候選，不能把 paid tracked changes 或 demo 當已覆蓋的免費組合 |
| Lexical | 可序列化 EditorState／NodeState、原生更新及人編輯 | NodeKey 不持久；自訂業務身分及拆分唯一性仍需核對，未證第一方完整修訂層。不能因核心易擴充便宣稱補齊成本低 |

**推薦的研究方向：**先比較「AI 更新同份工作稿，實際改動可檢視，員工能自然更正」在各核心能否完整成立；持久逐項待審是待比較的機制。任何版本比較路線也必須提供準確完整差異與可恢復效果，不能只保存整份舊稿就算完成。若其必要差異／局部回復需自建通用引擎，就列缺口回議，不能以繞過 suggestion 套件掩蓋相同成本。

當次先看候選再套用、先更新工作稿再檢視，以及長期逐項 pending，都是已有不同產品先例的政策。先前 Plate 優先是特定 pending 情境的工程假設，尚不足以為這個新主流程選定引擎。

## 5. 下一個可決定的單位

**本節為初次交付的討論順序沿革，已由頂部交接與 register 取代；不再另外提出同一問題或啟動以下已做過的驗證。**

**唯一下一題：員工發現先前一項 AI 改寫不對、而後面已繼續訪談並修改時，應如何更正或退回，同時讓他看清影響並保留無關工作？**這把一般共同編輯原則收斂成真正會改變 revision／diff／保存需求的產品選擇。

下一份 S3 情境稿應並列最多三種完整操作結果：聊天／手改更正最新版、當次候選先核對再套用、持久修訂的選擇性處理。比較員工需理解什麼、什麼時候被打斷、後續相依內容怎麼辦及免費原生缺口。以「協助被寫成主責」和組外新增任务作同一例子，給簡單畫面草圖與有理由的推薦；不再問 Owner 是否以訪談或 AI 主寫為主。

後續同一情境再處理刪除相關任務、匯出目前／已核對版本、AI 執行期间操作及真人取得資料；這些未決事項仍須在 S3／S4 前收斂，沒有因本稿而自動選定。

**有限驗證的重新分層（尚未執行）：**

1. 固定繁中文件及原生操作，先驗內容／結構／必要 metadata、手改後讀最新、serialize→全新 editor→reopen。這是三個候選都需回答的基礎。
2. 依選定審閱政策驗實際差異、修改相依與無關內容保留；若採 pending，再加入既有三個 suggestion 反例，不讓它們預定政策。
3. 以預定 tool call 驗 stale、partial、保存失敗／回覆遺失及重讀，區分 editor、App 保存與 agent 修復證據。

Pass 只支持被測的固定版本與流程；重要內容／來源遺失、誤改其他目標、錯誤宣稱已保存，或需自造通用引擎時 Stop 受影響路線並回 S3。沒有真模型／員工測試，就不宣稱顧問品質或 UX 已驗收。
