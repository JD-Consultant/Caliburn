## 2. 結論：建議有結構的文件，不把每句話拆成資料表

**推薦 B：文件有可辨識的內容區塊／項目，項目內仍是完整、自然的敘述。**

例如系統知道這是一項任務，旁邊是它的產出與完成要求；員工仍像編輯文件一樣改句子，不必把每句拆填成「動作、對象、目的、情境」。這是本產品候選，不是國際統一 schema。

| 方案 | 能做好的事 | 主要取捨 | 本輪判斷 |
|---|---|---|---|
| A 自由文字／標題文件 | 表達自由，書寫門檻低 | 工作類型與關係多靠人或模型重新判讀；精確選取與整項移動仍需定位機制 | 可作呈現／輸出方式，不優先作唯一的內容辨識方式 |
| **B 有意義的結構＋完整敘述** | 可定位職責、任務等內容；兼顧閱讀、移動及後續審核；不必所有內容都建關聯邊 | 仍須定義少量內容種類與編輯邊界；不能只裝套件就懂 JD | **Owner 同意作 Working 方向，技術細節未選定** |
| C 所有內容都建成獨立記錄及細密關係網 | 便於複雜關係查詢、影響追蹤及多種投影 | 要維護更多關係與操作一致性；並非每條關係都改善目前閱讀／編輯效果 | 當明確用途超過 B 可處理範圍時再評估，不先全面採用 |

以上比較的是**內容表徵與關係密度**，不是宣稱 A 沒有底層節點、B 必須一個 JSONB、C 必須圖形資料庫；也不是說三者不能混合。使用者像編輯文件，不代表底層只能存一大段文字。Notion 區分內容與 properties，Tiptap／Lexical 提供結構化編輯模型；SAP 另有職務內容與模板。它們支持這個方向有成熟先例，**不能證明 B 對所有產品最好**。[證據 E01–E05](2026-09-09-jd-document-model-official-evidence.md)

## 3. 建議的內容關係

以下承接 JD-R001 的內容取捨，尚不是 JSON、SQL、工具參數或固定 UI 樹。

| 內容 | 放置與關係建議 | 不應誤解成 |
|---|---|---|
| 名稱、目的、必要基本資料 | 屬於整份 JD；目的可隨完整工作理解修訂 | 第一次訪談就必須全部填妥 |
| 職責 | 有意義的工作分組；工作少時可以不分職責 | 每份 JD 一定有多層 Duty 樹 |
| 任務 | 用完整敘述表達一項工作；可放在職責下，尚未分組時仍可保留 | 沒有 Duty 就不能存在，或每個案例各是一項任務 |
| 產出、完成要求 | 任務底下兩組並列、各可多項；不與任務敘述合併 | 一對一、要求掛成果下、因敘述重複而省掉一組 |
| 知識、技能 | 先採職務層級總覽，保留必要用途／範圍；局部差異就近說明 | 每 Task 複製同一清單，或所有 K/S 都適用所有 Task |
| 邊界、頻率、重要條件 | 局部條件貼近工作，真正共通者集中；由內容交代適用範圍 | 把某案月檢放上層，便自動套給每個任務 |
| 已在JD但尚未能歸屬的內容 | 允許保留既有草稿，不強迫建立假的 Task／Duty；訪談未知仍沿Memory | 為了符合完整成品結構刪掉已寫內容，或把每個訪談線索都搬進JD |

**包含關係、專業適用關係及修改差異的範圍是不同概念。** 放在任務底下便於閱讀，不代表永遠不能移動；知識出現在總覽，也不代表與所有任務都有連線。現行持續工作稿沿實際前後版本呈現修改，不從父子關係推導逐筆核准群組。

### 共用知識技能：先避免重複，不先強制關係網

推薦先用「內容＋必要用途／範圍」說清楚。同一項介面契約知識可支援開發與故障診斷，不必複製兩條。若其中一項工作的專業範圍不同，應保留差異，不能只因名稱相同就合併。

**暫不要求每個 K/S 都填 Task ID 陣列。** 這是對 C04 職務層級總覽的延續，不是禁止關聯。若後續確定要「點技能列出全部使用任務」或自動判斷解除／刪除影響，再評估顯式引用的效益。屆時也須查框架能力，不先發明一套關係引擎。

### 2026-09-10：任務與知識技能的明確對應討論

**效力更新：**最初問句形成OPEN推薦；Owner之後大致同意完整格式，現在為可修訂WORKING產品方向，尚未施工。問題是讓成品清楚呈現專業用在哪些工作，不直接推定SQL表或工具欄位。

- **官方事實（2026-09-10 查閱）：**[OPM Job Analysis](https://www.opm.gov/policy-data-oversight/assessment-and-selection/job-analysis/)將工作任務、完成任務所需 competencies 及其 connection 納入分析；其用途包含甄選，不能整套搬入本產品。[iCAP 現行職能概念 §2](https://icap.wda.gov.tw/ap/knowledge_introduction.php)分別定義知識與技能為執行某項任務需要理解的內容與能力。兩者支持明確分析工作與專業的關係，沒有公開規定本案用哪種資料庫、關係欄位或閱讀介面；頁面未標精確修訂日。
- **本案推薦：**同一份 JD 內，任務↔知識、任務↔技能各自允許多對多。每項知識／技能保留一份完整說明，任務呈現其相關項目，總覽可看支援哪些工作；同名但不同專業範圍不能自動合併，不因此增加知識↔技能第三組關係或跨文件共用詞庫。
- **閱讀效果：**延續職責分組、完整任務與就近要求；總覽保留，任務旁只需能辨認所需專業。引用的外觀、是否點擊展開等仍待格式討論，不強制每項顯示相同欄數或要求員工填代碼。
- **分析責任：**顧問依實際工作判斷對應並在必要時釐清；不能為了配滿關係而替員工補造任務或技能。建構中的未釐清關係仍可保留，不因暫無連結自動刪內容。
- **產品代價：**共同項目修改會影響所有引用者的閱讀，須核對各任務適用性；任務特有條件應保留，不能用共享項目抹平。引用解除與刪掉共用項目須分清，具體操作行為於方向採用後核對。
- **效力與下一步：**相較原「總覽＋用途、暫不要求顯式引用」，這增加可辨認的任務對應；本輪未改樣稿或 schema。先確認此產品效果，再依現行框架能力研究引用維護、編輯及保存，不把專業分析共同原則稱為所有大廠同一套多對多實作。這裡的引用是 JD 內容間的適用關係；原始訪談／Memory 來源回查仍沿另一份來源契約。

### 未歸屬不是新分析系統

員工可能先提成果、方法或問題，再釐清任務；這些訪談線索沿既有Memory保留，資訊足以支持敘述時才寫JD。此處「未歸屬」限定已選擇寫入JD的有效內容或員工直接輸入的草稿，不等於訪談待釐清。**不因此增加第二份工作理解、Gap表、強制候選層或獨立未歸屬區。**

已成稿但未分職責的任務，以及已寫入但尚無Task的成果／要求，不為了階層完整而遺失，也不自動搬去Memory。若已确认組織本身仍未決定重要權責，可就近如實寫明；不能把所有未知假填為工作責任。分界見[Memory及草稿核對](evidence/2026-09-10-jd-memory-draft-boundary-audit.md)，未來匯出仍依PARKED範圍處理。

## 4. 定位與排版要分開

建議：**被改名或移動的同一內容，仍能被識別；畫面流水號及所在職責不是它的身分。** 例如任務由第二個職責移到第一個，不應僅因序號改變就變成另一個工作項目。

這不要求 LLM 生成 UUID、計算版本或自行猜目標。具體定位方式由後續工具與框架設計決定；需要持久識別時，優先用框架可保存的識別／metadata 能力。複製、拆分、合併的身分如何處理須逐情境確認，不能只根據外觀相同推定是同一項。

官方差異已確認：Tiptap 有可配置的 UniqueID；Lexical 的內部 NodeKey 不序列化，但另有 NodeState 可保存應用 metadata。**不能因 Lexical 有 key 就說永久定位已完成，也不能因此說它必須全部自寫。** [證據 E07–E09](2026-09-09-jd-document-model-official-evidence.md)

顏色、縮排、收合、閱讀序號屬呈現；必要的工作範圍及例外屬內容。Google Docs 的 property inheritance 描述外觀，不是工作責任可自動繼承的證據。[證據 E03](2026-09-09-jd-document-model-official-evidence.md)

| 刪分組／移除某處的共用內容 | 不把「去掉位置」默默等同「所有相關內容都刪除」 | 下一題核對已談的保留／連帶刪除與復原體驗 |

## 6. 框架已有什麼，不先判定全部自訂

本輪只核實相關能力，尚未選型或完整比較成本／授權。

| 能力 | 已核實的官方接點 | 仍須由後續設計確認 |
|---|---|---|
| 結構化內容、完整文字及編輯狀態 | Tiptap／ProseMirror 的 nodes、marks、schema、transactions；Lexical 的 editor state | 哪些 JD 概念需要可辨識的獨立項目 |
| 保存與恢復文件 | Tiptap JSON／HTML；Lexical JSON serialization | DB、伺服器接線與一致性；不是編輯器自動提供應用資料庫 |
| 持久項目 metadata | Tiptap UniqueID；Lexical NodeState | 複製／拆分／移動及保存後如何保持正確定位 |
| 異常結構處理 | Tiptap 初始化內容的 content checking／contentError | 貼上、後續寫入及保存須另核對；schema 合法不等於 JD 事實正確或內容無損 |
| AI 變更審閱 | Tiptap AI Toolkit review；Tracked Changes 個別／批次接受拒絕 | 持久性、編輯待審內容、整組操作及授權成本；不能把暫時裝飾當成持久待審 |

上列能力不都屬同一免費套件。Tiptap 的 Tracked Changes 是付費獨立產品，AI Toolkit 的另一條 suggestions 路徑是暫時的 decoration；後續須選對路徑。**因此不能先宣稱審核只能自寫，也不能宣稱現成套件已百分之百覆蓋本產品。** [證據 E10–E11](2026-09-09-jd-document-model-official-evidence.md)
