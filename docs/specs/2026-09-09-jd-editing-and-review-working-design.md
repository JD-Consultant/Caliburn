## 1. 本輪唯一決策

**新任務與必要內容、局部修訂、跨位置調整，各以何種最小完整範圍供員工審核？**

- 已確認、不重問：人與 AI 編輯同份最新文件；AI 改動可辨識且需明確審核；員工可直接編輯待審內容，編輯不等於接受；不處理仍待審，AI 可在最新內容上繼續工作。[C01 §1、§3、§5](2026-09-09-jd-document-relationships-working-research.md)
- 本輪新增的是具體分組建議，不是重新決定上述原則。未審核不應阻止繼續訪談；這不等於允許 AI 分析時人機同時寫入。
- 不做：重開 Memory、增加 JD 欄位、選框架／DB、定工具參數、改 prompt／UI／production、付費測試。匯出、刪除的保留／連帶刪除、操作中鎖定與失敗恢復另題細化。
- 資料分工：本文管操作候選及情境；[官方證據 §5](2026-09-09-jd-document-model-official-evidence.md#5-c02-編輯與審核接點複核)管事實、來源及限制；[父入口](2026-09-09-job-analysis-and-jd-content-research.md#2-文檔各負責什麼)管閱讀路由；[register](../current-decisions.md)管效力。

## 2. 官方能支持什麼，不能代決什麼

- **Official fact：**Word 支持在文件中逐項或整批接受／拒絕；隱藏標記不等於處理變更。Tiptap 提供保存式追蹤修訂，也另有暫時顯示的建議路徑，不能混用其保存性。[E10–E13](2026-09-09-jd-document-model-official-evidence.md)
- **重要差異：**本輪查到的 VS Code 現行頁面描述「直接修改並保存，再用 diff／版本控制審閱」，不是逐項 pending approval。共同最新文件可借鑑，但我們的員工明確審核是產品要求，不宣稱各家完全相同。[E12](2026-09-09-jd-document-model-official-evidence.md#e12-vs-code-現行文件不再可當逐項待核准的依據)
- **框架邊界：**Tiptap 的連續輸入分組、跨作者巢狀修訂與整段拆分有各自規則；不是名稱相近就等於 JD 的跨位置整組審核。尤其跨作者內層修訂可能另待審，不可直接套成「員工修改完接受這組最新版」。[E14–E15](2026-09-09-jd-document-model-official-evidence.md)
- **Caliburn mapping：**以下「依完整改動效果分組」是延伸既有產品要求的候選；不是官方保證能自動判斷 JD 語意依賴，也不是已決定要自行寫審核引擎。

## 3. 三種粒度及推薦

| 方案 | 優點 | 問題／取捨 |
|---|---|---|
| 每輪 AI 的全部修改一起審 | 操作少 | 不相關的任務被綁住；一項不對就得拒絕整輪 |
| 所有句子／欄位都能任意分開審 | 細緻、自由 | 拆分或移動可能只接受半邊；必要條件與工作本體可能脫離 |
| **最小但完整的一組改動（推薦）** | 無關者分開，相依者一起；組內仍可直接編輯 | 要讓員工看清範圍，後續須驗證框架的分組／回退接點 |

推薦判準：**只接受或拒絕其中一部分，是否會讓這次調整重複、漏失或改變原本要表達的工作意思？** 如果會，相關改動一起呈現；否則不要只因同一回合、同一職責或同一任務就綁在一起。

此判準不能把「有機會寫得更完整」都當強制依賴。文件可以建構中、任務可以未歸屬，內容未完整不等於不准保存。是否依賴是分析判斷，語意正確仍由員工確認；本輪未指定由何模型欄位、演算法或框架實現。

## 4. 用樣稿走具體情境

以下均為**另外假設的編輯情境**，不變更 r2 的虛構工作事實，也不表示真的從訪談取得新資料。

| 情境 | 建議審核範圍 | 原因 |
|---|---|---|
| 首次加入樣稿任務8「約定的定期維護」，包含適用範圍、周期、產出及必要要求 | 原則上作一組新工作內容；員工可改組內任何一句，再接受最新版 | 不把「有維護約定才做」拆掉，造成所有專案都月檢；不強制另有獨立產出欄 |
| 已存在的任務，補一條可獨立成立的完成要求 | 可單獨審這項增補 | 不因它在 Task 底下就重審整個 Task；若同時改了相依條件才合組 |

| 上述新任務同時帶出一條能獨立支援既有工作的共用技能修訂 | 不因同輪或相關就必須綁住；能獨立成立可另審 | K/S 是職務總覽，不自動跟某 Task 一起被核准或移除 |

「第一次新任務原則上含其必要內容一組」現為 Owner 暫時同意的粒度方向。不是永久將任務及所有子項鎖成不可拆分的核准單位，也不要求每項 Task 恰好一 O、一 P。

## 5. 員工直接編輯後會怎樣

以一組「AI 修改任務內容＋相依完成要求」為例：

1. 最新文件顯示建議內容；差異可辨識，必要時看到原內容。具體顏色／工具列位置後續再設計。
2. 員工直接改其中一句，不另開「修改後接受」表單。**保存的是目前待審內容，並未替員工接受。**
3. 人與 AI 之後使用的是修改後的最新版；不能仍取修改前的 AI 文句繼續生成。這是文件可讀取的要求，不代表每輪一定塞全份 JD 進 context。
4. 按接受：確認這組當下的內容，不偷偷退回 AI 初稿；不連帶接受其他組。
5. 按拒絕：依先前討論的整組回退概念，放棄這組待審版本（含員工在組內的修改），恢復該組修改前的內容；不得回退整份文件而抹去別處獨立修改。拒絕不用填理由。
6. 放著未決：維持待審；後續 AI 修訂仍須讓使用者看到目前差異，說明不能還指向已不存在的舊修改。

第5點不是「任何情況都可盲目套舊快照」：若後續改動依賴這組，如何共同調整／回退是下一個情境題，不能由本文直接推定已解決。也未決定要保存幾份文件、用何版本模型或新增哪些狀態欄位。

### 7.1 先分清已同意效果與尚未承諾的機制

目前有效的 B05／B06 要求：未確認的獨立建議能分開處理，接受其當下最新版；相依調整完整處理，取消不傷組外獨立修改。它沒有指定永久逐項 pending 是唯一底層，也沒有要求任意已接受歷史都能一鍵撤回。人工改 pending 的狀態及後续相依如何連動尚未定稿。

最新主體驗是持續訪談、AI 主寫、員工主要閱讀與核對事實；逐批接受不是預設必經路徑。「不強制逐批接受」與「仍提供可選的個別取消」可以並存，不能把兩者混為互斥選項。反過來，工作稿可更正與版本可查，本身也不等於已實現個別取消。

### 7.2 原生組合的完整責任與真正缺口

| 從一次建議到審閱完成 | 已有原生能力／必要 App 工作 | 現有證據的界線 |
|---|---|---|
| 提出有意義改稿 | 顧問決定內容，App 提供已讀範圍與 baseline；Plate 原生 transforms 執行 | 一次工具批次、Task ID、作者或回合都不是語意群組 |
| 記錄本次原生變更 | 從原生 suggestion APIs 讀實際 IDs，App 記建議與原生成員的關聯 | 原生可能沿用相鄰建議 ID；沒有通用的外部語意群組隔離參數。不能只收集「這次新生 IDs」就保證歸屬完整 |
| 同處人／AI 續改 | 在最新版使用原生 transforms；原生作者資訊與每次已保存變更分開保留 | R01 全句續改產生三 IDs。新 ID 如何加入原建議、與其他建議交疊時如何隔離，尚未證明 |
| 保存／重開 | 完整原生 pending value 由 SuperJSON 編碼後保存，解碼再建 editor | 四個固定情境通過；未驗全 profile／Python／DB，也不提供語意群組 |
| 接受／取消 | 對完整成員在候選 editor 呼叫原生 accept／reject；同 baseline 才提交結果 | R01-F 只證已知三 ID 的特定順序；正序拒絕有殘文與 raw keys。不能泛化成「一律反序」，也不能把查無 ID 當成功 |
| 讀取目前／已接受內容 | 依選定政策明列投影，與歷次實改分開；刪文不當成現行工作 | 在成員與相依規則未定前，不能由一份乾淨快照推出完整 accepted projection |

依據：[R01／R01-F](evidence/2026-09-09-jd-native-pending-review-comparison.md)、[codec](evidence/2026-09-09-jd-native-pending-codec-probe.md)、[App 工具／保存責任](2026-09-09-jd-editor-app-integration-design.md)。因此「App 關聯資料＋原生命令＋现成 codec」是可研究的組合，尚不是完整解法。新增一個 groupId 欄位不會消除成員隔離和結算的責任。

若保留完整續改待審效果，至少還需交付成員歸屬、相依範圍、原生結算與失敗恢復、員工可讀邊界及其驗收。若實現方法變成通用成員推導／相依圖／排序／before-image 重建，便是本專案自建審閱引擎；不能因叫 adapter 就降低其責任。**現階段沒有足夠證據估成幾個簡單函式，也沒有足夠資料估工時；不虛構精確成本。**

### 7.3 用同一份文件比較結果

以下皆是假想操作，不加入既有 r2 工作事實。所有建議在情境開始時都尚未被員工接受。

| 情境 | 保留原待審處理時的效果 | 持續工作稿時的效果與代價 |
|---|---|---|
| 原稿「有維護約定才月檢」。AI 誤改為「所有專案都月檢」，後來另補正確故障處理 | 可只取消月檢建議，恢復原条件，保留故障內容；聊天／手改亦可用 | 員工指出月檢寫錯，AI 對目前稿作新修正，或員工直接改；變更前後都可查。**沒有個別建議的確定性取消操作**；AI 修正可能失誤，須核對真實結果 |
| AI 加入月檢，員工補「B 案除外」，AI 再調整措辭 | 接受時保留最後全文；人改待審的效力及取消是否包含人工補充需明列 | 人與 AI 持續使用包含 B 案例外的最新版；手編另記一次實改。沒有必須結清的舊提案，也不把手編稱為批准整份 JD |
| AI 因月檢新增專用紀錄要求，另补可独立用于故障處理的技能 | 取消前必須顯示月檢與相依紀錄的完整影響，獨立技能保留；關係不能讓框架猜 | 顧問依更正回查，修正月檢及受影響要求，保留獨立技能；這是需驗收的內容修正能力，**不是已保證的群組回退** |

兩條路都要具備完整變更可見、人工編輯、保存／重開、來源回查，以及相依內容不自相矛盾的專業驗收。整版還原會影響其後所有內容，不拿它冒充上表的個別取消。

|---|---|---|---|
| A：保留可持續續改的待審建議 | 持續訪談、不強制每次處理；需要時接受／取消完整建議，亦可手編 | Plate＋codec 已有局部正證；§7.2 的歸屬／相依／結算設計仍需補足。必要时須另行同意擴充引擎範圍，不能先保證只是薄接線 | 保留 B05／B06；後續人工／相依細節仍需決定 |
| **B：持續工作稿＋完整變更查閱（本次推薦）** | AI 在理解足夠時更新工作稿；員工讀差異、聊天更正或手編；每次改稿可回看 | 使用已選 Plate 原生編輯／diff／history 接點及必要有限呈現、版本保存。省去長期未決建議歸屬，但不省略 diff 反例、來源或錯誤恢復驗收 | **取消持久的個別待審接受／取消流程**。更正後形成新版，不提供按早期未確認建議還原的保證。保存不等於員工批准或專業品質通過 |
| C：同處待審先處理，再繼續改 | 可以繼續訪談與其他工作；AI 或人要改同一待審範圍前，先接受／取消該建議 | 減少長期交疊鏈，但仍需原生成員隔離與單組結算驗收；「不重疊」不保證鄰接 ID 不沿用，不稱零額外整合 | 保留獨立待審處理，改變人與 AI 能直接續改待審內容的體驗；未處理時該處改稿會等待，員工增加確認操作 |

推薦 B 的產品理由：員工主要提供工作事實，AI 顧問負責轉寫，持續對話與最新稿是工作中心；員工有能力指出誤解，不必承擔每項修改歸屬的管理。完整差異与历史仍必需，**不是為了容易通過目前 probe 就降低內容保真或隱藏修改**。這是本案推論，沒有實際 UX 試用證明 B 一定優於 A；若 Owner 重視個別取消的操作保證，應保留 A 並正面處理其整合成本。

現行 [Codex review](https://learn.chatgpt.com/docs/code-review)以 Git 狀態、diff 與回饋續改提供檢查能力，也有 file／hunk revert；不能引用它證明「沒有個別取消更好」。[Claude Cowork](https://support.claude.com/en/articles/14729249-use-artifacts-in-claude-cowork)公開後續修改、每次保存新版、比較及還原；未公開任意語意建議分組。[VS Code](https://code.visualstudio.com/docs/agents/run/review-code-edits)同時說明新 Agent Host 直接保存、舊 extension host pending 路線。2026-09-09 定點複核結果集中於[證據 §2.12](evidence/2026-09-09-jd-app-tool-and-review-contracts.md#212-plate-選定後的審閱取捨複核)。**共同原則是可檢查及可修正，不能以「大廠共識」替 Owner 選 A／B／C。**

### 7.5 若採 B，完整流程及正式化影響

以下只使提案可評審，不先採用：

1. 持續訪談與既有 Memory／來源回查。某項工作理解足夠才 `jd_read`／`jd_edit`，不是每輪改稿。
2. 一批原生編輯在候選完成，App 核對 scope／baseline／內容／來源，再保存文件 revision 與結果。失敗及未知結果沿既有接線稿，不讓 AI 說成已完成。
3. 員工預設讀最新版，實際變動有入口與前後全文，刪除也可查。未讀的較早變動仍可找回，不能只留下最近一次摘要；具體已讀狀態不等於品質批准。
4. 員工可聊天補充／更正、選取請 AI 改或直接編輯。手編保存進同一文件；AI 下一次讀它，不用舊 Memory 強行覆蓋。重要事實衝突依既有訪談方法釐清。
5. 原生 session undo／redo 保留其已驗邊界；跨重開以已保存文件恢復。歷史比較唯讀；若另提供整版還原，必須明示整份影響，不能暗當個別取消。本次不把整版還原增為採 B 必備功能。
6. 匯出使用明示的已保存 working revision，與對應原始問答一起供真人後續核對。未引入登入、角色或專業「滿分」的自動核准標記。

B 一旦 Owner 同意，須將 B05／B06 的「個別接受／取消」部分明確 supersede，保留最新版、独立內容保留、完整相依修正及實際差異可查。B04 的人工續改 pending 分支不再適用，不能寫成自動接受。原 accepted view／核准文件 authority 必須由 successor ADR 明定新效力；**仍沒有 permission 可以直接改 production。**選 B 不等於 U／正式 profile／Agent 綁定／整份 JD 品質已驗收。
