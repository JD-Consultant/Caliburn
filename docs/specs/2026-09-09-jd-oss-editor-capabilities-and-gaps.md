## 2. 文件與資料庫：先確認可保存的文件，再決定資料表

以下是依文件能力推導的 **Mapping／待驗設計方向**，不是已採用格式或 DB schema。

| 保存路線 | 優點與必要限制 | 本輪判斷 |
|---|---|---|
| 編輯器正式結構文件＋工作稿版本／實改資料 | 保留段落、清單、工作身分、格式及必要來源引用；重開可持續編輯與查閱歷次差異 | 已选工作稿方向；按固定 clean profile 與交易實證定稿，不能只看到 JSON.stringify 就宣稱保真；不含持久 suggestion chains |
| 每項 JD 欄位各自拆成資料表，再組成編輯文件 | 可細粒度查詢，但必須另證明文字、位置、關係與審核狀態的雙向同步 | 暫不優先；C01 的語意結構不等於需要逐欄一張表或一個工具 |
| 純文字／Markdown 作主檔，另外解析為結構與審核資料 | 容易接文字 patch，但 rich text、身分與修訂如何往返仍需接線 | 保留為對照，不因 LLM 能編文字就推定適合本案 |

PostgreSQL 官方支持關聯資料與 JSON 並存，並建議 JSON 資料對應業務上不可合理拆開的原子單位；更新 JSON 所在列仍會取得整列鎖。`jsonb` 不保留 JSON 外層排版、物件 key 順序或重複 key，因此 byte-for-byte 的 JSON 字串相等不能作唯一完整性證據。這些是資料庫契約，不是「大廠規定 JD 必須用 JSONB」。[DB01：PostgreSQL 18 JSON Types／Designing JSON Documents](https://www.postgresql.org/docs/18/datatype-json.html)

**推薦的設計順序：**先取得候選真實的序列化文件，逐項確認內容、身分、pending 與已接受視圖；再設計文件保存單元、版本前置條件與讀取投影，最後才具體化資料表。現有 PostgreSQL 可作驗證起點，沒有現成證據要求新增另一套資料庫；本輪不升級 DB、不搬舊資料、不回接舊 schema。

資料庫交易可以讓多項 DB 寫入一同 commit／rollback，但瀏覽器已套用的 editor 操作不會因此自動回復，SDK retry 也不等於外部寫入只發生一次。後續設計要明列「畫面已改但未保存、保存已完成但結果未收到、版本衝突」的處理；是否需要交易內保存操作結果，要由實際執行位置及恢復需求決定，不先建通用事件引擎。[DB02：PostgreSQL 18 Transactions](https://www.postgresql.org/docs/18/tutorial-transactions.html)

Google Docs 的批次預檢、原子套用及 requiredRevisionId／targetRevisionId 提供版本與操作結果的公開參照；其 `SUGGEST` 寫入及 suggestion responses 在所讀 2026-07-07 文件中屬 Developer Preview，不能將最新預覽能力當成所有編輯器的成熟共同能力。[DB03：Google Docs batchUpdate](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/batchUpdate)

## 3. 專業顧問如何接到編輯器

此處只將已有核心知識映射到編輯能力，沒有改 prompt／Skill／Memory，也沒有新模型實測。

| 顧問情境 | 編輯器／工具需要支援的效果 | 內容依據 |
|---|---|---|
| 訪談資訊尚不足 | 可以繼續追問、保留未確認，不強制改稿或補齊所有欄位 | [完整工作分析指南 §2–§6](2026-09-09-complete-work-analysis-guide.md) |
| 已確認的新責任或條件 | 找到相關工作範圍，提出需要的局部修改；已有條件與未變工作保留 | [欄位與寫作指南](2026-09-09-jd-field-and-writing-guide.md) |
| 一個新案例 | 可供理解及說明依據，不自動新增一個永久任務 | [資訊取捨](2026-09-07-work-case-and-understanding-information-selection.md)及[深度校準](2026-09-09-customized-jd-depth-and-interview-calibration.md) |
| 員工更正先前說法 | 修改確實受影響的內容，不能把另一個有效案例或責任一起刪掉 | [深度校準](2026-09-09-customized-jd-depth-and-interview-calibration.md) |
| 員工直接改文件 | 下次顧問讀目前文件；不可只信舊 Memory 或前一份 AI 草稿 | C01／C02 最新文件方向 |
| 整份完成檢查 | 工作→JD 與 JD→依據雙向盤點；不把每輪局部編輯強制升級成全量重分析 | [樣稿依據與核對](2026-09-09-jd-sample-basis-and-review.md) |

**銜接建議：**同一主顧問按需要使用文件工具；背景 Memory 整理不變成第二個 JD 編輯者。工具傳回實際文件結果，語意理解不足仍回到訪談；不靠格式檢查器裁定工作事實真假。依[MEM-Q005](2026-09-04-memory-persistence-and-jd-effect-reconciliation.md)，未來同一 run 的理解及 JD 候選已通過自身驗證時，不一律等背景 Memory 落盤才能產生增量修改。

日後必須用未拿來調整工具的新職位案例驗證上述效果；目前 r2 受僱前端與 CT49 接案前端各自保留情境，不混成一份員工真相。本輪尚不能宣稱既有顧問已能穩定生成或續編 JD。

## 4. 免費開源候選與真實差距

以下為原始碼／官方測試閱讀的結果，**不是本機 editor 實測**。精確版本、來源與逐項可證範圍見[Plate 證據](evidence/2026-09-09-jd-oss-plate.md)、[其他開源方案](evidence/2026-09-09-jd-oss-alternatives.md)。

| 路線 | 已找到的免費原生能力 | 會改變選擇的差距 | 推薦用途 |
|---|---|---|---|
| Plate／SuggestionPlugin | suggestion 資料、文字與區塊修訂、按 suggestion ID 接受／拒絕、特定人工輸入與格式修改的正式 transforms | 任意底層 apply／move／split／set_node 不會因此全部變可退回修訂；持久保存、相依群組與重複 AI 改寫仍需核對 | **第一個有限驗證方向**，不是已採用完整產品 |
| Tiptap 開源核心／ProseMirror＋免費第三方修訂層 | 結構文件、transaction／mapping；找到有 license、原始碼及測試的第三方追蹤修訂 | T01 的一般 programmatic 文字插入／替換不自動追蹤，格式與特定節點操作另有接點；HTML metadata 往返與多重定位有具體 source 疑點；官方 track example 是 commit/revert 範例 | 保留對照；未證免費完整 AI 審核接線，不先補造通用層 |
| Lexical | EditorState、JSON 序列化、NodeState、歷史與正式編輯接點 | 未證第一方完整 suggestion 審閱產品；NodeKey 不持久；複製／拆分後業務身分需另外核對 | 作結構底座比較；缺原生審閱層時不為湊候選自造引擎 |

Plate 優先的具體理由是：已找到可由程式使用、能產生修訂的公開文字 transforms，以及依 suggestion ID 結算的免費接點；相較之下，T01 的一般 programmatic 文字修改會被追蹤判斷略過，T02 又有執行時取第一文字匹配與審核依 range 的限制。因此先驗 Plate 能較直接回答本案 AI 局部續編的問題；這不是成熟度排名或完整採用結論。

Plate 的官方 AI helper 必須與 SuggestionPlugin 分開：`applyAISuggestions` 的輸入整理會移除既有 suggestion metadata，`acceptAISuggestions` 的實作會接受 transient 修訂；不能把文件中「permanent」的措辭誤讀為「保留長期待審」。該 helper 路線與多組待審文件持續被 AI 改寫不是自然等價。優先候選使用[一般 suggestion transforms 的已知接點](evidence/2026-09-09-jd-oss-plate.md#9-最少整合路線既有-agent-只用-suggestionplugin-已覆蓋的-transforms)；選取定位、目前內容讀取、正確包裝接受／拒絕及結果回報仍是 App 整合工作。

保存疑點已由[實測 R01-4](evidence/2026-09-09-jd-native-pending-review-comparison.md)證實：移除粗體的 pending metadata 含 `bold:undefined`，JSON 往返丟掉该鍵，reject 不恢復粗體；記憶體控制組可恢復。這阻擋 raw suggestion JSON 直接作完整 durable codec，不否定 Plate 文件底座，也不代表換 DB 即修好。候選現成 codec 的來源與未驗界線已列於該稿 §6，原反例不改判。

**結論：Owner 已同意以 Plate 為文件底座，但目前沒有一個完整組合已由證據證明覆蓋所有 JD 效果。**R01、P01、F01 保留限定驗證；下一步是沿選定底座完成必要接線與審閱設計，不重跑原正證，也不由此直接啟動 production。

## 5. 大廠共同原則與產品政策不能混在一起

完整來源及版本差異見[App／工具／審閱契約](evidence/2026-09-09-jd-app-tool-and-review-contracts.md)。

**共同基礎（跨來源 Inference）：**模型取得合適的狀態與工具說明，提出操作；執行方檢查目標及範圍、執行、保存並回傳真實結果。格式合法不等於工作內容正確；工具呼叫完成不等於文件保存完成。定位不存在或過時時，回可行動資訊讓同一模型修正，不要求模型自行猜測行號或文件版本。

| LLM／App 情境 | 官方證據與本案需要驗證的接點 |
|---|---|
| 模型知道能做什麼 | 工具說明交代用途、輸入、結果與限制；App 已知的文件身分及目前狀態由 App 提供／核對。初稿、局部文字與結構操作分別對照候選公開能力，不先把每個 JD 欄位都做成工具 |
| 模型定位修改目標 | OpenAI patch 使用 diff 上下文；Anthropic `str_replace` 要唯一精確匹配，`view`／`insert_line` 仍使用行位置。因此不存在「行號工具一律淘汰」共識；本案應讓 App 提供目前選取與可驗證目標，再由 editor 原生能力推導定位形式 |
| 形狀錯誤、目標不存在或重複 | 格式驗證與語意檢查分開；錯誤指出哪個條件不成立及可重讀資訊。T02 多匹配執行仍取第一筆，正好說明不能只看函式名稱就信任唯一性 |
| 讀取後目標被人修改 | Google 精確 revision 前置條件是參照；編輯器位置 mapping 不保證工作身分或語意仍相同。App 需判定該目標還有效或回報過時，不能讓模型盲用舊位置 |
| 一批操作只有部分完成 | Google 提供原子 batch；OpenAI patch 由整合端決定原子性。Tiptap `chain.run()` 的 false 不保證沒有 dispatch。後續契約要列實際套用範圍，不能把布林值當整批回滾證據 |
| 保存失敗或回覆遺失 | 區分已套用未保存、已保存但結果未收到、結果未知。先讀實際版本與操作結果；相同 `call_id` 只關聯呼叫與回覆，沒有自帶去重或一次套用保證 |
| 模型修復或停止 | 對可修正且已知結果的錯誤提供有界修復；部分／未知結果先對帳。無法定位、無法確認副作用或重複無進展時停止該操作，留下可供員工處理的狀態；不直接套用供應商範例重試次數 |

表中後續 App 責任是跨契約的本案映射；不是已完成的錯誤格式或通用 retry engine。完整來源與各項 Fact／Inference／Unknown 見上述 evidence §2–§4。

**沒有唯一共識的是審閱政策：**

| 官方產品／模式 | 公開行為 | 對本案可借用的範圍 |
|---|---|---|
| Claude Code 的 VS Code 整合 | Manual mode 顯示編輯前提案，可在接受前人工修改 proposed diff，Claude 會得知人工調整 | 支持「人工修改不必等於接受」，但不是本案同一持久 pending 文件或保存交易的完整實作證據 |
| VS Code 新 agent-host | 直接套用保存，沒有 pending approval；以 diff／版本／checkpoint 等審閱 | 支持先改工作稿再審閱的不同生命週期，不能因此默默取消本案 AI 審核政策 |
| VS Code 舊 extension-host／舊 session | 有可重開的 pending 與 Keep／Undo；stage 可使 pending 自動接受 | 舊文件與新模式必須分開，不能當同一固定流程 |
| Word／Google Docs 的追蹤／建議模式 | 人工變更可被追蹤或作建議，再接受／拒絕 | 支持以編輯模式區分變更；人工改既有 suggestion 的 merge／split／身分細節仍需逐產品核對 |

因此 Owner 重議 B04 的要求成立：可以比較更簡單、更符合候選原生能力的政策，但不能說「業界已淘汰人工修改後仍待審」。採用任一方式仍是 JD 的產品選擇。

## 6. 可供討論的具體審核生命週期

**沿革閱讀註記：**下列 A／B／C 與 §6.1 是同意前的選項與判準。Owner 已依 §6.2 確認訪談主導的產品方向；不再要求重選框架式 A／B／C，原先持久逐項修訂優先的驗證排序須重新對照該效果。

| 後續完整情境 | 已知限制與需要決定的效果 |
|---|---|
| AI 新增任務，人補說明，再拒絕新增任務 | 原生刪除 insert block 會帶走 descendants；要決定哪些補充隨任務退回、哪些須保留或移出。不能把所有子內容預設為獨立，也不能默默丟失 |
| AI 改了兩處，其中一處再有相依修改 | suggestion ID、同輪操作與語意相依群組不是同一件事；首批先驗獨立修訂，跨位置依賴再決定合併審閱或限制操作順序 |

**先行產品題是員工如何理解、修正與確認 AI 轉寫的工作內容。**A／B／C 提供生命週期對照，不能代替 §6.1 的產品判準；上表隨同一方向收斂，不並行建立多套工具／資料模型。

### 6.1 從非 JD 專家員工的成品效果判斷

2026-09-09 Owner 進一步要求說明：產品是 AI 專業 JD 顧問，協助不擅長撰寫 JD 的員工形成符合本人實際職位的客製文件，應如何判斷審閱流程。**本節是研究者補充的產品推論／待討論建議，未取得新的產品裁決。**上方 A／B／C 是初步方案，不應把「底層持久修訂」與「何時、如何請員工確認」當成只能綁定選擇；Plate 先驗的工程理由也不足以證明 A 最適合員工。

**判斷目標：**讓員工能辨認及修正自己的工作被如何表達，讓顧問承擔工作分析、專業轉寫、適當粒度與完整性檢查。員工熟悉親身工作，不代表能一次說齊隱性判斷與低頻責任，也不代表能評估 JD 寫作方法；因此確認、追問與成品品質各有責任，不能用接受按鈕數量證明品質。內容依[分析指南 §3／§6](2026-09-09-complete-work-analysis-guide.md)及[客製化校準](2026-09-09-customized-jd-depth-and-interview-calibration.md)。

| 判準 | 對員工與顧問的具體要求 | 不足以證明成功的現象 |
|---|---|---|
| 工作事實與個人職位差異 | 看得出主責／協作、條件、範圍及重要遺漏；顧問以實例和中立問題補足 | 文字流暢、只替換職稱、員工按了接受 |
| 員工能作出判斷 | 呈現有上下文的完整工作敘述及重要差異；可用自己的話指出錯處 | 只顯示字詞 diff，要求員工判 Task／Duty 或相依修訂 |
| 能邊理解邊修正 | 尚未想清楚可保留未知、繼續說明、再改同一內容 | 必須先接受自己仍不同意的提案才能續談 |
| 合理的確認負擔 | 在有意義的工作範圍整理後確認，優先指出會改變責任的差異 | 每次潤飾都打斷，或把所有錯誤留到最後整份 diff |
| 意圖與操作後果清楚 | 改一句、確認整段、退回一項要能區分；確認取當下版本 | 人改一個數字便默認其他 AI 子句全部獲確認 |
| 專業完整性與可恢復性 | 顧問做工作→JD、JD→依據核對；員工能補漏與更正，退回不傷無關內容 | 把查漏與專業品質全交給非專家，或只證明按鈕可操作 |

**外部依據及效力：**查閱日 2026-09-09。[Microsoft HAX Design Library](https://www.microsoft.com/en-us/haxtoolkit/library/)現行仍列依情境介入、有效修正、疑義釐清及說明操作後果；它源自 2019 研究，是持續使用的設計基礎，不是本案員工實測或新的 LLM 契約。[Google PAIR Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/)要求回饋方式符合使用者的理解層次、清楚呈現回饋影響，並依任務能力與情境平衡自動化和控制；不能把互動行為直接等同某一意圖。兩者是行為設計參照，未採其程式、介面素材或新套件。上述 JD 流程是本案映射，不稱大廠共同規定。

**依產品目標的推薦假設：**同份工作稿持續共同編輯，由顧問在有意義的工作範圍整理後，引導員工確認是否符合實際工作；有疑義可直接說明或編輯、保留未確認，再續改。詳細字詞差異作核對工具，不要求員工逐個技術修訂作決策。顧問不能因有審閱功能便省略撰寫前的內容檢查；重點提示也不代表未提示的 AI 改動自動核准。

這保留 A 的持續性，借用 B 的聚焦確認節奏，**尚未選定底層資料或審核引擎**。B 的「同範圍必須先結算才能再改」可能妨礙釐清，C 的「事後全靠版本差異」可能使非專家漏看責任變動；這些是待驗假設，不是已測結論。若 native OSS 只能實現不同效果，仍應交回具體代價，不默默自造機制。

對人工續改目前較有產品理由的主張是：**修正局部不自動表示整個 AI 建議都已確認。**這不要求每次人工動作都另建修訂，也不預設永遠沿用同一 suggestion ID；待審如何歸屬與結算仍須以選定方案的實際行為說清楚。

**補充的產品驗證：**在 editor 能力驗證之外，以相同工作事實和完整畫面情境比較非專家是否能發現「協助被寫成主責」「特定案件條件被泛化」「重要低頻工作遺漏」，能否自然更正、保留不確定並理解確認／退回後果；另由 JD 專業準則核對成品。觀察錯誤保留、未變內容保留、確認與修正負擔及完成品質，不以接受率或速度單獨決勝。本輪未做員工測試，因此不給虛構分數或宣稱 UX 已驗收。

### 6.2 Owner 已同意的產品方向：訪談主導，AI 持續撰寫

2026-09-09 Owner 回覆「同意」，並說明理想體驗與真人顧問的後續使用。以下為 **G3／WORKING 產品方向**，取代仍等待選擇主流程的狀態；不是套件、資料庫、production authority 或完整 S3 細節已核准。

1. **員工以聊天室持續訪談為主，保留審閱能力。**員工提供經驗、回答問題、閱讀目前 JD，能隨時補充、更正或表達不確定；他可以判斷有沒有寫錯、理解錯、歸錯本人責任或漏掉工作。不能要求他具備判斷 JD 專業品質的能力，也不能把「主要閱讀」解讀為取消審閱。是否逐筆接受與確認時機是另一層規則，未由本次說明定死。
2. **AI 顧問承擔主要分析與撰寫。**使用已有訪談、理解與目前 JD，主動選擇有意義的補充、重寫、結構整理及完整性核對。持續優化指隨理解進展改善成品，不是每條訊息都必須修改或無限改寫。
   Owner 後續明確補充：先對某項任務取得足夠理解，能依真實資訊寫清其工作時才撰寫；新的有效責任、例外或更正實質影響原稿時再改。重述、佐證案例及尚未釐清的線索不自動觸發 JD 寫入。這是顧問依既有方法作的內容判斷，不設固定輪數、必填門檻或自評分數，也不把背景 Memory 每次整理當成改稿指令。
3. **人可直接編輯，但正常成功路徑不依賴人手修稿。**員工可編輯、真人顧問可在後續核對時修改；AI 後續續編須讀到當時最新內容，保留有效人工修正。既有「局部更正不等於確認整個 AI 建議」的意圖判準保留，不因此先定 suggestion ID 或每次操作的核准機制。
4. **App 可保存多份彼此隔離的文件。**每份文件對應一名員工一份完整職務工作的持續分析，而非單次問答或一項 Task；相對應的原始對話、理解與 JD 必須保持歸屬與可恢復性。這是產品工作單位，不預先指定一張表或一種 editor JSON。
5. **真人顧問後續取得相對應的原始訪談與 JD。**能核對 AI 是否忠實反映員工工作、查找依據、補充或修改。訪談與 JD 的配對和可閱讀性是必要效果；下載、匯出或在本機 App 接手等取得方式待設計。此角色分工不自行擴張為帳號、多租戶、遠端多人同步或權限系統。
6. **編輯系統是 App，LLM 是使用 App 的顧問。**App 提供讀取目前文件、執行原生編輯、保存、呈現與錯誤回報；LLM 使用這些能力完成分析與轉寫。編輯能力需同時服務 AI 與人的操作，不能以聊天室顯示全文作為已更新正式文件的證據。
7. **「完整、完美、滿分」是成品質量目標。**驗收須具體看完整工作覆蓋、本人責任與適用條件、必要專業、沒有補造或遺漏、來源可核對、員工更正被保留，並支持真人顧問複核。AI 自稱滿分、欄位填滿或談話輪數不等於達標；仍有重要未知時如實保留，不以無限追問或自行補齊取得漂亮成品。
8. **AI 修改必須可見、可對照，不可靜默帶過。**Owner 隨後明確補充員工仍可審閱，也需要知道 LLM 改了什麼。App 必須讓員工知道受影響的範圍，能核對全部實際新增、刪除與改寫的前後內容；顧問摘要或「我已更新」不能取代真實變更證據。員工可據此指出錯誤或請 AI 說明、更正。差異呈現、閱讀完整正文與是否逐筆接受分開設計；不因減少員工負擔就隱藏小改動或把未看過視為已確認。

**審閱責任的精確分工：**員工核對「符合我的實際工作嗎、是否誤解或遺漏」，AI 顧問承擔分析、撰寫與持續品質檢查，真人顧問後續對原始訪談及 JD 做專業核對或修改。員工可能發現品質問題，但產品不能以他能評估專業品質為成立前提；員工審閱過也不等於所有品質項目已通過。
