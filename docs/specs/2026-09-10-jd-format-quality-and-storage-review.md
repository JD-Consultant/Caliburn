# JD 內容、關係與保存設計核對

**Owner後續格式裁決（2026-09-10）：**本報告封存的是研究選項及當時核對結果。Owner之後大致同意[整份格式](2026-09-10-jd-format-review.md)，並明確指定成果與要求在任務底下兩組並列，不配對、不互為父子、不與任務敘述合併。下文「有增益才單列／可融入敘述」及K／S仍待整體採用的狀態因此成為沿革；內容範圍、未知界線及保存缺口仍有效。工作要求的新名稱另推薦「工作執行要求」，不新增內容類型或推定Owner已核准DB候選；正式分組／引用契約依register的下一G4單位完成。

## 1. 結論與效力

建議保留正文六章，將任務的九列分析面向收斂為五類閱讀內容：**任務敘述、工作成果／產出、工作要求、所需知識引用、所需技能引用**。時機、適用條件與分工依實際約束對象就近寫，不再預設三個平行欄位。任務可有多個成果、多項要求；兩者不強制一對一，也不強制所有要求只能放在成果下面。

不預設 JD「尚未釐清／尚未歸屬區」。訪談中的疑點與待追問事項沿既有 Memory 保留；已寫進 JD 的草稿及尚未分組的有效任務仍保存。會影響讀者理解職位的重要不確定性，不能全部藏在 Memory；已確認組織本身尚未決定權責，亦可能是可首次寫入的當前工作事實。

同一 PostgreSQL、完整文件不可變版本、head 與操作回執的保存方向仍有合理依據；**現行 v1 尚未表示可辨識的知識／技能項目與任務引用**。新增多對多效果需要擴充文件及操作契約，不能把節點有 ID、JSON 能保存或先前 201 項檢查通過，當成引用完整性已實現。優先推薦完整同版本文件內保存項目及單向引用，App 驗證整份候選；若另需SQL約束或查詢關係投影，再考慮同交易派生關係表，但其與正文的一致性仍須驗證。全面改為關聯式文件 authority 不是由「多對多」三字就能推出的結論。

## 2. 沿既有方法逐層核對品質

| 核對層 | 本輪實際檢查 | 結論／限制 |
|---|---|---|
| 目的與真實性 | 格式描述目前職位；r2 的職稱、部門、主管、本人與其他角色分工對回情境1–2、4–6、10–15 | 六章可承載；不得從姓名、職稱或員工背景推資格／權限 |

| 易讀與持續修訂 | 檢查同一限制是否被九列重複填、未知是否新增預設工作區、共用K／S改動影響 | 精簡面向的固定外觀，保留內容；共用項目需可看引用影響，不能靠模型記住所有連結 |
| 實際顧問與 App 品質 | 對照既有[責任稽核 §6](2026-09-10-jd-responsibility-and-evidence-audit.md#6-用實際成果證明選擇)的文件、模型工具、專業顧問、持續品質四層 | 本輪只到研究及有限 shape 反例；自然訪談、未見職位、長期更正、保存恢復、延遲成本依後續驗收 |

### 2.1 會不會少欄位

[分析指南十四個面向](2026-09-09-complete-work-analysis-guide.md#2-要完整理解哪些資訊)皆有可表達去處：

| 分析內容 | 成品去處／保留方式 |
|---|---|
| 定位、服務對象、目的 | 基本資料、職務目的與任務敘述 |
| 日常、周期、事件、專案、低頻、收尾 | 全工作範圍與不同任務；不新增固定八項上限 |
| 觸發、必要輸入、本人行動、專業判斷 | 任務敘述；會影響合理處理的部分亦可在工作要求中寫清 |
| 成果、接收者與交接 | 工作成果／產出，或明確指向該成果的交接要求 |
| 完成品質、時效、持續維持、異常 | 工作要求及其適用條件 |
| 權限、協作、前後依賴、資源／人員管理 | 任務敘述或局部要求；真正管理工作本身列為任務，不能只藏在表頭 |
| 頻率、負荷、風險、環境、感官／注意要求 | 按範圍就近表達，本職位跨任務共通者入工作條件；不從職稱推定能力分數 |
| 知識、技能、必要工具、資格 | K／S總覽與用途；真正必要資格在條件章，不將員工履歷全部轉職位門檻 |
| 時間、適用範圍、更正、未知 | 已支持的當前工作與局部限定；分析中的問題沿Memory保留，見 §4 |

**目前沒有新增核心章節的證據；有兩個應補清的內容提示：**工作敘述要能保留必要輸入與判斷，成果要能表達接收者／交接；非辦公工作要能表達操作、感官及持續注意要求。這些原已在分析指南，應補清其成品去處，並非再建立四組必填欄。UCSB 的實際JD指引要求具體行動、判斷及與工作直接相連的專業；O*NET另列工作情境，支持這些分析面向。兩者用途與固定項數等規則不能全部照抄。[^ucsb] [^onet]

## 3. 時機、條件與分工應放在哪裡

**先判斷它約束哪段工作，再決定放置位置。**它們是有適用對象的內容，不是天生只能放任務、成果或要求某一層的三種資料。

| 適用對象 | 放置建議 | 對照與反例 |
|---|---|---|
| 整項任務 | 任務敘述或其清楚標示的補充 | r2任務8：「對有月檢約定的專案按月檢查」。若只藏在一項品質要求下面，其他文字容易被讀成所有專案都有定期責任 |
| 單項工作要求 | 條件與要求同句／同項 | r2任務4：查詢逾時可重試；訂單結果不明須先避免重複及查狀態。提到任務頂層寫成通用「逾時就重試」會造成錯義 |
| 某項成果 | 在成果說明或明確指向它的要求中交代 | r2任務6：交付版本須與檢查結果一致；交接說明要供接收者使用。不能因兩者同屬一任務，就套用所有同一品質條件 |
| 執行、轉交或核准動作 | 相關敘述或要求 | r2任務2不得自行承諾報價／客戶期限；任務6客戶確認驗收。角色可以出現在表頭，但何時須確認仍要在工作中看得懂 |
| 多任務真正共通 | 職責說明或全份工作條件，明說範圍 | 「全部維護都依服務範圍」可集中；不能藉分組令沒有月檢合約的工作也按月執行 |

iCAP 的內容定義及 NOS 的 performance criteria／scope 提供可交叉核對的依據，並存不同放置層；詳細版本、原文位置及不能外推的部分見[內容與scope附件](evidence/2026-09-10-jd-content-scope-quality-audit.md)。**本案就近表達原則不是自製條件繼承引擎，也不要求 LLM 判填一個 universal scope enum。**

### 多個成果與多項要求

一個任務可以同時形成多個成果；工作要求可能約束過程、單個成果、多個成果或持續維持。保存不能要求 `一任務＝一O＝一P`；閱讀也不應強制 `Task→每個O→各自P`。需要辨認某要求約束哪項成果時，在文字中明指該成果；若未來有逐成果審核／驗收用途，才另研究可操作的顯式關係。本轮不預造 O↔P 全關係網。

以現有情境10整理任務6可寫成：

- **任務敘述：**準備前端交付內容，配合發布、驗收與維護交接。整理可辨識的交付版本、操作或維護說明、已知限制及交接事項，並配合處理發布過程中的前端問題。
- **工作成果／產出：**可辨識的前端交付版本；接收者可使用的操作／維護、已知限制及交接說明。
- **工作要求：**交付版本與檢查結果一致；發布問題提供重現資訊；涉及服務端部署時與負責該部署的後端工程師協作；客戶驗收由客戶確認。

這是既有明示內容的重排，不增加期限、測試數或交付物。可讀的條列就是多項表達，不等於每個句子都要獨立資料表。

## 4. 未知與未歸屬是否留在 Memory

前版將「尚未釐清／尚未歸屬」合成文件旁的一列，混淆了**尚未能成立的分析結論**與**已有文件內容的組織狀態**。建議移除這個預設區域。

| 情況 | 建議責任與呈現 | 不可丟失的界線 |
|---|---|---|
| 訪談線索、待追問、互相矛盾的說法 | 原文／既有Memory保留分析脈絡；顧問選擇追問，足以支持才寫JD | 不為填版型轉成確定任務，不另造Gap清單 |
| 已能寫清的任務，只是職責分組未定 | 在JD保留該任務，可先直接列工作章節，之後再分組 | 未分Duty不是未理解，也不要求虛構Duty |
| 員工直接輸入的草稿或未完成句子 | 沿原本手編與保存流程保留在JD；AI下一輪知道有人改動，必要時求證 | 不靜默刪除、搬Memory或冒稱已保存；保存失敗仍沿既有輸入恢復規則 |
| 已知工作仍有會改變責任解讀的不確定性，包括已確認組織本身尚未決定重要權責 | 保持有依據的限定，必要時在相關文字如實說明；不以先前已寫入JD為前提，分析脈絡仍留Memory | 組織確實未決與訪談尚未問清不同；不能把未知寫成確定，也不能擅自縮窄或撤銷有效工作 |

這裡不新設狀態碼、待辦抽屜、審閱權限或另一份工作理解。**「先不撰寫未知結論」與「不能遺失使用者已寫的草稿」可以同時成立。**實際Memory／原文owner及官方使用界線見[Memory／草稿附件](evidence/2026-09-10-jd-memory-draft-boundary-audit.md)。

## 6. 資料關係與保存：現有設計哪裡對、哪裡不足

### 6.1 先核對真實契約

[現行 schema](contracts/jd-editor-v1.schema.json)為86 defs；本輪觀測 SHA256 `CED26A3B625DE891989A63D5F12E4AC884484083D7F677CF10AD8C54E318B973`，未修改。

- `JdSavedElement`／`JdNewElement`有 `jd_section`、`jd_duty`、`jd_task`及一般富文字節點；`section_kind`可以辨識knowledge／skills章節，但不等於章內每項已有正式K／S身分。
- profile 的 `jd_task = body+` grammar（實際節點以 `children` 保存）可保留多段、多項清單與條件，已能承載多成果／要求；此為文字結構能力，沒有表示每個O／P都已成獨立業務物件。
- 沒有任務↔K／S連結欄位、K／S項目型別或其關係操作。新增任意知識ID屬性會被現行封閉schema拒絕。
- `source_refs`的責任是訪談依據，不是JD項目間的適用關係；不能借欄混用。
- 一般字串、標題、表格行或普通節點ID本身，不提供「這是一項完整知識」的契約；名稱、排列序號亦不能作永久身分。

上述由[DB與語意引用附件](evidence/2026-09-10-jd-semantic-relations-storage-audit.md)的實際定義核對與有限AJV反例支持。反例也證明shape通過不會自動抓出文字中不存在的K99或重複Element ID；後者本來就有App唯一性檢查責任，不能改報為新DB漏洞。

### 6.2 公開共同原則與差異

PostgreSQL官方允許JSON與關聯資料並存，建議JSON有可預期結構，並按不可獨立更新的業務單位考慮範圍；JSONB不會替應用提供內部ID引用外鍵，整row更新亦有鎖定代價。[^pg-json] FK／UNIQUE可以保護關聯表，CHECK不適合作跨row持續一致性驗證。[^pg-constraints]

Microsoft Cosmos DB、MongoDB的公開建模文件依共用、獨立存取、更新方式及關係複雜度討論嵌入或引用；AWS Amazon DocumentDB指引亦要求依查詢模式選模型。它們是不同資料庫的選擇判準，不證明PostgreSQL有相同限制，也不是跨產品同一份JD schema；各原始來源、版本、限制見[DB附件來源表](evidence/2026-09-10-jd-semantic-relations-storage-audit.md)。OpenAI／Anthropic未公開JD編輯內部資料庫，保持未知；不能用其產品行為猜SQL表。

本地與隔離配置是 `postgres:16`，只固定major，未由本輪取得正在運行的patch／digest；PG16仍在官方支援範圍。研究需看現行資料，但不用「較新major」本身當更換資料庫的理由；正式施工前記錄实际版本与运行配置。

### 6.3 三個實質候選

| 方案 | 正文與關係的唯一來源 | 優點／代價 | 推薦及切換條件 |
|---|---|---|---|
| **A 完整同版本文件＋項目引用** | 同revision JSONB內，每K／S正文一份，任務保存對應；反向用途由App導出 | 一份版本即可完整重開／比較；App須驗同文件同版本、target種類、唯一性及刪除影響，DB不直接FK到JSON成員 | **本版優先**：單人、整份JD原子發布、同文件共享；仍須補正式項目／工具／保存驗證，不能靠任意props |
| B 同一正文＋同交易派生關係表 | JSONB仍唯一正文；同revision成員／連線投影由App生成並用SQL約束 | 可加SQL FK與直接查詢；需同交易保證投影與正文完全一致，禁雙向手改；FK不證明抽取完整 | 需要關係投影的SQL約束或直接查詢時考慮；不是繞過App直接改JSON仍可自動保證引用完整性 |
| C 按版本拆成關聯式內容authority | Task／K／S／內容及edges為正式關聯資料，Plate是呈現 | 適合高度獨立共用與SQL查詢；需完整保住富文字順序、群組、history與同版本讀取，可能大改document owner | 只有產品主要用途轉為跨文件資料管理／獨立項目生命週期才重議，不能同時留下另一可寫Plate正文 |

A的「整份revision」是本案原子發布需要：員工讀到的任務、K／S和對應必須是同一版。並非宣稱Task不能單獨編輯，也非認為所有文件都應整份JSON保存。若將來分析、共享範圍改變，需按上述條件重新比較。

### 6.4 採 A 時仍必須補齊的效果

1. 每項完整K／S有穩定可識別身分；章節、表格、儲存格或文字名不隨意冒充。具體原生包裹／metadata及工具參數需依Plate能力定稿。
2. 語意判斷由顧問負責；App配身分、保存單向關係並產生反向清單。LLM不填雙向兩份關係、版本、資料庫鍵或展示流水號。
3. 引用只能解析到該文件該revision的正確種類項目；讀r1不能解析成r2的新文字；歷史頁不查current頭替換target。
4. 改名／移動保留身分與引用；引用解除不刪共享正文。刪仍被引用項目時須有明確影響處理，不能留下失效引用或靜默刪除其他任務；體驗細節隨格式採用後定稿。
5. 複製整份／部分文件、跨文件貼上必須核對ID重新分配與內部引用對應；不能只複製字串或只更新節點ID。來源回查仍沿原owner，與內容引用分開。
6. 拆分／合併Task或K／S時保留有依據的範圍，App不猜專業適用性。單一批次應以最終候選整體驗引用，且清楚區分草稿不完整與失效引用。
7. 文件、關係、實際差異、版本與回執在同一發布結果閉合。沿既有[保存契約](evidence/2026-09-10-jd-storage-contract-closure.md)的交易、base檢查、no_change與同operation對帳，不繞過先前ER03停止策略。
8. **首次建立及連結仍有契約缺口：**現行工具的目標由保存後讀取發配，模型不能替新K／S或Task猜ID。因此「同批新增項目並互相引用」尚無已證明接點。若允許中間保留未連結草稿，可研究先保存項目、重讀取得引用、再連結；若要求一次原子建立及連結，須再核官方原生／工具能力。不能默默自造批次暫存ID或把多次保存說成同一原子操作。

這些是選定方案需要承擔的責任，不是已完成的實作。以App完整檢查保護JSONB引用是有明確代價的選擇；B也只用FK約束派生關係，仍由App保證投影與正文完全一致。若要求繞過App的任意SQL寫入亦全面阻擋JSON內部失效引用，A與此處的B皆不足，須另評DB機制或C的關聯式authority，不在本輪默默新增trigger。
