## 1. 推薦與產品取捨

推薦 **一般文字預設自動保存，明示結構操作完成後整組保存，清楚顯示保存狀態與實際改動**。員工主要在訪談與核對工作內容，不應每改一段都記得按整份保存。保存只表示持久化了目前工作稿，不表示已完整、正確或經專業核准。

| 方案 | 員工效果與代價 | 本案判斷 |
|---|---|---|
| A．持續工作稿自動保存 | 文字短暫停頓後保存；新增／移動／刪除在完成明確操作後保存。需處理保存中的後續輸入、清楚的失敗狀態及更正方式 | **Owner 已選定方向**；符合反覆製作與降低忘記保存的目的 |
| B．只自動暫存，按保存才成為目前 JD | 可累積修改再整批決定，但需區分暫存稿與正式目前稿，AI 何時看見手改也更複雜 | 本案目前沒有保留這兩種可用正文的需求；不以它冒稱一般自動保存已完成 |
| C．維持整份明示保存 | 整批邊界清楚，但員工需記得保存；關頁前仍有遺失未提交內容的風險 | 現有草稿的行為，可作比較，不因先前寫過就不能重審 |

採 A 會改變「關頁時捨棄本輪全部修改」的含義：已成功保存的部分持續存在，關頁不能暗中撤銷。歷史查看、正文更正及撤回須有可理解的出口；不把自動保存等同任意早期修改的一鍵拒絕。

## 3. 推薦的使用者流程

| 情境 | 候選行為 | 不能混淆的界線 |
|---|---|---|
| 修改既有的一般文字欄位 | 輸入法完成、短暫停止輸入後自動保存；離開欄位或明示「立即保存」可加速送出。精確延遲及連續輸入的最長待存時間留待互動驗證 | 保存當下文字不代表顧問認定內容完整；不每字新增操作，不在中文組字中截斷送出 |
| 新增任務／成果／要求 | 新增入口先容納未完成輸入，完成這項新增動作後，將已填且可保存的內容一次寫入 | 沒填完可留草稿；不能為滿足 DB 必填補造文字，或先保存空殼再強制模型補填。可保存最低條件沿既有草稿研究重審 |
| 移動、刪除、選擇關聯 | 使用者明示完成後，由同一業務操作保存全組效果；刪除仍呈現影響，D01 保留任務 | 自動保存不代表自動決定刪除；不在拖曳經過中間職責、選單尚未完成時先改關係 |
| 修改有相依的多個欄位／項目 | 需提供能完成同一工作意圖的編輯單位，再整組保存 | 不能以任意輸入停頓切碎不可分割的更正；具體範圍與 UI 由 JR-R01／JR-R05 設計閉合。不是所有欄位都無條件獨立自存 |
| AI 修改 | 顧問有足夠資訊才提出完整業務操作，App 驗證並保存，回報真實結果；不再等員工按整份保存 | 輸出的 token、聊天說已更新、模型工具呼叫結束，都不能代替持久化結果；正常結束／取消以每項實際已保存結果為準 |
| 員工送出下一輪訪談 | App 先完成當下可保存的手改並核對結果，再形成模型可讀的最新版及人工變更通知 | 仍有無效輸入、保存失敗或結果未知時，先給明確出口；不默默讓 AI 依舊版覆蓋新輸入。保存 JD 不等於送出尚未提交的聊天，也不改寫 Memory |
| 開歷史、匯出、切文件／封存 | 同頁歷史保持可讀；匯出目前稿與離開動作先確認所需內容已保存，輸出綁定確切版本 | 不能丟掉尚未送出的內容，或在保存未完成時匯出舊內容卻稱為最新；其他文件不能受到此文件的延遲／錯誤污染 |

日常保存不要求再按整份「保存」。若保留「立即保存」或快捷鍵，只是提早完成同一待存工作，不增加另一套權威。需要保留何種快捷入口可由畫面可用性驗證決定，不要求 Owner 選時間參數。

## 4. 狀態、歷史與恢復的必要條件

1. **保存狀態：**區分「有尚未保存內容」「正在保存」「已保存」「保存失敗」「結果尚待確認」；只有服務確認這次資料與回執持久化才稱已保存。送出中不因畫面文字已改便顯示成功。
2. **保存時仍能打字：**一般文字的正常背景保存不應每次打斷輸入。候選方向是保留已送出的固定內容與後來的新輸入，同文件寫入依序完成；較舊回覆只能確認它自己的內容，不能清掉後續輸入。確切 buffer、版本承接及故障契約仍須有限設計／實驗，不能沿舊「保存時鎖輸入」直接聲稱已達成。
3. **前景 AI 與寫入互斥：**沿已同意 AI 回合暫停手改；啟動 AI 前先完成手改保存。自動保存的排程不能在 AI 已取得工作範圍後再偷送舊內容；舊讀取仍按版本規則拒絕，不為了自動保存就無條件換成新 base。
4. **歷史不是每個按鍵：**目前候選仍每個成功業務保存有可查 revision／receipt，不刪去已承諾的操作證據。可評估在歷史畫面分組連續打字，保留展開的精確改動與作者界線；不能只比較起終點而隱藏改了又改回，也不能讓人工事件因分組而不進模型通知。分組／保留政策未凍結，不照抄 Microsoft 的分鐘數或 Google 的版本限額。
5. **取消與更正：**尚未提交的輸入才可直接捨棄；已自動保存者須作明確更正或沿另定撤回流程處理。停止 AI 不能假稱撤銷先前已保存內容；不恢復舊 pending 接受／拒絕系統。自動保存推薦必須搭配撤回效果討論，舊「所有未按保存的操作一起捨棄」不再普遍成立。
6. **故障與重開：**保留尚未保存的候選並清楚提示；已送出結果未知時先依原 operation 查回。可恢復暫存是候選資料，不是第二份目前 JD。普通未送出輸入的重開保護、儲存空間不足及瀏覽器清理的處理須明定後再驗收，不能因有 AutoSave 就承諾斷電前所有按鍵均不遺失。
7. **重試：**首次自動提交與故障後重試不同。本輪不更改既有「未知先對帳、錯誤有限處理」；不打開所有 POST 的自動重送。若後續要對暫時故障自動重試，須先證明同意圖、同 payload、原 key、已知／未知結果、退避上限及舊請求晚到均有正確出口。[W1]

網際網路中斷可能影響雲端模型；本機 API 與 DB 正常時的手動管理不應因此失效。若本機保存服務本身停止，畫面只能按真實狀態顯示尚未保存或結果待確認，不能用「離線」一詞掩蓋差別。

## 5. 與現有設計的差異及下一工作

| 現有責任 | 採 A 後必須修訂的地方 |
|---|---|
| [整體設計 §3.2／5.1](2026-09-12-jd-relational-editor-design.md) | 原「全部先入 command buffer、按保存再提交」須改成按編輯種類明確觸發；不能只加 debounce。JR-R01 的完整新增／跨項更正同時閉合 |
| [原員工旅程 §4–5](2026-09-10-jd-employee-journey-design.md) | 保存時停輸入、普通 dirty 僅記憶體、切頁捨棄與送聊天先保存的銜接需改；原稿仍代表已驗隔離行為，研究推薦不抹去該結果 |
| [保存交易 §6–9](2026-09-12-jd-relational-schema-and-write-contract.md) | 自動觸發不改唯一 relational current authority；JR-R02／03 已修訂並通過[文件窄複核](evidence/2026-09-12-jd-relational-save-contract-review.md)，仍須實測；保存節奏造成的成本與增長列有限驗證 |
| [工具契約 §4／8](2026-09-12-jd-relational-agent-tool-contract.md) | 人與 AI 的整組效果一致；人工通知必須涵蓋所有已保存改動，但不能把每次打字暫停當需要顧問回應。通知可有界分組，原始事件仍可追查 |
| [手改恢復契約](2026-09-10-jd-manual-recovery-transport-design.md) | 保留 exact submission／receipt 對帳，不把更新中的 buffer 改成原請求內容；需明確接上送出後又輸入的新內容與普通草稿恢復 |

選方向後，按下列有限情境補可驗證設計；此清單目前均 **未執行**：

- 繁中組字、取消組字、換行、連續長輸入與離開欄位；空白或短暫不合欄位規則的輸入不被補造／靜默丟棄。
- 保存 A 送出後繼續輸入 B，A 回覆晚到；B 仍存在且最後正確保存，不出現假「全部已保存」。
- 多項任務資料一次新增、移動、D01 刪職責及含共通限制的更正；沒有半個業務效果。
- 手改立即送聊天、立即匯出、切另一文件；使用確切新版本，失敗有出口，未送聊天不被自動送出。
- DB 保存失敗、回覆遺失、服務重啟、正常關頁及程序崩潰；分清已存／待確認／可找回草稿，無重複或跨文件污染。
- 多次自動保存→AI 改→人改→重開→AI 續編；人工通知、實際歷史與當前內容一致，純訪談可以沒有 JD revision。
- 長段輸入的延遲、保存耗時、revision 增長及歷史可讀性；依觀察調整有限參數，不先造歷史壓縮或通用回退引擎。

**研究結束條件已達：**官方做法支持已選方向，精確觸發與可靠性需由本案情境驗證；不再廣搜等待某家公開同樣的 JD schema。後續[保存與 AI 交接設計](2026-09-12-jd-autosave-and-handoff-design.md)承接本稿 §3–5 的待補細節；共同業務操作／撤回與適用範圍仍需閉合，不直接施工或把 G4 標通過。

**本輪證據範圍：**一名唯讀子代理獨立核 Google／Microsoft 四份產品文件，主代理重開核對關鍵條文，並補讀 OpenAI／Claude／AWS／Web API。完成文件研究，未做保存實驗、自然模型或全設計獨立審查。
