## 2. 工具粒度：保留具名操作，補完整工作

| 候選 | 代價與判斷 |
|---|---|
| 原七個工具逐欄保存 | 無法一次新增已知完整任務，跨欄更正可能只成功一半；原反例已足以否定這個限制，不等待真模型犯同樣錯誤 |
| 具名操作＋完整新增＋有界內容修訂 | **採作驗證候選**。一般單欄簡單，完整更正能同時改正文、增刪成果／要求與調整引用；共用 domain command，不新造跨呼叫 transaction session |
| 任意 command array／整份 JD 替換 | 可表達範圍大，但要模型管理組合依賴、臨時身分與覆蓋範圍；目前有限操作足夠，不採為第一版入口 |

**新增任務：**一次包含已知名稱、完整敘述、成果、要求及對既有知識／技能的引用；name 或 description 至少一個有意義，其餘可空。App 產生任務與子項身分、順序和關係，全部驗證後一次保存。不是必填六套資料，也不先存名稱空殼。來源按任務、每項成果／要求及每條 K/S 引用分別附原有 refs，不能把同一來源盲掛所有子項。

共享知識／技能可獨立存在，先由具名新增操作建立並取得 refs，後續任務引用。新 task 不接任意臨時 ID 或跨新物件引用表。若先前已完成的独立能力定義仍存在、後續 task 新增失敗，須如實回報，不能宣稱整份 JD 已完成或自動刪掉共用資料。這是兩個明確業務效果；不可用它為拆碎同一任務正文辯護。

**相關內容修訂：**以 `jd_revise_work` 一次提交同文件、同基準的一項完整更正。允許既有欄位全文修正、任務成果／要求增刪、對既有 K/S 的 link／unlink，以及全職位條件增刪。例如澄清本人只做技術診斷時，可一起修正文、增加判斷／交接要求、移除誤寫承諾並解除錯誤的客服技能引用。僅限明列型別，不含職責／任務／K/S 定義／協作對象的建立刪除、移動、選區、任意路徑、遞迴命令或臨時 ID 相依圖。這些結構操作仍走各自入口。

全部 refs 先按同一 base 解譯；同欄重複、同項又改又刪、同一關係又 link 又 unlink，或排序 anchor 指向本次刪除項，整組拒絕。先組出並驗證最終候選，再一起寫入同列最終值；例如把僅有名稱的 task 改成「名稱空、敘述有內容」不能因逐欄中間狀態而誤拒絕。新增項目的身分由 App 產生，同容器／同 anchor 按輸入順序呈現，不讓模型引用本次尚未保存的新 ID。

**結構與必要內容調整：**任務跨職責移動或 D01 刪職責時，允許隨該具名操作修改相關既有欄位、為仍存活任務新增成果／要求。這是上述有限 variants 的 `set_field`＋`add_task_detail` 子集；不另造規則。不能先改 parent／刪 scope，再要求下一個工具補回內容，也不能因尚無成果／要求列而把內容塞錯欄。正常單純排序／刪子項的調整陣列為空；App 驗非空調整僅用於允許的結構操作與相關存活目標。

**有限上限：**初次契約驗證以最多 64 個內容變更、每欄 UTF-8 64 KiB、單請求 1 MiB，以及單次新增任務最多 128 個子項／K/S 引用合計作起始配置。這是防止無界 payload 的本案驗證參數，非官方數字，須以完整樣稿與長任務核對後固定。超限在 mutation 前整組拒絕、回可讀限制；不截斷、不偷偷拆批。若不可分割工作超限，調整明示上限或方案再驗證，不能宣稱局部完成等於完整操作。

## 3. R05 裁決：必要範圍隨任務，職責摘要不產生繼承

### 3.1 取捨與決定

採 **任務卡本身保留任務特有的必要範圍**。敘述＋成果＋要求共同表達完整工作；不要求一句話塞全部，也不強制同義重複。職責名稱與 scope_text 概括工作群組，不能是任務必要限制的唯一存放處；真正適用整份職位的條件仍在第六章，局部例外放回任務。

理由：既有研究要求動作、範圍及差異可辨認；本案又明確需要未分組任務、跨職責移動和 Excel 輸出。結合兩者，不能讓任務的必要含義只依 parent 文字存在。這是研究者依授權採用的產品映射，**不是 O*NET／AWS 規定所有文件都要重複條件**。

| 方案 | 取捨 |
|---|---|
| 必要範圍就近保留在任務卡 | **採用**；可能有少量必要重述，但讀取、移動、解除分組時含義較穩定；不新增 schema 欄位或繼承系統 |
| 共通限制只留職責 | 每次移動／刪除更依賴重新解讀 parent，且匯出單任務容易失去限制；不作新稿常態 |
| 另建條件庫、適用關係與自動繼承 | 能管理共用條件，但新增資料／使用負擔；目前只有知識技能共享有明確管理需求，沒有足夠證據擴張此模組 |

此裁決取代格式中「部分必要限制只存在職責說明也足夠」的可選路線，不取消職責摘要或全職位條件，不改成果／要求兩組並列或 K/S 多對多。不搬舊資料。

### 3.2 固定例子與同頁操作

**合成例子：**職責 A「約定維護」摘要寫「以下維護均限服務合約」，任務 T 只寫「處理系統異常」。員工希望把 T 移到「客戶問題處理」。已知實際工作仍受合約限制時，正確結果是 T 保留原身分，敘述成為「僅處理服務合約內系統的異常」，再改分組；不是直接複製 A 的全部摘要，也不繼承目的職責其他限制。沒有依據則先保留有依據的未知或追問，不猜合約範圍。

手動操作仍在原頁：顯示來源職責摘要、任務卡、目的職責摘要及變動範圍；需要時可直接修正任務敘述／要求，完成後一起保存。AI 的讀取也必須提供同樣相關上下文，再提出同一具名操作；不把「已讀 ref」當成它已專業理解。

刪 A 時，App 預覽完整 A 摘要及全部受影響任務；原任務保留未分組。仍有效但只在 A 的內容，在同一候選先放到適當位置再刪 A：整項任務的適用範圍放 description；安全隔離、交付前功能確認放 requirement；故障診斷與修復紀錄等交付物放 outcome。缺少對應子項時就在同次操作新增；不能為了限制工具形狀，把要求或成果塞回敘述。沒有受影響任務的獨立修改不進此操作，成果與要求兩組仍分開。

### 3.3 保存前置與責任界線

App 驗同文件／同基準、目標與來源／目的容器存在、完整影響資料已供目前操作預覽，以及內容調整只指向此次相關且保存後存活的目標。Web 的明示完成與模型的具名呼叫都提交完整候選。提供 preview 不增加另一套待審狀態或獨立稿；預覽版本過時就要求重讀，不能隱藏新出現的任務。

App 能驗的是關係、目標和原子性，**不能用 SQL、關鍵字或一個 reviewed=true 证明自然語言條件已保留**。工作含義的取捨由員工／顧問作；顧問指引及內容驗收必須檢查前後限制。UI 說明提示職責摘要的用途，仍完整展示即將移除的原文；不聲稱格式規則會自動阻止所有人工誤寫。若輸入本身違反「必要條件就近」規則，須先在當次整理候選修正，不能把這個反例藏在歷史而稱保真。

來源也不自動複製：原 duty links 隨 duty current 目標移除，歷史仍保留；存活任務舊 links 因文字改變按既有 digest 成為需重新核對。模型重新查原材料後才能對新文字附已發配 basis_refs；人工搬文字本身不等於重新驗證來源，也不寫 Memory。

### 3.4 從完整工作分析核對欄位與操作

已回讀[完整工作分析](2026-09-09-complete-work-analysis-guide.md)、[欄位與寫作](2026-09-09-jd-field-and-writing-guide.md)、[深度與訪談校準](2026-09-09-customized-jd-depth-and-interview-calibration.md)、[完整样稿](2026-09-09-frontend-engineer-jd-sample.md)與[樣稿依據／審查](2026-09-09-jd-sample-basis-and-review.md)，依[現行格式](2026-09-10-jd-format-review.md)映射。下表只記對操作的約束，不建立第二份欄位定義。

| 內容意義 | 對設計的約束 |
|---|---|
| 分析工作全貌、低頻責任、例外、判斷與交接 | 分析面向不是全部必填欄；重要差異不能為縮短文字或同類分類而丟失 |
| 任務：本人做什麼、對象及必要適用範圍 | name／description 不強制雙填；任務卡的正文及子項合讀仍可辨識完整工作 |
| 成果／產出：形成或維持什麼 | 可為服務結果或狀態，不強制生成文件；與要求分列，不做一對一配對 |
| 工作執行要求：如何適當完成、品質／安全／異常交接條件 | 有明確資料時可新增或修正要求列，不能塞進 description 以迴避工具缺口；案例中的失誤不自動成為正常標準 |
| 共享 K/S：完成工作所需理解與可運用能力 | 定義一份、任務引用；改正責任可解除錯誤引用，仍保留其他任務的使用；任務特有運用方式可就近說明 |
| 更正與未知 | 可撤回錯誤主張，保留其他有效工作、必要未知與案例差異；不是只允許在既有文字上追加 |

原初稿的「只改既有欄位」及「缺要求列可放敘述」與此基準衝突，已依內容審查修正；首敗與複核另存證據，不把原初稿稱通過。

## 4. R04：整欄與選區的唯一語意

整欄工具接 field_ref 與完整新全文；選區工具接 selection_ref 與只取代片段的新文字。空替換可移除所選片段，但不可用這項工具刪除任務。對 `prefix + selected + suffix`，唯一候選為 `prefix + replacement + suffix`，前後逐字保留；重複文字依 App 選区，不全文搜尋。

App-only 選取接法：

1. 員工按選取後請 AI 修改時，Web 捕捉同一 textarea.value、field identity、selectionStart／End；先依自動保存流程完成組字與保存。確認保存後欄位仍等於捕捉的 LF 值，才以新已確認 field_ref 建立選區；不在 rerender 後拿移動過的游標猜原選區。不符時保留請求並要求重新選取，不先送模型。
2. Web 把 start_utf16、end_utf16、selected_text 交 App 驗證；這些不進 LLM 參數。App 核同 revision 欄位全文、`0 ≤ start < end ≤ UTF-16 length`、精確片段與合法 Unicode 邊界，再發 opaque selection_ref。跨欄選取與空游標不冒稱選區，留原欄一般編輯。
3. 正式欄位換行在所有寫入入口統一 CRLF／CR→LF，再驗值及產 digest；不做 NFC、trim 非全空白文字或替换不可見字元。既有「全空白可選文字→NULL」規則只在最終整欄候選上執行，不能先 trim 所選片段或 replacement。
4. Python 後端採標準 UTF-16LE 嚴格編碼，以 code-unit 邊界分段後嚴格解碼 prefix／selected／suffix；不能直接 Python text[start:end]。切進 surrogate pair、倒置／超界或不合法 Unicode 明確拒絕。只做原生字串單位轉換，不造模糊定位、分詞或 grapheme 擴張引擎。
5. 保存時再驗基準、欄位全文及選區摘要；過時拒絕，不改找另一段同字，也不退回整欄替換。前端 setRangeText 可呈現候選，正式結果仍走相同保存 service。來源必須符合正式來源目標的整段內容，不因片段替換便把局部依據提升成整段已核。

## 5. 固定驗收與停止條件

下列均 **尚未執行產品實測**；研究用純字串計算不等於瀏覽器或 adapter 通過。

| 情境 | 必須結果 |
|---|---|
| 新增有正文、兩成果、一要求、既有 K/S 的任務；第二子項無效 | 全部不新增，只回真實保存結果；成功時整組一次 revision，無名稱空殼 |
| name=null、description 已有有意義內容 | 可保存不完整但有依據的任務；不強迫模型補名或其他未知 |
| 更正任務要求＋全職位權限，第二欄過時／無效 | 整組不變；不得靠下一個工具補救先提交的第一欄 |
| 更正相同欄兩次、混版本、超限 | 整組拒絕；不猜順序、不自動拆批 |
| 技術診斷誤寫成客服承諾，再得到澄清 | 同次修正文、增刪要求及解除錯誤 K/S link；另一項有效月結工作保留 |
| 被刪 duty 唯一載有安全隔離／功能檢查及維修紀錄交付；task 尚無子項 | 同次按意義新增 requirement 與 outcome，不混入 description、不新增兩者配對 |

## 6. JD 與 Memory 的反覆修訂

Owner 最新補充的是能力要求：**LLM 能反覆修正 JD 與 Memory**。兩者都可隨新資訊補充、更正、刪去錯誤主張或重新整理；初稿和已保存版本不是不可修改的終稿。顧問判斷本輪要修 JD、Memory、兩者，或先追問；不要求每輪修改，也不要求兩者一對一同步。

JD 使用本稿的共同業務操作；Memory 沿[既有即時修補與背景整併](2026-09-06-analysis-only-agent-memory-design.md)，現行接點以[決策入口](../current-decisions.md)的 CT24／25／30／35 路由為準。背景也會修正舊理解，不只追加；新資訊未形成已發布目標時沿既有累積策略。不藉本需求重啟已 PARKED 的额外收尾攔截／語意檢查、不重寫既有 patch 參數。

App 分別提供兩者的實際結果與有效版本；JD 已保存不代表 Memory 更新，反向亦同。一方失敗或結果未知，不能宣稱兩者共同完成；各沿原 owner 的 operation／receipt 對帳，不重做已成功的一方。JD 原子操作不涵蓋 Memory 發布，不建立跨兩者交易或通用回退引擎。

人工修改 JD 後，App 先提供[人工變更通知](2026-09-12-jd-relational-agent-tool-contract.md#8-人工修改如何進下一輪-context)，不直接寫 Memory、不冒充員工原話。顧問核對變更及依據，必要時釐清，再沿既有 Memory 能力修訂理解。來源沿[既有精確原始問答引用](2026-09-10-jd-context-change-and-source-research.md#4-jd-是否要引用-memory)：Memory 可協助找回材料，裸可變 Memory 路徑不能作永久 JD 依據。舊引用仍可開啟不表示它勝過較新更正；`needs_recheck` 目前只驗 JD target digest，不能假稱會自動判斷內容被後續談話推翻。

追加待驗：同一工作先寫→補充→更正，JD 與 Memory 各自可多次修訂且保留其他工作；兩者成功／失敗交叉及回覆遺失分開報告與恢復；手改→下一輪讀差異不污染原始問答；舊引用仍可讀但新理解已更正時不改回舊說法；含糊、新資料、純重述與已正確內容不被強制寫入。固定操作只能證明接線，自然訪談另驗是否正確判斷與保留資訊。
