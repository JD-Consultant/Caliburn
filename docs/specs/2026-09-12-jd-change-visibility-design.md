# AI 直接改稿後，員工如何看見實際變更

- 日期：2026-09-12；Topic：JD-R002；CV-01／G2 呈現候選，待 Owner 看示意後討論。直接改稿、不逐次接受的效果已確認。
- 接續：[需求 §13](2026-09-12-jd-relational-editing-requirements.md#13-cv-01ai-直接改稿與可見差異2026-09-12)、[結構化畫面](2026-09-12-jd-relational-editor-design.md#6-差異歷史與來源)、[整輪 JD 撤回](2026-09-12-jd-ai-turn-undo-design.md)。本稿未修改產品畫面或資料庫。

## 1. 員工要得到的效果

AI 有足夠資訊時可直接修改並保存 JD，不需要員工每次按接受。員工平常看到唯一的目前工作稿；能知道 AI 改過哪裡、看到確切修改前後，再決定直接更正、請 AI 改或撤回符合資格的整輪 JD 改動。查看或關閉差異不是保存、接受、專業核准或 Memory 寫入。

「讓員工知道」的可驗收含義是 App 主動提供持續可找回的變更提示與真實差異入口；不能宣稱提示出現就證明員工已閱讀或同意。聊天摘要可以解釋理由，但不可取代保存結果。

## 3. 呈現方案

| 方案 | 使用效果與代價 | 判斷 |
|---|---|---|
| A．目前稿標記＋同頁按需展開差異 | 平常讀乾淨的最新版，改過的欄位有具名標籤；本輪變更區統一包含刪除、移動與引用。點一下看改前／改後 | **推薦討論基準**；閱讀負擔較小，需點開才能看細節 |
| B．修改處直接展開改前／改後 | 改過的欄位立即顯示對照，同頁變更區補刪除與結構變動 | 較醒目，長敘述或整份初稿會佔篇幅；舊文須明示唯讀，避免誤認兩份稿 |
| C．只在聊天顯示摘要與歷史入口 | 畫面最簡單，但員工容易漏看正文變動，且摘要不保證完整 | 不推薦；不足以單獨滿足可見性要求 |

A／B 都不新增接受／拒絕待審流程，也不另開「更正稿」頁。合成示意可切換 A／B，最終預設尚待討論。

## 4. 建議的同頁操作

1. **成功保存時更新目前稿。**每次 confirmed commit 更新對應內容與本輪提示；AI 還在執行時顯示仍在整理，員工可看，手改按既有前景鎖暫停。未知結果顯示正在確認，不先宣稱保存成功；一輪部分已保存、後續失敗時分別列明。
2. **本輪有持續可查入口。**例如「這輪已修改任務敘述、新增成果、移動任務」，可展開完整變更。完成／取消後保留該輪入口；下一輪入口有明確輪次，歷史仍能找回。純訪談不偽造改稿提示。
3. **欄位與關係都看得到。**改寫提供完整欄位前後；新建顯示新項目及 owned 子項；刪除在變更區保留原文與所屬位置；移動顯示原職責→新職責；排序顯示原／新位置。新增／解除 K/S 引用與修改共用定義分開，後者列該版本受影響任務。來源連結的增減也列明。
4. **目前稿唯一可編。**歷史對照中的前後內容均唯讀；前往目前項目才去現行欄位手改或請 AI 更正。已刪項目不偽造目前編輯入口。觀看差異不阻擋下一次訪談，沒有看完才繼續。
5. **符合資格才可整輪撤回。**依 HR-02 顯示「撤回這輪 JD 改動」，明示訪談／Memory／案例保留；有較晚 JD 修改時停用並解釋。這不是每次編輯都要按的確認，也不是 AI 取消。

## 5. 差異的責任與版本

- App 沿 schema 的 stable ID／operation base-result snapshots 產生精確欄位及關係差異，Web 呈現同一 DTO。模型不填計數、版本或自行撰寫差異證據。
- **整輪與逐次分開。**正常連續一輪用 HR-02 的完整 run 歸屬得 S／E，預設看 S→E 的淨結果，並可展開全部已保存事件。同欄多次修改不遺失中間變動；改後改回時顯示「本輪沒有淨變更；曾有保存紀錄」。無 committed operations 時是沒有修改 JD，不用相同話術掩蓋曾改回的事件。
- 若同 run 不連續，不把 S→E 含其他人的變更都標成 AI；只列該 run 各 confirmed operation 的精確差異，標明無單一連續比較。無可信 run 歸屬時列已知逐次歷史，不能猜輪次或顯示整輪撤回。
- **歷史範圍固定。**該輪對照固定當時 before／after，不拿較晚 current 拼入。head 已前進時，標「這輪當時的改動；目前稿已有後續修改」；第一版清除舊輪目前稿欄位標示，保留歷史入口，不把人工較晚文字標成 AI 所寫。
- 查看不改資料。關閉展開區、點進或下一輪開始不代表員工接受，第一版不建已讀／核准資料表。刪除事件不會回流成模型眼中的有效任務。
- **完整欄位前後對照先保證資訊完整。**逐字高亮是可選輔助，未有實測必要性前不承諾原生能力；若採用，另核免費 OSS 授權、繁中／換行及效能。不為此恢復全文 Plate或自己發明字元定位、通用 diff 引擎。

## 7. 依大廠 UI 補核後的明確推薦

Owner 看過示意後詢問研究者推薦，並要求參考大廠 UI。**研究者仍推薦 A 作第一版預設：目前稿正常閱讀、修改位置具名標示、本輪入口持續可查、點開才看完整前後。**本節是推薦補強，尚不改寫為 Owner 已批准預設。

理由是本案員工主要核對是否忠實反映自身工作，JD 又有多層任務／成果／要求；長期同時展開全部改前改後，會增加閱讀篇幅、讓舊文字與現在工作混淆。這是由產品用途及上述公開 UI 推導的取捨，不是已完成員工測試的結論，也不是各大廠唯一相同的版型。

具體預設：目前欄位用「本輪修改／新增／移入」等文字提示；本輪入口列清楚變更種類，**有刪除也直接列出**，不可只靠已消失的卡片或短暫通知。點選後同頁展開完整前後、結構與引用變動；願意細看者可再開欄位內對照。新範圍及較晚手改仍依 §5 分界，舊輪從歷史找回，不增加接受／已讀狀態。所有差異來自 App 已確認的保存材料，不用模型摘要當證據。
