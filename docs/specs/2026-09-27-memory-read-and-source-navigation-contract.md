## 1. 已確認的讀取內容

| 入口／內容 | 模型取得什麼 | 接下來如何使用 |
|---|---|---|
| 工作理解導覽 | 目前讀取範圍內**所有工作理解**的可讀目標 `target_title`、`description`。 | 把所選 `target_title` 帶入理解讀取工具；不預載正文。 |
| 工作情境導覽 | 目前讀取範圍內**所有工作情境**的可讀目標 `target_title`、`description`。 | 把所選 `target_title` 帶入情境讀取工具；不必先經過理解。 |
| 讀一項工作理解 | 該理解的內容欄位 `title`、`description`、Markdown `body`；**分開的來源資料**列出被引用工作情境的可讀目標 `target_title`、導覽描述。 | 從來源列選 `target_title`，按需讀被引用情境。 |
| 讀一項工作情境 | 該情境的 `title`、`description`、Markdown `body`；**分開的來源資料**提供可供模型選取的正式訪談序號，App 保有其對應來源身分。 | 按序號讀指定歷史訪談訊息或範圍；正式序號與內部來源 ID 不混用，工具分支見 §2。 |

「所有」是目前職務檔案、讀取基準及 Agent 權限所允許的該層集合，不是所有檔案／所有歷史版本，也不因此把理解導覽交給 B1。導覽不是由檢索任意挑出的相關子集；若未來容量需要分頁或其他表示，另行說明完整性與取捨，不靜默漏項。

標題是模型可使用的目標定位資訊，供讀取及已授權的操作選物件；不要求模型猜內部 UUID 或 Memory 版本。同一職務檔案、同一候選／正式快照中，**各層內**有效 title 唯一，情境與理解可以同名；不跨 Memory 版本檢查重名。唯一性不授予跨層讀寫權限，層級及操作權限仍由相應介面和 App 綁定處理；標題正規化與改名後綁定仍見 §4。

## 2. 按需深入的流程

```text
工作理解 map：全部理解的 target_title＋導覽描述
    → 選 target_title → 理解正文＋被引用情境的 target_title／描述
                         → 選來源 target_title → 情境正文＋被引用訪談序號
                                                   → 選訪談序號 → 訪談內容

工作情境 map：全部情境的 target_title＋導覽描述
    → 選 target_title → 情境正文＋被引用訪談序號 → 按需讀訪談內容
```

以上是**目標資料流／未實作**。理解讀取不自動展開所有情境正文與原話；情境讀取也不自動附上所有被引用訪談全文。模型可依資訊需要停止或繼續深入，不要求每次寫 JD 都走完整條鏈。這不改 A 起始近期訪談與 B1 必處理原話的既定輸入責任。

例：理解「接案網站的前端逾時處理」的來源列出「電商訂單送出逾時」及「預約日期查詢逾時」各自的導覽描述。模型可只選前者讀完整情境，再依其正式訪談序號核對原話；內部來源 ID 由 App 映射。這是合成示意，不代表真實測試通過。

### 讀取入口與分支（工程設計／未實作驗證）

沿動賓命名選定 `read_work_situation_map`／`read_work_understanding_map` 取得相應完整導覽，模型 arguments 為 `{}`；`read_work_situation`／`read_work_understanding` 以 `{"target_title":"…"}` 取得單物件。這是既有讀取能力的具名表示，B1 只取得情境入口，A／B2 的資料基準仍依 §3；不以選工具取得其他層或版本的權限。

共用訪談讀取入口選定 `read_interview`，根為固定 `query` object，內含兩種互斥分支：

| `query.kind` | 模型參數及語意 | 結果 |
|---|---|---|
| `messages` | `sequences`：非空的正整數序號陣列；單則是一個元素，多則可不相鄰。重複序號按集合去重。 | 僅回所選有效訊息，依正式序號升序；不自動加未選訊息或重新編號。 |
| `range` | `start_sequence`、`end_sequence`：正整數且起點不大於終點，兩端均含。 | 回該閉區間內全部有效訪談訊息；不依相關度挑選。 |

所有模型參數均為選擇，檔案、來源資格與 A／B 的可讀上界由 App 注入。任一指定序號不存在、無效或超界，整筆拒絕，不返回部分成功的原文；容量不足回明確未完整讀取與可縮小範圍，不靜默截斷。兩分支不接受彼此欄位，不接受負數、零、小數、任意來源 ID 或模型自填 scope。schema 以 nested anyOf 生成，分支內 properties 全 required、禁止額外屬性，實際序列化與 provider 接受仍待驗。

訪談成功結果採精簡 JSON：`data_kind: "historical_interview"`、`messages[]`；每則含 `interview_sequence`、`speaker`、`text`，speaker 明辨 `app`／`employee`／`consultant`，text 為完整原文。起始 App 資料投影沿用這些逐則含意，工具本身仍是原生 function result；不因 speaker 欄位重包成新的 user／assistant 訊息。後續讀取或引用可直接選 `interview_sequence`。

```json
{"query":{"kind":"messages","sequences":[1,2,5,7]}}
```

```json
{"query":{"kind":"range","start_sequence":2,"end_sequence":7}}
```

### 訪談訊息、固定序號與回讀語境（目標／未實作）

**2026-09-28 Owner 最新補正：每則有效訪談訊息除了來源身分，還有職務檔案內固定的順序 ID；取消不用的輸入不佔正式訪談序號。**訪談可以是回答，也可以是員工主動提出新資訊；不限定為問答配對。按需讀取可選不相鄰訊息，也可選範圍；前版將所有語境都定成「連續訪談區間」過窄，本節取代該限制。Agent Turn 仍只指執行回合，不改成功完成才供背景取材的資格規則。

| 名詞 | 意義與界線 |
|---|---|
| 訪談訊息 | 訪談中正式成立的一則完整發話，包含 App 開場第 1 則、有效員工輸入或顧問完整正式答覆；有來源 ID、職務檔案內的固定訪談序號、真實出處／說話者及訪談原文。可包含多句、多段、補充、更正或問題，不是依標點拆成的一句話，也不是任意模型輸出 item。 |
| 來源 ID | 辨認「是哪一則原始訊息」的身分，不以它的字面大小、UUID 排序或 Agent 執行 ID 推斷先後。具體格式與保存接線未定。 |
| 訪談序號 | 表示一則有效訪談訊息在同一職務檔案內發話先後順序的固定編號；數字越小，發話越早，App 開場、顧問與員工共用同一套順序。不是本次工具結果的局部編號或 Agent Turn 編號。App 正式開場固定為第 1 則；其後員工輸入及顧問完整答覆待所屬 A Turn 成功完成才分配正式序號。取消輸入不佔號，既有正式序號不因取消、換 Memory 版本、查詢或壓縮而重編，不以奇偶推定出處。 |
| 訪談原文 | 一則訪談訊息的完整原始文字，保留說話者實際送出的內容；不是 App 摘要、改寫，也不是整段問答的合併正文。 |
| 訪談交流 | 包含 App 的正式開場引導、顧問後續引導與員工回答，也包含員工主動補充、新主題、更正或提問；問答只是其中一種關係，不強制配對或另建分組。 |
| 歷史訪談資料 | 過去已成立的有效訪談訊息，逐則提供訪談序號、說話者與訪談原文，明確標示為歷史訪談中的對話。可來自指定訊息或範圍，不要求序號相鄰，也不保證已包含完整主題；不含正在處理的當次輸入。 |
| 近期歷史訪談資料 | 歷史訪談資料中，App 依本輪固定的已發布 Memory 處理邊界組裝的尚未整理資料，並保留必要前問／顧問發話脈絡；不是固定最近幾輪，也不因個別訊息是否被引用而重定範圍。當次員工輸入另行提供。 |
| Agent Turn／執行回合 | 處理某次輸入的模型／工具執行，可有多個 Step；成功完成仍是來源准入邊界，但不是問答、引用或閱讀單位。 |

**2026-09-28 名稱已確認：**採用「歷史訪談資料」「近期歷史訪談資料」「訪談原文」；「訪談脈絡」不再列為待確認名稱，「訪談原文資料包」亦不採用。脈絡仍是需要保留的閱讀關係，不另建同名資料元件。包含導覽及近期歷史訪談的整份內容稱「模型參考資料」，承載它的訊息稱「App 資料訊息」；兩者的唯一共通定義見[上下文設計 §3.1](2026-09-26-consultant-context-and-state-design.md#31-app-資料訊息與原生項目的權限邊界目標已確認)。名稱不指定 JSON 欄位、儲存或新封裝元件。

**A 起始資料與按需查詢是兩種用途，不能混為一個選取規則。**

- **A 的近期歷史訪談資料：**App 依本 Turn 已固定的正式 Memory 處理邊界組裝完整近期歷史訪談資料，保留前問／顧問發話，本次員工輸入另外提供。這不授權只挑看似相關的未整理訊息。
- **超量例外（2026-09-29 目標／未實作）：**正常仍完整預載；超出容量時 A 可用下述同一訪談讀取工具按需取回有效近期訊息／範圍。App 應使未預載範圍可辨認，不把未讀資料說成已整理或已看見；不新增第二套搜尋入口。唯一產品邊界見[產品概念](../product-concept.md#顧問看得到哪些訪談原話目標產品決策尚未宣稱已實作)。
- **按需原文查詢：**允許選單則、多則不相鄰訊息（例如 1、2、5、7），或範圍（例如 2→7）。範圍查詢應保留範圍內完整有效訊息；指定訊息則不因不相鄰被拒絕。不再把工具能力限為向前幾輪，仍不引入語意／關鍵字搜尋。
- **共同呈現（Owner 已確認）：**context 預先放入的近期歷史訪談資料及工具回傳的歷史訪談資料，至少讓模型逐則看見**訪談序號、說話者、訪談原文**，且一眼辨認這是**訪談過程中的歷史對話**，不是目前的新發話、App 分析或工具撰寫的摘要。明示序號代表職務檔案內的發話先後，並保留來源身分；選 1、2、5、7 不重新編成 1、2、3、4，也不暗示中間沒有其他對話。不自行把相鄰視為問答關係或把分散訊息宣稱為完整主題。

**B1 同樣使用共用訪談讀取工具（2026-09-28 Owner 補充確認；目標／未實作）：**B1 也須取得與 A 相同的按訪談序號／範圍讀取能力，不是只有無參數的本批固定資料讀取。共同契約支援單則、多則及範圍，回傳相同的歷史訪談資料；B1 可選本批內的訊息，也可回查本批截止之前、更早的有效訊息。App 仍綁定職務檔案、合法來源及本批可讀上界；模型選擇讀哪些訊息，不得藉此改變本批必須整理的範圍、納入晚到訪談或取得未完成／取消的輸入。這是同一工具契約，不因 Agent 不同另造 B1 專用讀取規則；既有 B2 原話回查亦依共通契約及其授權範圍。起始資料的提供責任保持，具體參數／固定範圍重讀接線仍待工具細設，不在此新增入口或決定最終工具數量。

**B2 共用訪談歷史工具（2026-09-28 Owner 明確確認；目標／未實作）：**B2 為分析工作理解，可按需直接回查訪談原文，以釐清條件、責任、指涉及更正；不必每次請 B1 代查。沿用 A／B1 的單則、多則及範圍讀取契約，既可沿情境引用定位，也可按訪談序號讀取未被引用的有效訊息，不另造 B2 專用工具或搜尋機制。Runtime 固定同一職務檔案及本批訪談序號上界，排除晚到、未完成或已取消的輸入；模型不填控制上界。

B2 通常以工作情境為分析入口，資訊已足夠就不重讀；不要求每批重讀全部訪談，也不因此把全部訪談加入 B2 起始 context。讀取權不增加寫入權：發現情境缺漏或不一致，將具體問題與訪談依據交 B1，由 B1 處理情境；B2 只維護理解，不繞過情境層另造正式引用鏈。原話仍不足時保留未知，不靠回查能力宣稱已釐清。分責與回交流程依 [B1／B2 生命週期](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料007目標已確認)，不是固定互審。

**B2 待驗要求：**可讀允許範圍內已引用及未引用的有效訪談，保留正式序號、說話者與原文；超過本批上界及無效來源被拒；查到情境問題時可回交具體依據但不能修改情境。這是已確認的能力與限制，具體接線及驗收尚未完成。

Owner 的 A 起始例子仍可成立；其中 7…19 是歷史訪談序號的示意，不能用奇偶判斷角色。**當次輸入直接以 `role: "user"` 放入員工原始內容，不附訪談序號、來源標籤或「本次輸入」文字前綴。**以下 `content` 只是佔位說明，實際傳入原文，不傳這段說明：

```text
有效接續歷史／已採用的 compaction
user：App 資料訊息，承載模型參考資料（各導覽＋近期歷史訪談資料 7…19）
      7 是顧問發話；中間原順序保留；19 是本次輸入前的顧問發話
user：content = 員工這次輸入的原文（不加標籤、不改寫）
後續模型／工具 Step
```

本次輸入不重複塞入這次模型參考資料；既有接續歷史也不因重新提供近期歷史訪談資料而改寫。模型參考資料中的歷史顧問發話仍是帶來源角色的引文，不冒充現在模型產生的新 assistant 回應；工具回傳則維持原生工具結果。**2026-09-29 Owner 已確認的開場來源：**新職務檔案先由 App 提供開場引導與具體問題，整則作為正式訪談序號 **1**；首次員工輸入前須能回讀此真實前問。App 開場不冒充模型生成，也不能當作員工已確認的工作事實；後續模板變動不改寫既有職務檔案當時呈現的開場原文。具體保存接線未定，不因此新增一次開場模型 Turn。

**取消與正式序號（2026-09-28 規則；2026-09-29 開場例外；目標／未實作）：**App 開場第 1 則先行正式成立；其後每次 A Turn 成功完成、正式訪談資格成立後，才分配該次有效員工輸入與顧問完整答覆的正式訪談序號。執行中的員工輸入原樣送模型，不使用暫定訪談序號；取消、放棄或未完成時該輸入不進入正式序列、不佔號，也不取消或重編已成立的開場第 1 則。既有輸入保存及同輪恢復仍由 App 管理，不把「content 不加工」解讀成不保存輸入或不辨認原執行。成功完成依產品完成邊界判定，不是只收到模型 final。共享讀取入口仍須執行正式來源資格，不只靠未編號、畫面隱藏或模型自律防止其他程式取用候選。這確認分配時點，不決定資料表、計數器或交易接線。

**公開中間訊息的來源邊界（2026-09-29 Owner 已確認；目標／未實作）：**顧問在執行中公開給員工閱讀的中間文字，即使成功後可從歷史正式答覆展開回看，也不成為「歷史訪談資料」中的一則正式訊息，不分配訪談序號，不供工作情境／理解整理或 JD 引用。**App 開場第 1 則不屬這類模型中間訊息**；其後成功完成的有效員工輸入與顧問完整正式答覆才取得正式來源資格。不可因公開中間文字曾顯示在聊天畫面，就將它插入按序號回讀、近期歷史訪談或背景批次範圍。此限制不要求改寫或刪除模型原生接續 items；顯示與接續資料、正式引用來源分別依自己的用途管理。唯一產品語意見[產品概念](../product-concept.md#訪談原話與正式答覆的保存承諾目標未實作)。

**歷史對話的辨識範例（只示意可讀效果，不指定 wire）：**

```text
【歷史訪談資料】
以下是已完成訪談中的原始對話，不是當次新輸入。
訪談序號表示本職務檔案內的發話先後順序；數字越小，發話越早。

訪談序號：7
說話者：職務顧問
訪談原文：「這項盤點通常多久做一次？」

訪談序號：8
說話者：受訪員工
訪談原文：「每個月；另外我也負責臨時補貨。」
```

實際返回完整原文，不由 App 改寫成上述示例或分析摘要；外層標示與逐則欄位須能區分資料和本次發話。A 起始投影仍是 App 組裝的 user 資料，按需讀取仍是原生工具結果，不能把歷史顧問發話提升為目前模型的新 assistant 訊息。具體 JSON／文字格式及引用輸入另議；標示歷史不等於已證明防提示詞注入。正式序號供後續歷史投影與查詢使用，不因此原地改寫既有原生模型接續歷史。

**處理進度與閱讀範圍分開：**最新版已發布 Memory 決定尚待整理的資料，補前問可跨到已整理範圍，但不倒退處理進度、不複製出新的原始來源。尚待整理的完整有效訪談不能因只挑相關片段而漏掉；即使沒有尚待整理的歷史，仍須處理本次回答所接的前問，不能直接推論近期歷史訪談資料必為空。A 的本次輸入依其私有執行資格提供，B1／B2 不因此可以讀尚未完成或已取消的輸入；各自固定範圍與權限不變。

### 起始訪談範圍與前置語境（工程設計／未實作驗證）

本節將[產品的固定發布基準與近期資料](../product-concept.md#memory-與近期訪談的-turn-讀取基準目標未實作)、[背景固定取材與涵蓋](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料007目標已確認)推導成確切起訖，不新增對話分組。K／H／F 是文件中的 App 計算符號，不是模型須填的參數或三份獨立 authority。

| 符號 | 取得時點與意義 |
|---|---|
| K | 從該 A Turn／B 批次固定採用的同一份已發布 Memory 取得正式訪談涵蓋上界；正常為該發布截止的最後一則員工輸入。首次無 Memory 時為 0。不同 A／B 工作可以固定不同 publication 及 K。 |
| H | A Turn 開始前已成立的有效歷史訪談序號上界；同 Turn／恢復不刷新，不含尚未正式編號的本次輸入。 |
| F | B 批次固定上界：觸發要求的 A Turn 最後員工輸入在成功完成後取得的正式序號；不包含其後顧問回答，亦不因背景延後啟動、回交或恢復而擴大。 |

1. **A 正常起始：**完整提供 `(K,H]` 的有效歷史訪談，另加本次員工原文；本次輸入不預編序號，也不重複放入歷史集合。首次 K=0、H=1 時包含 App 正式開場第 1 則。正常 K 指向員工發話，其後 `K+1` 的顧問完整答覆若已成立，便自然落在近期集合中，可作下次回答的前問；角色仍按實際記錄判定，不由奇偶猜算。
2. **B1 必處理：**完整提供 `(K,F]` 的有效訪談；B2 不重做 B1 的涵蓋工作，按需回讀 `≤F` 的有效訊息。只有 F>K 才有新的必處理區間；若要求已被正式涵蓋，不以空區間再造待處理批次。首次 K=0 時 B1 新資料包含 App 第 1 則；開場仍不是員工事實。`F+1` 即使已正式保存為顧問答覆，也不納入這批起始、補前問或按需讀取。
3. **補前問的工程規則：**若起始集合開頭是員工訊息且未帶其前置引導，補最接近、合法且更早的一則顧問完整答覆或 App 開場；若 A 歷史集合為空，仍以本次輸入之前的有效歷史找該前問。已有前問則不重複加，找不到不捏造。補入資料與原集合按正式序號排序及去重，明標為附加語境；不改 K、H、F、B1 必處理區間或正式涵蓋。B 的補充同樣不得超過 F。這是一則前置語境的選取規則，不聲稱它與回答必為問答配對或已包含完整主題；不足再按需查原話。
4. **處理中與失敗不推進 K：**背景正在整理、B1 已讀、B2 已完成候選或工具已成功都不是正式發布。A／B 原工作維持固定 K；另一次工作才可從新的成功發布取得 K。未發布失敗區間不能被下一批跳過。
5. **容量：**A 超量沿已確認例外，App 明示未預載的序號／範圍及 `read_interview` 入口，不冒稱已讀或改小近期範圍。B1 的指定來源超量不能套用 A 的例外而悄悄漏交新資料；依既有合法準備／壓縮及有界恢復處理，仍不能容納則停止並保留原範圍與恢復點，不推進涵蓋，不自行拆批或換模型。容量計量、閾值與提示需實作 gate 驗證。

例：已發布 K=30，A 開始前 H=39，則近期為 31–39；若 B 固定 F=38，B1 必處理為 31–38，不能加顧問答覆 39。背景即使正在處理到 38 或同輪發布新版，A 仍保留 K=30／H=39。若另一個選取範圍從員工訊息 34 起且缺前問，附加合法顧問訊息 33 只補語境，不宣稱新增或倒退涵蓋；此例不是 B1 可任意縮小必處理區間。

**引用與附加語境分開：**定位一則訊息，不等於永遠只能讀它；讀到的資料也不自動全部成為引用。若其他訊息實際支持所寫內容，引用如何明確選取它，留給來源寫入契約。原文資料可以跳號、跨主題，目的是讓模型取得理解所需的前後文；必須保留真實順序，不宣稱未讀到的中間內容不存在。選取更多訊息或範圍有助核對「每月」「剛剛另一件」等指涉，但不保證整件事已完整或沒有範圍外的更正；不足時仍須查詢或由 A 釐清。

**研究依據與取捨分開：**先前核對的 [OpenAI Citation Formatting](https://developers.openai.com/api/docs/guides/citation-formatting)建議先定可引用單位、使用穩定來源 ID，並讓來源容易連同周圍語境核對；它允許文件、區塊等不同粒度，沒有規定訪談必須按 Turn 或固定問答切片。本次來源身分與序號分開、可指定訊息／範圍，屬 Owner 的產品選擇，不宣稱是官方指定格式。附件的固定三則包、JSON 範例與評測方案僅供參考，未一併採納。

## 3. App 管理讀取基準與權限

- **A：**讀本 Turn 已固定的已發布 Memory；背景發布新版不在 Turn 中途偷偷改變其 map 或正文基準。同輪恢復沿用原基準。
- **B1／B2：**依本批固定正式基底及各自權限，讀本批候選的有效內容；已成立的候選修改須能讀回。這不等於候選整批不可修改，也不讓候選對 A／JD 正式讀取路徑外露。
- **B1：**可讀情境及有效原始訪談，不可取得理解 map、正文或來源資料。**B2：**可讀情境／理解及允許範圍內的原話，不可修改情境。完整規則以既有權限表為準。
- **每次結果必須一致：**map 與物件 read 均反映該 Agent 此時有權讀取的目前內容：A 是本 Turn 固定的已發布 Memory，B1／B2 是本批可見的最新工作稿；物件標題、描述、正文與目前來源須彼此一致。B2 交接期間情境不並行改動；A 不因背景發布而中途刷新 Memory。
- **候選關係與正式歷史引用分開：**B1／B2 候選關係連物件身分，read 給目前可見的候選內容；B2 根據變更資料重評語意。正式已發布 Memory 與 JD 當時採用的引用固定修訂，不隨候選改動；A 若需核對 JD 的舊依據，App 提供舊→本 Turn 已發布新基準的差異，並只讓 A 按需讀新基準全文。人與 App 的歷史精確回查仍屬正式來源保存責任，不表示 Agent 有舊版物件 read 入口。

### Memory 本批的固定訪談序號上界（目標／未實作）

**2026-09-28 Owner 已確認：Memory 整理及其訪談讀取以「本批訪談序號上界」限制，不以 Agent Turn 編號作工具過濾條件。**A 在 X Turn 提出整理要求，等 X Turn 成功完成後才啟動背景整理；App 以 **X Turn 最後一則使用者輸入取得的正式訪談序號**固定本批上界，包含該則輸入，**不包含 X Turn 在它之後產生的顧問回覆**。啟動時點與資料截止點是兩件事，不能取 Turn 完成時的最後一則訊息或當下最大序號代替。這修正先前將該 Turn 正式顧問回覆也納入本批的解讀；上界以前的有效員工與顧問訊息仍依既定範圍提供，不是只篩員工發話。執行時由 Runtime 自動注入該上界，不由模型產生、填寫或修改，也不作模型必須閱讀的控制資訊。具體內部欄位、保存與注入方式仍未定。

- **模型選擇與執行限制分開：**模型只選要查的訪談序號／範圍；Runtime 綁定職務檔案、有效來源資格與本批固定上界。上界不放進模型可填的工具參數，不能靠 Prompt 要求模型自己守住；各則資料仍照約定顯示訪談序號，不因隱藏控制參數而隱藏正常來源資訊。
- **同批固定：**B1、B2 的起始取材、後續訪談工具與來源回查均不得讀取超過本批上界的訊息。延後啟動、同批 Step、B2 回交 B1 或中斷恢復均沿用原上界，不以當下最新訪談序號重新計算；只有另一次合法的新整理工作才綁定自己的範圍。
- **上界不是本批必處理範圍的起點：**B1／B2 仍可回查上界以前更早的有效歷史，以理解指涉；不因此改動本批必須整理的新資料範圍或發布進度。來源是否有效與是否在上界內都須成立，不只檢查數字大小。
- **例子只是序號示意：**第 18 Turn 提出要求並成功完成，其最後一則員工輸入取得訪談序號 38、後續顧問回覆取得 39，則本批上界固定為 38，不能讀 39。第 19 Turn 的輸入即使稍後完成並取得正式序號 40，本批也不可讀 40；取消／未完成時則根本沒有正式訪談序號與共享資格。上界由原輸入身分對應的正式序號取得，不由 Turn 編號、奇偶或「下一個輸入序號減一」猜算。39 仍是有效歷史訪談，只是不在這批範圍，不能因此刪除或宣稱已被本批整理。

請求超出上界時不得外露界線之後的內容，也不得靜默擴大本批範圍。**工程設計：整筆拒絕**，依[共同錯誤契約](2026-09-27-agent-tool-contract-design-research.md#7-錯誤回傳與恢復責任)回範圍錯誤與合法下一步，不返回超界內容或假稱完整；同樣適用不存在或無資格的序號。模型輸入沿本頁 `read_interview` 分支；strict schema 與隔離驗收待實作。

這些是已定產品規則對讀取契約的約束，不是聲稱 App 已具備相應接線。不得只寫「Runtime 處理」便視為 title 對版本的辨認已完成。

## 4. 未決接縫與停止線

1. **來源 ID、正式序號與查詢介面。**模型選正式訪談序號，App 映射內部來源 ID；成功編號、取消不佔號及共享資格已定。起始 K／H／F、前問、messages／range 分支與整筆拒絕均由本頁工程設計收斂，剩餘是序列化、容量數值及上界保存／注入驗證。A 的未編號本次輸入可作 JD 候選依據，模型使用 [JD 契約的 `current_input`](2026-09-29-jd-model-tool-contract-review.md#42-直接來源的最小選擇推薦設計待實作驗證)，不放入共享訪談 read、不擅加 user 前綴；正式引用保存與取消依原業務責任驗證。
2. **標題操作與讀取觀察的綁定。**title 作模型選擇值已定，不重開 title／UUID 二選一；同一歷史 context 可能仍留有舊觀察，B1 也可改名或修訂候選。新物件 read 一律按 Agent 當下有權使用的目前基準解析，不讓模型選舊修訂；App 仍須以真正物件身分解析標題、辨別歷史引用及形成差異，不能靠未明示的「最後一次讀取」猜目標。
   - **2026-09-28 最新補正：**同名不足以辨認不同物件或舊引用，但不因此需要 Agent 讀取舊版正文、填版本參數或持有新的代號 registry。舊基準是引用實際綁定的修訂，新基準是該 Agent 此時可見的同身分修訂，兩者由 App 比較。
   - 反例：B2 的候選理解 U 關聯情境 C；B1 修改 C 後，U 的候選關係仍指向 C，情境 map／read 給新版，App 提供前後差異。B2 根據差異判斷 U 需要改正文、改關係或保留不變；不需模型逐條確認換版。正式發布時固定 U、C 的當時修訂與關係，較早正式 Memory 不被改寫。diff 的比較範圍、名稱篩選與 Markdown 詳情沿[背景差異工具契約](2026-09-25-b1-b2-information-gap-lifecycle.md#差異讀取的最小工程契約2026-09-29-推薦待實作驗證)，生成 wire 與接線仍待驗。
   - 較早曾建議所有精確操作帶回觀察參照；同日經 Owner 指出本批候選由 Runtime 管理，已撤回其作為一般候選編輯首選的建議。下方候選比較仍保留研究沿革，其中讓 Agent 讀舊版正文的路徑已由本次最新補正取代；不得把它當成下一步實作。名稱重用已允許，最新 read／map 始終解析當前可見作用域；不新增模型版號、強制重讀或候選逐引用確認。JD 的既存來源核對則用 App 提供的既存引用定位，不能拿新標題字串代替舊引用身分。
3. **正式工具註冊與錯誤接線。**本頁已選模型入口、分支及正常／拒絕語意；按[共同工具規範](2026-09-27-agent-tool-contract-design-research.md)生成 schema、串接來源 owner 並驗實際回傳。資料表或示例不是已驗 strict wire；無權、無目標與容量未完整不得合成正常空結果。

**標題選取的確切工程規則：**新 read／update／delete 及新的來源選擇，以當前有權作用域的標題映射 ID；比較採原字串精確相等，不模糊選取、不自動做大小寫折疊、去空白或 Unicode 正規化。純空白 title 不合法，保存內容不被偷偷正規化；重名檢查與解析共用同一比較規則。已建立的候選關係、歷史固定引用與已綁定原操作則沿各自 ID，不再以名稱解析。C 從 X 改名 Y、D 重用 X 後，新請求 X 指向 D；原引用仍指 C，原操作重入仍查 C 的原結果。若原操作目標已失效不能改派 D；不能因模型歷史仍含 X 就拒絕所有新操作或要求新 proof。工程驗證含 Unicode／空白、同層唯一及重入，但名稱重用本身不再是產品待決。

以上產品效果已有定義；剩下工程映射由[共用執行](2026-09-27-shared-agent-execution-and-state-design.md)、[資料與交易](../architecture/persistence.md)及角色工具契約承接，不再要求 Owner 逐欄裁決。strict wire、名稱解析與固定歷史的反例仍須驗證，不能以文件完整宣稱已實作。

### 同名不同版本的定位候選

**2026-09-28；G2 研究／候選，未採納、未實作、未驗收。**本輪只解決「模型選的標題，如何對應它要讀、改或引用的那份內容」；不重開三層分責、title 定位、固定引用或整版發布，不決定永久短碼、資料表及保存期限。

**歷史研究／已被最新目標取代：以下候選比較不作施工依據。**它把目前工作稿與歷史來源版本的模型讀取混在一起；其中讓 Agent 用 `read_ref` 讀舊版正文及逐條確認候選引用的路徑已撤回。現行目標是 B1／B2 的 map／read 給當前候選、候選關係沿身分；A 只讀本 Turn 固定正式 Memory，JD 當時依據仍需依差異另行核對。`read_ref` 從未升格為已採納契約。

**外部依據：**[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)建議已知參數交給程式、不讓模型填寫，並明確定義工具用途與結果。這不表示 App 能從含糊的標題推知模型選的是哪次觀察。[Google AIP-154](https://google.aip.dev/154)與 [Azure 樂觀並行控制](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage#optimistic-concurrency)都提供「讀取時取得服務端產生的基準值，寫入時帶回比對，過期則拒絕」的成熟模式。[S3 特定版本讀取](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RetrievingObjectVersions.html)另明確區分讀目前版本與指定版本。這些支持**選物件、選版本、檢查寫入基準是不同問題**；下述模型介面是 Caliburn 候選，不是大廠統一格式，也不引入 S3 或讓模型自行填 ETag／DB 版本。

| 候選 | 效果與代價 | 建議 |
|---|---|---|
| 所有操作只傳 title，App 一律取當前版本或最後一次讀取 | 參數少，但同名舊引用、名稱重用及歷史觀察無法可靠區分；單靠 patch 匹配也不能證明版本相同。 | 不滿足已定固定引用要求，不採。 |
| title 選物件；讀取結果附 App 產生的觀察參照，精確回查／修改／來源選取時原樣帶回 | 明確指出哪份觀察；App 仍管理真正身分、修訂及權限。多一項模型選擇資訊，須驗證抄回與恢復。 | **首選候選。** |
| 每次明列 publication、物件 ID、修訂及來源路徑，讓模型組合 | 能表達，但重複 App 已知資訊、增加錯配組合；不符已定的模型責任界線。 | 不採作預設工具輸入。 |

首選把觀察參照暫稱 `read_ref`，例如示意代號 `R7`。**名稱與短碼格式未定；它不是永久物件代號、DB 主鍵、保存回執或權限憑證。**App 將其綁定到已提供的確切內容及所屬讀取範圍；必要資訊包括職務檔案、物件身分、修訂與發布／候選資格，但不要求另建映射服務或一張表。模型只選擇並原樣帶回，不生成或計算底層版本；任一工具仍重新檢查權限。

| 意圖 | 候選定位方式 | 不得發生 |
|---|---|---|
| 從 map 讀目前工作資料 | 模型選 `target_title`；App 用 A 本 Turn 固定 publication，或 B 本批合法候選的當前視圖映射。結果附自己的 `read_ref`。 | A 中途切最新 publication；把候選外露成正式來源。 |
| 沿已讀理解回查當時來源 | 理解的來源列仍提供情境 title／description，另附各來源的 `read_ref`；模型選來源標題並帶回對應參照。 | 丟掉原引用版本，再以同名 title 查目前候選。 |
| 修改／刪除已選候選物件 | `target_title` 加該物件觀察的 `read_ref`；App 固定 ID，檢查 title 與觀察對應，再核對候選修訂仍適用，最後才採用修改。 | 以新同名物件取代原目標；基準過期卻改用 latest 套 diff。 |
| 將 Memory 作為新的引用依據 | 模型選已核對來源的 title 及 `read_ref`；App 轉為正式固定身分／版本，按 A／B 的來源資格檢查。 | 直接存代號為正式引用；自動把舊依據更新為最新；把來源存在當成語意支持。 |

以上是意圖與定位責任，不是四個新工具，也不是正式 JSON schema。來源列提供參照只代表可以定位，不代表模型已讀其正文或已核對語意；需要細節仍須讀取。既有來源保留時，不要求模型每次重傳或重新閱讀。訪談序號及本次輸入依據循各自契約，不因本候選全部改用 read_ref。

**例子（較早 read_ref 候選，不是已採納的模型參數；末句改綁方式已由後續決策取代）：**B2 讀到 U v3，其來源列的「訂單異常處理」參照綁定 C v7；B1 後來修成同名 C v8。B2 沿 U 的來源參照讀回 C v7；明確按目前候選讀該標題，則取得 C v8 與新的參照。兩份觀察可同時留在歷史 context，不互相覆寫。讀取本身不改寫引用；依最新決策，B2 核對後須明確確認保留引用的對齊，App 才形成新的 U 修訂並綁定 C v8。最終發布仍須滿足同一 Memory 選定單一情境版本的既定規則。

首選候選的必要生命週期與限制：

- **不偷換意圖：**只有 title 的一般 read 明確表示讀目前綁定範圍；歷史精確回查、修改及新引用不可猜用最後讀取。參照和 title 不一致或無法解析時拒絕，回報重新取得正確觀察的方向。
- **觀察參照與新鮮度分開：**舊參照仍可在授權範圍讀回舊內容，不代表仍可寫入當前候選。歷史資料不會因過期就自動改指新版；已失效或不能取回時明說。這不是用正文 hash 取代修訂身分，正文改回仍是新修訂。
- **同次改名：**先由舊 title＋參照固定原物件，再處理新 title。成功結果可提供新 title 與修訂參照；後續不得把舊 title 自動別名到其他物件。部分結果不冒充已讀完整新正文，必要時仍重讀。
- **回交與恢復：**B1 修改使 B2 舊情境觀察可能過時，依既定重評處理；同輪／同批恢復須能承接已保存工具結果中的參照。已回退、棄用候選的參照不得重新取得寫入／發布資格，也不可重派給另一物件。具體承接方式依共同保存審查方法選定，不能先宣稱 checkpoint 已足夠。
- **參照不是第二份 authority：**正式關係仍由 Memory／JD 保存 ID 與固定版本；參照只協助模型選擇，來源支持是否合理仍由 Agent 判斷。有效期、編碼、是否可由現有狀態還原及具體錯誤碼屬後續有限細設；無需因此建立永久 alias registry、新 receipt 或新來源 DB。

**待驗反例（未執行）：**同名 C v7／v8 分別可讀；舊基準寫入拒絕；改名後別物重用舊名稱不誤改；只改來源關係也使修訂基準失效；正文回改不復用舊修訂身分；跨檔案／跨權限及已棄用候選不能靠參照繞過；恢復不重派參照；A 新引用不能採用背景候選。離線通過後才評估模型是否選對並正確帶回，不能由文檔比較宣稱錯誤率已降低。

**當時提出的裁決題（已由下節分開收斂）：**是否接受「標題選物件＋App 提供的觀察參照選確切版本」。不得沿這個歷史下一步直接加參數或施工。

### 本批候選編輯與歷史版本回查分開

**2026-09-28 同日續議／研究建議修正；未實作。**Owner 指出 B1／B2 反覆修改的是本批未發布候選，對外讀者不會看見中途改版；Runtime 可以掌握本批目前修訂。此點符合[既定分責、交接與發布流程](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料007目標已確認)。因此**不能由「候選會改版」直接推導模型每次必須帶回 `read_ref`**。

一般候選讀寫已定義為「操作本批目前有效的工作稿」：模型提供 `target_title` 及修改意圖；Runtime 綁定原工作、權限、目前候選、映射後的物件 ID 與執行基準。修改成功後，依[更新結果契約](2026-09-27-memory-object-update-tool-contract.md#6-成功回傳已成立的候選效果)回傳真正採用的修改，供模型接續；不為每次內部修訂增加模型必填版本代號，也不因此發行一版正式 Memory。具體儲存、修訂配置與條件提交仍待實作驗證。

這與「Runtime 猜模型指哪個歷史版本」不同：一般編輯的目標已明確是當前工作稿，不兼任歷史版本編輯。候選理解關係沿物件身分讀當前情境；沿 JD 既有正式來源閱讀時，模型讀到本 Turn 固定的新基準，App 仍依 JD 當時固定舊引用形成差異；不能把「read 給新版」誤作「JD 舊依據已核對」。舊版物件正文不另給 Agent 讀，人的正式歷史來源回查由原資料責任保留。

必要條件沿既定責任處理，不新增元件：

- **Runtime 掌握目前候選，不等於模型已理解最新內容。**自己的修改結果須真實回傳；B1 交付後，B2 依變更資料及按需新內容重評，不能只因候選綁定持續存在就宣稱語意一致。B2 完成是整階段語意判斷，不是逐條引用確認；歷史 context 與已發布來源不改寫。
- **分責不自動保證執行沒有競爭。**既定主流程是 B1 → B2、需要時回交；同物件依序修改、程序重入、過期工作與保存時基準核對仍由執行／候選 owner 保護。不把「沒有外部修改」當成可移除重入與條件提交檢查的理由；並行策略尚未完整定案。
- **新名稱選擇與既存身分分開。**依本頁確切解析規則，新請求可選重用名稱的當前物件；既存關係與原操作不改指。找不到當前唯一目標才拒絕，不猜舊名稱別名，不增加模型必填 read_ref、重讀或觀察 proof。
- **一般編輯與重新執行分開。**新修改操作指當前工作稿；中斷後再次進入同一已保存操作，仍按原操作查回結果，不把它當成一筆新的 latest 修改。

[LangGraph State 指引](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph#step-3-design-your-state)支持由程式承接跨步驟工作資料；[PostgreSQL 交易隔離](https://www.postgresql.org/docs/current/transaction-iso.html)說明讀寫基準與並行的實際限制。兩者都不替本案保證模型理解正確，也沒有規定基準必須由 LLM 作參數傳回。本節是依產品工作範圍作的簡化建議，不宣稱框架已自動滿足。

**下一步：**以「本批目前工作稿由 App 綁定」處理一般編輯，實作時驗證候選差異、名稱歧義、JD 正式舊依據→新基準的差異及其核對；不把草稿操作變成模型選版本或新增 Agent 的舊版正文 read。反覆修改、B1 回交、重啟重入及名稱重用的反例均未驗，不宣稱完整工具契約可施工。

## 5. 驗收要求與後續順序

以下均**未執行**：

- 導覽列出授權範圍的完整標題／描述，能直接選理解或情境；來源回傳不混入 `body`。
- 理解來源只展開目前可見情境的 target_title／description；情境來源提供可回讀的正式訪談序號，內部來源 ID 由 App 管理。原話保留角色與順序，不把顧問假設當員工事實。
- A 固定版本與背景候選彼此隔離；B1 無任何理解層存取，B2 不藉讀取入口修改情境。
- 同層重名拒絕、跨層同名允許，不誤拒不同版本或不同職務檔案沿用標題；改名、名稱重用、候選更新與歷史引用不造成靜默重定向。Agent 的 map／read 均反映其可見目前基準；已發布歷史引用維持原綁定，App 對 JD 所需新舊修訂提供正確差異，不以當前描述冒充舊引用正文。
- 模型輸入 title 經 App 映射後，資料庫收到的是 ID 定位；讀／改／刪及正式引用均不以 title 尋址，改名不改物件身分或既有固定引用。
- 取消／被替換輸入不取得有效來源資格、不佔正式訪談序號；如底層保留該輸入的保存身分，不等於可經 Agent 查詢或引用。來源資格與本批範圍沿既定規則。
- A 執行中／暫停／取消時，當次輸入沒有正式訪談序號，模型收到的 user content 保持員工原文；其他 Agent 的訪談讀取不取得該候選。只有完成條件成立後才可編號／正式回讀，不能僅因模型回覆已產生就提前外露。恢復同一已完成結果不再次編號。
- 起始近期歷史訪談資料與工具結果均清楚標示為「歷史訪談資料」，逐則具有固定訪談序號、說話者、完整訪談原文，明示序號的發話先後意義；不能只列號碼與文字卻讓模型誤認成新 user／assistant 發話，也不能用摘要冒充原文。歷史投影的編號不改寫原生模型接續 items。
- 同一訊息跨 context、工具結果及 Memory 版本均有相同正式序號與來源身分，不以查詢結果重編；角色不依 ID 奇偶推定。指定 1、2、5、7 與範圍 2→7 的結果不同，原序號／說話者均保留；不把跳號說成連續，也不漏掉範圍內合法原文。
- B1 使用與 A 相同的訪談讀取契約，能按序號選本批內或更早的有效歷史訊息／範圍；App 拒絕超出本批可讀上界、跨檔案或未完成／取消來源。選取讀取內容不改變本批必處理範圍，不以只能無參數讀整批取代其按需回查能力。
- Memory 本批上界由 Runtime 注入、不出現在模型可填參數；起始 context 與 B1／B2 訪談／來源回查遵守同一固定序號界線。測試「X Turn 成功完成後，最後員工輸入為 38、該 Turn 顧問回覆為 39」「後續正式輸入 40」「延後啟動」「B2 回交」「中斷恢復」均只允許讀至 38，不能讀 39／40，且仍可合法回查更早的員工與顧問訊息；不拿 Turn 號、奇偶或當下最大序號作替代。上界在內不代表取消／未完成來源可讀；本批發布進度不得把上界後的顧問回覆算成已處理。
- 員工主動開新話題不必假造前問；真正有指涉缺口才查詢或釐清。App 開場引導有真實出處，無前文時不造前文；補前問不改 Memory 處理進度。本次輸入只在這次新增起始資料中提供一次，不因補語境外露給背景 Agent。

- K／H／F 依同一發布及有效歷史求得；首次 K=0 包含 App 第 1 則，K+1 的顧問回答自然保留。補前問只加合法較早一則並去重，不改涵蓋、不越 B 的 F。A 超量標未附範圍供回讀；B1 不能漏交指定新來源，容量不符時保留範圍並依既有有界恢復／停止處理。
