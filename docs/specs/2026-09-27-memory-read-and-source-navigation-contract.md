# Memory 導覽、正文讀取與來源回查契約

Memory 導覽幫助模型找到相關情境與理解，再按需讀正文、沿來源回查訪談原話。App 管理可見基準與權限，模型選標題或正式訪談序號，不選內部 ID 或歷史版本。

內容與來源的關係見[產品概念](../product-concept.md#分層工作記憶)，版本與角色界線見[固定版本鏈](2026-09-24-caliburn-layered-architecture-map.md#來源與版本)及[B1／B2 權限](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料)。全產品關係見[架構導覽](../target-architecture-map.md)及[Memory 子圖](2026-09-24-caliburn-layered-architecture-map.md)，工具接線見[Memory 工具](../implementation/memory-tools.md)，實測限制見[驗收矩陣](../architecture/verification.md)。本文不涵蓋來源寫入、V4A 執行器、儲存、快取、Memory 短 ID、搜尋或 provider 接線。

## 1. 已確認的讀取內容

| 入口／內容 | 模型取得什麼 | 接下來如何使用 |
|---|---|---|
| 工作理解導覽 | 目前讀取範圍內**所有工作理解**的可讀目標 `target_title`、`description`。 | 把所選 `target_title` 帶入理解讀取工具；不預載正文。 |
| 工作情境導覽 | 目前讀取範圍內**所有工作情境**的可讀目標 `target_title`、`description`。 | 把所選 `target_title` 帶入情境讀取工具；不必先經過理解。 |
| 讀一項工作理解 | 該理解的內容欄位 `title`、`description`、Markdown `body`；**分開的來源資料**列出被引用工作情境的可讀目標 `target_title`、導覽描述。 | 從來源列選 `target_title`，按需讀被引用情境。 |
| 讀一項工作情境 | 該情境的 `title`、`description`、Markdown `body`；**分開的來源資料**提供可供模型選取的正式訪談序號，App 保有其對應來源身分。 | 按序號讀指定歷史訪談訊息或範圍；正式序號與內部來源 ID 不混用，工具分支見 §2。 |

「所有」是目前職務檔案、讀取基準及 Agent 權限所允許的該層集合，不是所有檔案／所有歷史版本，也不因此把理解導覽交給 B1。導覽不是由檢索任意挑出的相關子集；若未來容量需要分頁或其他表示，另行說明完整性與取捨，不靜默漏項。

標題是模型可使用的目標定位資訊，供讀取及已授權的操作選物件；不要求模型猜內部 UUID 或 Memory 版本。同一職務檔案、同一候選／正式快照中，**各層內**有效 title 唯一，情境與理解可以同名；不跨 Memory 版本檢查重名。唯一性不授予跨層讀寫權限，層級及操作權限仍由相應介面和 App 綁定處理；標題正規化與改名後綁定仍見 §4。

**導覽與定位：**map 是可按需深入的導覽，不是物件正文清單。模型可見的每一項用 `target_title` 標出可直接帶入對應 read 工具的目標，旁邊是 `description`；理解讀取結果中的 `work_situation_references` 也以每筆 `target_title`／`description` 提供下一層可讀目標。物件本身的內容欄位仍是 `title`；同一項目不重複回 `title` 與 `target_title`，也不另加 `can_read` 布林值。`target_title` 只是模型與 App 之間的選擇值，不是資料庫 ID、固定版本參照或授權憑證。App 須在 Agent 的可見基準內按真實物件身分映射：B1／B2 沿候選關係讀目前可見情境，A 沿已發布快照讀固定情境；**已建立的引用**不因同名而改指別的物件；**新的標題操作**按當前作用域解析，改名／刪除後標題允許被另一物件重用。候選關係隨同身分目前內容而變，正式歷史引用仍固定在其快照版本。僅收到標題字串不能證明模型心中指的是哪個歷史物件；不增加強制重讀／觀察代號，這是已知語意風險，不宣稱 App 能猜出未表達的舊意圖。

以下示意**模型可見的導覽項目與下一次讀取參數**；入口名稱與結果表示由本頁 §2 定義；示例不替代正式 schema 或實測：

```json
{"items":[{"target_title":"月末庫存盤點","description":"每月核對帳實差異；關鍵詞：月末、盤點。"}]}
```

```json
{"target_title":"月末庫存盤點"}
```

**標題只在模型／App 邊界作映射，資料庫不以標題定位目標。**依 [010 的 ID 邊界](../product-concept.md#分層工作記憶)，流程是「模型選標題 → App 映射並核對 ID／讀取基準 → 資料介面以 ID 讀寫或建立引用」。不能把 App 映射實現成資料庫以 title 尋找操作目標；§4 已定精確解析、新操作與原操作重入的分工，映射及恢復接線依 Memory 工具與保存文件，不新增獨立儲存。

本表定義資料效果；讀取表示沿用已確認的 `interview_references`／`work_situation_references` 名稱，不另用籠統的 `sources`。完整物件 read 一律含本層來源集合；沒有引用回 `[]`，不以省略表示「未讀」或漏回。理解來源列包含目前可見情境的 `target_title`／`description`，情境來源列是正式訪談序號，不搬用寫入的 add／remove 形狀。來源不嵌入 Markdown 正文；正文提到名稱不會自動建立引用。共同風格見[工具規範 §2.1](2026-09-27-agent-tool-contract-design-research.md#21-共用風格)。

**最小回傳：**模型可見的 read 結果不附 `stage: candidate`／`published`；範圍由工具契約及 App 基準、權限決定。正常物件 read 直接回 `title`／`description`／`body` 與本層來源集合，不再加 `status: read`；map 回 `items`，合法空導覽為 `{"items":[]}`。無權、找不到及不完整讀取依共同錯誤契約區分，不偽裝成空集合。結果仍須提供真正讀到的內容，不以模型曾看過 arguments 為由省略。

**導覽也可按需重讀。**重讀沿用本表的欄位、全體集合及 §3 的讀取基準／權限；候選導覽反映本工作已成立修改，A 不因此取得候選或新發布基準。跨 Agent 共通規則集中在[工具契約 §6.1](2026-09-27-agent-tool-contract-design-research.md#61-起始參考資料亦可按需重讀)，B2 專用的 B1 變更資料及 diff 比較另見[背景交接設計](2026-09-25-b1-b2-information-gap-lifecycle.md#b1-變更資料與-b2-按需回讀)；不在此新增第二份差異規範。

## 2. 按需深入的流程

```text
工作理解 map：全部理解的 target_title＋導覽描述
    → 選 target_title → 理解正文＋被引用情境的 target_title／描述
                         → 選來源 target_title → 情境正文＋被引用訪談序號
                                                   → 選訪談序號 → 訪談內容

工作情境 map：全部情境的 target_title＋導覽描述
    → 選 target_title → 情境正文＋被引用訪談序號 → 按需讀訪談內容
```

以上是**讀取資料流**，不是驗收結果。理解讀取不自動展開所有情境正文與原話；情境讀取也不自動附上所有被引用訪談全文。模型可依資訊需要停止或繼續深入，不要求每次寫 JD 都走完整條鏈。這不改 A 起始近期訪談與 B1 必處理原話的既定輸入責任。

### A 顧問的閱讀與停止條件

處理已整理的工作時，A 預設由工作理解導覽定位相關正文。已讀的理解涵蓋本次判斷所需的事實、精確數值、適用條件與責任界線，且與目前資訊沒有已知衝突，就直接使用並引用該理解，停止向下讀取。這是對本次判斷的資訊充分性要求，不是每次都要走完「理解 → 情境 → 原話」，也不要求先讀完全部工作。

沒有相關理解或理解有具體缺口時，才讀相關情境；情境已足夠也可直接作為 JD 依據。已完成整理的現行工作，預期由這兩層支持一般分析；不將查原話設成必經步驟。若已確認的必要事實在兩層都缺漏，可回查原話查明，但這是整理或導覽缺口的補救，不是「按需讀取」理所當然的成本；整理責任及診斷方式見[分析指南 §10.4–10.5](../guides/2026-09-09-complete-work-analysis-guide.md#104-小範圍足夠深理解應能直接使用)。

原話入口仍供原句查證、歷史舊說法追溯，以及有具體線索的指涉／矛盾核對。不因物件附有引用就展開全部來源；已明確記錄「尚未確認」、且沒有新資料或疑點時，重讀相同來源不會得到新答案。未知影響當前判斷時，由 A 中立追問，而非因為它重要就盲查到底。

導覽只供定位，不能代替正文。A 可沿用本輪已讀且固定的導覽與正文，不為每次操作重讀。尚未整理的新資訊仍可直接由近期歷史訪談與本次輸入支持 JD；不強迫先找 Memory，也不因舊 Memory 的說法不同就忽略新更正。引用跟隨實際支持內容的已讀來源，不為引用理解而另加其全部情境或原話。

**按需也包含橫向選讀。**本次涉及另一項工作時，從導覽再選相關理解；本次需要同一工作的具體經過或原始指涉時，才沿來源向下讀。局部問答與完整工作整理的取捨見[工作分析指南 §10.7](../guides/2026-09-09-complete-work-analysis-guide.md#107-收斂後的整理與選讀準則)。不用一項理解回答所有問題，也不把來源清單當成必讀清單；此方法補充不增加工具或強制讀取門檻。

此規則不改工具權限、來源資格或本輪固定基準；也不免除 JD 人工修改與來源換版後的核對責任。讀取充分不等於引用已對齊，核對仍依 [JD 工具契約](2026-09-29-jd-model-tool-contract-review.md)。B1／B2 的輸入與分工沿各自規格，不套用 A 的理解優先順序。

例：理解「接案網站的前端逾時處理」已寫清訂單結果不明時須避免重複送單，足以支持本次 JD 修改，A 就引用該理解。若要了解某次異常的具體經過，才從來源列選「電商訂單送出逾時」讀情境，不另讀無關的「預約日期查詢逾時」。若問「這項期限更正前，員工原本怎麼說」，才沿正式訪談序號查原話；不能把歷史舊期限當現行規則。內部來源 ID 由 App 映射。這是合成示意，不代表真實測試通過。


### 讀取入口與分支

沿動賓命名選定 `read_work_situation_map`／`read_work_understanding_map` 取得相應完整導覽，模型 arguments 為 `{}`；`read_work_situation`／`read_work_understanding` 以 `{"target_title":"…"}` 取得單物件。這是既有讀取能力的具名表示，B1 只取得情境入口，A／B2 的資料基準仍依 §3；不以選工具取得其他層或版本的權限。

共用訪談讀取入口選定 `read_interview`，根為固定 `query` object，內含兩種互斥分支：

| `query.kind` | 模型參數及語意 | 結果 |
|---|---|---|
| `messages` | `sequences`：非空的正整數序號陣列；單則是一個元素，多則可不相鄰。重複序號按集合去重。 | 僅回所選有效訊息，依正式序號升序；不自動加未選訊息或重新編號。 |
| `range` | `start_sequence`、`end_sequence`：正整數且起點不大於終點，兩端均含。 | 回該閉區間內全部有效訪談訊息；不依相關度挑選。 |

所有模型參數均為選擇，檔案、來源資格與 A／B 的可讀上界由 App 注入。任一指定序號不存在、無效或超界，整筆拒絕，不返回部分成功的原文；容量不足回明確未完整讀取與可縮小範圍，不靜默截斷。兩分支不接受彼此欄位，不接受負數、零、小數、任意來源 ID 或模型自填 scope。schema 以 nested anyOf 生成，分支內 properties 全 required、禁止額外屬性，實際序列化與 provider 接受仍待驗。

訪談成功結果採精簡 JSON：`data_kind: "historical_interview"`、`messages[]`；每則含 `interview_sequence`、`speaker`、`text`，speaker 明辨 `app`／`employee`／`consultant`，text 為完整原文。起始 App 資料投影沿用這些逐則含意，工具本身仍是原生 function result；不因 speaker 欄位重包成新的 user／assistant 訊息。後續讀取或引用可直接選 `interview_sequence`。

```json
{"query":{"kind":"messages","sequences":[1,2,5,7]}}
```

```json
{"query":{"kind":"range","start_sequence":2,"end_sequence":7}}
```


### 訪談訊息、固定序號與回讀語境

**每則有效訪談訊息具有來源身分及職務檔案內固定序號；取消輸入不佔號。**訪談可以是回答，也可以是員工主動提出新資訊；不限定為問答配對。按需讀取可選不相鄰訊息，也可選範圍；Agent Turn 仍只指執行回合，不改成功完成才供背景取材的資格規則。

| 名詞 | 意義與界線 |
|---|---|
| 訪談訊息 | 訪談中正式成立的一則完整發話，包含 App 開場第 1 則、有效員工輸入或顧問完整正式答覆；有來源 ID、職務檔案內的固定訪談序號、真實出處／說話者及訪談原文。可包含多句、多段、補充、更正或問題，不是依標點拆成的一句話，也不是任意模型輸出 item。 |
| 來源 ID | 辨認「是哪一則原始訊息」的身分，不以它的字面大小、UUID 排序或 Agent 執行 ID 推斷先後。格式及保存由訪談責任模組管理。 |
| 訪談序號 | 表示一則有效訪談訊息在同一職務檔案內發話先後順序的固定編號；數字越小，發話越早，App 開場、顧問與員工共用同一套順序。不是本次工具結果的局部編號或 Agent Turn 編號。App 正式開場固定為第 1 則；其後員工輸入及顧問完整答覆待所屬 A Turn 成功完成才分配正式序號。取消輸入不佔號，既有正式序號不因取消、換 Memory 版本、查詢或壓縮而重編，不以奇偶推定出處。 |
| 訪談原文 | 一則訪談訊息的完整原始文字，保留說話者實際送出的內容；不是 App 摘要、改寫，也不是整段問答的合併正文。 |
| 訪談交流 | 包含 App 的正式開場引導、顧問後續引導與員工回答，也包含員工主動補充、新主題、更正或提問；問答只是其中一種關係，不強制配對或另建分組。 |
| 歷史訪談資料 | 過去已成立的有效訪談訊息，逐則提供訪談序號、說話者與訪談原文，明確標示為歷史訪談中的對話。可來自指定訊息或範圍，不要求序號相鄰，也不保證已包含完整主題；不含正在處理的當次輸入。 |
| 近期歷史訪談資料 | 歷史訪談資料中，App 依本輪固定的已發布 Memory 處理邊界組裝的尚未整理資料，並保留必要前問／顧問發話脈絡；不是固定最近幾輪，也不因個別訊息是否被引用而重定範圍。當次員工輸入另行提供。 |
| Agent Turn／執行回合 | 處理某次輸入的模型／工具執行，可有多個 Step；成功完成仍是來源准入邊界，但不是問答、引用或閱讀單位。 |

用語採「歷史訪談資料」「近期歷史訪談資料」「訪談原文」。包含導覽與近期訪談的內容稱「模型參考資料」，承載訊息稱「App 資料訊息」，共通定義依[Context §3.1](2026-09-26-consultant-context-and-state-design.md#31-app-資料訊息與原生項目的權限邊界)，不另建資料元件。

**A 起始資料與按需查詢是兩種用途，不能混為一個選取規則。**

- **A 的近期歷史訪談資料：**App 依本 Turn 已固定的正式 Memory 處理邊界組裝完整近期歷史訪談資料，保留前問／顧問發話，本次員工輸入另外提供。這不授權只挑看似相關的未整理訊息。
- **超量例外：**正常仍完整預載；超出容量時 A 可用下述同一訪談讀取工具按需取回有效近期訊息／範圍。App 應使未預載範圍可辨認，不把未讀資料說成已整理或已看見；不新增第二套搜尋入口。唯一產品邊界見[產品概念](../product-concept.md#上下文與分析接續)。
- **按需原文查詢：**允許選單則、多則不相鄰訊息（例如 1、2、5、7），或範圍（例如 2→7）。範圍查詢應保留範圍內完整有效訊息；指定訊息則不因不相鄰被拒絕。不再把工具能力限為向前幾輪，仍不引入語意／關鍵字搜尋。
- **共同呈現：**context 預先放入的近期歷史訪談資料及工具回傳的歷史訪談資料，至少讓模型逐則看見**訪談序號、說話者、訪談原文**，且一眼辨認這是**訪談過程中的歷史對話**，不是目前的新發話、App 分析或工具撰寫的摘要。明示序號代表職務檔案內的發話先後，並保留來源身分；選 1、2、5、7 不重新編成 1、2、3、4，也不暗示中間沒有其他對話。不自行把相鄰視為問答關係或把分散訊息宣稱為完整主題。

**B1 使用共用訪談讀取工具：**B1 也須取得與 A 相同的按訪談序號／範圍讀取能力，不是只有無參數的本批固定資料讀取。共同契約支援單則、多則及範圍，回傳相同的歷史訪談資料；B1 可選本批內的訊息，也可回查本批截止之前、更早的有效訊息。App 仍綁定職務檔案、合法來源及本批可讀上界；模型選擇讀哪些訊息，不得藉此改變本批必須整理的範圍、納入晚到訪談或取得未完成／取消的輸入。這是同一工具契約，不因 Agent 不同另造 B1 專用讀取規則；既有 B2 原話回查亦依共通契約及其授權範圍。起始資料的提供責任保持；固定範圍沿同一 read_interview 分支重讀，不另增工具。

**B2 使用共用訪談歷史工具：**B2 為分析工作理解，可按需直接回查訪談原文，以釐清條件、責任、指涉及更正；不交 B1 代查。沿用 A／B1 的單則、多則及範圍讀取契約，既可沿情境引用定位，也可按訪談序號讀取未被引用的有效訊息，不另造 B2 專用工具或搜尋機制。Runtime 固定同一職務檔案及本批訪談序號上界，排除晚到、未完成或已取消的輸入；模型不填控制上界。

B2 通常以工作情境為分析入口，資訊已足夠就不重讀；不要求每批重讀全部訪談，也不因此把全部訪談加入 B2 起始 context。讀取權不增加寫入權：發現情境缺漏或不一致，B2 只在理解中如實保留未知及矛盾，不回交 B1、不修改情境，也不繞過情境層另造正式引用鏈。原話仍不足時保留未知，不靠回查能力宣稱已釐清。分責與單向發布依 [B1／B2 生命週期](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料)，不是固定互審。

**B2 讀取邊界：**可讀允許範圍內已引用及未引用的有效訪談，保留正式序號、說話者與原文；超過本批上界及無效來源被拒；查到情境問題時不能修改情境或回交。實際覆蓋依驗收矩陣。

A 起始示例中 7…19 是歷史訪談序號的示意，不能用奇偶判斷角色。**當次輸入直接以 `role: "user"` 放入員工原始內容，不附訪談序號、來源標籤或「本次輸入」文字前綴。**以下 `content` 只是佔位說明，實際傳入原文，不傳這段說明：

```text
有效接續歷史／已採用的 compaction
user：App 資料訊息，承載模型參考資料（各導覽＋近期歷史訪談資料 7…19）
      7 是顧問發話；中間原順序保留；19 是本次輸入前的顧問發話
user：content = 員工這次輸入的原文（不加標籤、不改寫）
後續模型／工具 Step
```

本次輸入不重複塞入這次模型參考資料；既有接續歷史也不因重新提供近期歷史訪談資料而改寫。模型參考資料中的歷史顧問發話仍是帶來源角色的引文，不冒充現在模型產生的新 assistant 回應；工具回傳則維持原生工具結果。**開場來源：**新職務檔案先由 App 提供開場引導與具體問題，整則作為正式訪談序號 **1**；首次員工輸入前須能回讀此真實前問。App 開場不冒充模型生成，也不能當作員工已確認的工作事實；後續模板變動不改寫既有職務檔案當時呈現的開場原文。保存依訪談責任模組，不新增開場模型 Turn。

**取消與正式序號：**App 開場第 1 則先行正式成立；其後每次 A Turn 成功完成、正式訪談資格成立後，才分配該次有效員工輸入與顧問完整答覆的正式訪談序號。執行中的員工輸入原樣送模型，不使用暫定訪談序號；取消、放棄或未完成時該輸入不進入正式序列、不佔號，也不取消或重編已成立的開場第 1 則。既有輸入保存及同輪恢復仍由 App 管理，不把「content 不加工」解讀成不保存輸入或不辨認原執行。成功完成依產品完成邊界判定，不是只收到模型 final。共享讀取入口仍須執行正式來源資格，不只靠未編號、畫面隱藏或模型自律防止其他程式取用候選。這確認分配時點，不決定資料表、計數器或交易接線。

**公開中間訊息的來源邊界：**顧問在執行中公開給員工閱讀的中間文字，即使成功後可從歷史正式答覆展開回看，也不成為「歷史訪談資料」中的一則正式訊息，不分配訪談序號，不供工作情境／理解整理或 JD 引用。**App 開場第 1 則不屬這類模型中間訊息**；其後成功完成的有效員工輸入與顧問完整正式答覆才取得正式來源資格。不可因公開中間文字曾顯示在聊天畫面，就將它插入按序號回讀、近期歷史訪談或背景批次範圍。此限制不要求改寫或刪除模型原生接續 items；顯示與接續資料、正式引用來源分別依自己的用途管理。唯一產品語意見[產品概念](../product-concept.md#保存正式資格與使用者控制)。

**歷史對話的辨識範例（只示意可讀效果，不指定 wire）：**

```text
【歷史訪談資料】
以下是已完成訪談中的原始對話，不是當次新輸入。
訪談序號表示本職務檔案內的發話先後順序；數字越小，發話越早。

訪談序號：7
說話者：職務顧問
訪談原文：「這項盤點通常多久做一次？」

訪談序號：8
說話者：受訪員工
訪談原文：「每個月；另外我也負責臨時補貨。」
```

實際返回完整原文，不由 App 改寫成上述示例或分析摘要；外層標示與逐則欄位須能區分資料和本次發話。A 起始投影仍是 App 組裝的 user 資料，按需讀取仍是原生工具結果，不能把歷史顧問發話提升為目前模型的新 assistant 訊息。JSON／引用輸入依各工具契約；標示歷史不等於已證明防提示詞注入。正式序號供後續歷史投影與查詢使用，不因此原地改寫既有原生模型接續歷史。

**處理進度與閱讀範圍分開：**最新版已發布 Memory 決定尚待整理的資料，補前問可跨到已整理範圍，但不倒退處理進度、不複製出新的原始來源。尚待整理的完整有效訪談不能因只挑相關片段而漏掉；即使沒有尚待整理的歷史，仍須處理本次回答所接的前問，不能直接推論近期歷史訪談資料必為空。A 的本次輸入依其私有執行資格提供，B1／B2 不因此可以讀尚未完成或已取消的輸入；各自固定範圍與權限不變。


### 起始訪談範圍與前置語境

本節將[產品的固定發布基準與近期資料](../product-concept.md#上下文與分析接續)、[背景固定取材與涵蓋](2026-09-25-b1-b2-information-gap-lifecycle.md#讀寫權限與交接資料)推導成確切起訖，不新增對話分組。K／H／F 是文件中的 App 計算符號，不是模型須填的參數或三份獨立 authority。

| 符號 | 取得時點與意義 |
|---|---|
| K | 從該 A Turn／B 批次固定採用的同一份已發布 Memory 取得正式訪談涵蓋上界；正常為該發布截止的最後一則員工輸入。首次無 Memory 時為 0。不同 A／B 工作可以固定不同 publication 及 K。 |
| H | A Turn 開始前已成立的有效歷史訪談序號上界；同 Turn／恢復不刷新，不含尚未正式編號的本次輸入。 |
| F | B 批次固定上界：觸發要求的 A Turn 最後員工輸入在成功完成後取得的正式序號；不包含其後顧問回答，亦不因背景延後啟動或恢復而擴大。 |

1. **A 正常起始：**完整提供 `(K,H]` 的有效歷史訪談，另加本次員工原文；本次輸入不預編序號，也不重複放入歷史集合。首次 K=0、H=1 時包含 App 正式開場第 1 則。正常 K 指向員工發話，其後 `K+1` 的顧問完整答覆若已成立，便自然落在近期集合中，可作下次回答的前問；角色仍按實際記錄判定，不由奇偶猜算。
2. **B1 必處理：**完整提供 `(K,F]` 的有效訪談；B2 不重做 B1 的涵蓋工作，按需回讀 `≤F` 的有效訊息。只有 F>K 才有新的必處理區間；若要求已被正式涵蓋，不以空區間再造待處理批次。首次 K=0 時 B1 新資料包含 App 第 1 則；開場仍不是員工事實。`F+1` 即使已正式保存為顧問答覆，也不納入這批起始、補前問或按需讀取。
3. **補前問的工程規則：**若起始集合開頭是員工訊息且未帶其前置引導，補最接近、合法且更早的一則顧問完整答覆或 App 開場；若 A 歷史集合為空，仍以本次輸入之前的有效歷史找該前問。已有前問則不重複加，找不到不捏造。補入資料與原集合按正式序號排序及去重，明標為附加語境；不改 K、H、F、B1 必處理區間或正式涵蓋。B 的補充同樣不得超過 F。這是一則前置語境的選取規則，不聲稱它與回答必為問答配對或已包含完整主題；不足再按需查原話。
4. **處理中與失敗不推進 K：**背景正在整理、B1 已讀、B2 已完成候選或工具已成功都不是正式發布。A／B 原工作維持固定 K；另一次工作才可從新的成功發布取得 K。未發布失敗區間不能被下一批跳過。
5. **容量：**A 超量沿已確認例外，App 明示未預載的序號／範圍及 `read_interview` 入口，不冒稱已讀或改小近期範圍。B1 的指定來源超量不能套用 A 的例外而悄悄漏交新資料；依既有合法準備／壓縮及有界恢復處理，仍不能容納則停止並保留原範圍與恢復點，不推進涵蓋，不自行拆批或換模型。容量計量、閾值與提示的實際效果仍需對應證據。

例：已發布 K=30，A 開始前 H=39，則近期為 31–39；若 B 固定 F=38，B1 必處理為 31–38，不能加顧問答覆 39。背景即使正在處理到 38 或同輪發布新版，A 仍保留 K=30／H=39。若另一個選取範圍從員工訊息 34 起且缺前問，附加合法顧問訊息 33 只補語境，不宣稱新增或倒退涵蓋；此例不是 B1 可任意縮小必處理區間。

**引用與附加語境分開：**定位一則訊息，不等於永遠只能讀它；讀到的資料也不自動全部成為引用。若其他訊息實際支持所寫內容，引用如何明確選取它，留給來源寫入契約。原文資料可以跳號、跨主題，目的是讓模型取得理解所需的前後文；必須保留真實順序，不宣稱未讀到的中間內容不存在。選取更多訊息或範圍有助核對「每月」「剛剛另一件」等指涉，但不保證整件事已完整或沒有範圍外的更正；不足時仍須查詢或由 A 釐清。

**研究依據與取捨分開：**先前核對的 [OpenAI Citation Formatting](https://developers.openai.com/api/docs/guides/citation-formatting)建議先定可引用單位、使用穩定來源 ID，並讓來源容易連同周圍語境核對；它允許文件、區塊等不同粒度，沒有規定訪談必須按 Turn 或固定問答切片。本次來源身分與序號分開、可指定訊息／範圍，屬 Caliburn 的產品選擇，不宣稱是官方指定格式。

## 3. App 管理讀取基準與權限

- **A：**讀本 Turn 已固定的已發布 Memory；背景發布新版不在 Turn 中途偷偷改變其 map 或正文基準。同輪恢復沿用原基準。
- **B1／B2：**依本批固定正式基底及各自權限，讀本批候選的有效內容；已成立的候選修改須能讀回。這不等於候選整批不可修改，也不讓候選對 A／JD 正式讀取路徑外露。
- **B1：**可讀情境及有效原始訪談，不可取得理解 map、正文或來源資料。**B2：**可讀情境／理解及允許範圍內的原話，不可修改情境。完整規則以既有權限表為準。
- **每次結果必須一致：**map 與物件 read 均反映該 Agent 此時有權讀取的目前內容：A 是本 Turn 固定的已發布 Memory，B1／B2 是本批可見的最新工作稿；物件標題、描述、正文與目前來源須彼此一致。B2 交接期間情境不並行改動；A 不因背景發布而中途刷新 Memory。
- **候選關係與正式歷史引用分開：**B1／B2 候選關係連物件身分，read 給目前可見的候選內容；B2 根據變更資料重評語意。正式已發布 Memory 與 JD 當時採用的引用固定修訂，不隨候選改動；A 若需核對 JD 的舊依據，App 提供舊→本 Turn 已發布新基準的差異，並只讓 A 按需讀新基準全文。人與 App 的歷史精確回查仍屬正式來源保存責任，不表示 Agent 有舊版物件 read 入口。


### Memory 本批的固定訪談序號上界

**Memory 整理及其訪談讀取以「本批訪談序號上界」限制，不以 Agent Turn 編號作工具過濾條件。**A 在 X Turn 提出整理要求，等 X Turn 成功完成後才啟動背景整理；App 以 **X Turn 最後一則使用者輸入取得的正式訪談序號**固定本批上界，包含該則輸入，**不包含 X Turn 在它之後產生的顧問回覆**。啟動時點與資料截止點是兩件事，不能取 Turn 完成時的最後一則訊息或當下最大序號代替。上界以前的有效員工與顧問訊息仍依既定範圍提供，不是只篩員工發話。執行時由 Runtime 自動注入該上界，不由模型產生、填寫或修改，也不作模型必須閱讀的控制資訊。保存與注入依[Memory 保存](../implementation/memory-storage.md)。

- **模型選擇與執行限制分開：**模型只選要查的訪談序號／範圍；Runtime 綁定職務檔案、有效來源資格與本批固定上界。上界不放進模型可填的工具參數，不能靠 Prompt 要求模型自己守住；各則資料仍照約定顯示訪談序號，不因隱藏控制參數而隱藏正常來源資訊。
- **同批固定：**B1、B2 的起始取材、後續訪談工具與來源回查均不得讀取超過本批上界的訊息。延後啟動、同批 Step 或中斷恢復均沿用原上界，不以當下最新訪談序號重新計算；只有另一次合法的新整理工作才綁定自己的範圍。
- **上界不是本批必處理範圍的起點：**B1／B2 仍可回查上界以前更早的有效歷史，以理解指涉；不因此改動本批必須整理的新資料範圍或發布進度。來源是否有效與是否在上界內都須成立，不只檢查數字大小。
- **例子只是序號示意：**第 18 Turn 提出要求並成功完成，其最後一則員工輸入取得訪談序號 38、後續顧問回覆取得 39，則本批上界固定為 38，不能讀 39。第 19 Turn 的輸入即使稍後完成並取得正式序號 40，本批也不可讀 40；取消／未完成時則根本沒有正式訪談序號與共享資格。上界由原輸入身分對應的正式序號取得，不由 Turn 編號、奇偶或「下一個輸入序號減一」猜算。39 仍是有效歷史訪談，只是不在這批範圍，不能因此刪除或宣稱已被本批整理。

請求超出上界時不得外露界線之後的內容，也不得靜默擴大本批範圍。**工程設計：整筆拒絕**，依[共同錯誤契約](2026-09-27-agent-tool-contract-design-research.md#7-錯誤回傳與恢復責任)回範圍錯誤與合法下一步，不返回超界內容或假稱完整；同樣適用不存在或無資格的序號。模型輸入沿本頁 `read_interview` 分支；strict schema 與隔離效果須各自有實測證據。

讀取契約與各分支實測分開；Runtime 的身分／版本解析效果仍需對應證據。


## 4. 定位與權限界線

1. **來源 ID、正式序號與查詢介面。**模型選正式訪談序號，App 映射內部來源 ID；成功編號、取消不佔號及共享資格已定。起始 K／H／F、前問、messages／range 分支與整筆拒絕依前述規則；序列化、容量數值及上界保存／注入的實際效果仍需對應證據。A 的未編號本次輸入可作 JD 候選依據，模型使用 [JD 契約的 `current_input`](2026-09-29-jd-model-tool-contract-review.md#42-直接來源的最小選擇)，不放入共享訪談 read、不擅加 user 前綴；正式引用保存與取消依原業務責任驗證。
2. **標題操作與讀取觀察的綁定。**title 作模型選擇值已定，不重開 title／UUID 二選一；同一歷史 context 可能仍留有舊觀察，B1 也可改名或修訂候選。新物件 read 一律按 Agent 當下有權使用的目前基準解析，不讓模型選舊修訂；App 仍須以真正物件身分解析標題、辨別歷史引用及形成差異，不能靠未明示的「最後一次讀取」猜目標。
   - 同名不足以辨認不同物件或舊引用，但不因此需要 Agent 讀取舊版正文、填版本參數或持有新的代號 registry。舊基準是引用實際綁定的修訂，新基準是該 Agent 此時可見的同身分修訂，兩者由 App 比較。
   - 反例：B2 的候選理解 U 關聯情境 C；B1 修改 C 後，U 的候選關係仍指向 C，情境 map／read 給新版，App 提供前後差異。B2 根據差異判斷 U 需要改正文、改關係或保留不變；不需模型逐條確認換版。正式發布時固定 U、C 的當時修訂與關係，較早正式 Memory 不被改寫。diff 的比較範圍、名稱篩選與 Markdown 詳情沿[背景差異工具契約](2026-09-25-b1-b2-information-gap-lifecycle.md#差異讀取契約)，生成 wire 與接線仍待驗。
3. **工具分支與錯誤語意。**模型入口、分支及正常／拒絕結果依[共同工具規範](2026-09-27-agent-tool-contract-design-research.md)；schema 由正式來源生成，資料表或示例不代表 strict wire 已通過。無權、無目標與容量未完整不得合成正常空結果。

**標題選取的確切工程規則：**新 read／update／delete 及新的來源選擇，以當前有權作用域的標題映射 ID；比較採原字串精確相等，不模糊選取、不自動做大小寫折疊、去空白或 Unicode 正規化。純空白 title 不合法，保存內容不被偷偷正規化；重名檢查與解析共用同一比較規則。已建立的候選關係、歷史固定引用與已綁定原操作則沿各自 ID，不再以名稱解析。C 從 X 改名 Y、D 重用 X 後，新請求 X 指向 D；原引用仍指 C，原操作重入仍查 C 的原結果。若原操作目標已失效不能改派 D；不能因模型歷史仍含 X 就拒絕所有新操作或要求新 proof。Unicode／空白、同層唯一與重入均適用此精確解析規則，名稱重用本身允許。

以上產品效果已有定義；具體工程映射由[共用執行](2026-09-27-shared-agent-execution-and-state-design.md)、[資料與交易](../architecture/persistence.md)及角色工具契約承接，strict wire、名稱解析與固定歷史的反例仍須驗證，不能以文件完整宣稱已驗證。


### 定位、版本與並行核對的方法來源

[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling#best-practices-for-defining-functions)支持 App 填入已知參數、工具清楚表達用途。[Google AIP-154](https://google.aip.dev/154)、[Azure 樂觀並行控制](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage#optimistic-concurrency)及 [S3 特定版本讀取](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RetrievingObjectVersions.html)分別提供基準核對與版本讀取的公開例子，支持**選物件、選版本、檢查寫入基準是不同問題**。

Caliburn 由 App 管理身分、基準及條件提交；Memory 模型介面只按目前可見範圍選標題，不增加觀察 proof、`read_ref` 或歷史正文入口。這是本案取捨，並非上述平台統一規定。名稱重用仍可能使模型選到它未表達的舊意圖以外的物件；App 不能從單一標題猜出該意圖，既存關係與原操作則始終以原身分處理。

### 本批候選編輯與歷史版本回查分開

B1／B2 操作本批未發布候選；對外讀者只看正式發布版。Runtime 管理目前候選及基準，不因候選修訂便要求模型每次帶回觀察參照。

一般候選讀寫已定義為「操作本批目前有效的工作稿」：模型提供 `target_title` 及修改意圖；Runtime 綁定原工作、權限、目前候選、映射後的物件 ID 與執行基準。修改成功後，依[更新結果契約](2026-09-27-memory-object-update-tool-contract.md#6-成功回傳已成立的候選效果)回傳真正採用的修改，供模型接續；不為每次內部修訂增加模型必填版本代號，也不因此發行一版正式 Memory。具體儲存與條件提交依 Memory 保存接線。

這與「Runtime 猜模型指哪個歷史版本」不同：一般編輯的目標已明確是當前工作稿，不兼任歷史版本編輯。候選理解關係沿物件身分讀當前情境；沿 JD 既有正式來源閱讀時，模型讀到本 Turn 固定的新基準，App 仍依 JD 當時固定舊引用形成差異；不能把「read 給新版」誤作「JD 舊依據已核對」。舊版物件正文不另給 Agent 讀，人的正式歷史來源回查由原資料責任保留。

必要條件沿既定責任處理，不新增元件：

- **Runtime 掌握目前候選，不等於模型已理解最新內容。**自己的修改結果須真實回傳；B1 交付後，B2 依變更資料及按需新內容重評，不能只因候選綁定持續存在就宣稱語意一致。B2 完成是整階段語意判斷，不是逐條引用確認；歷史 context 與已發布來源不改寫。
- **分責不自動保證執行沒有競爭。**既定主流程是 B1 → B2 → 發布，不回交；同物件依序修改、程序重入、過期工作與保存時基準核對仍由執行／候選所屬領域模組保護。不把「沒有外部修改」當成可移除重入與條件提交檢查的理由。
- **新名稱選擇與既存身分分開。**依本頁確切解析規則，新請求可選重用名稱的當前物件；既存關係與原操作不改指。找不到當前唯一目標才拒絕，不猜舊名稱別名，不增加模型必填 read_ref、重讀或觀察 proof。
- **一般編輯與重新執行分開。**新修改操作指當前工作稿；中斷後再次進入同一已保存操作，仍按原操作查回結果，不把它當成一筆新的 latest 修改。

[LangGraph State 指引](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph#step-3-design-your-state)支持由程式承接跨步驟工作資料；[PostgreSQL 交易隔離](https://www.postgresql.org/docs/current/transaction-iso.html)說明讀寫基準與並行的實際限制。兩者都不替本案保證模型理解正確，也沒有規定基準必須由 LLM 作參數傳回。本節是依產品工作範圍作的取捨，不宣稱框架已自動滿足。

**反例：**候選反覆修改、改名與名稱重用、原操作重入、取消／放棄後的遲到結果，以及 JD 正式舊依據→新基準的差異，須依相應層級驗證。不能以同名或正文相同替代身分；Memory 讀當前候選，JD 才有既存引用的明確核對。


## 5. 讀取邊界與反例

以下列出讀取契約的關鍵行為；實際覆蓋與未驗範圍見驗收矩陣：

- 導覽列出授權範圍的完整標題／描述，能直接選理解或情境；來源回傳不混入 `body`。
- 理解來源只展開目前可見情境的 target_title／description；情境來源提供可回讀的正式訪談序號，內部來源 ID 由 App 管理。原話保留角色與順序，不把顧問假設當員工事實。
- A 固定版本與背景候選彼此隔離；B1 無任何理解層存取，B2 不藉讀取入口修改情境。
- 同層重名拒絕、跨層同名允許，不誤拒不同版本或不同職務檔案沿用標題；改名、名稱重用、候選更新與歷史引用不造成靜默重定向。Agent 的 map／read 均反映其可見目前基準；已發布歷史引用維持原綁定，App 對 JD 所需新舊修訂提供正確差異，不以當前描述冒充舊引用正文。
- 模型輸入 title 經 App 映射後，資料庫收到的是 ID 定位；讀／改／刪及正式引用均不以 title 尋址，改名不改物件身分或既有固定引用。
- 取消／被替換輸入不取得有效來源資格、不佔正式訪談序號；如底層保留該輸入的保存身分，不等於可經 Agent 查詢或引用。來源資格與本批範圍沿既定規則。
- A 執行中／暫停／取消時，當次輸入沒有正式訪談序號，模型收到的 user content 保持員工原文；其他 Agent 的訪談讀取不取得該候選。只有完成條件成立後才可編號／正式回讀，不能僅因模型回覆已產生就提前外露。恢復同一已完成結果不再次編號。
- 起始近期歷史訪談資料與工具結果均清楚標示為「歷史訪談資料」，逐則具有固定訪談序號、說話者、完整訪談原文，明示序號的發話先後意義；不能只列號碼與文字卻讓模型誤認成新 user／assistant 發話，也不能用摘要冒充原文。歷史投影的編號不改寫原生模型接續 items。
- 同一訊息跨 context、工具結果及 Memory 版本均有相同正式序號與來源身分，不以查詢結果重編；角色不依 ID 奇偶推定。指定 1、2、5、7 與範圍 2→7 的結果不同，原序號／說話者均保留；不把跳號說成連續，也不漏掉範圍內合法原文。
- B1 使用與 A 相同的訪談讀取契約，能按序號選本批內或更早的有效歷史訊息／範圍；App 拒絕超出本批可讀上界、跨檔案或未完成／取消來源。選取讀取內容不改變本批必處理範圍，不以只能無參數讀整批取代其按需回查能力。
- Memory 本批上界由 Runtime 注入、不出現在模型可填參數；起始 context 與 B1／B2 訪談／來源回查遵守同一固定序號界線。在「X Turn 成功完成後，最後員工輸入為 38、該 Turn 顧問回覆為 39」「後續正式輸入 40」「延後啟動」「B1 交接後 B2 讀取」「中斷恢復」等情境中，均只允許讀至 38，不能讀 39／40，且仍可合法回查更早的員工與顧問訊息；不拿 Turn 號、奇偶或當下最大序號作替代。上界在內不代表取消／未完成來源可讀；本批發布進度不得把上界後的顧問回覆算成已處理。
- 員工主動開新話題不必假造前問；真正有指涉缺口才查詢或釐清。App 開場引導有真實出處，無前文時不造前文；補前問不改 Memory 處理進度。本次輸入只在這次新增起始資料中提供一次，不因補語境外露給背景 Agent。

- K／H／F 依同一發布及有效歷史求得；首次 K=0 包含 App 第 1 則，K+1 的顧問回答自然保留。補前問只加合法較早一則並去重，不改涵蓋、不越 B 的 F。A 超量標未附範圍供回讀；B1 不能漏交指定新來源，容量不符時保留範圍並依既有有界恢復／停止處理。

來源增刪與結果依[更新契約](2026-09-27-memory-object-update-tool-contract.md#10-來源與正文共同修訂)。schema、容量、來源映射、保存及模型效果須各自驗證；契約文件完整不代表產品品質已通過。
