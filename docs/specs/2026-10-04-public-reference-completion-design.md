# 公版參考的整體與任務收尾用途

日期：2026-10-05。狀態：**已接入角色 runner，可由明示設定啟用；現行共用服務未重啟** 。使用者已接續授權「現在接入 tool」，取代前輪先不接模型的限制；採用權責見 [ADR0080](../adr/0080-opt-in-public-reference-agent-tools.md)，接線驗證見[驗證紀錄](../experiments/engineering/README.md#角色接線)。檢索策略仍依[檢索設計](2026-10-04-public-reference-retrieval-design.md)；本文件定義顧問如何使用公版與保存必要的跨輪資訊。

## 最新確認：只保留明確否認的工作範圍

使用者在第一版工具完成後明確修正：「員工回答來源……我覺得不用」，並確認用途是「避免繼續問，因為也不放 memory」。本節取代前版的 `confirmations(subject, answer_refs)`；不再保存一般確認事項或員工回答來源。

保留兩項內容：目前選用的固定公版 ID，以及員工明確說沒有做／不負責的具體工作範圍。否認範圍獨立於 Memory，供顧問在查漏與追問前閱讀；不寫入 Memory，不自動混入 embedding／rerank 的 query。B1／B2 內容方法維持既有指引，透過下方唯讀工具取得責任邊界。

```json
{
  "selected_reference_ids": ["<前端公版 reference_id>", "<後端公版 reference_id>"],
  "excluded_work": ["正式環境部署由維運團隊負責，本人不執行部署"]
}
```

- `selected_reference_ids: null` 表示尚未選擇；`[]` 表示評估後沒有合適參考。可多選、重選；單次搜尋最多五份，不是選用 state 的永久配額。
- `excluded_work` 是明確否認的工作範圍文字，不是公版職稱、T code、來源索引或完成狀態。保留必要條件，不能把「不做正式部署」擴張成「不做所有維運」。
- 「不知道、部分適用、沒回答、拒答」不等於沒有做；只有已明確否認的部分才列入。模型仍須理解員工語意，工具不自動辨識否認。
- 已有排除範圍用來避免再問同一事項；員工更正、新增責任或原範圍已不適用時，可以解除或更換。這不是永久禁止追問，也不自動移除整份公版或宣告 JD 完成。
- 新搜尋、排名／Memory 更新及重選公版不清除排除範圍。取消或失敗的 Turn 不把新排除帶到後續輪次。

<a id="工具與保存契約未接模型"></a>
## 工具與保存契約（明示設定啟用）

公版工具沿既有模組分工。bootstrap 決定是否建立 HTTP client，runner 按原請求提供工具；未配置時保留原工具清單。使用說明只追加在啟用的新請求，不改既有顧問／B2 指引檔，也沒有新增 App HTTP endpoint。

| 程式責任 | 管理的內容 |
|---|---|
| `transport/model_tools` | 驗證模型參數、呼叫查讀或準備寫入命令、將實際結果轉成工具回傳；不自行保存另一份 state。 |
| `workflows` | 協調來源可讀性、檔案與 writer 資格、候選位置及短交易；不判斷員工是否負責某工作。 |
| `features/occupation_references` | 管理選用／否認規則、候選及不可變操作結果，維護重播與回復保護。 |
| `adapters/occupation_references` | 處理獨立 RAG HTTP 請求、來源身分與回傳驗證；不擁有 JD、Memory 或員工工作事實。 |

下表列出模型可用的操作；正式欄位與型別仍由 JSON Schema 定義。

| 工具 | 參數及效果 |
|---|---|
| `search_occupation_references` | `query` 使用已確認主要工作；回傳最多五份概述與完整已解析任務名稱目錄，模型端不接收相似度作認定。排除清單不由系統拼入查詢，查詢忠實性仍待模型驗證。 |
| `read_occupation_reference` | `reference_id` 與 `task_id`；null 讀整體目錄，指定任務定位才讀細節。未選公版也可以讀；公版只作線索。 |
| `read_occupation_reference_state` | 空參數，讀本輪所選公版與排除範圍。 |
| `select_occupation_references` | `reference_ids` 取代選用集合，驗證固定來源可讀，保留排除範圍。 |
| `update_excluded_work` | `add`／`remove` 兩個文字陣列；新增明確否認的範圍，或在員工更正時精確解除已存在範圍。不接受來源欄位。 |

正式 wire 以 [App tools JSON Schema](../../apps/api/contracts/tools/) 為準，Python／TypeScript 使用既有 generator。`record_work_confirmation` 與其輸入 schema 已由 `update_excluded_work` 取代，不保留並行兩種紀錄模式。

### 工具契約接續改善（2026-10-05）

選用 description 與 `reference_ids` 參數明說全集合替換：要保留的舊 ID 必須一起提交。讀取 description 說明可用工具或 state 的固定定位，未選公版也可先讀；選用、搜尋與來源讀取的業務行為不變。

新的選用／排除寫入成功只回 [OccupationReferenceWriteResult](../../apps/api/contracts/tools/occupation-reference-write-result.schema.json)：

```json
{"status":"updated"}
```

此結果表示本輪候選已成立，不提交整輪，也不認定 JD 完整。完整 `selected_reference_ids + excluded_work` 沿既有 `read_occupation_reference_state({})` 按需讀取；讀取超量仍整筆拒絕，不截斷。寫入不再重送整份 state，也不在已成功保存後回傳「未改」的容量錯誤。Domain 不可變操作結果仍保存完整 state，prepared command 的格式與 App 身分不變。

五項工具的不合法參數沿同一 `status/code/message/next_action` 錯誤格式，各自指出合法欄位及下一步。逾時／服務不可用交 App 處理連線，索引不相容交 App 處理索引，來源失效則核對固定定位；故障不等於空候選。沒有新增 validator 或重試機制。

寫入回傳格式由本輪已保存的原請求決定：

- **新請求：** 兩個寫入工具的 description 均帶固定後綴，成功回精簡結果。
- **舊請求：** 兩個 description 均沒有該後綴，維持原本完整 state 回傳；恢復後仍使用舊格式。
- **已保存結果：** 原 request、prepared command 與 native output 原樣接續，不重新轉成新格式。

固定後綴為 `成功只回 {"status":"updated"}；需要完整 state 時再按需讀取。`。這段文字用來識別持久格式，後續潤飾 description 必須保留；不能依當前設定或自由文字語意猜模式。

公版工具組缺工具、名稱重複或兩項寫入格式混用時，App 在建立候選前拒絕。handler 使用原 captured request，不新增模型版本參數、資料表或恢復器。

可選角色指引同步說明替換與小型成功回傳，已有足夠有效內容可沿用；排除維護可以在訪談中進行。只影響新的啟用請求，舊輪次仍使用原指引。搜尋仍回最多五份完整已解析目錄，三層候選概覽仍是另案比較。工程反例、獨立審查與驗證見[接續紀錄](../experiments/engineering/2026-10-05-occupation-reference-tools/hardening-verification.md)。

`add` 以原字串去重、保留原順序；`remove` 用讀回的精確字串。新增與移除有交集、兩者皆空、移除不存在項目、空白或 NUL 均整批拒絕。更換文字可同次移除舊範圍並新增修正版；沒有另建語意去重或判斷模型。搜尋失敗不當成無合適公版，回傳超量不靜默截斷。

feature 仍擁有 `occupation_reference_candidates`（位置）與 `occupation_reference_operations`（不可變結果）兩表。App 綁定檔案、writer、generation、revision 與 operation，模型不提供。prepare 固定變更，execute 以短交易核對檔案／writer／revision；原命令重送回原結果。checkpoint 缺欄位不得補預設值；回復至本 Turn 可達祖先會更換 generation，拒絕舊分支操作。

只有 execution completed **且** 有對應正式員工 exchange 的候選，才成為後續 Turn 可見 state；依正式員工序號取最新者。這是本輪正式生效資格，不是回答來源欄位或模型否認判讀的證明。中間未使用工具的輪次不清空 state。

`0024` 只用於隔離測試 schema，未在本次套用正式資料庫；接線沿用其既有 JSON shape，不新增 migration、不改寫舊實驗原件。正常 runner 接續沿已保存的 prepared command 與 operation result，不倒帶候選或重選公版；完成／取消沿既有資格機制。

獨立呼叫先 `workflow.start(writer)` 再建 `OccupationReferenceTools(workflow, client, writer)`。讀取用 `invoke`；寫入用 `prepare → 保存 prepared → execute`。來源讀取上界已不屬這組工具參數；它沒有員工來源導覽責任。HTTP client URL、有限 timeout 及關閉仍由組裝者管理。

## Memory 的排除範圍唯讀入口

Memory 整理需要知道責任界線，以免將員工未負責的工作補回理解；不需要複製所選公版或整份排除清單。已確認的本人工作與必要交接關係仍沿既有 Memory 方法整理，`excluded_work` 的權威保存仍在本 feature。

提供獨立 `read_excluded_work({})`，成功只回：

```json
{"excluded_work": ["正式環境部署由維運團隊負責，本人不執行部署"]}
```

參數必須是空物件；模型不能填職務 ID、執行 ID、版本、stage 或上界。入口沒有搜尋、選公版、更新排除清單的權限。完整清單超過容量時明確拒絕，不截斷或假裝為空；此結果不是原話引用或完成判定。

App 建立 `ExcludedWorkReadWorkflow(sessions)` 與 `ExcludedWorkReadTools(workflow, binding)`，`binding` 沿現有 `MemoryReadBinding`。B1／B2 使用 `CandidateMemoryRead`，從持久批次及有效 stage 取得固定 F；可見的正式 Turn 必須 completed 且其正式**員工輸入序號 ≤ F** 。觸發批次的顧問回覆可能晚於 F，仍須讀到該 Turn 已正式化的排除範圍。後續 Turn 的新增／解除不回流舊批次；active、取消或沒有正式 exchange 的候選不生效。`PublishedMemoryRead` 則沿既有固定訪談上界。兩者都核對 execution ACTIVE，候選另核對 stage／generation，沿既有 Memory 讀取契約，不新增模型提供的範圍欄位。

`workflows/occupation_reference_reads.py` 共用正式 state 查詢；顧問 start 在 file lock 中固定當前 frontier 後也使用此查詢。沒有第二份排除資料、Memory 寫入、資料表或新的發布狀態。工具 schema 由既有 generator 生成；B1／B2 只在啟用的原請求上增加唯讀工具。角色內容指引未因本切片重寫，模型按需讀取與否認判讀由後續訪談比較評估。

## 可選接線與執行中的工作

`Settings.occupation_references` 預設 None。設定 `CALIBURN_OCCUPATION_REFERENCE_URL` 才建立公版 HTTP client，timeout 由 `CALIBURN_OCCUPATION_REFERENCE_REQUEST_TIMEOUT_SECONDS` 設定，預設 30 秒。bootstrap 以既有 AsyncExitStack 管理 client；不使用系統代理、不跟隨重導，服務錯誤仍回明確工具錯誤。RAG 服務保持獨立，不因啟動 JD App 就自動啟動。

啟用的新 A 請求追加五工具與收尾查漏使用說明；B1／B2 追加 `read_excluded_work`。`RoleContextHistory.resolve_template` 從本執行／角色已保存的 preparation request 還原模板；held recovery 必須核對相符的原 saver 邊界，缺少原邊界時拒絕。capture initial context 及 native Step 仍沿原快照。實際 handler 依 capture 後的原 request.tools 綁定，所以新設定不會把工具插入已開始的舊訪談或舊批次。原 A 請求已啟用而後續缺 client 時，在模型請求前明確拒絕。

正常工具重播直接沿 Graph 已保存的 JSON command/result，不另建恢復器，也不在每次重入呼叫 `restore_candidate`。只有原 request 已宣告完整公版工具組時才啟動／找回本輪 reference candidate。B1／B2 的讀取仍由持久 F 固定可見範圍。

本次只完成程式及隔離驗證，沒有更改其他人使用中的環境檔或重啟共用服務。實際啟用步驟見 [API README](../../apps/api/README.md#公版參考工具的可選啟用)。

## 最新確認：只記確認事項與員工回答來源

2026-10-05，使用者同意顧問準備收尾時依已確認主要工作搜尋代表職位，參考任務目錄查漏，再由顧問自然追問、更新 JD 及判斷收尾。使用者進一步指定：「確認事項，依據只用填員工回答來源就可以；我們只需要確認就好，其它他自己判斷。」

確認紀錄只保留以下兩項，取代先前三欄的「事項／結果／依據」建議：

| 內容 | 意義 |
|---|---|
| 確認事項 | 正在確認的具體工作或責任範圍，例如「是否負責正式環境部署」。 |
| 員工回答來源 | 可回查的相關員工回答；依據只填這類來源，不要求另填公版來源、模型判斷或 JD 對應。 |

顧問讀取回答，自行判斷有做、沒做、部分負責、仍未知，以及是否需追問、改稿、沿用或重核。不另要求填確認結果、狀態、分數、完成條件或後續動作。這筆紀錄只協助找回問過的範圍與回答，不增加另一套員工事實正文。

有回答來源不等於已釐清；「不知道」「部分有做」「暫不回答」也可能有來源。App 不因紀錄存在就自動標完成、隱藏公版或排除後續確認。尚未回答不能填造來源；未解問題如何接續仍由顧問依既有脈絡處理。

Memory 整理或搜尋名次變動不自動清除紀錄。員工更正相關責任時，顧問依新回答判斷受影響範圍，不能因已有紀錄就忽略更正。來源的檔案範圍、正式資格及定位沿既有契約，由 App 核對；本次工具與保存見下節，顧問 consumer 尚未啟用。

最小驗證聚焦能否找回回答、避免不必要重問，以及面對部分回答、未知與後續更正時仍能正確接續。整份 JD 是否可交付仍由顧問綜合判斷並另外驗證，不由確認紀錄數量決定。研究依據見[長任務收斂研究](../research/work-analysis/2026-10-05-jd-long-task-convergence.md)。

## 公版參考 state：先選主要參考，再按需核對

狀態：2026-10-05 使用者已同意以下資料內容與使用流程，作為後續實作目標。這次確認不把既有獨立 RAG 自動接入正式 App，也不將文件或 schema 通過當成顧問品質驗收。

目的：讓顧問延續「目前拿哪些公版作主要工作參考、問過什麼及答案在哪」，避免每輪重讀五份全文。公版選擇是參考使用決定，不能寫成員工正式職位或本人工作事實。

### 先看目錄，再選擇

1. 依目前已確認的主要工作搜尋，取得最多五份候選。
2. 先看各候選的職位名稱、原始概述、工作單元與任務名稱目錄，保留固定讀取定位；這一層不展開全部 O/P/K/S 正文。名稱只協助導覽，顧問仍依工作內容選擇。目錄若過長，可先看單元導覽再按需讀完整任務目錄，必須明示尚有內容未展開，不靜默截斷。
3. 顧問選可共同代表員工主要工作範圍的公版，允許多選，也允許沒有合適參考。一份可涵蓋一個主要面向，不要求每份都單獨代表整位員工；例如全端工作可選前端與後端參考。低頻但重要的本人責任可屬主要範圍，僅有偶發幫忙或詞彙相似不作主要選擇依據。
4. 概述或名稱不足以判斷時，顧問可以先讀任何候選的必要任務正文再決定，不要求先選中才有閱讀權限。對選用公版的目錄比對既有工作及確認紀錄，再自然追問有價值的缺口。

目前[獨立 API](2026-10-05-occupation-reference-api-design.md)及其 [DTO](../../packages/indexer-contract/src/indexer_contract/references.py)已回傳 `title`、`overview`、`units` 及全部已解析任務名稱，並支援固定來源／任務讀取；它尚未提供 Agent consumer、選用 state 或分頁導覽。第一版可沿用現有目錄，不必先加一個模型生成摘要或額外篩選 Agent。先看導覽、持定位按需讀正文的原則也見 [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（2026-10-05 核對）；它不保證本案選擇品質或總耗時下降。

### 最小資料形狀

名稱 `OccupationReferenceState`。以下是已確認的資料內容示意，正式工具 wire 由下節 JSON Schema 定義；占位符必須由實際讀取回傳的合法定位替換：

```json
{
  "selected_reference_ids": ["<前端公版的 reference_id>", "<後端公版的 reference_id>"],
  "confirmations": [
    {
      "subject": "是否負責正式環境部署",
      "answer_refs": ["<員工回答來源>"]
    }
  ]
}
```

| 內容 | 用途 |
|---|---|
| `selected_reference_ids` | 目前選用的公版固定 ID，可多選及重新調整。`null` 表示尚未選擇；`[]` 表示已評估但目前沒有合適參考。空清單不代表工作完整，搜尋失敗也不能冒充評估後的空清單。 |
| `confirmations[].subject` | 已進行確認的具體事項，範圍足以讓顧問辨識，不綁定公版單一 T code。 |
| `confirmations[].answer_refs` | 一個或多個相關員工回答來源；顧問按需讀回、自行判斷。其餘結論／狀態／分數不另存。 |

初始值為 `selected_reference_ids: null`、`confirmations: []`。此 state 不另複製公版正文、搜尋分數、Memory 或員工回答；未選清單可由本次搜尋結果與所選 ID 比對得到，不維護永久排除表。職務檔案範圍、來源身分、內部版本及保存結果由 App 綁定與驗證，不讓模型生成。

### 責任與更新

- state 屬職務檔案的顧問參考使用資料；RAG 服務只管搜尋／來源讀取，B1／B2 繼續維護工作 Memory。顧問決定選用參考及確認事項，App 保存並提供讀寫能力，工具及儲存配置見下節。
- 採用既有本輪候選及完成安全點：同輪可讀自己的更新，成功完成後才成為後續輪次的有效 state；取消或失敗沿原有恢復責任，不能讓未提交的選擇取代正式資料。不新建另一套提交／恢復機制。
- 下一輪需要繼續查漏時讀目前 state，已選公版正文仍按需讀取。Memory 整理、單純改字及排名變化不自動清除 state；新增主要工作、更正責任或新候選／來源內容可能補上主要缺口時，由顧問決定是否重核選擇。
- 未選公版仍可回看，不視為本人不負責；取消選用某公版不刪員工回答來源。新搜尋結果不包含舊公版，也不自動清除舊選擇與確認紀錄。固定來源無法讀取時回報不可用，不以同名新版本代替。
- 五份是目前 API 的單次候選上限，不是選用 state 的永久累積配額。後續補搜仍以目前主要範圍重新調整所選集合，不把每次命中全部累積；也不為了固定留下某個數量而刪除必要的主要面向。此政策不修改既有 top-5 檢索控制初值。

### 比較與驗證範圍

直接把五份所有正文交顧問最省選擇步驟，但內容負擔大；只讓顧問看命中片段容易看不到同公版的其他工作。使用者已選定先看概述與完整名稱目錄，再按需讀正文並保存選用集合；尚未證明省 token、速度更快或品質更好。

固定同一批五份候選、員工資料及模型，比較直接使用五份參考與先選主要參考兩種流程。檢查混合前後端是否保留兩個主要面向、跨公版重疊是否不重問、抽象名稱時是否先回讀、全不適合時是否避免強配，以及部分回答／未知／責任更正是否被正確接續。另測壓縮或恢復後選擇與回答定位能否沿用、職務檔案是否隔離。記實際閱讀量、呼叫、token／耗時及篩選新增的漏失；尚未執行此比較。

### 最小落地與驗證順序

以下保留接續切片與完成條件；第一個工具／保存切片的實際進度見[驗證紀錄](../experiments/engineering/README.md#公版參考工具)，後續模型品質與接線仍未執行。不在本節增加產品欄位。

1. **state 保存與回讀。** 先用固定資料驗 `null`、空選擇、多選、重選後保留確認紀錄，以及不同職務檔案隔離。只接受有效公版定位與該檔案的員工回答來源；有來源但回答為未知／部分負責時，程式不得自動判定完成。
2. **獨立公版 consumer 資料流。** 沿現有 API 接概述／目錄及按需正文讀取，驗未選公版仍可讀、空候選與服務失敗分開、固定來源失效不以同名替換。這一步只能證明工具資料流與 state 行為，不證明顧問會挑選正確。
3. **固定案例的顧問比較。** 固定員工資料、五份候選、模型與預算，比較直接使用五份與先選主要參考；記主要工作涵蓋、重問、閱讀量及實際成本。尚有來源但內容未釐清、混合職位及後續更正須保留為反例。真模型執行仍依有效資料與費用授權，不沿用過去盲評外送額度。
4. **正式 App 接續驗證。** 接線時沿同輪候選、成功 Turn 提交、取消／失敗／恢復及正式來源資格，驗跨輪與壓縮後仍可正確讀回。獨立保存測試不能替代真實交易及 Agent 旅程；最後再驗整份 JD／PDF 收尾。

上述切片均維持兩項 state 內容，不新增每任務狀態、完成分數或額外篩選 Agent。不能由文件或工具測試通過自動產生 production 整合授權。

## 本輪收斂：以整份 JD 收尾為主

使用者在確認現行分析方法後，決定**先不補單項 JD 任務的完整度分析／收尾機制** 。本輪以職位整體參考協助整份 JD 收尾：讓顧問理解員工大致從事哪些工作類型，使用相關公版的完整已解析任務目錄提示可能未提到的工作。客製化職位仍可跨多份公版，不固定成單一職稱；檢索依員工實際工作及 Memory，而非先指定職稱套模板。

工作任務細節參考保留為後續方向，暫不實作或新增其完整度驗證。現有顧問依情境、案例與工作理解追問及撰寫 JD 的方法繼續使用。下文的兩用途與細節進度保留既有討論，**本輪只細化整體任務目錄的確認進度** ，不要求第一版同時建立兩套用途。

候選整體收尾規則：

1. **參考範圍明確。** 使用本輪員工資料找出的相關公版集合；每份可讀完整已解析任務目錄，不能把只有命中片段的清單冒充完整公版。此處的全部是該參考集合內的工作線索，不是全資料庫全部職業。
2. **目錄中的工作線索均有確認結果。** 已確認有做、部分適用且範圍已釐清、不負責，或已由其他實際工作涵蓋；保留對應範圍與依據。既有明確答案可沿用，未確認才詢問；跨來源重複可共同確認，公版與 JD 維持多對多。正在訪談、未回答、拒答或不確定不能冒充已確認。
3. **已知重要問題已處理，實際工作已整理進 JD。** 包括公版之外員工自行提出的工作、矛盾、更正及可能影響責任的疑問；用現行分析方法處理，不另補單項任務完整度元件。確定不屬本人的內容有排除理由，不能為對齊公版而增補責任。
4. **員工有最後核對機會。** 可檢視整體工作範圍及目前 JD，補充或更正；沉默不代替確認。新增或更正若影響前述結果，局部接續處理，再判斷當前是否可以收尾。

這把「公版任務確認完，其他問題解決後完成」落成可記錄的候選停止條件，不以公版勾選數代替 JD 內容核對，也不宣稱尚未提到的所有工作一定已發現。收尾效果仍須實驗；目前只有文件層檢索及離線導覽結構證據。

## 參考用途：本輪整體、後續細節

| 參考 | 顧問按需看什麼 | 要協助判斷的問題 |
|---|---|---|
| 職位整體參考 | 每份候選公版的職位概述、完整已解析任務目錄及必要短說明；需深入才讀任務細節 | 員工是否還有未提到的工作面向？相關面向確認後，整份 JD 是否可以收尾？ |
| 工作任務細節參考（後續） | 與某個實際工作面向相關的公版任務正文、產出、行為及必要上下文；K／S 可按需查閱 | 這個實際工作面向是否還有未說清楚的內容？該項 JD 任務是否可以收尾？ |

職位整體參考的閱讀粒度是任務目錄，不必先塞入整份公版的所有細節。這裡的「局部」是各份來源公版提供的視角；顧問最後仍須綜合員工的全部實際工作及可能跨多份公版的參考，不以讀完一份公版代表員工整體已完整。

兩種參考都協助顧問判斷，不另設兩個自動核准元件，也不把向量分數、公版任務數或來源閱讀數當完成率。現有實驗只證明文件候選涵蓋及來源導覽結構；沒有證明任務細節搜尋或顧問收尾有效。

## 確認的是員工實際範圍

公版列出的內容先作可能線索。顧問根據員工回答與既有資料，釐清哪些是本人工作、哪些不負責、哪些已由另一項實際工作涵蓋、哪些仍有重要疑點。已確認不負責的內容不需要補進 JD；未知不能直接當不適用。不能要求員工把所有來源公版的全部任務做完或說完。

整體收尾的候選判斷，是員工實際工作已被合理涵蓋、值得確認的公版線索已釐清、實際 JD 任務已說清楚並寫入 JD，且沒有尚未處理的重要疑點。這仍須結合分析方法、員工新增或更正及 JD 內容核對；公版資料可能抽取不全，檢索也可能漏失，因此公版檢查完畢本身不是充分證據。

任務收尾則聚焦該實際工作的目的、範圍、產出、做法、條件與本人權責等必要內容是否足以表達。公版能提示尚未談到的細節；不為照抄公版而追問與本人無關的內容。這些描述是待驗的顧問判斷方向，不強制 JD／Memory 增加固定分析欄位或完成百分比；本文件的參考處理進度另由 App 保存。

## 公版任務與 JD 任務保持多對多

比對對象是工作內容及涵蓋範圍，不能只用任務名稱、代碼或數量對齊。多個公版任務可以支持一個 JD 任務；一個公版任務也可以分別支持數個 JD 任務；公版中只有部分內容適用也成立。相同公版內容多次被引用，不算多份獨立證據。

例如員工的「開發產品功能」可能同時參考前端介面開發及後端 API 任務；公版的「部署與復原」也可能分別支持 JD 的「服務上線」與「事故回復」。是否合併或拆開取決於實際工作，不能為配合公版而改成一對一。

一項公版任務含數個工作面向時，其中一部分已談過不代表其餘部分已確認；反之，兩項 JD 任務共同涵蓋參考內容時，不因找不到單一同名任務就判缺口。細節層與整體層都需要保留這種部分及共同涵蓋關係。

## 原本要問的是否負責，改由員工直接選答

使用者確認的是互動方式：把顧問原本要問的「你有沒有做這項工作」改成 App 選項，減少 LLM 對答案作有／沒有的分類。顧問仍挑值得確認的線索，不把所有檢索來源的任務一次交員工勾選。問題針對本人目前實際負責的工作，包含低頻或例外情況；不能用能力、職稱認同或公版代碼代替實際責任。

選答先採「有做／部分有做／沒做／不確定或看不懂」四個概念，不預先選定答案；略過及拒答保留未知，允許補充、更正及自由提出其他工作。只對當次顯示範圍成立：有做可以結束該範圍的適用性問題，但細節仍須確認；部分有做須釐清適用部分；沒做不再反覆問同一範圍；不確定改用例子釐清。這些是介面候選，未生成正式 enum 或 API。

例如「清點庫存、調整帳務與回報差異」選部分有做，補充「只清點與回報，沒有調帳權」。顧問據此處理實際責任，不把整段公版當本人任務，也不因此把任務細節標為完整。抽象或多動作內容需要可展開正文、具體問題或分開確認；問題表述與其固定來源要能回查。

App 保存固定問題、顯示範圍、明確選答及補充，後續不再要求 LLM 重分類答案。員工回答與顧問對範圍涵蓋、細節充分及 JD 表達的判讀分開；模型不覆蓋員工的明確選擇，有歧義或前後更正才接續問。既有確認及更新後局部重核仍沿下節的範圍／用途進度，不按同名自動跨任務排除。

現行沒有獨立勾選來源契約。第一個實作候選沿[完成安全點](2026-09-29-core-value-loop-lifecycle.md)，把選答與補充作為下一 Turn 的員工輸入，原輸入先可靠保存，成功完成後才取得正式訪談資格並影響後續進度；不是要求模型再次批准答案。若希望勾選立即生效且不啟動模型 Turn，另需定義人直接確認的保存與正式來源資格，本討論未切換該契約。

驗證比較同一批原本要問的問題在自由文字／LLM 解讀與直接選答下的責任分類、部分誤寫、重問、閱讀操作時間、澄清輪數及模型成本。合成資料可驗機制與反例，真人操作負擔須另外測。節省回答解讀不等於任務相關性、線索去重或 JD 收尾已通過；方法詳見[研究 §3.1／§8](../research/retrieval/2026-10-04-public-reference-progress-and-context-selection.md)。

## App 記錄參考處理進度與控制提供內容

使用者提出由 App 記錄顧問已處理的公版線索與任務細節，後續不再當新資料反覆提供。這是本輪新增的候選 consumer 責任，尚未實作。原生模型接續可以延續分析；若 App 要確定排除已處理參考，就需要可查的處理結果，不能推測模型內部想法、靠曾讀過工具結果或看過相似字串來標完成。

員工明確選答由 App 綁定原問題及回答；顧問交付仍需分析的處理範圍、結論及必要來源依據。App 保存、查回並組裝下一輪可見資料。職務檔案、固定公版內容定位、版本及真實來源身分由程式綁定，不讓模型猜 ID。保存方式、最小工具及 schema 留待 consumer 契約設計；不從本討論直接新增資料表、通用事件引擎或第二套 Memory。

經研究建議，以「員工是否負責美容店庫房的季度盤點」等確認範圍作處理單位，而非只把整份公版或 T code 標 done。同一事項可引用多份公版，對應零個或多個 JD 任務；辨認是否負責與釐清細節是不同用途。只為實際開始處理的範圍保存結果，不強制逐句標記全部公版。沒有處理紀錄的內容仍未核，不能自動排除。

必要資訊是穩定短定位、範圍／用途、公版來源集合、進度／結論／接續事項、所用正式依據及本輪生效資格。內部身分由 App 配發，不以 Memory 標題或 publication 換版重編。進度概念先維持未處理、進行中、已處理；以下各種結論是處理結果及投影行為，不先建立大量互斥狀態。來源變動的提示保留原結論，語意是否受影響仍由顧問判斷。

| 處理結果／進度 | 後續如何提供 |
|---|---|
| 尚未處理 | 提供精簡線索／定位，正文按需讀。 |
| 正在訪談或等待回答 | 提供目前問題、待釐清事項及必要定位，讓顧問接續；不當成新線索重啟同一訪談。 |
| 已確認本人不負責 | 從預設待處理參考排除；保留結論與依據，必要時可回查。 |
| 已確認員工有這項工作 | 職位目錄中的「有沒有這項工作」已處理，不再重複提供該線索；任務細節是否完成另判。 |
| 相關任務細節已說清楚 | 從該實際工作範圍的預設細節參考排除；不反覆塞入正文，結果與依據可回查。 |
| 依據改變，需要重核 | 先提供變更提示、既有結論與相關定位；需要才重讀正文或追問。 |

表格描述候選行為，不是已生成的正式 enum／API。已處理全文不預設重送，但顧問可按需回查歷史結論及依據；本輪資料組裝也保留必要的已處理摘要與正在進行事項，避免只看到待辦子集就失去全局。這是新資料的投影規則，不任意刪改既有原生接續歷史；能省多少 token 仍須實測。

現行原生接續歷史可能仍包含先前讀到的公版工具結果，因此控制後續不再投放全文不等於原內容立刻從上下文消失。需要檢查實際模型 payload、讀取／追問及 token，不能藉投影直接宣稱完全零重新分析或零成本。完整公版目錄仍可按需取得；待處理導覽是明示範圍的子集，不冒充完整來源。

「使用者拒絕」需辨認其意思：明確不負責可結束適用性線索；不願回答或暫時不談是尚未釐清，不等於確認 JD 完整。「已提到」也不直接等於細節足夠；由顧問確認已辨認實際工作範圍後，結束整體參考的該項探索。正在訪談是接續進度，不是完成。

進度綁定的是本職務檔案中的公版工作面向、處理用途與實際工作範圍／依據，不能只按整份公版、任務名稱或某個 Memory 物件去封鎖。整體線索處理完畢不封鎖其細節讀取；一個公版任務僅部分已確認時，剩餘內容仍待處理。同一公版內容可能支持不同實際工作或多個 JD 任務，也不能因其中一處完成而全部隱藏；重複參考能否共同結束由顧問確認涵蓋關係，App 不按同名猜測。

處理結果沿[完成安全點](2026-09-29-core-value-loop-lifecycle.md)生效：本輪候選可供本輪接續，成功完成後才改變後續輪次的提供規則；取消、失敗或放棄的進度不把參考永久隱藏。恢復沿既有執行與保存責任，不另造新的恢復機制。員工事實仍由原話／Memory／JD 承擔；這裡只保存參考處理用途與結論，不把它當完整度真值或新的分析記憶層。

機制依據：[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)區分執行 checkpoint 與應用自行定義的持久資料；[Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)討論按需取用與保存必要進度以控制上下文。兩者提供公開機制／原則，沒有保證本案公版判讀正確，也沒有指定本案應使用哪個新 Store／schema。App 保存顧問明確結果、依處理用途投影參考，是本案的候選取捨。來源查閱於 2026-10-04。

## Memory 更新與參考刷新

本節是候選檢索 consumer 的更新方式，不修改現行 Memory 發布或顧問執行契約。現行顧問同 Turn／恢復固定一版已發布 Memory，新 Turn 採最新發布版；另提供尚未整理的有效訪談及本次原話，見[顧問上下文](2026-09-26-consultant-context-and-state-design.md)與[讀取契約](2026-09-27-memory-read-and-source-navigation-contract.md)。Memory 既有物件身分、修訂及來源固定關係沿[保存責任](../implementation/memory-storage.md)，不另建一套可寫 Memory。

第一版先從本輪固定版本重新組出完整查詢集合，重組兩種參考；不先實作按語意 diff 判斷受影響任務的增量引擎。B2 物件和 JD 任務未必一對一，Memory 也可能改名、改寫、拆分、合併或更正權責，不能只拿標題或文字 diff 推定哪些完成判斷仍有效。

重新查詢或 Memory publication 換版不清空參考處理進度。App 先匹配原固定公版位置、處理用途及實際工作／來源關係，檢查本輪範圍與可確定的依據變動，再套用可以沿用的處理結果並投影尚未處理、接續中及需要重核的部分。無法確定原結果涵蓋新來源／新範圍時保留待確認，不能按同名或同公版代碼自動隱藏。再搜到同一公版不等於重新判讀整份公版；本輪沒有查到舊來源也不自動刪除已確認結論。Memory 更新與顧問進度分別沿自己的責任保存。

重組查詢不表示每次全部重新 embedding／rerank。實際送入模型的查詢文字（含有使用到的描述或 B1 脈絡）、前處理／分段方式、索引語料、embedding／reranker 身分與搜尋參數均相同時，可以重用原搜尋結果；有變才重新計算。內部 cache 身分由程式產生，員工來源與查詢關係仍綁定本輪資料，不因相同字串把舊來源或舊適用性判斷搬過來。這是待驗的效率候選，不宣稱快取已實作或一定省多少時間。

兩種導覽由當前有效查詢的命中關係重新彙整。移除或改寫的查詢不把舊命中邊繼續算作當前支持；同一公版若仍由其他有效查詢找到則保留。先前已確認的員工事實仍依 Memory／原話／JD 的責任保存，不能因新搜尋不再回傳同一來源就當作工作不存在；舊參考可回查，但不冒充本輪搜尋結果。

收尾是依當時實際工作與 JD 的判斷，不是公版或 Memory 物件上不可重開的「已完成」標記。Memory 更新了無關工作、或相關依據未變時，既有處理結果仍可沿用。員工更正權責、新增適用範圍、相關原話／Memory 來源改變、JD 內容改動或公版內容換版時，才對可能受影響的處理結果提供重核提示。已知新資訊即使尚未進 Memory，也須納入這個判斷。

App 可核來源及內容版本有無變動，不能僅憑 hash 或 publication 換版判定語意是否影響結論；依據變動先提供必要差異，顧問判斷保留結論、局部重開或追問。不重送所有已處理正文，也不一律把全部進度清為待處理。純改名／重新表述不自動要求員工重答；拆合後是否仍為同一已確認範圍也不能只按新名稱自動承接。需要多少局部重核及其成本，是更新實驗要驗的效果，不能承諾所有 Memory 更新都零分析。

員工剛提出新工作或更正、但背景尚未發布時，顧問已能看見原話，不能等新版 Memory 才承認該資訊。按當次／近期原話補充搜尋是下一輸入實驗的候選，沿本輪可見範圍；正式觸發與工具契約待設計。整體與任務收尾都須一起核對未整理的新資訊及目前 JD，不以 Memory 版本沒變推定工作沒變，也不要求每次回答先等背景整理完成。

原話不可改寫，因此新增更正不一定改變舊依據的 hash；只看既有依賴 diff 也找不到所有新增工作。完整新資料及新版 Memory 導覽仍交顧問辨認影響，不讓舊處理結果對新事實作否決。顧問判讀已清楚但尚未寫入 JD 時，也可以結束該參考判讀，但不能據此宣告整份 JD 已表達完整。

更新情境的驗證須加入：未改查詢可重用排名但來源重新綁定、新增次要工作、取消本人責任、只改名／重述、物件拆合、正文相同而來源更正，以及舊查詢仍在途時新版本已發布。舊結果可以保存為歷史，不能改標版本後混入新結果；漏失、過早收尾、重複追問及實際時間成本分開記錄。這些更新與收尾效果尚未通過實驗。

參考進度另須驗：已拒絕同項線索不重問、已辨認工作仍可深入細節、訪談中接續既有問題、細節完成後不重送正文、同一公版部分完成不隱藏其他工作、同範圍的多個支持來源不重複提問，以及取消／重開恢復不丟進度或錯誤封鎖。比較有／無 App 處理進度時，記模型實際看見的全文與摘要、重新判讀次數、重複追問、更新後遺漏及 token／時間；未處理清單空了也不能直接當整份 JD 已完整。

## 後續效果實驗方向

目前仍先完成 Memory 輸入、檢索單位／相關內容及參數實驗。本文件不啟動模型或完整訪談測試。檢索可靠後，優先比較相同顧問、現行分析方法及員工情境下的「分析方法本身」與「加入職位整體參考及確認進度」，驗整份 JD 收尾。任務細節參考及兩者都加的比較保留後續；正式協定、案例及費用另行固定。

案例須包括尚未提到的次要或低頻工作、跨職位客製工作、已明確不負責的公版內容、公版／JD 任務拆合，以及一部分已說清楚但另一部分仍缺資訊。驗收依合成員工的固定實際工作與可交付 JD 內容，不能以參考公版本身作完整度真值。

本輪後續優先觀察整份 JD 的過早收尾、重要內容遺漏、錯把參考寫成本人責任，以及內容已完整仍重複追問；記錄訪談輪數、模型／檢索時間與 token／費用。單項任務完整度驗證暫不追加。沒收尾、輪數上限或工具失敗須分開記錄，不能當成功完成。最終完整旅程仍包括 JD 核對及正式 PDF 內容／排版驗證。

暫不依賴分析方法無線索發現未知是本次工作假設，不是既定失敗結論。未來上述對照仍須保留沒有公版的控制組，補測這個假設。現階段沒有新增顧問品質、收尾或 PDF 驗收結果。
