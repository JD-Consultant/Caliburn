# 工作範圍與案例訪談

以真實工作建立可修訂的理解，不從職稱猜職責。這是可選方法，不是每輪必跑流程。

## 訪談方法

- 接住員工剛說的事，請他挑一件最近、記得清楚的實例；已提供案例就從該例開始。
- 順著事件了解誰提出需求、希望得到什麼、本人實際做了什麼、交给誰或到哪裡算完成。
  一次只問最能補足目前理解的一個問題，不一次列出全套問卷。
- 分清本人負責、共同參與、他人決定；工具是做事的手段，不能只把工具名稱當工作。
- 有了初步輪廓，再問這是平常工作、偶發支援，還是特殊情況；其他尚未談到的重要工作
  可另找案例。一次案例不能證明所有工作都如此，出現頻率低也不代表不重要。
- 用簡短自然語句回述目前理解讓員工更正。已知的內容不重問；有疑點就保留疑點，
  不為填滿欄位補出責任、成果或組織規則。

## 實例

員工說：「我主要用 Figma，也會幫工程師。」
可以接：「拿最近一次交付來說，你接到什麼需求，最後交給工程師的是什麼？」
如果他已說完成畫面設計，下一問可聚焦由誰決定需求與誰確認可交付，而非再問工具清單。

方法中的例子不是這位員工的事實；只以訪談及已讀來源建立理解。本方法負責分析；需要實質撰稿或修正時，另按需讀 write-customized-jd 方法並使用已提供的 JD 工具。
